# IR の読み取りを markdown-schema のエンジンに置き換える

kotowari が IR の Markdown を自前で読むのをやめ、同じ workspace の `kotowari-markdown-schema` が宣言したスキーマで検証し値を抽出する形にする。判断の記録は [2026-09-22-ir-engine](../decision/records/2026-09-22-ir-engine.md)（A1〜A62、Revisions）。承認は 2026-09-22 に会話の中で得た。この仕様自身は IR ではなく kotowari の検査を受けない。

10 ラウンドの壁打ちの途中で、既にある2つの要求に反する案になっていることが分かった。[REQ-core-090](../ir/core/form-contract.md#REQ-core-090) はスキーマのファイルを読むことを禁じ、[REQ-core-089](../ir/core/form-contract.md#REQ-core-089) は形をコードに固定すると定める。スキーマをバイナリに埋め込むことでどちらも文のまま成り立たせる（A36）。禁止の出どころである [R4](../decision/records/records.md#R4) の理由（ミニ・スキーマ言語を作ることになる、形は今1つしかない）は、言語が実在して 52 件の要求で仕様化され、スキーマが3つある今はもう成り立たない。[REQ-core-091](../ir/core/form-contract.md#REQ-core-091)（外部の mdschema）には反しない。[A18](../decision/records/2026-09-17-check-reach.md#A18) が crate として取り込む道を禁止の外に置いている。

## 結果を一文で

`crates/kotowari-core/src/ir.rs` の Markdown の読み取りが `kotowari-markdown-schema` の呼び出しに替わり、IR の形の宣言が Rust のコードからバイナリに埋め込んだ YAML に移り、利用者から見える`指摘`は新しい3種類が増えるだけで、ほかは種類・detail・行・出る順のすべてが今と同じまま。

## 用語

`ノード`、`文`、`表`、`抽出`、`継続段落`、`項目`、`前置部`、`節`、`フィールド行`、`コードブロック`、`用語集`、`指摘`、`停止`、`除外` は、kotowari の用語集（`docs/ir/core/CONTEXT.md`）と markdown-schema の用語集（`docs/ir/schema/CONTEXT.md`）の意味をそのまま使う（どちらにも在ることを確認した）。

この文書が新しく使う語は4つで、IR を書く段で markdown-schema の用語集に足す。

- エンジン: `kotowari-markdown-schema` のライブラリ。スキーマで`文書`を検証し値を`抽出`する。この文書の中だけで使い、用語集には足さない
- 導かれる値: `抽出`の宣言で、`文書`の文字ではなく位置や識別子から導く値。行番号（`line`）、`項目`の見出しの ID（`id`）、`項目`の見出しの名前（`name`）、`生の行`（`raw`）の4つ。概念は REQ-schema-048 が定めているが用語集には無いので足す
- 要素の値: `抽出`で、その要素そのものから取れる値。`導かれる値`（位置や識別子から導くもの）と区別する。R16 が導入する
- ノードの名前: スキーマが宣言した`ノード`の名前。`フィールド行`なら `種類` や `出典`、`節`なら節の名前。`題名`のように宣言上の名前を持たない`ノード`もある。R4 が導入する

`生の行` は markdown-schema の用語集に既にあるが、`指摘`の側だけを述べている。R2 と R17 が`抽出`の側にも使うので、定義を「`指摘`が指す行、または`抽出`の要素の行の文字そのまま」に広げる。

## 要求

### R1: 表の行の鍵の出どころ

`表`の行の鍵は、スキーマが `header` を宣言したときはその名前、宣言しないときは列の位置（配列）にし、**`文書`のヘッダ行の文字を鍵に使わない**。これは`導かれる値`の宣言の有無に関わらず常にそうする。`header` の宣言と`文書`の列数が違うときは宣言した名前の数を正とし、`文書`の列が足りなければその鍵を省き、多ければ余りを捨てる（`table_header_mismatch` の`指摘`は今までどおり出す）。

`導かれる値`を宣言したときは行が要素オブジェクトになり（R16）、行番号はそのデータ行そのもので、ヘッダの行と区切りの行は数えない。宣言しないときの`抽出`の形は今と同じ行の並びで、鍵の出どころだけが変わる。`表`が繰り返すときは`配置パス`の直下に表ごとの段を作り、要素の形は繰り返しの有無で変えない。

`文書`のヘッダ行のセルは空でも重複でもよく、そこから鍵を作ると値が黙って消える（実測: `|  |  |` の表で `{"": "2"}` になり1列目の値が失われる。`| a | a |` も同じ）。`header` を宣言しても今の実装は塞げない（`table_header_mismatch` は出るが`抽出`は`文書`側の文字で続く）。鍵の出どころをスキーマと位置に限ることで、この経路を検出ではなく不成立にする。

- 成功の条件: `header` を宣言した表の fixture で行の鍵が宣言した名前になる。宣言しない表で行が配列になる。ヘッダのセルが空の表と、同じ名前の列が2つある表のどちらでも列の値が1つも失われない。`導かれる値`を宣言しない略記（`extract: rows`）の出力が、鍵の出どころを除いて今と同じ行の並びである。ヘッダとデータ3行を持つ表に`導かれる値`を宣言したとき、行ごとの `line` がデータ行の行番号と一致する。繰り返す表で`配置パス`の直下が表ごとの段になる
- 反例: `文書`のヘッダ行の文字を鍵にする（今の振る舞い）。`導かれる値`を宣言しない略記の出力まで形を変える。表の開始行が最上位に配列で1つだけ出る。ヘッダの行を1行目のデータ行として数える
- 確かめ方: 上の6つの fixture を `mds values --format json` に通し、鍵・値・行番号を fixture と比べる

### R2: 文の行ごとの抽出

`文`の`抽出`が`導かれる値`を含むとき、行ごとの要素にする。空行で区切って続く段落（今は別の`文`として読まれるもの）も同じ並びに入れる。`要素の値`は前後の空白を取り除いた行の文字にし、字下げと末尾の空白を含む行そのままは`導かれる値`の `raw` で取る（R17）。`導かれる値`を宣言しないときの`抽出`は今と同じ1つの文字列にする。

一覧の行の`継続段落`はここに入らない。`継続段落`は用語集が「一覧の行の後に空行で区切って続く、その行の子である段落」と定めており、`mds.md` の R9 が`文`に数えないと述べている。

- 成功の条件: 3行の`文`と、空行を挟んで続く段落を持つ`項目`の fixture に`導かれる値`を宣言したとき、行の数と同じ数の要素が出る。字下げのある行で、`要素の値`が前後の空白を取り除いた文字、`raw` が字下げと末尾の空白を含む文字になり、2つが別物である。`導かれる値`を宣言しない略記（`extract: text`）の出力が今と同じ1つの文字列である
- 反例: 段落を1つの文字列に繋ぎ、開始行だけを返す（今の振る舞い）。`要素の値`と `raw` を同じものにする（今の振る舞いは行の値が生の行そのもので、2つの語で同じ物が取れる）。一覧の行の`継続段落`を`文`の`抽出`の要素に入れる。`導かれる値`を宣言しない略記まで行ごとに分ける
- 確かめ方: 字下げと末尾の空白を持つ行、空行を挟んだ段落、`フィールド行`の`継続段落`をすべて含む fixture を `mds values --format json` に通し、要素の数と`要素の値`と `raw` と行番号を fixture と比べる

### R3: 指摘の行番号

エンジンは`指摘`に行番号を付ける。違反した`ノード`があるならそのノードの開始行、`ノード`の欠落ならそれを含む`ノード`の開始行にする。

- 成功の条件: 必須の`フィールド行`が無い`項目`の`指摘`が、その`項目`の見出しの行を持つ。同じ`フィールド行`が2つある`指摘`が、2つ目の行を持つ。表の行の列の数が合わない`指摘`が、その行を持つ
- 反例: 行番号を持たない（今の振る舞い）。列の数が合わない行の`指摘`がヘッダの行を指す（今の振る舞い）
- 確かめ方: 必須の`フィールド行`を1つ落とした fixture、同じ`フィールド行`を2つ書いた fixture、列の足りない表を持つ fixture の3つを `mds check --format json` に通し、行番号がそれぞれ`項目`の見出しの行・2つ目の行・その行であることを見る

### R4: 指摘のノードの名前

エンジンは`指摘`に、それが指す`ノード`の宣言された名前を持たせる。宣言上の名前を持たない`ノード`の`指摘`では省く。

- 成功の条件: `種類` が無い`項目`の`指摘`のノードの名前が `種類` である。`検証` が無いときは `検証` である。`題名`の`指摘`にはノードの名前が無い
- 反例: 名前を detail の英文の中だけに持つ（今の振る舞い）
- 確かめ方: R3 と同じ3つの fixture の出力でノードの名前の鍵を見て、`題名`の`パターン`に合わない fixture の出力にその鍵が無いことを見る

### R5: 指摘が指す行の生の文字

エンジンは、行を持つ`指摘`にその行の生の文字を持たせる。字下げと末尾の空白を含み、再構成しない。英文の detail はエンジン自身の CLI の出力のために残す。

- 成功の条件: `項目`の`ID`が宣言した形に合わない fixture の`指摘`が、`### REQ-BAD: 名前` の行をそのまま持つ
- 反例: 見出しの名前だけを持ち、呼ぶ側が `### ` と `: ` をつないで組み立てる
- 確かめ方: `ID` の形に合わない見出しを持つ fixture を `mds check --format json` に通し、`指摘`の生の行が fixture の行と一文字も違わないことを見る

### R6: スキーマはバイナリに埋め込み、文書の種類で選ぶ

kotowari は3つのスキーマを `include_str!` でコンパイル時に取り込み、実行時にスキーマのファイルを読まない。IR の`文書`の種類（`用語集`、`問題の記録`、`話題ごとの文書`）に応じて埋め込んだスキーマを選ぶ。IR の`文書`はスキーマを宣言せず、`docs/ir/schema/` の`文書`からも宣言を外す。`文書`に frontmatter があっても形の宣言として使わない。

- 成功の条件: `docs/ir/` のどの`文書`にも frontmatter が無く、`kotowari check` の指摘が R12 の3種類を除いて0件。`.mds/schemas/` を消しても `kotowari check` の出力が変わらない。壊れた YAML を `.kotowari/schema.yaml` に置いても読まれない（[EX-core-040](../ir/core/form-contract.md) が今固定している振る舞い）
- 反例: 実行時に `.mds/schemas/ir.yaml` を開く。`文書`の frontmatter の宣言を優先する
- 確かめ方: `.mds/schemas/` を一時的に退避して `kotowari check` の出力を前後で比べる。`docs/ir/` の全`文書`の1行目が `---` でないことを見る

### R7: kotowari は Markdown を読まない

kotowari は IR の`文書`の Markdown の構造を自前で読まない。生の行を読むのは次の3つだけで、どれもエンジンが構造として返さないものである。

- gherkin の塊の中身（タグの構文、`@id` の値の形、シナリオの組み立て）
- 閉じないコードブロックの検出
- `文書名の参照`の走査（コードブロックの外の全行を見る。TBL-core-014）

- 成功の条件: `crates/kotowari-core/src/ir.rs` に残る、生の行を読む関数が上の3つのためのものだけである。見出し・`フィールド行`・`表`・`前置部`を読む関数が無い
- 反例: detail のために生の行をもう一度読む（R5 でエンジンが渡すので要らない）。`用語`と`曖昧語`の検査のために行を読み直す（R2 でエンジンが行ごとに渡すので要らない）
- 確かめ方: 人が `crates/kotowari-core/src/ir.rs` の関数の一覧を見て、生の行を読む関数が上の3つに対応するものだけであることを確認する

### R8: スキーマに宣言する行番号

`出典`の`フィールド行`と`具体例`の`コードブロック`に行番号の`抽出`を、`文`に行番号と`生の行`の`抽出`を宣言する。`出典`の行番号は `source_invalid` の行（[REQ-core-115](../ir/core/sources.md) が「`項目`なら "- 出典:" の行」と定める）に使い、`コードブロック`の開始行は gherkin の中の`指摘`の絶対の行を数える起点に使う。`文`の `raw` は、R2 が`要素の値`を前後の空白を取り除いた文字にしたため、`unclosed_backtick` の detail（TBL-core-008 が「読んだ行の文字そのまま」と定める）を R15 のとおり保つのに要る。前の2つはエンジンの今の機能で足りる。

- 成功の条件: `出典` の書式が正しくない`項目`の `source_invalid` の行が "- 出典:" の行である。gherkin のタグの行を指す`指摘`の行が`文書`の先頭から数えた行である。字下げのある`文`の `unclosed_backtick` の detail が置き換えの前後で一致する
- 反例: `出典` の`指摘`が`項目`の見出しの行を指す。gherkin の`指摘`の行が塊の中の相対の行になる
- 確かめ方: 置き換えの前後で、これらの`指摘`を出す既存のテストが通ることを見る

### R9: 指摘の対応表

`docs/ir/core/findings.md` に、エンジンの`指摘`を kotowari の種類へ写す決定表を置く。列は5つにする。

| 列 | 中身 |
|---|---|
| エンジンの種類 | エンジンが出す`指摘`の種類 |
| ノードの名前 | 写し先を分けるのに使う名前。使わないときは空 |
| kotowari の種類 | 写し先。今のスキーマでは発生しないものは「発生しない」と書く |
| "line" の扱い | そのまま使う、または null にする（[REQ-core-027](../ir/core/finding-order.md#REQ-core-027) の9種類） |
| detail の材料 | エンジンの`指摘`のどの要素から作るか（生の行、ノードの名前、`文書`名など） |

名前が同じで意味が違うものにはその旨を書く。エンジンの `invalid_id` は`項目`の見出しの `ID` で、kotowari の `invalid_id`（`@id` の値）とは別物である。エンジンの `missing_table` は`用語集`では `glossary_invalid`、`決定表`では `missing_table` に分かれる。

- 成功の条件: 表の行がエンジンの`指摘`の種類（`crates/kotowari-markdown-schema/src/finding.rs` の列挙）を過不足なく覆う。`invalid_id` と `missing_table` の行に別物である旨がある。REQ-core-027 の9種類を写す行の「"line" の扱い」が null である
- 反例: 表を3列にして、`missing_required_field` を1つの kotowari の種類へ写す（kotowari では4つに分かれる）。`glossary_invalid` を写す行が "line" をそのまま使う
- 確かめ方: 人が対応表と `finding.rs` の列挙を突き合わせ、過不足が無いことと、REQ-core-027 の9種類の行の "line" の扱いを見る

### R10: 写し先の無い指摘は停止にする

kotowari は、対応表に行が無いエンジンの`指摘`と、「発生しない」と書いた行の`指摘`を受けたとき`停止`する。黙って捨てない。

- 成功の条件: 表に行が無い種類と、「発生しない」と書いた種類の両方で`停止`する
- 反例: 知らない種類を無視して検査を続ける（スキーマに宣言を足したとき検査が静かに緩む）
- 確かめ方: 写す関数に、表に行の無い種類と「発生しない」と書いた種類をそれぞれ渡すテストで`停止`することを見る

### R11: kotowari に残す検査

次はエンジンに移さず kotowari に残す。

- 文書をまたぐもの: `ID` の重複、`用語`の重複、参照切れ、`ID` の名前と置き場の一致
- 上限: 行数と要求の数
- `出典`の検査: TBL-core-012 の6条件。スキーマから`出典`の書式のパターンを外す（A30）
- `文`に基づくもの: `用語`、`曖昧語`、閉じないバッククォート。R2 が行ごとに渡す生の行を使う
- `文書名の参照`
- gherkin の中身
- 閉じないコードブロック

- 成功の条件: これらの`指摘`の種類・detail・行が置き換えの前後で変わらない
- 反例: `出典`の書式をスキーマにも宣言し、同じ入力に2件の`指摘`が出る。`用語`の検査のために生の行を読み直す
- 確かめ方: 置き換えの前後で、これらの`指摘`を出す既存のテストが通ることを見る

### R12: 新しくなる3つの指摘

エンジンが見つけて kotowari が今`除外`として読み飛ばしているものを、`指摘`にする。種類は3つ足す。A3 の「新しい種類は足さない」はエンジンの`指摘`の写し方の規則で、kotowari が新しく見るようになった場面には及ばない。

| 種類 | 場面 | detail | "line" | 重大度 |
|---|---|---|---|---|
| unknown_line | `節`の直下にある宣言外の素の文 | 行の文字 | その行 | 誤り |
| unknown_code_block | `具体例`の節にある gherkin でないコードブロック | 開始の行の文字 | 開始の行 | 誤り |
| glossary_title_invalid | `用語集`の題名が `用語集` でない | 題名の行の文字 | 題名の行 | 誤り |

`除外`の列挙との関係は3件で違う。

- `節`の直下の素の文は「"## " の見出しの直下で最初の "### " より前の空でない行」として列挙にあるので、列挙から外す
- gherkin でないコードブロックは「コードブロックの中（gherkin を除く）」として中身が列挙にある。中身を読まないことは変えず、ブロックの存在そのものを`指摘`にするので、列挙は変えない
- `用語集`の題名は今どの列挙にも無く、読み飛ばしてもいない（検査そのものが無い）ので、列挙は変えない

- 成功の条件: 3つの場面をそれぞれ置いた`文書`で、その種類の`指摘`が1件ずつ出て、detail と行が上の表のとおりである。kotowari 自身の IR 42 文書では3種類とも0件
- 反例: 3つの場面を置いた`文書`で`指摘`が0件になる。`節`の直下の素の文を`除外`の列挙に残したまま`指摘`を出す（REQ-core-120 に反する）
- 確かめ方: 3つの場面をそれぞれ置いた`文書`で `kotowari check --format json` を走らせ、種類・detail・行を見る。kotowari 自身の IR で3種類が0件であることを見る

### R13: 停止の境界

抽出結果を型へ写せないこと、対応表に写し先が無いことは kotowari の`停止`にする。理由は1つ足し、既にある5つの文言（TBL-core-018）に並べる。利用者の入力で起きる`停止`（`文書`が読めない、UTF-8 でない）は今のままにする。スキーマはバイナリに埋め込むので（R6）、スキーマが読めない`停止`は無い。

- 成功の条件: 新しい`停止`の文言が1つで、`skills/kotowari/references/findings.md` の`停止`の表と TBL-core-018 の両方にある。読めない`文書`を置いたときの文言が今と同じ
- 反例: スキーマの不具合を利用者向けの`指摘`として出す。`停止`の理由を2つ以上足す
- 確かめ方: 写せない値を返すスキーマを埋め込んだビルドで`停止`の文言を見る。`stop` の文言の集合の一致を見る既存のテスト（REQ-core-127）が通ることを見る

### R14: 検証に落ちた文書も文書をまたぐ検査を受ける

エンジンの`指摘`が出た`文書`でも、kotowari は`抽出`の得られた分で文書をまたぐ検査を続ける。`文書`を飛ばさない。

- 成功の条件: 必須の`フィールド行`が欠けた`項目`を持つ`文書`で、形の`指摘`と同時に、その`項目`の `ID` の重複や参照切れの`指摘`も出る
- 反例: 形の`指摘`が出た`文書`を文書をまたぐ検査の対象から外す（`指摘`の集合が変わる）
- 確かめ方: 形の`指摘`と文書をまたぐ`指摘`が同じ`項目`に付く`文書`を置き、両方が出ることを見る

### R15: 振る舞いは R12 を除いて変わらない

置き換えの前後で `kotowari check --format json` の出力全体の差分が、R12 の3種類の`指摘`だけである。

- 成功の条件: 置き換えの前の出力と後の出力の差分が、R12 の3種類の追加だけ。ほかの`指摘`の種類・detail・行・出る順に差が無い。既存のテストが、R12 と R13 に由来する期待値の追加を除いて全件通る
- 反例: `指摘`の行や detail が変わったのを、テストの期待値を書き換えて通す。数が合わないのを印や要求を足して合わせる
- 確かめ方: 置き換えの前に `kotowari check --format json` の出力を保存し、後の出力と `diff` を取る。差分が R12 の3種類だけであることを見る

### R16: 抽出の宣言の形

`抽出`は1つの入れ子の宣言にする。`配置パス`（`path`）は出力の置き場で、必ず1つ。要素ごとの`導かれる値`を宣言するとき、`要素の値`の置き場は要素オブジェクトの中の鍵として `value` に宣言する。`value` は省いてよく、省いたときの要素オブジェクトは`導かれる値`の鍵と、内側の`ノード`が宣言した`配置パス`（REQ-schema-047）だけを持つ。`導かれる値`を宣言しないときは `value` も要らず、要素そのものが値になる。名前付きキャプチャ（`group`）は `path` の兄弟のままにし、`of` の下に入れない（`group` は`要素の値`を正規表現で切り出すもので、要素から導く別の値ではない）。`of` も `group` も無いときは `path` だけの略記（`extract: <名前>`）を許す。この形はすべての`ノード`に同じく使い、`箇条書き`（行ごと）と`コードブロック`（ブロック単位）にも及ぶ。

```yaml
extract:
  path: glossary          # 出力の置き場（必ず1つ）
  value: cells            # 要素の値を置く、要素オブジェクトの中の鍵（省いてよい）
  of: { line: line }      # 要素ごとの導かれる値
```

今の`抽出`は書式の並びで、置き場になるのは `of` を持たない書式である。置き場と要素の中の鍵が同じリストに並び、見分けが `of` の不在という書かれていない手がかりになっている。個数の規則もリストの形の中に居場所が無く、置き場が0個なら出力が黙って空になり（実測）、2個なら同じ内容が両方に複製される（実測）。入れ子にすると、どちらも YAML の構造として書けなくなる。

- 成功の条件: `path` の無い`抽出`を宣言したスキーマが`停止`する。`value` を省いて `of` だけを書いた宣言で、要素オブジェクトが`導かれる値`の鍵だけを持つ（内側の`ノード`が`抽出`を宣言していればその`配置パス`も持つ）。`of` も `group` も無い宣言を略記で書いたとき、出力の形が今と同じになる（`表`の行の鍵の出どころだけは R1 のとおり変わる）。`箇条書き`と`コードブロック`に `of` を宣言できる
- 反例: `抽出`を書式の並びのままにし、`of` の無い書式が置き場になると決める。置き場が0個の宣言を`停止`で弾いて形は変えない（間違えやすさが残る）
- 確かめ方: `path` の無いスキーマ、`value` を省いたスキーマ、略記のスキーマ、`箇条書き`に `of` を宣言したスキーマの4つを `mds values --format json` に通し、1つ目が`停止`し、残り3つが上の出力になることを見る

### R17: 導かれる値の語と宣言できる範囲

`導かれる値`は4つ。`line` はその`ノード`または要素が現れた行番号（1始まりの数値）、`id` は`項目`の見出しの ID、`name` は`項目`の見出しの名前、`raw` は`生の行`である。`line` と `raw` はどの`ノード`にも宣言でき、`id` と `name` は`項目`にだけ宣言できる。ほかの語は`停止`にする。

要素の単位と `raw` が指す行は`ノード`ごとに次のとおり。

| ノード | 要素の単位 | `要素の値` | `raw` が指す行 |
|---|---|---|---|
| `表` | データ行 | 行（`header` を宣言すればその名前のオブジェクト、しなければ配列） | その行 |
| `文` | 行 | 前後の空白を取り除いた行の文字 | その行 |
| `箇条書き` | 行 | 行の文字 | その行 |
| `コードブロック` | ブロック | ブロック全体の文字列 | フェンスの開始行 |
| `項目` | 項目 | 見出しと本文をつないだ文字列 | 見出しの行 |
| `題名`・`フィールド行`・`節`・`前置部` | 分けない（1つ） | その`ノード`の今までの値 | その`ノード`の開始行 |

「分けない」`ノード`でも、`value` か `of` を宣言すれば`配置パス`の下にオブジェクトができ、その中に鍵を持つ。R18 の重複の`停止`はその形にも及ぶ。`ノード`が `repeat` で繰り返すときは`配置パス`の直下に段が増え（A59 を全`ノード`に広げる）、要素の形は繰り返しの有無で変えない。

`raw` を語の1つにすることで、`文`の行が生の行を暗黙の鍵で必ず持つ形をやめる。暗黙の鍵はその名前を仕様が定めないまま実装が決めることになり、宣言された`導かれる値`と名前を取り合う（実測: `{path: text, of: line}` を宣言すると行番号が生の行を黙って上書きする）。

- 成功の条件: `題名`に `raw` を宣言した fixture で見出しの行がそのまま出る。`表`の行に `raw` を宣言した fixture でそのデータ行がそのまま出る。`項目`に `raw` を宣言した fixture で見出しの行が出る。gherkin の塊が2つある fixture の`コードブロック`に `line` を宣言したとき、塊の数と同じ数の開始行が出る。`表`に `id` を宣言したスキーマが`停止`する
- 反例: `raw` を`文`だけの暗黙の鍵にする。`line` と `raw` で宣言できる`ノード`の範囲を変える（2つの語の差を覚える必要が出る）。`コードブロック`を要素の単位から外す（R8 が塊ごとの開始行を要る）。繰り返す`ノード`の行番号を最上位の配列にする
- 確かめ方: 上の5つを `mds values --format json` に通し、生の行を fixture の行と一文字ずつ比べ、最後の終了コードが2であることを見る

### R18: 要素オブジェクトの中の鍵の重複は停止にする

1つの要素オブジェクトの中で、内側の`ノード`の`配置パス`、`value`、`of` の鍵のいずれかが重複するスキーマは、スキーマを読んだ時点で `schema_invalid` の`停止`にする。この判定は`文書`を読まずに行う。

判定は`配置パス`全体で行う。`a.b` と `a.c` はドット区切りの入れ子を共有するだけで別の鍵であり（REQ-schema-036）、重複にしない。`a` と `a.b` のように片方が他方の親になる組だけが重複である。

`文書`を読んだあとに`停止`する道は採らない。`validate` の署名は契約の入口6つの1つ（`docs/ir/schema/library.md#TBL-schema-010`）で`停止`を返せず、入口を足すのも契約の変更にあたる。`停止`の理由も5つに閉じた一覧（`mds.md` の R19、`docs/ir/schema/cli.md` の TBL-schema-009）で、6つ目を足すと公開の種類の名前が増える。鍵の重複はすべてスキーマ側の宣言どうしの比較なので、`文書`を見ずに判定でき、どちらにも触れずに済む。

- 成功の条件: 内側の`フィールド行`が `extract: line` を宣言し、外側が `of: { line: line }` を宣言したスキーマが終了コード2と `schema_invalid` で`停止`する。`value: cells` と `of: { cells: line }` を並べたスキーマも同じく`停止`する。`a` と `a.b` を並べたスキーマが`停止`し、`a.b` と `a.c` を並べたスキーマは通る
- 反例: 後から置いた宣言が先の値を黙って上書きする（今の振る舞い）。`文書`を読んだあとに`停止`する
- 確かめ方: 上の4つのスキーマを `mds values` に通し、終了コードと標準エラーの`停止`の種類を見る

## 却下したもの

- kotowari が`抽出`の構造から欠けたフィールドを判定し、エンジンの`指摘`を捨てる（判定が2か所に分かれる。A21）
- `指摘`の行が無くなることを受け入れる（A5 に反する。A21）
- エンジンの detail の文言を仕様で固定して kotowari が読む（人向けの英文を機械の契約にする。A27）
- 用語集だけ kotowari の行ベースの読み取りを残す（A1 の例外を増やす。A7）
- 表の開始行から数えて行を導く（不正な行が`抽出`から落ちると数がずれる。A7）
- IR の`文書`にスキーマを宣言させ、宣言の無い`文書`を検出する検査を足す（足し忘れうる作業を恒久的に抱える。A8）
- スキーマのファイルを実行時に読み、REQ-core-090 を廃止する（埋め込めば禁止を残せる。A36）
- `用語`・`曖昧語`・閉じないバッククォートの検査を kotowari に残して生の行を読む（「Markdown を読まない」が形だけになる。A37）
- スキーマの宣言を緩めて R12 の3件を発生させない（スキーマが IR の形を語る力が落ちる。A33）
- R12 の3件を kotowari の層で捨てる（A33）
- スキーマに`出典`の書式のパターンを残す（同じ入力に2件の`指摘`が出る。A30）
- CLI のバイナリの名前の変更をこの仕様に含める、または先に別の工程でやる（別の関心。A26）
- 仕様書を2本に分ける（エンジンへの機能追加は置き換えのためだけに足すもので独立した価値を持たない。A15）
- `導かれる値`を使う`表`に `header` の宣言を必須にする（kotowari の IR の`決定表`は表ごとに列の名前も数も違うので `header` を宣言できず、`決定表`が`導かれる値`を一切使えなくなる）
- 常に列の位置を鍵にする（`用語集`が列を名前で読んでいる。REQ-core-060 が出典の列、`docs/ir/core/terms.md` が意味の列を対象外にする）
- `文書`のヘッダ行から鍵を取り、空のセル・重複した列名・`導かれる値`との衝突を検出して`指摘`か`停止`にする（検出止まりで、間違えやすさ自体が残る）
- 位置と名前を結ぶマッピングをスキーマに別途宣言する（`header` の宣言がそのままそのマッピングなので、別の機構は重複）
- `抽出`を書式の並びのままにし、置き場がちょうど1つであることを `schema_invalid` で強制する（置き場と要素の中の鍵が同じリストに並ぶ読みにくさが残る）
- 要素オブジェクトの鍵の重複を`文書`を読んだあとに`停止`する（`validate` の凍った署名と、閉じた`停止`の理由の一覧に触れる。R18）
- `導かれる値`の`配置パス`と`表`の列の名前の衝突を`停止`にする規則を残す（REQ-schema-048 が今そう定めているが、R16 の入れ子で列の名前は `value` の下に入り、`of` の鍵と同じ階層に並ばなくなるので成立しえない。R18 の重複の`停止`が置き換える）
