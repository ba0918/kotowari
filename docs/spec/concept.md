この文書は、LLMを用いた仕様駆動開発の改善案を壁打ちするための構想メモである。
承認済みの仕様、実装計画、採用技術ではない。

## 目的

この構想が目指すのは、「要求された仕様を矛盾なく実装に落とし込み、それをテストで証明できること」である。
そのための流れを次のように置く。

```text
brainstorm -> ADR -> 仕様IR -> （必要な部分だけ）形式手法による証明 -> plan -> implement
```

仕様IR、機械検査、生成、追跡は、この目的のための手段である。
LLMに渡すコンテキストの縮小や、既存の仕様の問題の発見は、手段から得られるかもしれない副産物であり、目的ではない。
実験001では、この2つを主な利点として測った。
コンテキストの縮小は成立せず、問題の発見はIRを作らなくても得られた（「実験001の結果」）。

## 背景

現在の `agentic-workflow` は、概ね次の単純なループで開発を進める。

```text
brainstorm -> plan -> cycle
```

`kakoi` もこのワークフローを使って実装されている。
しかし、工程を明確に分け、仕様と実装の対応を確認していても、次の問題は発生する。

- 仕様の内部に矛盾が残る
- 実装中に不足していた仕様が発見される
- 実装が先行し、その結果に合わせて仕様を修正する
- 長い自然言語の仕様を工程ごとにLLMが再解釈する
- 同じ文章から、人間やLLMが異なる意味を読み取る
- 局所的な変更が仕様全体のどこへ影響するか分かりにくい

これは単にワークフローが不足しているというより、長文の自然言語を仕様の正本にしていることに由来する可能性がある。
自然言語の仕様には情報がすべて含まれていても、その意味構造と依存関係は文章の中に埋まっている。
読み手は毎回、それを頭の中で再構築しなければならない。

`kakoi` のように、Linuxの名前空間、マウント、パス解決、シンボリックリンク、権限、環境変数、認証情報、失敗時の安全性が相互作用する製品では、この認知負荷が特に大きい。
完全な仕様書を一読して全体を理解すること自体が、現実的な前提ではない。

## 問題仮説

現在は、先に人間向けの長文仕様を書き、LLMがそこから実装に必要な意味を取り出している。

```text
brainstorm
    -> 人間向け長文仕様
    -> LLMによる解釈
    -> plan
    -> implementation
```

この構造では、仕様を読むたびに意味の復元が起きる。
文章を詳細にするほど条件や相互参照も増え、必ずしも曖昧さが減るとは限らない。

順序を逆転し、先に意味を構造化してから、人間向け文書を派生させるほうがよいのではないか。

```text
brainstorm
    -> 構造化された仕様モデル
    -> 検査可能な要求・例・性質
    -> 人間向け仕様書
```

注意すべきは、この構造でもLLMによる解釈は消えないことである。
brainstormから仕様モデルへの正規化は依然として解釈であり、再解釈が「工程ごと」から「一回」に集約されるにすぎない。
この構想の価値は解釈の排除ではなく、解釈を一箇所に集めて検査対象にすることにある。
したがって、正規化の一回で起きる誤りや補完を検出する仕組みが、構想全体の成否を左右する。

## 中心となる考え方

自由な自然言語を直接実装へ渡さず、brainstormの結果を一度、機械検査可能な仕様モデルへ正規化する。
この仕様モデルを意味の正本とし、EARS、Gherkin、人間向け仕様書、テスト、必要に応じた形式モデルを派生させる。

ここでいう「LLM向け仕様」は、LLMだけが読む専用形式ではない。
人間、LLM、lint、テスト生成器、形式手法が共通して扱える、解釈の自由度を制限した中間表現を指す。

仮にこれを「仕様IR」と呼ぶ。

## 想定する開発フロー

### 1. brainstormで探索と意思決定を行う

brainstormでは、従来どおり自由な自然言語を使う。

- 解決する問題
- 利用者とユースケース
- スコープと非スコープ
- 脅威モデル
- 選択肢とトレードオフ
- 採用した判断と却下した判断
- 未解決事項

重要な設計判断と理由はADRへ残す。
brainstormは発散と判断の工程なので、この段階をEARSやGherkinだけで記述することは想定しない。

brainstormとADRが揃ったら、正規化とは別に、矛盾、欠落、曖昧さを探すだけのレビューを行う。
実験001の対照実験では、構造化させずに問題だけを探させたセッションが、正規化と同じ問題を挙げ、候補をより多く、より安く挙げた。
問題を見つける役割は正規化に持たせず、この独立したレビューに持たせる。
見つかった問題は人間が判断してADRに記録してから、正規化へ進む。

実験002では、この独立したレビューを行わず、brainstormの中で行った敵対的レビュー3回で代えた。
それでも、正規化が欠落と曖昧さを5件、実装計画のレビューがさらに3件見つけた。
brainstormの中のレビューを重ねても、欠落は残る。
独立したレビューがこれらを見つけられたかは測っていないので、`kakoi-net` ではこのレビューを省かずに行う。

### 2. brainstormの結果を仕様IRへ正規化する

確定した要求、状態、イベント、応答、不変条件、用語などを構造化する。

正規化はLLMが行い、人間がIRを直接書くことは想定しない。
要求の数と構造の細かさを考えると、人間が手で書き続けることは現実的でないためである。
人間の役割は、LLMが書いたIRの差分をレビューして承認することにある。

概念例:

```yaml
id: KAKOI-NET-001
kind: event_driven
subject: kakoi
trigger:
  event: network_namespace_creation
  result: failure
required_response:
  process_spawned: false
  exit_code: 125
diagnostic:
  kind: network
rationale: ADR-012
provenance:
  - source: brainstorm/2026-08-30-network.md#fail-closed
    quote: "（出典の該当文をそのまま引用する）"
    digest: sha256:...
verification:
  - integration:test_network_namespace_failure
```

実際の保存形式をYAMLにすることは未決定である。
この例の目的は、文章の中に隠れていた主体、条件、応答、根拠、検証方法を個別の要素として扱えることを示すことにある。

#### 出典（provenance）を必須にする

`provenance` は、その要求がbrainstormまたはADRのどの記述に由来するかを指す参照であり、すべての要求で必須とする。
目的はLLMによる補完の検出である。
構文検査は構造の欠落を捕まえるが、LLMがもっともらしく作った要求は構文的に正しいまま通過する。
出典のない要求を `check` で落とすことで、「brainstormで決めていないことをIRが勝手に決めた」状態のうち、出典をまったく持たないものは機械的に検出できる。

ただし、参照先が実在することは、参照先がその要求を述べていることを意味しない。
たとえば `#fail-closed` 節が実在しても、そこに終了コード125まで書かれているとは限らない。
LLMは実在する節を出典に挙げながら、その節が決めていない値を補うことができるので、参照先の存在確認だけではこの種の補完を捕まえられない。

そこで出典は、参照先の位置（`source`）に加えて、引用した原文の範囲（`quote`）とその内容のハッシュ（`digest`）を持つ。

- 要求と引用元の数行を並べて照合できるので、「出典はこの要求を本当に述べているか」の確認が、レビューでもLLMでも小さな作業になる
- brainstormやADRの文章が変わると `digest` が一致しなくなるので、上流が変わって再確認が必要になった要求を機械的に列挙できる

引用範囲との照合は意味の判断なので、`check` ではなくレビューが担う。
`check` が担うのは、出典があること、引用範囲が参照先に実在すること、`digest` が一致することまでである。

出典は、照合のための引用（`quote`）とは別に、追跡のための範囲（節や段落）も持つ。
実験001では、引用をその要求を支える最短の範囲にさせたところ、補完の照合はしやすくなった一方で、要求を変更したときに同じ段落の中の食い違う文が影響範囲から漏れた。
引用は短く保ち、影響範囲を挙げるときは範囲の側を使う。

出典が存在しない要求が本当に必要な場合は、brainstormへ戻して判断を記録してからIRへ追加する。
これはIRがbrainstormを追い越さないための規律であり、例外を設けない。

最小実験に限り、既存の長文仕様の節も仮の出典として認める（「最小実験案」の「長文仕様の扱い」を参照）。
これは出典のない要求を認める例外ではない。
人間が個別に決めた記録ではない出典を、種類を区別したうえで一時的に認めるものである。

#### 要求種別ごとの扱いを分ける

仕様IRは単一種類の要求だけで構成するとは限らない。
少なくとも次の表現が必要になる可能性がある。

- イベント駆動要求
- 状態依存要求
- 常時成立する要求
- 禁止事項
- 不変条件
- 状態遷移
- 決定表
- 順序制約
- データ型と語彙
- 具体例と反例
- 非契約事項
- known gaps

これらのうち、イベント駆動要求、状態依存要求、禁止事項、不変条件はIRの中に条件と応答を直接書ける。
一方、アルゴリズム、優先関係の合成、パス間の関係判定のような手続き的な要求は、IRの中に手続きを書き始めるとRust実装の写しになり、仕様が実装より肥大化する。

そこで手続き的な要求については、IRは手続きそのものを持たず、次の参照だけを持つ方針を最初から採る。

```yaml
id: KAKOI-POLICY-004
kind: algorithm
subject: policy_composition
defined_by:
  - decision_table: tables/policy_precedence.md
properties:
  - narrower_wins
  - deterministic_plan_for_same_input
verification:
  - property:policy_composition_props
provenance:
  - source: adr/ADR-007.md
    quote: "（出典の該当文をそのまま引用する）"
    digest: sha256:...
```

IRが保証するのは「この要求はこの決定表で定義され、これらの性質を満たし、この方法で検証される」という対応関係であり、アルゴリズムの内容は決定表、性質、PBTの側に置く。
この線引きを実験前に決めておかないと、2件目と3件目の実験でIRの表現力を上げる方向に引きずられ、肥大化の危険を自分で実現することになる。

実験001では、この線引きのまま2件目と3件目を表せた（「実験001の結果」）。
一方で、条件と応答を直接持つ要求は、条件の語が依存する決定表や用語を参照できなかった。
たとえば「露出する組になったら止める」という要求は、何が露出する組かを決める決定表に依存するが、それを書く場所がなく、追跡でその要求にぶら下がる例を取りこぼした。
そこで、どの種類の要求も、条件や応答で使う語の定義元（決定表、性質、用語）を参照として持てるようにする。
構造化フィールドの語を用語集で縛る許可リスト（「3. 仕様IRを機械的に検査する」）と組み合わせ、語から定義への参照として持たせる案を第一候補にする。

### 3. 仕様IRを機械的に検査する

実装へ進む前に、仕様そのものを検査する。

- IDが一意である
- 参照する要求、ADR、用語が存在する
- 主体、条件、応答が欠落していない
- MUSTとMUST NOTが同じ条件で衝突していない
- 状態遷移に未定義の状態や到達不能状態がない
- エラー経路に終了状態がある
- 要求に検証方法が対応している
- 未定義の抽象語や曖昧語が使われていない
- 同じ意味の要求が重複していない
- 要求間に循環した依存がない、または循環が明示的に許可されている
- すべての要求に出典（provenance）があり、参照先と引用範囲が実在し、`digest` が一致する
- `kind: algorithm` の要求が `defined_by` と `properties` を持ち、IR内に手続きを持っていない

すべての矛盾を自動検出できるとは想定しない。
構造から決定的に判定できる問題を機械へ移し、意味判断が必要な部分だけを人間とLLMのレビュー対象にする。

正規化で情報が落ちることは、上の検査では見つからない。
実験001では、`check` が正規化の取りこぼしを1件も見つけなかった一方で、IRから文章を書き戻させ、元の文章と同じ盲検の判定にかける方法で18件が見つかった。
そこで、正規化のあとに次の検査を置く。

- IRから人間向けの文章を書き戻す
- ADRとbrainstormの決定のそれぞれが書き戻した文章に書かれているかを、どの文章かを知らないLLMセッションに判定させる（実験では、判定の基準にする決定を正規化の前に一覧として固定する）
- 書かれていない決定は、IRに戻して足す

検査項目のうち、実装コストが低く効果が大きいのは次の3つであり、最初の実験でもこの3つは入れる。

- スキーマ検証とID・参照の解決
- 出典の存在確認（引用範囲の実在と `digest` の一致を含む）
- 禁止された曖昧語の検査（「適切に」「必要に応じて」「通常は」「など」といった、条件や応答を未定義のまま残す語を明示的に列挙する）

曖昧語リストは、LLMが仕様を書くときに逃げ道として使う語を実際の仕様から集めて作る。
一般的な文章作法の禁止語ではなく、このプロジェクトでLLMが実際に使った語を対象にする。

ただし、禁止語リストが効くのは自由記述のフィールドに限る。
主体、イベント、状態のような構造化フィールドには、用語集に定義された語だけを許す許可リストを使う。
禁止語リストは列挙していない逃げ道を通してしまうが、許可リストは用語集にない語をすべて落とせるためである。
最初の実験ではまだ用語集がないので禁止語リストだけを使い、許可リストは用語集を用意する段階で加える。
実験001では、同じ事実を指すイベント名が正規化の回ごとに違う語になった（`bwrap_itself_failed`、`bwrap_self_failure`、`bwrap_own_failure`）。
また、「診断を出して終わる」を、ある件では終了コードまで書き、別の件では診断の種類だけを書いて終わることを書かなかった。
実験002からは用語集を用意し、許可リストと、診断や終了のような共通の事実の書き方の決まりを入れる。

正規化の検査は、最初の正規化のあとの1回で終わりにしない。
実験002では、正規化の検査のあとにIRへ戻した判断（正規化が挙げた問題への判断5件と、実装計画のレビューから戻した3件）に、`check` しかかけなかった。
計画の段で足した「列は文字で数える」という判断は、文字の単位を決めておらず、実装が黙って決めた。
IRへ戻した判断にも、補完の照合レビューと、書き戻しと盲検の判定をかけ直す。

### 4. EARSとして要求を表示する

EARSは、要求の条件と応答を制限された自然言語で表現するビューとして使う。

```text
ネットワーク名前空間の作成に失敗したとき、
kakoiは対象プロセスを起動せず、
種類networkの診断を出して終了コード125で終了しなければならない。
```

EARSは仕様IRから生成するビューとし、正本にはしない。
ただし、イベント駆動、状態依存、常時成立、禁止事項の4種については、IRとEARSの間で情報が落ちない対応を保つ。

EARSのテキストを直接編集したくなった場合、それはIRの表現力が不足しているシグナルとして扱い、EARSではなくIRのスキーマを見直す。
この規律により、EARSが第二の正本になることを防ぐ。

### 5. Gherkinで具体例と境界例を定義する

Gherkinは、要求を利用者または外部観測者から見た具体的なシナリオへ展開する。

```gherkin
@requirement=KAKOI-NET-001
Scenario: ネットワーク名前空間を作成できない
  Given network.mode is "none"
  And creating the network namespace returns EPERM
  When kakoi is requested to execute "sh"
  Then the target process is not spawned
  And kakoi exits with code 125
  And the diagnostic kind is "network"
```

Gherkinは手書きとし、IRからは生成しない。
IRから機械生成した例は要求の言い換えにしかならず、境界例や反例を含まない不毛なものになりやすい。
人間またはLLMが具体的な状況を考える工程として手書きを残す。

代わりに、GherkinをIRに対してlintする。

- `@requirement` タグがIRの要求IDに解決する
- Given/When/Thenで使う語彙がIRの用語集または状態・イベント定義に存在する
- 各要求に少なくとも1件の正常系と1件の境界例または反例がある

Gherkinは独立した新しい要求を追加してはならない。
シナリオの作成中に要求の不足が見つかった場合は、Gherkinだけを修正せず、仕様IRへ戻って要求を変更する。

### 6. 必要な部分だけ形式手法で検査または証明する

仕様全体を形式化するのではなく、誤りの影響が大きく、状態や組み合わせとして表現しやすい部分へ限定する。

`kakoi` で候補になり得るもの:

- ポリシーの段の合成
- narrower-wins
- 指令間の優先関係
- 根の項目の判定
- 露出する組
- fail-closed
- 検査段階の順序
- パス間の祖先・子孫関係
- 同一入力から同一計画が得られる決定性

形式化の途中で矛盾や定義不足が見つかった場合は、証明を通すために形式モデルだけを変更せず、仕様IRまたはbrainstormへ戻す。
形式手法は証明器だけでなく、仕様のデバッグ手段として扱う。

形式モデルと仕様IRを完全に自動変換できない場合は、定理やpropertyが検証する要求IDを記録する。

証明する性質は、設計を分ける前に決める。
実験002では、Rustのコードに直接当てられる検証器（Kani）で、判定の2つの性質を証明した。
文字列を扱う部分は検証器で解き終わらない見込みが高かったので、判定を「当たったルールを求める段」と「当たったルールだけから結果を決める段」に分け、後の段にだけ証明を当てた。
証明は2つとも通ったが、後の段は分岐が3つの関数になり、証明のうち1つは空の入力を1通り調べるだけだった。
証明しやすい継ぎ目で設計を分けると、性質の中身は証明の外（ここでは性質のテストの側）へ出ていき、証明には中身が残らない。

### 7. 人間向け仕様書を組み立てる

人間向け仕様書は、仕様IR、EARS要求、決定表、Gherkin例、ADRへの参照などから生成または構成する。
これは意味の正本ではなく、用途別に読みやすくしたビューとする。

想定するビュー:

- 製品概要
- 目的と非目的
- 用語集
- CLI契約
- ポリシー
- セキュリティモデル
- アルゴリズム
- 状態遷移と決定表
- 診断一覧
- 利用例
- known gaps
- 非契約事項
- IR差分のレビュー用ビュー（変更された要求と、その出典の引用範囲を並べる）

生成物に誤りや不足を見つけた場合、原則として生成されたMarkdownを直接修正せず、仕様IRまたは生成規則へ戻して修正する。

### 8. planとcycleは確定した要求IDを単位に進める

planは長文仕様を再解釈してタスクを作るのではなく、確定した要求IDと検証方法からタスクを組み立てる。

```text
KAKOI-NET-001
    -> ADR-012
    -> scenarios/network.feature
    -> tests/network.rs::network_namespace_failure
    -> crates/kakoi-net/src/...
```

実装中に仕様不足が発見された場合は、実装に合わせて仕様書を黙って修正しない。
cycleを一度止め、仕様変更として仕様IRへ戻す。
仕様変更後に検査と派生物の更新を行ってからcycleを再開する。

実験002では、IRへ戻す手順は計画の段で3回働いたが、実装の後の調査で、IRのどの要求からも決まらない振る舞いが4件見つかった。
そのうち2件（公開する型に付ける性質、TOMLとして読めないときの列の数え方）は、実装が黙って決めていた。
そこで、次の2つをplanとcycleに加える。

- planで、公開する型と関数の形（型に付ける性質や、誤りの表示の仕方を含む）を列挙し、IRが決めていないものはIRへ戻して決めるか、実装に委ねると記録する
- IRのどの要求にも当たらない振る舞いを探す調査を、実装の完了後ではなく、cycleのレビューの中で行う。見つかったものはcycleを止めてIRへ戻す

#### この規律はツールで強制する

上の規律は、スキルの指示だけでは守られない。
開発者が1人の環境では承認境界が実質的に存在せず、LLMは仕様書を黙って直す代わりにIRを黙って直すようになる。
失敗モードが別のファイルへ移るだけで何も改善しない。
過去にpre-commitフックが `--no-verify` と環境変数で迂回された経験からも、エージェントが書き換えられる場所に置いた制約は機能しないと考える。

そこで `kakoi` と同じ発想で境界をエージェントの外側に置く。

- cycleで動くエージェントは `spec/` 配下へ書き込めない（隔離側のマウント設定で実現する）
- IRの変更は実装と別コミットとし、コミットにrationaleまたはbrainstormへの参照を必須にする（判定はcycle起動側のガードまたはリモートのCIで行い、エージェントが迂回できるフックには置かない）
- `check` が失敗した状態ではcycleを開始できない（スキルではなく、cycle起動側のガードで判定する）

ただし、ここで書き込みを禁じられるのはcycleで動くエージェントだけである。
正規化はLLMの仕事なので、specifyを担うLLMは正当に `spec/` へ書き込む。
こちらは書き込みを禁じて守ることができないため、防止ではなく検出で守る。

- 出典のない要求は `check` が落とす
- 出典はあるが出典が述べていない要求は、引用範囲との照合で見つける
- IRの差分は、実装とは別に必ず人間のレビューに回す

cycle側は書き込めないことで守り、specify側は書かれたものを必ず見つけられることで守る。

これらが揃って初めて「cycleを止めて仕様へ戻る」が実在する工程になる。
逆に言えば、この強制ができないなら、この構想はワークフロー文書を増やすだけで実装精度には寄与しない。

## EARS、Gherkin、形式手法の役割

これらは競合する記法ではなく、異なる問題を扱う。

| 手段 | 主な役割 | 苦手なもの |
|---|---|---|
| EARS | 一般要求の条件と応答を明確にする | 複雑な組み合わせ、アルゴリズム |
| Gherkin | 具体例、境界例、受け入れ条件を示す | 一般性の証明、内部構造 |
| 決定表 | 条件の組み合わせを網羅する | 時間的な状態変化、理由 |
| 状態遷移 | 状態とイベントの関係を示す | 詳細なデータ変換 |
| PBT | 広い入力について不変条件を検査する | モデル自体の正しさの証明 |
| 形式手法 | 限定されたモデルについて性質を証明する | 実装との対応、曖昧な要求 |
| ADR | 判断理由と却下案を残す | 現在の振る舞いの完全な定義 |

一つの記法ですべてを表現するのではなく、仕様IRを中心に適切なビューへ分ける。

## スキルと専用ツールの分離

この仕組みを `agentic-workflow` のスキルだけで実現するのは難しい。
スキルは、エージェントがいつ、なぜ、どの操作を行うかを案内する。
一方、構文検査、参照整合性、生成、追跡は専用ツールが担う。

```text
agentic-workflow skills
    - brainstorm
    - specify
    - plan
    - cycle
    - review
             |
             v
specification engine
    - check
    - render
    - trace
    - query
```

スキル側の責務:

- brainstormの結果から仕様候補を抽出する
- 仕様ツールを呼ぶタイミングを決める
- 機械検査で決められない問題を利用者へ返す
- 仕様変更時に適切な工程へ戻す
- plan、cycle、reviewへ要求IDを受け渡す

ツール側の責務:

- 仕様IRを読み書きする
- スキーマを検証する
- 参照、重複、単純な矛盾を検出する
- EARSと人間向けMarkdownを生成する
- 手書きのGherkinをIRに対してlintする
- 要求、ADR、テスト、実装、証明の対応を追跡する
- LLMが必要な仕様部分だけを取得できるようにする

## `AGENTS.md` をアダプターとして使う案

専用ツールは `agentic-workflow` に密結合させない。
各リポジトリの `AGENTS.md` に、使用するコマンドと成果物の場所を記述することで後付けできる形を検討する。

概念例:

```markdown
## Specification

- Canonical specification: `spec/requirements/`
- Validate: `spec-tool check`
- Render documentation: `spec-tool render`
- Show requirement trace: `spec-tool trace <REQUIREMENT_ID>`
- Before planning or implementation, validation must pass.
- If implementation reveals a missing or conflicting requirement, stop the cycle and return to specification work.
- Generated files under `docs/spec/` must not be edited directly.
```

これにより、スキルを導入していないエージェントでも `AGENTS.md` を読めば同じ仕様操作を利用できる。
また、リポジトリごとに別の仕様ツールを使う場合も、コマンドを差し替えることで適応できる可能性がある。

ただし、自由なコマンド記述だけでは、スキルが出力形式を理解できない。
将来的には、終了コード、JSON出力、診断形式などについて小さなアダプター契約が必要になる可能性がある。

アダプター契約の標準化は、2つ目のリポジトリで使うまで行わない。
1リポジトリでの利用から抽象化した契約は、実際には `kakoi` 固有の都合を一般化したものになりやすい。

## 最小実験案

この節は実験001の設計であり、2026-09-11 に実施した。
結果は「実験001の結果」に、詳細は `experiments/001-kakoi-ir/LOG.md` に記す。

最初から完全な仕様管理システムを作らない。
まず `kakoi` の既存仕様から性質の異なる3項目だけを抜き出し、仕様IRとして表現できるか試す。

1. ネットワーク隔離失敗時のfail-closed要求（イベント駆動）
2. 指令の組み合わせと優先関係（アルゴリズム・決定表）
3. パス解決、根の項目、露出する組に関する規則（アルゴリズム・関係判定）

1件目はEARSにもIRにも素直に収まる要求であり、通ることが分かっている。
この実験の本体は2件目と3件目であり、手続き的な要求を「参照のみを持つIR」で扱えるかが問われる。
1件目が通った段階で構想の妥当性を判断しない。

### 長文仕様の扱い

`kakoi` には、brainstormの記録やADRが独立したファイルとしては残っていない。
判断の記録は、承認済みの長文仕様 `docs/spec/kakoi.md` にまとまっている。
そこでこの実験では、長文仕様を正規化の入力にする。

ただし、長文仕様は正本ではなく被検体（この実験で調べる対象）として扱う。
長文仕様はLLMが書き、文書全体として承認されたものであり、この構想の出発点である「LLMに書かせた長文仕様は自己矛盾を抱えやすい」という仮説の実物にあたる。
3件を構造化する過程で長文仕様の矛盾や欠落がいくつ見つかるかは、この仮説の直接の証拠になる。

被検体として扱うため、次の規則を置く。

- 長文仕様の節は、この実験に限って仮の出典にしてよい。
  ただし人間が個別に決めた記録ではないので、出典の種類を区別して記録する（例: `source_kind: legacy_spec`）
- 正規化の途中や `check` で長文仕様の矛盾や欠落が見つかっても、正規化を行うLLMに解決させない。
  矛盾する読みをそれぞれの出典とともに並べ、印を付けて返させる
- 印の付いた箇所は人間が判断し、その判断をADRとして記録する。
  その要求の出典は、長文仕様の節からADRへ付け替える

この規則がないと、長文仕様がすでに抱えている補完や矛盾がIRへそのまま写る。
その場合、実験に通っても「IRは長文仕様を忠実に写せる」ことしか示せない。

この実験で確かめられるのは、アルゴリズム系の要求をIRで表現できるか、構造化によって長文仕様の矛盾が見つかるか、LLMの補完を捕まえられるか、コンテキストを小さくできるかである。
brainstormからADRを経てIRを作る流れが矛盾をはじめから防げるか、形式手法による証明にどれだけ価値があるかは、この実験では確かめられない。
これらは「`kakoi-net` での試験導入」で確かめる。

### 成功基準

実験開始前に次の基準を固定し、終了後に基準ごとに判定する。
基準を満たさない項目があっても構想全体を否定しないが、どの基準がどう外れたかを記録する。

| 基準 | 測定方法 | 合格条件 |
|---|---|---|
| コンテキストの縮小 | 要求1件について `query` 相当の出力トークン数と、現在planに渡している長文仕様の該当箇所のトークン数を比較する。`kind: algorithm` の要求では、`defined_by` が指す決定表と性質の本文も出力に含めて数える | 出力が該当箇所より小さく、かつ次の「条件の欠落なし」を満たす |
| 条件の欠落なし | 実験開始前に、長文仕様の該当箇所が定める条件の一覧を作って固定する。新規セッションに `query` 相当の出力だけを渡してテストを書かせる試行と、長文仕様を渡してテストを書かせる試行を、それぞれ3回行う | 一覧の各条件について、IRから書かれたテストがその条件を検証した回数が、長文から書かれたテストの回数を下回らない。矛盾の印が付いた条件は集計から外す |
| 不備の検出 | LLMが正規化した3件（混入前）に `check` を実行する。出典の特定や正規化の作業中に見つかった不備と、`check` が見つけた不備は分けて記録する | `check` が矛盾または欠落を1件以上検出する。正規化の作業中に見つかった不備は `check` の成果に数えない。0件の場合は「仕様が良い」と「検査が弱い」を区別できないため、結論保留とする |
| 補完の検出 | LLMが正規化した3件に、(a) 出典を持たない要求と、(b) 実在する節を出典に挙げながらその節が述べていない値を持つ要求を1件ずつ混ぜ、`check` と引用範囲との照合レビューにかける。混ぜる役は正規化とも照合レビューとも別のセッションが担い、照合レビューはどれが混ぜられた要求かを知らない状態で行う | (a) を `check` が落とし、(b) を照合レビューが見つける。照合レビューが (b) 以外に指摘した要求は、LLMが自然に行った補完の候補として記録する |
| 肥大化しない | 3件のIRの行数（`defined_by` が指す決定表と性質の行数を含む）と、対応する実装およびテストの行数を比較する | IRが実装とテストの合計を超えない。アルゴリズム系ではIR本体が20行程度に収まる |
| 追跡可能 | 既存の実装とテストへ要求IDを付け終えてから、変更する要求を1件選ぶ。その要求を変更し、影響する例、テスト、実装、文書を要求IDから列挙する | 手作業で確認した影響範囲と一致する |
| 再構成可能 | 3件からMarkdownを再構成する | 元の長文の該当箇所と比べて情報が落ちていない。矛盾を人間が判断した箇所は、ADRの判断に従っていればよい。読みやすさは主観評価として別に記録する |

次の2つは上の表に含めず、合否に使わない。
実験後に記録だけを残す。

- 「人間が元の長文より理解しやすいか」の主観評価
- 同じ入力で独立に行った正規化どうしの差分。
  回ごとに値が変わるフィールドは、元の文章からは決まらずLLMが補った可能性がある。
  この差分が補完の目印として使えるかは未検証の仮説なので、この実験では観察にとどめる

### 実験の手順

1. 3件について、長文仕様の該当箇所を特定する。
   あわせて、成功基準「条件の欠落なし」で使う条件の一覧を該当箇所から作って固定する。
   該当箇所の中で互いに矛盾する条件には印を付ける。
   この一覧は、正規化を行うLLMには渡さない
2. 新規セッションのLLMに、長文仕様を渡して3件をYAMLへ正規化させる。
   コードは渡さず、読める状態にもしない。
   実装から読み取った内容に長文仕様の出典を付けられると、出典の検査が意味を失うためである。
   IRのスキーマ、出典の書き方、曖昧語リスト、「長文仕様の扱い」の規則（矛盾や欠落を解決せず、印を付けて返す）はプロンプトに直接書き、使ったプロンプトを記録する。
   YAMLは保存形式の決定ではなく、実験用の暫定形式とする
3. 同じ入力で、独立したセッションにさらに2回正規化させ、3回分の差分を記録する。
   以降の手順には1回目の結果を使う。
   印の付いた矛盾や欠落は、この時点では解決しない
4. スキーマ検証、ID・参照解決、出典確認、曖昧語検査を行う100行程度のスクリプトを書く。
   専用CLIとしては設計しない。
   書いたスクリプトで、1回目の結果に `check` を実行し、成功基準「不備の検出」を判定する
5. 成功基準「補完の検出」を判定する。
   正規化とも照合レビューとも別のLLMセッションが、1回目の結果に (a) と (b) を1件ずつ混ぜる。
   どの要求を対象にし、どの値を入れるかも、そのセッションが決める。
   混ぜたセッションの記録は、照合レビューが終わるまで開かない。
   照合レビューは、混ぜた内容を知らない人間または別のLLMセッションが、全要求を引用範囲と照合して行う。
   混ぜる役とレビューする役が同じだと、どれを混ぜたかを知ったうえで探すことになり、見つかって当然になるためである。
   判定後、混ぜた2件は取り除く
6. 正規化で印の付いた矛盾や欠落と、`check` が見つけた不備を、人間が判断してADRに記録する。
   該当する要求の出典は長文仕様の節からADRへ付け替え、条件の一覧の該当する条件にも矛盾の印を付ける。
   手順4より前に解決すると、`check` が見つけられたはずの不備を測れなくなるため、ここで解決する
7. `query` 相当の出力を手作業で作り、新規セッションでのテスト生成比較を行う。
   IR側と長文側をそれぞれ3回試行する
8. 既存の実装とテストへ要求IDを付け終えてから、変更する1件を選んで追跡実験を行う。
   変更する要求を先に決めてからIDを付けると、影響範囲を知ったうえで付けることになり、手作業の確認と一致して当然になるためである
9. 成功基準ごとに結果を記録し、次に進むか、IRの線引きを変えるか、構想を縮小するかを判断する

### 実験で実装しないもの

専用CLI、Lean連携、Gherkin実行環境、EARS生成、`AGENTS.md` アダプター。
LLMが書いた数件のデータと検証スクリプトだけで、仕様IRの表現力と認知負荷を評価できる。

### 想定される結果と、それぞれの解釈

- 3件とも基準を満たす場合: 最小ツール案へ進む
- 1件目のみ満たし、2件目と3件目でIRに手続きを書かないと表現できない場合:
  「アルゴリズム系はIRの対象外」という線引きが結果であり、失敗ではない。
  IRの範囲をイベント駆動・状態依存・禁止・不変条件に限定し、アルゴリズム系は決定表とPBTのみで扱う
- コンテキストの縮小が成立しない場合: 構想の主要な利点が消えるため、構想を縮小するか中止する
- 不備の検出が0件の場合: 結論保留。
  検査項目を増やすか、別の3件で再実験する
- 補完の検出で (b) を見つけられない場合: LLMの補完を捕まえる手段がないまま、正規化をLLMに任せることになる。
  構想の成否を左右する仕組みが成立しないため、構想を縮小するか中止する

## 実験001の結果

成功基準ごとの判定は次のとおりである（詳細と数値は `experiments/001-kakoi-ir/LOG.md`）。

| 基準 | 判定 | 要点 |
|---|---|---|
| コンテキストの縮小 | 不合格 | 1件目と2件目はIRのほうが大きく（1.73倍、1.44倍）、3件目は小さい（0.79倍）が条件の欠落なしを満たさない |
| 条件の欠落なし | 不合格 | IRから書いたテストのほうが少ない回数しか確かめなかった条件が138件中20件。確かめた総量はIR側が344、長文側が335 |
| 不備の検出 | 結論保留 | `check` が見つけた被検体の不備は0件 |
| 補完の検出 | 合格 | 混ぜた2件を、`check` と盲検の照合レビューがそれぞれ見つけた |
| 肥大化しない | 合格（実験者の読み） | IRは対応する実装とテストの合計の0.34〜0.54倍。アルゴリズムの要求そのものは15〜20行 |
| 追跡可能 | 不合格 | 実装とテストは取りこぼさなかったが多すぎた。仕様書は手作業の範囲の約4分の1しか挙げられなかった |
| 再構成可能 | 不合格 | IRから書き戻した文章で18の条件が落ちた。18件ともIRの側に情報がなかった |

構想の「想定される結果と、それぞれの解釈」のうち、「コンテキストの縮小が成立しない場合」に当たった。
一方、「2件目と3件目でIRに手続きを書かないと表現できない場合」には当たらず、アルゴリズムの要求を参照だけで持つ線引きは成り立った。

結果の読み方として、次のことが分かった。

- 不合格の直接の原因の多くは、IRという形ではなく、正規化での情報の落ち、要求どうしの依存を書けないスキーマ、1条件ずつ比べる合格条件がばらつきに弱いことにあった
- `query` の出力に含めた検証方法（`verification`）の文は、IR側の入力の25〜30%を占め、テストを書く側の範囲を狭めることがあった
- 既存の仕様の問題（矛盾1件を含む）は実際に見つかった。ただし対照実験で、構造化させずに問題だけを探させても同じ問題が見つかったので、問題の発見はIRの価値にはならない
- IRから範囲を絞って書き戻した人間向けの文章は、元の仕様書よりずっと読みやすいという主観評価を得た

これを受けて、構想は中止せず、手法を直して実験002を行う。
直す内容は、「1. brainstorm」の問題を探すレビュー、出典の追跡用の範囲、要求どうしの依存の参照、用語集の許可リスト、正規化の取りこぼしの検査である。

## 小さなプロジェクトでの試験導入（実験002）

実験001は既存の長文仕様を後から構造化したもので、「目的」に置いた流れをbrainstormから通したことは一度もない。
`kakoi-net` は失敗したくない開発なので、先に小さな題材で流れを最後まで通し、手法を仕上げてから `kakoi-net` に持ち込む。

### 題材

通信先の許可ルールを判定するライブラリを作る。
ホスト名、ワイルドカード、ポートで書いた許可と拒否のルールを読み、ある通信先を通すか止めるかを決める純粋なライブラリで、ルールの設定が壊れていれば通信をすべて止める（fail-closed）。

この題材を選んだ理由は次のとおりである。

- `kakoi-net` が加えようとしている「特定の通信先だけを許可する」段階の中心部分に近く、仕上げた手法と成果物をそのまま持ち込める
- ルールの優先順位と一致の規則はアルゴリズム系の要求になり、決定表、性質のテスト（PBT）、形式手法による証明のどれも試せる
- 数百行程度に収まる見込みで、流れを最後まで通せる

言語は `kakoi` と同じRustとし、`kakoi` とは独立したライブラリとして `experiments/002-*/` に置く。
ライブラリの名前と正確なスコープはbrainstormで決める。

実験002でも専用CLI（`spec-tool`）は作らず、実験001と同じく実験用のスクリプトで検査、書き戻し、追跡を行う。
専用CLIを作る条件（「最小実験の成功基準を満たしてから」）は実験001で満たされていないためである。
スクリプトには、用語集の許可リスト、どの種類の要求にも持たせる定義元の参照、書き戻しと盲検の判定を加える。
IRの保存形式は引き続きYAMLを暫定とする。

### 流れ

1. brainstormで判断し、ADRに記録する
2. brainstormの記録とADRから、決定の一覧を作って固定する。この一覧は正規化を行うLLMに渡さない
3. 問題を探すレビューを行い、見つかった問題を人間が判断してADRに記録する
4. LLMが仕様IRへ正規化する。出典はbrainstormの記録とADRにする
5. `check`、補完の照合レビュー、書き戻しと盲検の判定で正規化を検査し、不足をIRへ戻す
6. 必要な性質だけ形式手法で証明する（任意）
7. `query` 相当の出力からplanを作る
8. cycleで実装する。テストと実装には要求IDを付ける。仕様の不足が見つかったらcycleを止め、IRへ戻す
9. IRから人間向けの文書を生成する

### 成功基準

実験001の反省から、試行どうしの回数を比べる基準は置かず、あるかないかで判定できる基準にする。

| 基準 | 測定方法 | 合格条件 |
|---|---|---|
| 実装の段で仕様の矛盾が見つからない | plan以降（plan、実装、テスト、レビュー）で見つかった仕様の矛盾と欠落を、見つかった段と入った段とともにすべて記録する | 矛盾が0件。欠落は、cycleを止めてIRへ戻す手順で処理され、実装の側で黙って決めたものが0件 |
| 実装がIRにない振る舞いを持たない | 実装の完了後、実装を書いていない別のLLMの調査役が、IRと実装のコードを読み、IRのどの要求にも当たらない振る舞いを挙げる | 挙がったものがすべて、IRへ戻して判断した記録を持つ |
| テストが要求を証明する | 要求IDでテストと要求の対応を数える。実装に小さな変更を入れるミューテーションテストを行う | テストのない要求と、要求IDの付いていないテストが0件。要求に対応する実装で見逃された変更が0件（等価な変更と判断したものは理由を記録して除く）。アルゴリズム系の要求はすべて性質のテストを持つ |
| 追跡可能 | 完成後、固定した種で要求を1件選び、変更の影響を要求IDから挙げ、IDを使わない別の調査役が挙げたものと比べる | 実装、テスト、IR、生成した文書のどれでも、IDからの範囲が別の調査役の範囲を取りこぼさない。多すぎた分は記録する |
| 再構成可能 | IRから人間向けの文書を生成し、手順2で固定した決定の一覧と、どの文書かを知らないLLMセッションに突き合わせさせる | 落ちた決定が0件 |

次のものは合否に使わず、記録だけを残す。

- 形式手法で扱った性質、見つかった仕様の不備、かかった手間
- 工程ごとの時間と費用
- 生成した人間向け文書の読みやすさの主観評価

### 想定される結果と、それぞれの解釈

- すべての基準を満たす場合: 仕上げた手法で `kakoi-net` の試験導入に進む。あわせて、実験用のスクリプトのどこまでを専用CLIにするかを決める
- 実装の段で仕様の矛盾や欠落が見つかった場合: 1件ずつ、brainstormとADRの時点で見つけられたかを判断する。見つけられたのに見逃したものは、問題を探すレビューか正規化の検査の不足であり、その工程を直す。brainstormとADRの時点では見つけようがなかったもの（実装して初めて分かる制約など）は、流れの限界として記録し、cycleを止めてIRへ戻す手順が働いたかで評価する
- 実装がIRにない振る舞いを持っていた場合: その振る舞いが要求の不足を示すのか、実装の都合による補完なのかを分ける。前者はbrainstormへ、後者はcycleの規律（「8. planとcycleは確定した要求IDを単位に進める」）の不足として扱う
- ミューテーションテストで見逃された変更があった場合: テストを足す前に、要求がその変更を区別できるほど具体的かを確かめる。要求が曖昧ならIRへ戻し、要求は具体的なのにテストが見ていないなら、テストの書き方の決まりを直す
- 追跡で取りこぼしがあった場合: 取りこぼしごとに、要求どうしの依存の参照が足りなかったのか、出典の追跡用の範囲が足りなかったのかを分け、スキーマか出典の決まりを直す

### 開始前に決めること

- 比較対象を置くか。同じ題材を今のやり方（brainstorm、長文仕様、plan、cycle）でも作れば、この流れが今のやり方より良いかまで分かるが、費用と手間はおよそ倍になる。置かない場合、分かるのは「この流れで目的に届くか」までである
- brainstormに `ba0918-brainstorm` をそのまま使うか。このスキルは長文の仕様書を書くので、その文書をbrainstormの記録として出典に使うのか、判断の記録とADRだけを出典にするのかを決める
- 「8. planとcycleは確定した要求IDを単位に進める」の強制（cycleのエージェントが `spec/` に書き込めない）を、`kakoi` のマウント設定で実際に行うか
- 形式手法の道具。Rustのコードに直接当てられる検証器か、Leanなどの別のモデルか
- 題材を小さく保つための上限。brainstormのあとの決定の数や、実装の行数の目安を決め、超えそうならスコープを削る。題材が `kakoi-net` 並みに育つと、小さく試す意味がなくなる

## 実験002の結果

成功基準ごとの判定は次のとおりである（詳細と数値は `experiments/002-allowlist/LOG.md`）。

| 基準 | 判定 | 要点 |
|---|---|---|
| 実装の段で仕様の矛盾が見つからない | 不合格 | 矛盾は0件。計画の段で見つかった欠落3件はIRへ戻す手順で処理した。しかし実装が黙って決めたものが2件あった |
| 実装がIRにない振る舞いを持たない | 合格（実装の後に戻した） | 挙がった4件すべてを、実装の後にIRへ戻して判断した |
| テストが要求を証明する | 合格 | テスト114件のすべてが要求IDを持ち、テストのない要求は0件。ミューテーションテストの見逃しは、理由を記録した等価な変更4件だけ |
| 追跡可能 | 不合格 | 別の調査役が挙げたテスト18件のうち、IDから挙げられたのは7件。実装の関数はIDから挙げられなかった |
| 再構成可能 | 合格 | IRから書き戻した文章に、固定した決定59件のすべてが書かれていた |

実装の段で見つかった欠落と、黙って決められたものを、brainstormとADRの時点で見つけられたかで分けると次のようになる。

- 誤りの位置の数え方の2件は、使ったTOMLのライブラリが誤りの位置をバイトの範囲でしか返さないことから出た。実装の道具を確かめて初めて分かる制約であり、IRへ戻す手順が働いたので、流れの限界として記録する
- 「ライブラリの関数は2つ」が、戻り値のメソッドを数えるかで2通りに読めた1件は、brainstormの時点で見つけられた
- 公開する型に付ける性質は、brainstormでも決められたが、誰も問わなかった。planで公開する形を列挙しなかったことが原因である（「8. planとcycleは確定した要求IDを単位に進める」に変更を加えた）
- 列の文字の単位は、計画の段でIRへ戻した判断が入れた曖昧さである。戻した判断に正規化の検査をかけ直さなかったことが原因である（「3. 仕様IRを機械的に検査する」に変更を加えた）

ただし、実験002では流れの3（問題を探す独立したレビュー）を行っていない。
見つけられたのに見逃したものを、そのレビューの不足とは読めない（「1. brainstormで探索と意思決定を行う」）。

IRにない振る舞いの4件は、要求の不足が1件（列の文字の単位）、実装の都合による補完が1件（公開する型の性質）、IRから導けるものが1件、IRの中の性質の文と決定表の食い違いが1件だった。
最後の1件は、「末尾に点を1つ付けても取っても当たるかは変わらない」という性質の文が、末尾に点が2つある通信先で表と食い違ったもので、性質の文を直した。

追跡の取りこぼしは、「想定される結果」に書いた2つの原因（要求どうしの依存の参照、出典の追跡用の範囲）のどちらでもなかった。
1つ目の原因は、1つの要求を選んでから変更の中身を決めたので、変更がほかの要求（誤りの順と種類の表）に及んだことである。
2つ目の原因は、実装の関数がIDを持たないことである。
どちらも `trace` の方針に反映した（「最小ツール案」の `trace`）。

再構成可能は合格したが、入力が決定を1行ずつ書いた判断の記録だったので、実験001との違いが手法の変更の効果なのか入力の違いなのかは分けられない。
また、判定の基準にした決定の一覧は正規化の前に固定したので、正規化のあとに足した判断（10件）は判定していない。

記録だけを残すものは次のとおりである。

- 形式手法: 証明は通ったが、証明の境界の引き方のために中身がなかった（「6. 必要な部分だけ形式手法で検査または証明する」）
- 費用: 正規化とその検査で約6ドル。cycleは報告値で1回目4.96ドル、3回目51.88ドル（3回目の値がサブエージェントの分と、メモリ不足で止まった2回目の分を含むかは確かめていない）
- 読みやすさ: 書き戻した文章への利用者の評価は「なんともいえない」で、判定に使える評価は得られなかった

「想定される結果」のうち「すべての基準を満たす場合」には当たらない。

## `kakoi-net` での試験導入

実験002で流れと手法を仕上げてから始める。
候補は、`kakoi` のネットワーク制限を担う内部crate `kakoi-net` である。
現状のネットワーク制限は `host` と `none` の二択であり、特定の通信先だけを許可する中間の段階を加える構想がある（`kakoi` の `.agents/artifacts/network-policy-notes.md`）。
構想はまだ承認前のメモの段階なので、brainstormから始められる。
実験002の成果物（許可ルールの判定ライブラリ）を部品として持ち込めるかも、このときに判断する。
判定の基準は、実験002の結果を見て開始時に定める。

## 最小ツール案

仕様IRの実験が成立した場合、最初のCLIは小さく保つ。

```console
spec-tool check
spec-tool render
spec-tool trace KAKOI-NET-001
spec-tool query --for-plan KAKOI-NET-001
```

### `check`

- スキーマ検証
- IDと参照の検査
- 構造化フィールドの用語の許可リスト検査と、自由記述フィールドの禁止語検査
- 単純な要求衝突の検査
- 検証方法（`verification`）の存在確認
- GherkinのIRに対するlint

### `render`

- 人間向けMarkdown
- EARSビュー
- 手書きのGherkinシナリオを要求IDごとにまとめた一覧（シナリオ自体は生成しない）
- 決定表や一覧
- IR差分のレビュー用ビュー

### `trace`

- 要求からADR、例、テスト、実装、形式モデルへの対応を表示する
- 逆方向にも検索できることが望ましい
- 影響範囲を挙げる起点は、選んだ1つの要求ではなく、IRの差分で変わった項目すべてにする。実験002では、起点を変えるだけで、別の調査役が挙げたテストのうちIDから挙げられたものが18件中7件から14件に増えた。ただし残りの4件と、ADRの節1件は、IDの参照ではつながらなかった
- 実装の関数へは、IDの付いたテストからたどる候補を第一にする（未測定）。実装の関数にIDのコメントを付けても、そのコメントを検査するものがないので、実装が変わるとずれるためである

### `query`

- planやcycleが必要とする要求、その依存、用語、例外だけを返す
- 長文仕様全体を毎回LLMへ渡さない
- 機械利用向けに安定したJSON形式を持つ
- 検証方法（`verification`）の文を返すかは用途で分ける。実験001では、テストを書く側がこの文に書かれた場面だけを試し、要求の範囲より狭いテストになることがあった

## 想定される利点

- 長文仕様全体をLLMが毎回再解釈する必要が減る（実験001では、渡すコンテキストの大きさは縮まらなかった）
- 人間とLLMが同じ要求IDを参照できる
- 機械的に検出できる仕様不備をレビューから除外できる
- 人間向け文書を、用途ごとの読みやすいビューに分けられる
- 実装中に生じた仕様変更を独立したイベントとして扱える
- テストが製品仕様の何を検証しているか追跡できる（実験002では、すべてのテストが要求IDを持った）
- 形式手法を全面導入せず、価値の高い部分へ限定できる
- `AGENTS.md` を介して既存リポジトリへ段階的に導入できる

## リスクと未解決事項

### 仕様の正本が増える危険

EARS、Gherkin、形式モデル、人間向け仕様書、テストを別々に手書きすると、現在より同期対象が増える。
どれが正本で、どれが派生物または部分的な写像なのかを決める必要がある。

### 仕様IR自体が巨大化する危険

自然言語の複雑さを構造化データへ移しただけになる可能性がある。
構造化によって検索、検査、生成が改善するかを評価し、単なる冗長化になっていないことを確認する必要がある。

### すべての意味をスキーマに押し込む危険

理由、背景、トレードオフまで形式化しようとすると、brainstormとADRの役割を侵食する。
構造化する対象は、実装と検証に必要な契約へ限定する必要がある。

### 検証の検証が際限なく続く危険

仕様を検証するテスト、そのテストを検証する仕組み、さらにその検証を確認する仕組みという再帰に陥る可能性がある。
機械検査の適用範囲と終了条件を明示し、製品仕様へ追跡できない検証を増やさない。

### 形式モデルと実装の乖離

Leanなどでモデルを証明しても、Rust実装がそのモデルに従う保証は自動では得られない。
形式化の価値、対応付けの方法、維持コストを要求ごとに判断する必要がある。

### LLMが形式を満たすだけになる危険

構文検査に通っても要求の意味が正しいとは限らない。
LLMが不足した要求をもっともらしく補完したり、検査を通すためだけの定義を作ったりする可能性がある。
brainstormでの判断と独立レビューは引き続き必要である。

### 仕様管理製品へ肥大化する危険

UI、履歴、承認フロー、共同編集、一般的な課題管理まで含めると、仕様管理版Jiraになり得る。
当面はローカルファイル、CLI、既存のGit履歴、`AGENTS.md` に限定する。

### 失敗モードが別のファイルへ移るだけになる危険

現在の問題は「LLMが実装に合わせて仕様書を黙って直す」ことである。
IRを導入しても、LLMが実装に合わせてIRを黙って直せるなら、正本の形式が変わっただけで問題は残る。
「8. planとcycle」で述べたツールによる強制がこの危険への対処であり、強制なしの導入は行わない。
specifyを担うLLMは書き込み自体を禁じられないため、同節で述べた検出で対処する。

### 実験で1件目だけを見て判断する危険

イベント駆動要求はどの記法でも綺麗に表現できるため、1件目の成功は構想の妥当性を示さない。
成功基準は3件すべてに適用し、特に2件目と3件目の結果で判断する。

## 壁打ちしたい論点

決着したもの（これまでの改訂で仮決定）:

- EARSは生成ビューとする。
  編集したくなったらIR設計の不足シグナルとして扱う
- Gherkinは手書きし、IRに対してlintする
- アルゴリズム、決定表、状態遷移は同じIRで「参照」として扱い、内容はIRの外に置く
- 仕様変更の承認境界は、エージェントの外側のツールとマウント設定で強制する。
  cycle側は書き込み禁止による防止、specify側は出典の検査と差分レビューによる検出で守る
- `AGENTS.md` のアダプター契約は2リポジトリ目まで標準化しない
- 専用CLIは最小実験の成功基準を満たしてから実装する
- 仕様IRはLLMが書き、人間はIRの差分をレビューする
- 専用CLIを実装する場合の言語はRustを想定する
- 最小実験では既存の長文仕様を被検体として入力にし、正本にはしない
- 問題を探す役割は正規化から切り離し、brainstormとADRへの独立したレビューに持たせる（実験001の対照実験）
- 正規化の取りこぼしは、書き戻しと盲検の判定で検査する（実験001）
- どの種類の要求も、条件や応答の語の定義元を参照として持てるようにする（実験001）
- `kakoi-net` の前に、小さな題材（通信先の許可ルールの判定ライブラリ）で流れを通す（実験002）
- planで公開する形を列挙し、IRにない振る舞いを探す調査をcycleのレビューの中で行う（実験002）
- IRへ戻した判断にも、正規化の検査をかけ直す（実験002）
- 追跡の起点はIRの差分で変わった項目すべてにする（実験002）
- 形式手法で証明する性質は、設計を分ける前に決める（実験002）

未決着のもの:

- IRの表層構文は何にするか（実験ではYAML暫定）。
  LLMが書き、機械が検証し、人間が差分でレビューする前提なので、LLMが崩さずに書けるか、機械で検証しやすいか、人間が差分でレビューしやすいかで選ぶ
- 一つの要求にどこまで情報を持たせるか
- 複数の表現形式をプラグインとして扱うか
- planとcycleへ渡す最小コンテキストは何か（実験001の「条件の欠落なし」では決着せず、`verification` を返すかどうかの影響も未測定）
- 既存テストや実装とのtraceをどう記述するか（実験002では、実装の関数はIDから挙げられなかった。IDの付いたテストからたどる候補は未測定）
- `agentic-workflow` の一部にするか、独立プロジェクトにするか
- 出典や定義元の参照を、ファイルのパスではなくIDで持つか。
  実験002では出典をファイルのパスと判断の番号で指したので、ファイルを動かすと参照が切れる。
  案は、判断にも仕様の項目にもドメインを頭に付けた全体で重ならないIDを振り、IDがどのファイルにあるかは道具が解決する形である。
  こうすれば置き場所に意味がなくなり、ディレクトリの切り方を後から変えられる
- 運用時の成果物をどう置くか。
  案は、`docs/` の下を種類で先に分け、その中をドメインで分ける形である。
  `docs/decisions/` は判断の正本（brainstormの判断とADR。人間が承認する）、`docs/ir/` は仕様IRの正本（LLMが書き、人間が差分を承認し、cycleからは読み取り専用）、`docs/spec/` は人間向けの生成物、`docs/plans/` は変更ごとの計画とする。
  IRの「中間」は流れの中の位置のことで、一時的という意味ではない。
  種類で先に分けるのは、誰が書くか、cycleから書き込めるか、生成物かという決まりが種類ごとに違い、決まり1つにパス1つで済むためである。
  ドメインをまたぐADRや共有の用語集にも置き場所ができる。
  ドメインが別のcrateとして切り出される場合は、文書をそのcrateの中に置く。
  `kakoi` の仕様書で試してから決める

## 現時点の仮説

- brainstormとADRは自由な自然言語のまま残す
- brainstorm終了後に、LLMが仕様を機械検査可能な形へ正規化する工程を置く
- 正規化は解釈を消すのではなく一回に集約するものであり、その一回を引用範囲付きの出典で検査する
- 仕様IRを意味の正本とする案を第一候補にする
- IRが条件と応答を直接持つのは、イベント駆動・状態依存・常時成立・禁止事項・不変条件に限定する
- 手続き的な要求はIRに参照だけを持たせ、内容は決定表・性質・PBTの側に置く
- EARSは一般要求の生成ビュー、Gherkinは手書きの具体例として役割を分ける
- 人間向け長文仕様は正本ではなく生成ビューにする
- 形式手法は高リスクで形式化しやすい部分に限定する
- スキルは工程と判断を制御し、専用ツールは検査、生成、追跡を担う
- 「cycleを止めて仕様へ戻る」規律は、スキルではなくエージェント外側のツールで強制する
- `AGENTS.md` をアダプターとして既存リポジトリへ後付け可能にする
- 最初は `kakoi` の難所3件で表現力を検証し、成功基準を固定してからツール実装を判断する（実験001で実施）
- 本来の流れがはじめから矛盾を防げるかは、小さな題材の実験002で確かめ、仕上げた手法で `kakoi-net` の試験導入を行う（実験002では矛盾は出なかったが、実装が黙って決めたものが残った）
- 製品仕様へ追跡できない検証を増やさず、検証の終了条件を持つ

## 非目標

現時点では次を目的にしない。

- 自然言語を完全に排除すること
- すべての仕様を形式証明すること
- LLMの判断を不要にすること
- 一般的な要件管理・課題管理サービスを作ること
- 既存のテストフレームワークを置き換えること
- `agentic-workflow` を直ちに全面的に作り直すこと
- `kakoi` の現在の仕様を直ちに新形式へ移行すること

この構想の目的は「目的」の節に置いた一文であり、実験はそれに届く流れと手法を小さく確かめるために行う。
