# 実装の先行を LLM の側で捕まえる仕組みを決め直す

## Context

[変更照合](./2026-10-01-change-conformance.md)は、cycle で実装が先行して IR や判断の記録に無い選択が入るのを捕まえる目的で作った。作ったものは、変更したファイルごとに実装役とレビュー役の記録を書かせ、機械は記録の漏れと古さだけを見る仕組みで、選択が IR に無いことを見抜くのはレビューの役目だった（同記録の A6）。2026-10-06 の allow-test-findings で、実装役が面のファイルを用語集より狭く実装して照合記録に「既存の仕様の範囲」と書き、changes はそれを通した。捕まえたのは cycle の適合レビュー（LLM）だった。過去の照合記録にも changes が起点の発見は無く、記録のためのコミットは136個ある。利用者の前提は、人が一切関与せず LLM の側の自浄作用で捕まえること、kotowari を重くしすぎないこと。

Position: 承認・コミット済み（8cfff12）。実装のレビューで同じ根から穴が続いたため、第8ラウンドで A31〜A33 を決め、A34 を導いた。IR の REQ-core-361 と REQ-core-363 を改め、照合は2回目で0件になった。利用者が承認した（2026-10-06）。

## Agreements

- A1 実装の先行を捕まえる仕組みは、人が一切関与しない、LLM の中の自浄作用としてのガードレールとする。
  - why: 人の判断は信用できない。LLM の側で捕まって直らなければ意味が無い
  - decided_by: 利用者
  - superseded_by: [A9](#A9)
- A2 捕まえる対象は、IR に記録が無い隙間と、IR と違うことをしているなど IR と整合が取れないもの。
  - why: 利用者の要求そのもの（2026-10-06 の allow-test-findings で、面のファイルを用語集より狭く実装した件がその実例）
  - decided_by: 利用者
- A3 捕まえる役は、レビューとは別の専用のフェーズ、あるいは専用の観点での検証にする。
  - why: 今は適合レビューが条件つきで立つだけで、整合を見ることが専任の仕事になっていない
  - decided_by: 利用者

- A4 守るべきは手順ではなく仕様である。実装が仕様を守れているか、決めた仕様に隙間が無いか、仕様に矛盾が無いかを確かめる。手順が守られたかだけを保証する帳簿（今の照合記録）は要らない。
  - why: 照合記録が機械で保証するのは、変更が記録で覆われていることと記録の後に変わっていないこと（手順）だけで、記録の申告が仕様に合っているかは保証しない。それができないなら形骸化した帳簿でしかない
  - decided_by: 利用者
- A5 A3 の検証は cycle の中の専用のフェーズとする。走らせるかは毎回判断してよく、小規模な変更のように隙間が生まれにくいものでは走らせない。
  - why: 観点を増やしても subagent が1体増えるだけで効果は同じだが、それなりの費用がかかる
  - rejected: レビューの観点の1つにする（品質の指摘と同じ席で読まれ、整合が薄まる）
  - decided_by: 利用者
- A6 フェーズが見つけたものは、IR の穴か、コードの誤りか、単に決めていないだけかを見分けて片付ける。LLM の側に根拠があり、実測でき、既存の IR と整合するなど問題が無いなら、LLM が IR と判断の記録に足してよい。
  - why: 条件は多岐にわたり、一律にコードを IR に合わせると正しい具体化まで捨てる。根拠と既存の IR との整合が、自分の実装の追認との境目になる
  - rejected: 既定でコードを IR に合わせ、IR を足すのは承認済みの記録に根拠があるときだけにする（推奨案。狭すぎる）
  - decided_by: 利用者
- A7 LLM の側に根拠や実測があり既存の IR と整合すると確信できるなら、コードを正として IR と判断の記録を足す（A6）。根拠から決められない意味の決めごとが出たときだけ、コードを IR の書いてある範囲に戻し（足した振る舞いは外し）、その隙間を問題の記録（FLAGS.md）に残して、人を待たずに進める。
  - why: 人は関与しない（A1）ので止めて待つ選択肢は無く、決まっていない振る舞いを入れないのがいちばん安全。FLAG が残る間 status の complete は false になり、欠けが見える
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A8](#A8)

- A8 フェーズが見つけたものは、IR の穴でもコードの誤りでも、必ず IR とコードが整合した状態に片付ける。コードが正しく IR に穴があるのに、コードを IR に合わせて戻すことはしない。
  - why: IR に穴があるとき、コードを IR の範囲に戻すと、正しいものを捨てて欠けた仕様に合わせることになる。利用者の望みは「いい感じにしてほしい」で、整合した良い状態に着地することが目的
  - decided_by: 利用者

- A9 片付けの拠り所は根拠と実測である。既存の IR と整合しない選択は、その食い違いに十分に配慮したうえで選ぶ。根拠と実測を尽くしてもどうしても判断が必要なものだけを、最後の手段として人に戻す。
  - why: 「いい感じ」を自分の実装の追認と分けるのは根拠と実測。人の判断は信用できないが、根拠から導けない意味の決めごとを LLM が決めてしまうのはさらに悪い
  - decided_by: 利用者

- A10 kotowari changes と照合記録を、製品からもこのリポジトリの手順からも外す。外すのはコマンド、照合記録の形式、設定の changes の節、それを定める IR、スキルの照合の節、このリポジトリの照合の CI と記録である。整合は記録に対してではなく、コードベースに対して確かめる。
  - why: 今は役に立っていない（A4）。製品に残すと、changes を有効にした利用者のプロジェクトでスキルが記録を書かせ続ける
  - rejected: 製品には残し、このリポジトリの手順からだけ外す（要らないと分かった仕組みを勧め続ける）
  - decided_by: 利用者
- A11 整合のフェーズを走らせるかは、オーケストレータである cycle か、メインセッションのエージェントが決める。
  - why: 走らせるかを毎回決めてよい（A5）が、それを決められるのは段取りを持つ役だけ
  - decided_by: 利用者
- A12 整合のフェーズは、実装と IR の食い違いに加えて、IR そのものの隙間と矛盾も見る。
  - why: 守るべきは、仕様に隙間が無いこと、矛盾が無いことも含む（A4）。実装して初めて見える隙間は多い
  - decided_by: 利用者

- A13 整合のフェーズは、見つけたものを次のように片付ける。観測で決まるものは実測や再現で確かめて決める。既存の IR と整合する具体化は根拠を示して IR と判断の記録に足す。既存の IR と食い違うものは、その項目が引く判断の記録の理由を制約として読み、実測で IR の誤りを示せたときだけ IR を改めて理由を残し、示せなければコードを IR に合わせる。実験で決まらない意味の決めごとは、IR と矛盾しない既定値で整合させて進め、問題の記録（FLAGS.md）に人の判断待ちとして残し、最後の報告に既定値とそれを覆す一言を載せる。決めたことは判断の記録に decided_by を整合のフェーズとして、選択、理由、根拠のポインタ（実測のコマンドと結果、file:line）と一緒に書く。直した後はもう一度フェーズを走らせ、書き残した根拠が選択を支えるかも読む。フェーズは実装役と別系統のモデルで走らせるのが望ましいが必須にしない。
  - why: 根拠と実測を拠り所にし、既存の IR との食い違いに配慮し、人に戻すのは最後の手段とする（A9）。pstack も、観測で決まることは自分で確かめ、人に戻すのは実験で決まらない判断と取り消せない行為と行き詰まりに限り、既定値で進めて覆す一語と報告し、判断は別系統のモデルに確かめさせる
  - decided_by: 利用者（推奨を採用）
- A14 毎回のフェーズが見る範囲は、差分で変わったコードとそれが呼ぶ・呼ばれる直接の周辺、差分が触った IR の項目である。コードベース全体と IR 全体の突き合わせは、別に頼まれたときだけ行う。
  - why: 今日の件は差分の中のコードと用語集の突き合わせで捕まる。全体を毎回読むのは重い
  - decided_by: 利用者（推奨を採用）
- A15 A12 の IR の隙間と矛盾を見る範囲は、差分が実装・変更した IR の項目、その項目が使う用語、項目どうしの関係（定義の表、@about、参照）に限る。
  - why: IR 全体の矛盾は壁打ちの敵対的レビューと照合が担当する
  - decided_by: 利用者（推奨を採用）
- A16 フェーズを省いてよいのは、差分が利用者から見える振る舞いを足しも変えもしないとき（文書だけ、テストだけ、振る舞いを変えないリファクタ）だけで、迷ったら走らせる。省いたときは最後の報告に1行の理由を書く。
  - why: 隙間の生まれやすさは行数ではなく振る舞いが動くかで決まる。2026-10-06 の件は小さな差分で振る舞いを足していた
  - rejected: 1件の指摘の直しを省いてよいものに入れる（指摘の直しも振る舞いを変えうる。2026-10-06 の直しがそうだった）

  - why: kotowari を重くしすぎない。スキルを増やすと入口の案内やスキルどうしの受け渡しの決まりまで増える。フェーズを動かすのは cycle とメインセッション（A11）だけ

  - why: 捕まえ損ねは回数ではなく範囲と分類で起きる。直しごとに走らせるとレビューの往復ごとに席が増える

- A29 敵対的レビューの指摘から、決定に基づいて次を IR に書く。範囲の項目は計画が扱う ID と差分が付けた印の ID でも決め、範囲の項目と用語が引く判断の記録も読む。用語や表の定義より広げる・狭める読みは具体化ではなく食い違いとする。IR の誤りを示す実測は、IR どうしの矛盾か実現できないことの再現に限り、テストが通ることは根拠にしない。フェーズは実装役と別の文脈の LLM が走らせる。フェーズ自身が IR、判断の記録、問題の記録、コードを直してコミットし、cycle はそのコミットを記録するだけにする。これは cycle の「IR は直し役に任せ、矛盾は人に戻す」という扱いを置き換える。判断はその実行の新しい判断の記録に書き、英日の対と一致の記録をそろえて check を通す。新しい指摘が出なかった回を収束とし、同じ指摘が2回続けば cycle の進まないときの終わり方に入れる。順は実装、整合のフェーズ、品質のレビューとする。メインセッションの直接の修正（A11、A19）も要求に入れ、適合の観点を外したことは cycle と iterate の文言でも確かめる。
  - why: 書いたままでは 2026-10-06 の件が範囲から外れる道と、具体化に分類されて IR を書き足す道が残った（敵対的レビュー）。いずれも A13〜A19 から導ける
  - decided_by: LLM（A13〜A19 から導いた。承認の時に利用者に示す）

- A30 照合で、今回の変更の前から出典が書いていなかった次の振る舞いを、今の振る舞いとして追認する。"overview build" が "--port" と "--tool" を受けないこと（REQ-core-004）。置き場の誤りの詳細が基準のディレクトリからの相対のパスであること（TBL-core-020）。"surface.files" の既定が空の一覧であること（TBL-core-004）。overview build と serve が参照を解くために ADR の置き場も読むこと（REQ-core-278）。二重引用符の中を曖昧な語と文書名の参照の検査から外すこと（用語集の「除外」）。停止の終了コードが2であること（EX-core-219、EX-core-241）。
  - why: 記録されていない（実装と既存のテストがこの振る舞いで、決めた理由は残っていない）
  - decided_by: LLM（照合で見つかった既存の出典の欠け。承認の時に利用者に示す）

- A31 整合のフェーズが見つけたものは、cycle の指摘のファイルに、レビューの指摘と同じ形で載せ、観点を consistency とする。毎回の実行で、フェーズは前の回までのフェーズの指摘ごとに still_present か no_longer_visible を返し、新しく見つけたものと、直したもののコミットを返す。止め方は cycle の既存の決まり（2回続けて still_present、閉じた原因が戻る、利用者の上限、再開）にそのまま従い、フェーズ用の独自の状態は持たない。
  - why: フェーズに cycle と別の独自のループを持たせたため、指摘の ID、止め方、往復、人の答えの受け渡し、再開をフェーズ用に作り直す穴が直すたびに出た（2026-10-06 のレビュー）。レビューのループの仕組みに乗せれば作り直しが要らず、kotowari を重くしない
  - rejected: フェーズ用の状態（実行ごとの記録、new と repeat の印）を足して穴を一つずつ埋める
  - decided_by: 利用者（推奨を採用）
- A32 根拠から決められない意味の決めごとは、IR と矛盾しない既定値で整合させ、問題の記録に残したうえで、その指摘を human_judgment として開いたまま最後の報告に回す。フェーズが人に戻して止まる道は設けない。人の判断は最後の手段で、極力減らす。human_judgment にする指摘には、試した根拠と実測と、それで決められなかった理由を書く。
  - why: human_judgment はループを止めずに最後の報告へ回す扱いで、A13 の「止まらずに既定値で進め、最後に覆す一言と報告する」と合う。利用者は人の判断を極力減らすべきだとする
  - decided_by: 利用者（推奨を、人の判断を極力減らす条件つきで採用）
- A33 直しが収束した後の実行の範囲の起点として、指摘のファイルに最初の品質のレビューが見た head を1つだけ持つ。
  - why: A28 の「直し全体の差分」を再開しても再現できるようにする。足す状態はこれだけにする
