# 変異テストを push の待ちから外し、PR の CI で止める

## Context

変異テストは pre-push のフックで origin/main との差分を回している（[A25（変異テスト）](./2026-09-17-mutation-tests.md#A25)）。
差分はまだ push していないコミットの分だけ膨らむ。2026-10-04 の公開クレートの分割では、差分の変異 680 件に約1時間かかった。
LLM で実装は速くなったが、少し実装するたびに push が1〜2時間止まり、作業時間の大半が待ちになった（利用者）。
見逃しを機械が止める関門は残したまま、人と LLM が待たない場所へ移す。

Position: 利用者が方針を承認した（2026-10-04。関門は PR の必須チェック、手元は並列化だけ今やる）。手元の並列化は測ったら遅くなったので、既定を変えずに A6 に結果を残した。

## Agreements

- A1 pre-push のフックでは変異テストを回さない。pre-push はテスト全件と check だけを回す
  - why: 待ちの原因は、push のたびに差分の変異を手元で1件ずつ回すこと。手元を速くするだけでは、ブランチが大きくなればまた待つ
  - rejected: 手元の実行を速くするだけにする
  - decided_by: 利用者（推奨を採用）

- A2 見逃しを止める関門は main への取り込みの前に置く。GitHub Actions が PR ごとに、PR の基準との merge-base からの差分に入る変異を回し、等価の一覧の分を除いた見逃しが1件でも残れば失敗する。main のブランチ保護でこのチェックを必須にし、管理者にも適用する
  - superseded_by: [A9](#A9)（差分の起点だけ）
  - why: 「LLM が必ず通る関門で、機械が終了コードで止める」（[A24（変異テスト）](./2026-09-17-mutation-tests.md#A24)、[A25（変異テスト）](./2026-09-17-mutation-tests.md#A25)）を保ったまま、手元の待ちを無くす。LLM は利用者と同じ権限で動くので、管理者に適用しないと関門を素通りできる
  - rejected: リリースのときだけ止める（見逃しに気づくのがリリースの直前までずれる）。CI で回して報告だけにする（ガードレールでなくなる）
  - decided_by: 利用者（推奨を採用）

- A3 CI の変異テストは8つに分けて並列に回す（cargo-mutants の `--shard k/8`）。分担ごとに自分の結果を `kotowari mutants` に読ませて見逃しで失敗し、全部の分担を待つまとめのジョブ1つを必須のチェックにする
  - why: 1本で回すと PR の待ちが1時間前後になる。必須にするチェックの名前を分担の数から切り離しておけば、分け方を変えてもブランチ保護を直さなくてよい
  - decided_by: 利用者（推奨を採用）

- A4 リリースの変異テストは release.yml で、バイナリを作る前に A3 と同じ分け方で回し、見逃しがあれば Release を作らない。範囲は [A1（リリースの変異テストの範囲）](./2026-09-27-release-mutants-scope.md#A1) のまま、同じ製品の1つ前のリリースのタグとの差分で、前のタグが無いときだけ全体
  - why: タグの push は A1 で変異テストを通らなくなるので、リリースの関門を GitHub の側へ移す
  - decided_by: 利用者（推奨を採用）

- A5 main には、必須のチェックが通った commit だけを入れる。scripts/release.sh が作るリリースの commit も、ブランチに push して PR のチェックを通してから main とタグを push する
  - why: A2 のブランチ保護は main への直接の push も止める。チェックが通った commit と同じ commit なら直接の push も受け付けられる
  - decided_by: 利用者（推奨を採用）

- A6 手元の scripts/mutants.sh は、同時に回す変異の数を環境変数 MUTANTS_JOBS で変えられるようにするが、既定は1のまま。メモリ上限つきのサービスと居残りの見張りはそのまま使う。CI では環境変数 MUTANTS_SERVICE で systemd のサービスを使わずに回す
  - superseded_by: [A11](#A11)（CI で systemd を使わない部分だけ）
  - why: 2026-10-04 に同じ44件（acquisition.rs と cli/output.rs）を測ると、1件ずつで312秒、3件ずつで348秒（さらに時間切れが1件、1件ずつでは捕まえた変異）、4件ずつで380秒だった。写しごとのビルドが CPU を取り合い、速くならないうえに偽の時間切れが出る。速さは CI で別々のマシンに分けて得る（A3）。CI のランナーにはユーザーの systemd が無い
  - rejected: 手元の既定を3にする（利用者は並列化を承認していたが、測ると遅くなった）
  - decided_by: 利用者（推奨を採用）。既定を1に保ったのは測定の結果による

- A7 変異を入れたクレートのテストだけを走らせる案は今回は採らない。CI で、見逃しが増えないかをワークスペース全体のテストと比べてから決める
  - why: 分割の後は core のテストの多くが core の下にあるが、ルートの CLI のテストが core の変異を捕まえている分は比べないと分からない
  - decided_by: 利用者（推奨を採用）

- A8 この決まりは IR に書かず、この記録と scripts/mutants.sh、.github/workflows、lefthook.yml のコメント、PROJECT.md に書く
  - why: 0件の強制は関門の設定で、IR の要求にはしない（[A27（変異テスト）](./2026-09-17-mutation-tests.md#A27)）
  - decided_by: 利用者（推奨を採用）

- A9 PR の変異テストは、同じ PR の commit のうち、まとめの mutants のチェックが成功した一番新しいもの（PR の先頭の祖先に限る）からの差分だけを回す。そういう commit が無いときだけ、PR の基準との merge-base からの差分を回す。
  - why: A2 のままだと、PR に push するたびに merge-base からの差分を全部回し直す。2026-10-04 の PR #4 では1回で変異が約1100件、8台で最長46分かかり、直しの commit を1つ足すたびに同じだけ回すことになる。Actions の枠と待ち時間を、もう確かめた変異に使わない。変えていないコードの見逃しを関門にしない考え（[A2（リリースの変異テストの範囲）](./2026-09-27-release-mutants-scope.md#A2)）と同じ線で、前に通った commit からの差分に入る変異は、その後の commit で確かめている
  - rejected: push のたびに merge-base からの差分を全部回す（A2 のまま）
  - decided_by: 利用者（推奨を採用）

- A10 CI では、変異1件のテストの時間切れを20秒に決めて渡す。
  - why: PR #4 では cargo-mutants が基準の実行から時間切れを38〜40秒に決め、止まらない変異1件ごとにそれだけ待った。CI のテスト全体は7秒ほどで、20秒なら通常のテストを打ち切らずに待ちを半分にできる。時間切れは見逃しでなく注意として数えられる
  - decided_by: 利用者（推奨を採用）

- A11 CI でも変異テストはメモリ上限つきの systemd のスコープの中で回す（上限12G、スワップ無し、上限に当たったプロセスだけを止めて続ける）。
  - why: PR #4 で8台のうち1台が、止まらない変異の実行中にランナーごと落とされた（原因は確かめていないが、手元では上限で抑えている種類の暴走と同じ形）。ランナーの systemd は sudo で使えるので、A6 の「CI では systemd を使わない」を改める
  - decided_by: 利用者（推奨を採用）
