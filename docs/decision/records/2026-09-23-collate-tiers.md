# 壁打ちの記録: 照合レビューを中身に応じて変える

## Context

kotowari-brainstorm の承認の手順2の照合レビュー（[A24（kotowari-skill）](./2026-09-14-kotowari-skill.md#A24)、[A26（kotowari-skill）](./2026-09-14-kotowari-skill.md#A26)）は、壁打ちの中身に関係なく毎回、別セッションの LLM に IR の置き場の文書すべてと判断の記録すべてを渡し、最大3回まわる。このリポジトリでは要求 212 件とシナリオ 199 件、判断の記録 20 本を毎回渡すことになる。

利用者が費用を払い切れない前提で工程を作ると決めた（[A12（workflow-split）](./2026-09-23-workflow-split.md#A12)）。一方で、照合は過去の壁打ちで実際に食い違いを見つけてきた（2026-09-17 の record-form と mutation-tests、2026-09-19 の read-commands と mutants-followup、2026-09-20 の query-status、2026-09-22 の ir-engine）。照合を中身に応じてどう変えるかを決める。

Position: 第1ラウンドで照合の範囲、段の分け方、回し直しの範囲を決め（A1〜A3）、モデルは未決に残した（U4）。U4 は A7 で決めた。第2ラウンドで変えた項目の見つけ方、規則の置き場、改める過去の決定を決めた（A4〜A6）。木は尽きた。承認待ち（2026-09-23）。

## Agreements

- A1 照合に渡す項目は、その壁打ちで足したか変えた項目と、その壁打ちで変えた決定を出典に持つ既存の項目に限る。判断の記録は、それらの項目の出典が指す決定だけを渡す
  - why: 今は IR の置き場と判断の記録のすべてを毎回渡すので、照合の費用が変更の大きさでなくリポジトリの大きさで決まる（このリポジトリで要求 212 件、シナリオ 199 件、記録 20 本）。決定を改めるとそれを出典に持つ古い項目の裏付けが崩れうるので、その項目は含める
  - rejected: 今までどおりすべてを渡す。小さな壁打ちでもリポジトリ全体の費用を払う
  - decided_by: 利用者（推奨を採用）

- A2 照合は2段にする。A1 の範囲が0件なら照合しない。1件以上なら、今までどおり別セッションの LLM が照合する。どちらにしたかは、決める前に理由を1行書く
  - why: 範囲を絞れば、小さな確認の壁打ちでも渡すのは項目数件と決定数行で、別の LLM を呼んでも安い。IR を触らない壁打ちには照合するものが無い
  - rejected: 範囲が小さいときは主セッションが自分で突き合わせる中間の段を置く。自分で書いた IR を自分で裏付けありと判定すると甘くなりやすく、段が増えるとどの段かの判断もぶれる
  - decided_by: 利用者（推奨を採用）

- A3 2回目と3回目の照合には、前の回で裏付けが無いと挙がった項目と、その後に直した項目と決定だけを渡す。照合の回数の上限は3回のまま
  - why: 1回目で裏付けがあった項目を回し直しのたびに渡し直すのは、同じ判定に費用を払い直すことになる
  - decided_by: 利用者（推奨を採用）

- A4 A1 の範囲は主セッションが起点（壁打ちのブランチが分かれたコミット）からの差分で機械的に数える。足したか変えた項目は、IR の置き場の差分で変わった行を `kotowari list` の `path` と `line` に突き合わせて拾い、`kotowari list` に出ない用語集の用語は差分で変わった表の行から拾う。変えた決定を出典に持つ項目は、判断の記録の差分で変わった決定の番号を拾い、`kotowari list` の `sources` がそれを指す項目を `jq` で選ぶ
  - why: 書いた本人の記憶で「今回書いたもの」を挙げると、漏れても気づけない。`kotowari list` は各項目の `sources` を返すので、出典からの逆引きも機械でできる（`records.md#A22` で3件が取れることを確かめた）
  - rejected: 主セッションが今回書いた項目を記憶から列挙する
  - decided_by: 利用者（推奨を採用）

- A5 何を照合に渡すか（A1、A3、A4）は kotowari スキルの `collate.md` に置き、照合を走らせるかどうか（A2）は kotowari-brainstorm の承認の手順に置く
  - why: 渡すものは照合そのものの入力の形で、kotowari スキルだけを入れた人にも要る。いつ走らせるかは工程の流れ（[A11（workflow-split）](./2026-09-23-workflow-split.md#A11) と同じ線引き）
  - decided_by: 利用者（推奨を採用）

- A6 [A24（kotowari-skill）](./2026-09-14-kotowari-skill.md#A24) の「IR の各項目を渡す」を A1 と A2 で改め、`docs/spec/kotowari-skill.md` の R5 の手順2を書き換える。3回の上限（A26）と、直したら check に戻ること（A35）は変えない。IR は変えない
  - why: 照合の範囲と走らせる条件だけが変わり、回数と回し直しの手順はそのまま使える
  - decided_by: 利用者（推奨を採用）

- A7 照合には、使える中で判断力が最も高い段のモデルを使い、費用のために下の段へ下げない。工程の skill にはモデルの名前を書かない。2つのモデルで比べる実測はしない
  - why: 照合は「この決定からこの項目が言えるか」の判断で、甘いと裏付けの無い項目が承認に通る。利用者の使用経験では、1つ下の段のモデルは判断力が足りない（実測はしていない）。A1〜A3 で渡す量を絞ったので、1回の単価が高くても費用は変更の大きさで収まる。モデルの名前を書くと特定の LLM に縛られ、世代が変わるたびに直すことになる
  - rejected: 同じ照合を2つのモデルで回して実測してから決める（U4 の当初の決め方）。下の段を選ばないと決まっているなら、比べる実測に費用を払う理由が無い
  - rejected: skill に特定のモデルの名前を書く。特定の LLM に縛られる
  - decided_by: 利用者
