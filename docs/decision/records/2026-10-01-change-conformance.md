# 変更の照合と、実装中に生まれた判断の書き戻し

## Context

実プロジェクトで、実装や計画が選んだ順序・ロック・配置・同時刻の選択が、判断の記録や IR に戻らない摩擦が起きた。
既存要求の ID を付けたテストでも、その期待値を実装に合わせて変えると、仕様に無い選択を固定したまま対応の検査を通せる。レビューで気づいた仕様の穴も、記録だけとして残る経路があった。
根拠のある自律判断を許容し、変更に対する照合の欠落と古さを機械で検出する仕組みと、判断の意味を確認するスキルを組み合わせる。
この記録は通常の対話で行った検討を保存する。brainstorm の起動自体を記録の前提にせず、未決の細部を決まったこととして補わない。

Position: 方針の文書は利用者がレビューで採用した。U1〜U6 はこの方針を記録した時点の未決事項で、具体案は [変更照合の具体的な契約](./2026-10-01-change-details.md#Agreements) に残す。

## Agreements

- A1 実装や計画で IR に無いこと、または IR と違うことを選んだときは、取り込む前に選択と根拠（実測、資料、理由）を判断の記録に残し、振る舞い・制約の仕様を変える選択は IR にも反映する。実装役による判断は、誰が判断したかを実装役と明記する。
  - why: 根拠のある自律判断自体を禁止する必要は無い。選択と根拠が残らなければ、後から仕様として決めたことと実装の誤りを見分けられない
  - decided_by: 利用者（問題の定義と推奨を採用）
- A2 変更に対する照合の検査は kotowari の専用コマンド "kotowari changes" に置く。通常の "kotowari check" は、設定された照合記録の形式と参照を検査し、Git の比較元を必要とする差分の取りこぼしと鮮度の検査は changes が行う。check の成功だけを、今回の変更が照合済みである証拠にしてはならない。
  - why: 現在のファイルの整合性と、指定された変更の照合済みかどうかでは必要な入力が違う。専用コマンド名は利用者が changes を選んだ
  - decided_by: 利用者（推奨を採用、コマンド名は回答で確定）
- A3 changes は、呼び出し元が指定した比較元と対象から変更を独立に列挙し、設定された検査対象ファイルの追加・変更・削除を、ファイル単位で照合記録と対応させる。照合記録に書かれたファイル一覧だけを検査対象の一覧として使ってはならない。
  - why: 申告しなかった変更も拾う必要がある。関数単位の解析から始めるより、ファイル単位ならテストを変えない製品コードの変更にも対応できる
  - decided_by: 利用者（推奨を採用）
- A4 照合記録は変更の意図ごとにまとめ、複数ファイルを1件で扱える。各件は比較元、対象ファイル、対象内容の識別値、関連する IR とその内容の識別値、結論、理由、必要な判断の記録への参照、照合した役を持つ。対象ファイルや関連仕様が照合後に変われば、その件は再照合が必要になる。
  - why: ファイルごとの作文を避けつつ、どの変更をどの仕様と照合したかを追えるようにする。コミット番号だけでは照合記録自身のコミットで対象を変えてしまう
  - decided_by: 利用者（推奨を採用）
- A5 照合の結論は、既存仕様の範囲、新しい判断、保留を区別する。既存仕様の範囲には要求への参照と理由、新しい判断には根拠を記した判断の記録への参照、保留には理由と引き継ぎ先が必要である。新しい判断が仕様を変えるときは変更後の IR とも対応させる。
  - why: 全変更に IR の書き換えを要求せず、既存仕様に従う実装と仕様を補う判断を区別して記録する
  - decided_by: 利用者（推奨を採用）
- A6 機械検査は、対象変更の照合漏れ、照合後の内容変更、必須の根拠・決定・保留先への参照の欠落を検出する。根拠が選択を支えるか、仕様と実装の意味が一致するか、委譲範囲内かは review が確認する。
  - why: 内容の意味の正しさは指紋や参照の存在だけでは証明できない。機械が保証する範囲を明確にする
  - decided_by: 利用者（機械検証とスキルによる補強の方針を採用）
- A7 要求 ID のあるテストの追加・期待値変更・削除は、優先して再照合する箇所として提示する。期待値が変わらないことだけを理由に、製品コードや補助関数の変更を検査対象から外してはならない。
  - why: 実測では問題4件を対象にできたが、テストの変更だけでは製品コードだけの変更や補助関数の変更を拾えない。期待値の緩和や削除は判断漏れでなくても再照合に意味がある
  - decided_by: 利用者（実測後の推奨を採用）
- A8 pre-commit は HEAD とステージ済みの内容を対象に、実装側の判断・根拠・対応記録までを要求する。cycle の最終検査と CI は比較元から対象ブランチ全体の変更を対象に、実装側とは別の review による照合までを要求する。途中のコミットごとに最終 review を要求しない。
  - why: 実装を一つの関心ごとにコミットしながら、取り込み前の保証を強くする
  - decided_by: 利用者（pre-commit で気づき、cycle で解消し、CI で止める流れを採用）
  - superseded_by: [照合を取り込み前だけで要求する A1](./2026-10-01-conformance-at-integration.md#A1)
- A9 フックと CI は機械検査と指摘の出力を担当し、cycle の LLM が指摘を読んで照合記録、判断の記録、必要な IR を更新する。記録の欠落だけを理由に毎回人へ戻さない。自律更新は委譲範囲内で根拠があるときに行い、範囲を超える変更、根拠から選択を決められない場合、不可逆・危険・外部公開の操作は人へ戻す。
  - why: 利用者は人への確認が必要以上に入らない流れを望んでいる。一方で、記録を書けることを承認済みの制約を変える権限にしない
  - decided_by: 利用者（流れの提案と、確認を限定する推奨を採用）
- A10 review は、指摘の重要度や修正アクションとは別に、仕様の穴に当たるかを分類する。仕様の穴は、判断の記録と IR への反映、仕様に合わせたコードの修正、判断の記録での明示的な保留のいずれかに対応させる。"info" や "record_only" という扱いだけを処理済みの証拠にしてはならない。
  - why: 実測で、仕様の前提の食い違いに気づいた指摘が info / record_only / open のまま残っていた
  - decided_by: 利用者（仕様の穴の処理先を要求する推奨を採用）
- A11 検査が読む照合記録と仕様の穴の処理先には、cycle 専用の findings JSON に依存しない共通の形式を定める。cycle はその形式で書き、kotowari は読み取って検査する。最終的な照合記録はリポジトリに残し、別の環境でも CI が検査できるようにする。kotowari が標準出力・標準エラー以外へ書き出さない契約は維持する。
  - why: 別の実装・レビュー手順でも使えるようにし、既存の状態を保存しない契約と両立させる
  - decided_by: 利用者（推奨を採用）
- A12 ローカルと CI は同じ検査エンジンを使い、途中の検査と最終の検査で要求する照合の段階を変える。CI の比較元と対象は CI のイベントから呼び出し元が決め、照合記録の自己申告だけから採らない。取り込み前に check と changes の両方を必須にする。
  - why: フックだけでは実行されない経路が残る。PR の先端とマージ用コミットの取り違えや、都合のよい比較元の自己申告で検査が狭くなることを避ける
  - decided_by: 利用者（CI にも組み込む推奨を採用）
- A13 判断の記録は、brainstorm の起動の有無を問わず、判断を行った検討のまとまりごとに日付と題を付けて残す。既存の決定の行を別の決定で上書きせず、変更は追加の決定と改訂の参照で残す。
  - why: 通常の対話で合意した内容も、実装役が根拠を持って決めた内容も、同じように追う必要がある
  - decided_by: 利用者（今回の対話から decisions と IR を書く依頼）
- A14 今回は合意した方針を文書化する。記録形式・細かな引数などの未決事項は Undecided と IR の FLAGS に残し、実装役が自己判断で埋める前提の計画は作らない。
  - why: 実装してみる方針と、まだ話していない契約の細部を決まったことにすることは別である
  - decided_by: 利用者（コマンド名の質問に添えた未決事項の扱いを採用）

## Prohibitions

- P1 changes は「照合記録が揃った」という結果を、根拠や判断の意味の正しさを機械が証明したという結果にしてはならない。
  - why: 形式・対応・鮮度と、内容の妥当性を分ける（[A6](#A6)）
  - decided_by: 利用者（推奨を採用）

## Delegated

- D1 今回の文書作成では、ファイルの分け方、既存の続きから取る IR の番号、文章の言い換えを作成者に委ねる。機械検査の意味、記録の保存形式、CLI の引数、除外や保留の合否はこの委譲に含めない。
  - why: 合意を文書へ写す作業を進め、未決の仕様を作成者の都合で確定しない
  - decided_by: 文書作成者（文書化の依頼に含まれる作業範囲の解釈）

## Rejected

- R1 コードを変えたコミットには常に IR の更新を同居させる方式は採らない。
  - why: 実測した3つの cycle の Rust 変更コミットは計102件で、同じコミットに IR・判断の記録の更新があるものは0件だった。仕様更新は別コミットでも行われており、同居だけでは重要な判断を絞れない
- R2 テストの ID が存在すること、あるいは実装側が申告した一覧に記録があることだけで変更の照合済みとする方式は採らない。
  - why: 既存 ID のまま期待値を変えた例と、申告しない変更を拾えない穴がある

## Undecided

- U1 changes の引数名・必須引数・既定値と、比較元・コミット対象・ステージ対象・途中と最終の段階を指定する具体的な構文。通常の check が読む照合記録を指定する設定の鍵と既定値も決める。
  - decides: 次の検討で利用者が決める。実装役には委ねない
  - related: A2, A8, A12
- U2 共通の記録形式、保存場所、版、必須の鍵と値、参照の具体的な表記、内容の識別値の算出方法と対象範囲。照合記録自身を鮮度検査に含める循環の扱いも決める。
  - decides: 次の検討で利用者が決める。ガイド用の8桁の指紋をそのまま流用すると決めていない
  - related: A4, A5, A11
- U3 検査対象ファイルの設定、Git の追加・削除・移動・種類変更、未追跡ファイルと除外、空の対象設定、履歴が無い・比較元が無い場合の停止の契約。ステージ対象の検査で関連する IR と照合記録をどの内容から読むかも未決。
  - decides: 次の検討で利用者が決める。申告のない変更を黙って除外しない
  - related: A3, A6
- U4 仕様の穴の分類の値、未分類の扱い、処理先の具体的な構造、最終検査で保留を通す条件。保留先が存在するだけで通すかどうかは未決。
  - decides: 次の検討で利用者が決める。重要度と処理済みを混同しない
  - related: A5, A10
- U5 指摘の種類・path・line・detail、JSON/text の出力、件数、終了コード、check の成功と changes の成功を区別する出力と status の扱い。
  - decides: 次の検討で利用者が決める。既存 status の complete を最終照合の証明にしない
  - related: A2, A6, A12
- U6 スキルへの組み込み箇所、既存の「cycle は仕様を編集しない」「欠けた設計判断は戻す」との境界、レビュー対象が照合後に変わったときの再実行の粒度、フック・CI の導入方式。
  - decides: 次の検討で利用者が決める。今回の依頼ではスキル・フック・CI の実装は変更しない
  - related: A8, A9, A10, A12

## Measurement

固定した履歴から選んだ問題4件と明確な対照2件を、読み取りだけの比較スクリプトで調べた。要求 ID のあるテスト本文の追加・変更・削除を対象にする条件では、問題4件と対照1件が対象になった。追加・削除・ID 変更・assert 系の検証内容変更を対象にする条件では、問題4件を残し、明確な対照2件は対象外になった。
期待値の緩和・テスト削除の2例は、判断漏れとは別に再照合が必要な例として扱った。型を別モジュールへ移す例は、構造上の判断があるため「新判断なし」の対照から外した。
これは少数の既知事例についての対象抽出の測定であり、判断漏れの自動判定の検出率ではない。製品コードだけの変更、補助関数だけの変更、計画に入った判断はテスト差分だけでは拾えない。

## Revisions

- 通常の対話で、問題の定義、履歴の調査、候補条件の測定、専用コマンドとフック・CI の分担を検討した。利用者の「ここから decisions と ir を書けますか」を受けて文書化した。
- コマンド名の確認に利用者が「changes を採用する（推奨）」と回答し、[A2](#A2) を確定した。
- U1〜U6 の具体案を [変更照合の具体的な契約](./2026-10-01-change-details.md#Agreements) に記録した。方針の決定行は変更せず、具体案の採用は次の文書レビューで確定する。
- [照合を取り込み前だけで要求する判断](./2026-10-01-conformance-at-integration.md)により、A8 の pre-commit での照合を取り下げた。
