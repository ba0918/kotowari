# 壁打ちの記録: 導入で追認した要求の検証

## Context

kotowari-adopt（[導入の記録](./2026-09-26-adoption.md)）は、旧資料と実装が一致する振る舞いを追認して要求にするが、その要求の "- verification:" の値と、成功条件と反例のシナリオを書くかどうかを決めていなかった。
一致の判定にテストの有無は使わない（[A10（導入）](./2026-09-26-adoption.md#A10)）ので、根拠のテストが無い追認の要求が出る。検証が unit ならそれは requirement_without_test の誤りになり、承認後の印付けでは消えない。
kotowari 自身の pre-push は check の終了コード0を求め、remote-merge も check を pre-commit と CI に入れると決めている（remote-merge の "docs/decision/records/2026-09-26-development-check-hooks.md" の A1、A2）ので、残った誤りは導入先の push や CI を止める。

Position: 承認済み（2026-09-26）。第1ラウンドで A1〜A4 を決めて木が尽きた（導入の記録の A25 は A2 で改めた）。IR は docs/ir/core/adoption.md（2026-09-26）。

## Agreements

- A1 追認した要求の "- verification:" は振る舞いの中身で決め、実装の振る舞いは unit、入力の全体に成り立つ性質は property、コードの外のもの（文書、運用手順）は review にして how_to_verify に確かめ方を書く。一覧に検証の列を足して見せ、人には聞かない。テストが無いことを理由に review にはしない
  - why: テストが無いことを理由に review にすると、テストの無さが仕様の側に隠れて見えなくなる
  - decided_by: 利用者（推奨を採用）

- A2 adopt はテストに印を付けず、テストを消さず、移さない。承認の後に、根拠のテストが要求を十分に確かめるかを審査して十分なものだけに印を付ける作業、細部をなぞるだけのテストを削除の候補として人がまとめて消すかを決める作業、印を付けるテストを "tests.files" の範囲に入れる作業（中に移すか "tests.files" を広げるかはプロジェクトの既存の設定に従う）、根拠のテストが無い要求のテストを書く作業を1つの依頼文にまとめて人に渡し、どの工程で回すかは kotowari-using-workflow が決める。依頼文はファイルに残さない。adopt の skill は、"tests.files" の外のテストは kotowari の対象外で印が無くても誤りにならないこと、テストの無い要求の requirement_without_test はテストを書くまで残り、push や CI で check を求めるプロジェクトではそれで止まるので adopt と後のテストの作業を同じブランチで進めることを案内する
  - why: 一致の判定にテストの有無を使わない（導入の記録の A10）ので根拠のテストの無い追認の要求が出て、印付けでは消えない。後回しは作っていない振る舞いに使うもので、作られている振る舞いに使うと意味が違う。導入の記録の A25 の理由（adopt の成果物は IR と記録に限る、件数に応じて入口が工程を決める、見えないテストが誤りにならない理由を示す）は変わらない
  - decided_by: 利用者（推奨を採用）

- A3 追認した要求に成功条件と反例のシナリオは必須にせず、旧資料か根拠のテストに具体的な場面があるときだけ書く
  - why: brainstorm と同じく要求ごとに求めると話題1つの仕事量がおよそ倍になる。書かなくても status の without_examples に数が出るだけで誤りにならない
  - decided_by: 利用者（推奨を採用）

- A4 A1 と A3 は "docs/ir/core/adoption.md" に要求を1つ足して書き、A2 は REQ-core-220 の文と how_to_verify を直して入れる
  - why: 導入の仕様を1つの文書にまとめておく
  - decided_by: 利用者（推奨を採用）
