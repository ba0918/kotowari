# 壁打ちの記録: 収束しないループで前提を疑わせ、工程の skill を削る

## Context

kotowari の工程の skill は、事故のたびに条件や例外を足してきて、同じ指示の重複や、委譲先に貼る契約と呼ぶ側の規則の混在が増えている。
また、cycle の改善ループが「直すたびに同じ根から新しい指摘が出る」もぐらたたきになったとき、今の止め方（Endings 3）は人に戻して止まり、直しが共通に置いている前提を自分で疑って抜ける段を持たない。
利用者は brainstorm 後は人を待たずに自走させたいので、収束しないときに前提を疑う段を足し、同時に肥大化を抑えたい。

Position: 第1〜第5ラウンドで A1〜A21 を決めて承認された（2026-10-06）。計画の反対の立場からのレビューで見つかった3つを第6ラウンドで決めた（A22〜A24。A22 は A9 を言い直す）。IR は変えない（A8）。

## Agreements

- A1 削る作業と、前提を疑う段を足す作業は、1本のブランチと1つの記録で扱う。先に削り、あとで足し、コミットは分ける
  - why: 足す段は cycle の Endings まわりに入るので、先に重複や使われない分岐を削っておくと足す場所が見えやすい
  - decided_by: 利用者（推奨を採用）

- A2 止める条件が揃ったら、cycle はすぐ人に戻さず、それまでの直したちが共通に置いた前提を段ごとに書き出し、いちばん上の前提を取り替える案を作る。前提が実装の側にあれば取り替えを fixer に委譲してループを続け、IR や判断の記録の側にあって根拠と実測で決められるものは整合のフェーズに渡し、決められないものだけを前提の段の一覧を付けて人に戻す
  - why: 利用者は brainstorm の後は人を待たずに自走させたい。今の Endings 3 は、もぐらたたきを前提の取り替えで抜けられる場面でも人に戻して止まる。整合のフェーズは既に根拠と実測で記録を書き IR を直せるので、その範囲を超えない
  - rejected: 前提の側を問わず人に戻す（今の振る舞い。自走の目的に反する）
  - rejected: IR の側の前提も cycle の中で決める（意味の判断は brainstorm の後に人を待たずに決めてよい範囲を超える）
  - decided_by: 利用者（推奨を採用）

- A3 前提を段ごとに書き出すのは cycle 自身で、新しい役のエージェントは足さない
  - why: 指摘の記録ファイルを持ち履歴を全部見られるのは cycle で、判断を cycle に置く今の決まり（Judgment stays here）とも合う。利用者は費用に敏感で、理由の無い席を足さない
  - decided_by: 利用者（推奨を採用）

- A4 前提の取り替えは、止める条件が揃うたびに1回だけ試す。取り替えた後にまた揃ったら Endings 3 として止め、報告にそれまでの前提の段を載せる
  - why: 取り替えを繰り返すと、もぐらたたきが前提の層に移るだけになる
  - decided_by: 利用者（推奨を採用）

- A5 前提を疑う段は `kotowari-cycle/references/` の新しい reference に書き、cycle、iterate、implement の止める箇所から名指しで読ませる。独立した skill にはしない
  - why: 3か所に同じ規則を書くと肥大化の原因そのものになる。独立した skill にすると配る単位と依存の向き（[A5（workflow-split）](./2026-09-23-workflow-split.md#A5)）が変わる
  - decided_by: 利用者（推奨を採用）

- A6 今回足す考え方は「前提を疑う」と、今回の進め方としての「足す前に引く」だけにする
  - why: 「人を待たない」と「走らせて分かることは事実として扱う」は、cycle の Editing contract と implement の試しの段落に同じ趣旨が既にある。関係者ごとの偏りを数える手順や、作業を道具化する手順は今回の問題に直接効かない
  - decided_by: 利用者（推奨を採用）

- A7 肥大化の削減に数値の目標は置かない。重複、もう使わない分岐、委譲先が実行時に要らない説明を削り、結果は語数の前後で報告する
  - why: 行数や語数を目標にすると、責務と関係ない切り方になりやすい
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A13](#A13)

- A8 前提を疑う段は IR に書かず、この判断の記録だけに残す。ただし [REQ-core-363](../../ir/core/consistency-phase.md#REQ-core-363) の「cycle の既存の規則で止まる」と食い違わないように合わせる
  - why: kotowari の工程の skill の中身は判断の記録で決めてきた（[A6（workflow-split）](./2026-09-23-workflow-split.md#A6)）。使う人から見て変わるのは止まるまでの振る舞いだけである
  - decided_by: 利用者（推奨を採用）

- A9 前提を疑う段に入る合図は、新しく出た見える指摘（直す対象の指摘）の根拠の位置が、直前のラウンドで閉じた見える指摘の根拠の位置と、同じファイルで行範囲が重なることが、2ラウンド続くこととする。根拠の位置が空の指摘はこの判定に使わず、今の Endings 3 の数の比較に任せる
  - why: 2026-09-24 の review-panel の cycle（`.agents/artifacts/reviews/review-panel.json`）に当てはめると、今の Endings 3 で最初に発火するのは連鎖の4つ目（#8）で、この合図なら3つ目（#7）で発火し、#10 と #11 では誤って発火しない。1回の重なりで発火させると、普通の直しで隣の小さな穴が1つ見つかる場面まで捕まえる
  - rejected: 重なりが1回で発火させる（#5 で捕まえられるが、普通の直しの場面まで捕まえる）
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A22](#A22)

- A10 閉じた指摘と同じ原因かどうかの突き合わせを、full review と整合のフェーズの新しい指摘だけでなく、diff review の新しい指摘にも当てる
  - why: もぐらたたきの新しい指摘は diff review で出るので、今の文言では突き合わせの対象から外れ、「閉じた原因が戻る」が捕まえない
  - decided_by: 利用者（推奨を採用）

- A11 Endings 3 の「同じ指摘が2ラウンド続けて still_present」は、見える指摘（直す対象の指摘）だけに当てると明記する
  - why: 今の文言は記録だけの指摘まで含むと読め、字義どおりだと review-panel の #4（直していない info の指摘）で誤って発火する
  - decided_by: 利用者（推奨を採用）

- A13 肥大化とは長さではなく、無駄な指示、冗長な文章、フロンティアモデルに効果の薄い指示、重複する指示、一度に読む必要のない文章が skill にあることを指す。文字数・行数・語数では測らない。削る作業は、この5種類を基準に各 skill を校正し、構造化し、分離する作業として行い、洗い出した重複や候補の一覧はその入力として使う
  - why: 長い文書でも、どれも要る指示なら肥大化ではない。数で測ると、要る指示を削るか、移すだけで減ったと数える誤りになる
  - rejected: 1回の呼び出しで読まれる語数で測る（第2ラウンドの Q10 の推奨。数で測る点で同じ誤り）
  - decided_by: 利用者

- A14 承認後は kotowari-plan で計画を書き、kotowari-cycle で回す。モデルを走らせて振る舞いを比べる評価はしない
  - why: 9つの skill にまたがり、skill の文は振る舞いなので整合のフェーズを飛ばせない。今回足す前提を疑う段を最初に使う場にもなる。振る舞いの評価は費用がかかり、利用者が頼んだときだけ行う
  - rejected: 主セッションで直接編集し、レビューを1回だけ行う（IR との読み合わせを自分でやることになり漏れやすい）
  - decided_by: 利用者（推奨を採用）

- A15 フロンティアモデルに効果の薄い指示とは、モデルが既に知っているか言われなくてもする振る舞いを言い直す指示（訓練された既定の振る舞いの言い直し、強調のための言い直し、役割の一文だけで中身の無い指示など）、今のモデルでは起きない失敗への回避策、そして今の規則を変えない経緯の記述を指す。作者だけが知る文脈（環境の事実、品質の基準、道具の契約、判断の難しい場面、制約の理由）は長くても残し、消すと同じ失敗がまた起きうる禁止も残す
  - why: 利用者の挙げた例（「あなたはシニアエンジニアです」のような指示は今のモデルに効果が薄い）に合わせる。削る対象を古くなった指示の種類で決め、長さで決めない点で [A13](#A13) と同じ立場をとる
  - decided_by: 利用者（推奨を、利用者の挙げた例に寄せて採用）

- A16 校正して書き直すときは、skill の書き方の規範（ba0918-skill-authoring）を物差しにする。物差しにするのは書く側の作業だけで、kotowari の skill の本文はそれを名指ししない
  - why: 読む量と reference の分け方、規則の種類ごとの書き方が、A13 の5種類に当たる。書く側の物差しなので [A3（workflow-split）](./2026-09-23-workflow-split.md#A3) とぶつからない
  - decided_by: 利用者（推奨を採用）

- A17 削り終わったことは数ではなくレビューで確かめる。cycle の full review に A13 の5種類（A15 の読み方を含む）を見る項目として渡し、別に IR の要求が how_to_verify で求める文が消えていないかを読み合わせる
  - why: A13 で数では測らないと決めたので、確かめる手段もレビューの判断になる
  - decided_by: 利用者（推奨を採用）

- A18 重複する指示は A13 のとおり肥大化に数える。skill のファイルに置く規則の正本は1か所にし、ほかの場所はそこを指す。委譲先は skill を読まないので、cycle が実行時に正本から委譲先のプロンプトへ貼るのは重複に数えない
  - why: 食い違っていない写しでも、置き場が複数あると直すときにずれる。Evidence conditions が3か所に写っているのは、実行時に貼ることと、ファイルに写して置くことを分けていなかったためと見られる（推論）
  - rejected: 食い違っていない重複は残す（A13 の定義に反する）
  - decided_by: 利用者（推奨を採用）

- A19 過去の事故から生まれた禁止で、その事故が今のモデルでも起きうるか判断できないものは、短い書き方に直して残す。削るのは、今の規則を変えない経緯の記述と、ほかの規則に完全に含まれる言い直しだけにする
  - why: A14 で振る舞いの評価をしないので、削った禁止が要ったかどうかは事故が再び起きるまで分からない
  - decided_by: 利用者（推奨を採用）

- A20 前提の取り替えを試した記録は、cycle の指摘の記録ファイル（`.agents/artifacts/reviews/<branch>.json`）に1回ごとに足す。発火したラウンド、書き出した前提の段、取り替えた前提、渡した先（fixer、整合のフェーズ、人）を持つ。再開時はこれを読んで同じ発火で2回試さず、最後の報告の前提の段もここから書く
  - why: [A4](#A4) の「揃うたびに1回だけ」は、再開をまたぐと記録が無ければ守れない。記録ファイルを書くのは cycle だけという今の決まりに収まる
  - decided_by: 利用者（推奨を採用）

- A21 implement も、1回やり方を変えても進まないときは、人や cycle に戻す前に自分の文脈で同じ段を踏む。それまでの試みが共通に置いた前提を書き出し、いちばん上の前提を取り替えて1回だけ試し、それでも進まなければ前提の段を付けて cycle に戻す。前提が計画や仕様の側にあるときは、今までどおり cycle に戻す
  - why: 実装の中で閉じるもぐらたたきは、cycle まで上げなくても抜けられる。前提の段を付けて戻せば、cycle や次の工程が同じ前提を繰り返さない
  - decided_by: 利用者（推奨を採用）

- A22 前提を疑う段に入る合図は、修正のすぐ後のレビューで新しく上がった見える指摘の根拠の位置が、その修正が直した見える指摘の根拠の位置と、同じファイルで行範囲が重なることが、修正をまたいで2回続くこととする。根拠の位置が空の指摘はこの判定に使わない
  - why: [A9](#A9) の「直前のラウンドで閉じた」は、指摘の記録ファイルに上がったラウンドも閉じたラウンドも無く、diff review は前の指摘を閉じた同じ回で新しい指摘を上げるので、字義どおりには判定できない。どの修正がどの指摘を直したかは fixer の報告として記録ファイルに既にあるので、ラウンド番号を足さずに判定できる。review-panel の記録では #5 が #2 を直した修正の後に #2 と重なり、#7 が #5 を直した修正の後に #5 と重なって発火し、#10 と #11 は #9 の根拠の位置が空で発火しない
  - decided_by: 利用者（推奨を採用。計画の反対の立場からのレビューで見つかった）

- A23 Endings 3 の条件のうち、A22 の合図、見える指摘が2回続けて still_present、閉じた原因が戻る、新しい見える指摘の数が消えた数以上のことが2回続く、の4つでは、止める前に前提を疑う段に入る。レビューが1回やり直しても成功しないときは、前提を疑う段に入らず今までどおり止める
  - why: [A2](#A2) の「止める条件が揃ったら」がどの条件を指すか決めていなかった。レビューが成功しないのは道具の失敗で、直しの前提の問題ではない
  - decided_by: 利用者（推奨を採用）

- A24 kotowari-using-workflow の主セッションが直接直す道でも前提を疑う段を使い、fixer の役は主セッション自身が担う。using-workflow も前提を疑う段の reference を名指しで読ませる
  - why: 直接編集の道も cycle の Endings で止まるので、Endings を変えればこの道の振る舞いも変わる。この道だけ人に戻して止めると自走の目的に合わない。[A5](#A5) は名指しする箇所に using-workflow を挙げていなかった
  - decided_by: 利用者（推奨を採用）
