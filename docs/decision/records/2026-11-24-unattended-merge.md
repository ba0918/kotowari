# 仕様の承認からマージまでを人なしで通す

## Context

いまの工程では、1つの依頼のあいだに人が4回出る。壁打ちの答え、仕様の承認、計画の承認、最後の確認とマージ。
利用者は、最初の目的を渡したら完了まで LLM だけで走る形に近づけたい。
この壁打ちでは、まず1つの依頼について、人の確認が要るマージと要らないマージの線を決め、要らない側を仕様の承認のあとマージまで人を待たずに通す形を決めた。
実測した事実は次のとおり。このリポジトリの PR の検査は約2分、差分の変異テストは約1分。main の保護は2つの検査を必須にし、承認のレビューは求めていない。ある要求の唯一のテストを消すと `kotowari check` は requirement_without_test で落ちる。

Position: 壁打ちは収束した（2026-11-24）。この依頼そのものは、線の手順を書く skill に触れるので、決めた線では人が確認する側に入る。いまの工程で通し、人がマージする。

## Agreements

- A1 まず1つの依頼について、人の確認が要るマージと要らないマージの線を決め、要らない側を、仕様の承認のあとマージまで人を待たずに通す。壁打ちと仕様の承認は人のままにする
  - why: 人が出る4回のうち、計画の承認と最後の確認は、線を決めれば機械と LLM に渡せる。仕様の承認まで外すと、仕様の書き間違いを人が読んで止める場面が無くなる
  - decided_by: 利用者（線の定義が重要だという利用者の指摘から）

- A2 仕様をコードの側に寄せる話は、この壁打ちでは扱わない。IR を前提にした既存の検査はそのまま使う
  - why: IR に乗っている仕組みを全部見直す大きな決定で、人の介入を減らす話と一緒には決められない
  - decided_by: 利用者

- A3 人が確認するのは3種類とする。(1) 戻せない操作（リリース、公開、タグ、消す操作）。差分の性質ではなく操作そのもので、いまある止まる条件が受け持つ。(2) 仕様を変える変更。パスではなく、工程の止まる条件（測っても決まらない食い違い、承認済みの要求の変更や削除）が受け持つ。(3) 検査の定義と、線そのものを変える変更。パスの一覧が受け持つ。ほかは機械の検査がぜんぶ通ればマージする
  - why: 確認の要否は0か100かではなく、変更の種類で決まる。検査の定義を変える変更は、通す基準そのものを動かすので、同じ検査では測れない
  - rejected: 最初は全部人が確認し、記録を見て種類ごとに外していく（人なしで通る1本目が出るまで、今と同じだけ人が出る）
  - decided_by: 利用者

- A4 計画を、承認する成果物として扱うのをやめ、工程の段としても置かない。大きい依頼で実装役が要ると判断したときだけ、自分の作業メモとして書く。人は読まず、コミットもしない
  - why: 承認を外しても書く段が残れば、仕様と実装のあいだに書くものが1つ残る。手順を決めるのは実装役の仕事にできる
  - rejected: 計画は書くが人の承認を待たない。計画の承認を人に残す
  - decided_by: 利用者（利用者の言葉）

- A5 払ってよいのは、後ろの出戻りを減らすもの（仕様の段階で穴を潰す、実装役が作り込む、機械の検査を手前に置く）とする。効きを示せない固定の席は足さない。足すかどうかの根拠は記録に置く
  - why: 費用は量ではなく、必要か無駄かで分ける。毎回のフルレビューのような固定の席は、効いている裏づけが無いまま依頼ごとに乗る
  - decided_by: 利用者

- A6 今回は記録を残すところまでにする。記録を読んで工程を直すループは次の話題にする
  - why: 記録が1件も無いうちにループの形を決めることになる
  - decided_by: 利用者（推奨を採用）

- A7 検査の道具は、それが無いと通ってしまう場面を示せることと、マージを止める側に置くなら数分に収まることの両方を満たすものだけ入れる。収まらないものは裏で回し、見つけた取りこぼしは記録に入れる。証明の道具も同じ条件で候補に入れる
  - why: 検査が遅いと工程が回らなくなる罠を、このリポジトリで実際に踏んだ。証明の道具も、場面を示せるなら気軽に入れてよい
  - rejected: 場面を示せなくても、証明の道具を1本試しとして裏で回す（維持する対象が1つ増え、モデルと実装の一致を別に見ることになる）
  - decided_by: 利用者

- A8 マージを止める検査の合計時間の目安は5分とする
  - why: いまの PR の検査と差分の変異テストの実測（合わせて約3分）に、足す検査の余地を見た値
  - decided_by: 利用者（代決を承認）

- A9 新しいコマンドは作らない。決めたパスの一覧に差分が触れたかを git で調べ、触れていれば人が確認する。扱いは、確認が要るか要らないかの2段とする
  - why: 決めた線を守るのに要るのは、決めたパスに触れたかどうかだけで、git がそれを答えられる。事実の種類分けや3段の扱いは、線に対して余計な複雑さだった
  - rejected: 差分を読んで扱いを返す kotowari の新しいコマンド。線の判定を、skill を読んだ LLM に任せる（同じ差分でも判定が揺れ、線が守られたかを後から確かめられない）。線の判定を GitHub の側の設定に任せる（GitHub を使わないプロジェクトでは働かない）
  - decided_by: 利用者（利用者の言葉）

- A10 既存のテストを消す変更や、検査の抑制を足す変更では止めずに通し、裏で回す全体の変異テストに任せる。見つかった取りこぼしは記録に入れる
  - why: 消されたテストが質の悪いテストなら改善にあたり、人が読んでも良し悪しを正しく判定できるとは限らない。守りが減ったかは変異テストのほうが正確に測れる。要求の唯一のテストを消す変更は、既存の検査が落とす（実測）
  - decided_by: 利用者

- A11 依存の変更では止めない。壁打ちでわかる依存は壁打ちで決める。実装の途中で足す依存は、理由と目的を書いて足し、人はマージのあとで確かめる
  - why: 理由と目的が残っていれば事後に確かめられる。リリースまでは外して戻せる
  - decided_by: 利用者（利用者の言葉）

- A12 人の確認が要らない側は、cycle がプルリクエストを作り、必須の検査が通ったら自動でマージされる設定にする。実際にマージするのはホスティングの側で、マージ先の保護が最後の関門になる。人の確認が要る側は、プルリクエストを作るところまでで止める
  - why: 手元でマージして push する形は、必須の検査を求める保護に拒まれる。人がボタンを押す形は、待ちが1回残る
  - decided_by: 利用者（推奨を採用）

- A13 出戻りの記録は新しく作らない。cycle が依頼ごとに書いている指摘のファイルに、3項目だけ足す。線の判定の結果（当たったパスを含む）、どの依頼の手直しか、どの終わり方で終わったかとその理由（前の段へ差し戻した理由、人を呼んで止まった理由を含む）。置き場は git の外のままで、コミットしない
  - why: 往復の回数は、指摘のファイルの回ごとの判定と修正の記録からすでに数えられる。置き場が git の外なので、検索に当たって今の決まりと取り違えられる心配も無い。持ち運びが要るとわかったら、ループを作る話題で置き場を決め直す
  - decided_by: 利用者（推奨を採用）。足す項目を2つから3つに改めたのは、主セッションが指摘のファイルの形を読み直した結果で、見直しのラウンドで利用者に示した

- A14 記録から読めるようにするのは4項目とする。レビューと修正の往復の回数、前の段へ差し戻した回数と理由、線の判定の結果と理由、途中で人を呼んで止まった理由。人の手直しは、次の依頼がどの依頼を直したものかを指す形で残す。費用は記録しない
  - why: ループを作る話題で、どこに払うと出戻りが減るかを読むのに要る最小の項目
  - decided_by: 利用者（代決を承認）

- A15 人に戻すのは、人でないと決められないことだけとする。人に残すのは、何を作るか（壁打ちと仕様）、戻せない操作、物差しの根っこ（線を決める一覧と、検査の定義）。ほかは実測と機械の判定で決め、測れないものは LLM が決めて理由を残し、人は事後に読める。機械で測れないことは、人に回す理由にしない
  - why: 人に戻しても、それで正しい舵を切れるとは限らない。ほとんどのことは実測や機械の判定で決められ、本当に人の判断が要ることは一部しかない
  - decided_by: 利用者

- A16 触れたら人が確認するパスの一覧に入れるのは2つとする。検査の定義（CI、フック、検査を走らせるスクリプト、変異テストの設定、静的解析と道具の版の設定）と、線そのもの（一覧のファイルと、線の手順を書いた skill）。仕様と判断の記録の置き場は入れない。それ以外の工程の skill は、ふつうのコードと同じに扱う
  - why: 仕様の置き場を入れると、壁打ちから始めた依頼と、整合のフェーズが具体化を書き足した依頼がぜんぶ止まる。このリポジトリの候補の一覧を過去のマージ済みの依頼32件に当てると、当たるのは8件だった
  - rejected: 工程の skill をぜんぶ一覧に入れる（skill を直す依頼がぜんぶ1回止まる）。検査の定義を一覧から外し、壊した見本で検査を実測する仕組みを今回作る（検査の定義を変える依頼で止まった回数を記録で見てから決める）
  - decided_by: 利用者

- A17 マージを止める理由になるのは、走らせて示せる間違いだけとする。読みにくさや構造の好みは LLM が決めて、止めない。実装役が下した判断（依存を足した理由を含む）は、何を・なぜ・証拠の1行ずつで最後の報告に並べ、報告はマージのあとに届く。見直しの席は足さない。走らせて示せない意図とのずれは、仕様の穴として壁打ちの側の出戻りに数える
  - why: 設計の良し悪しは、人が読んでも正しく舵を切れるとは限らず、A15 の原則と逆向きになる
  - rejected: 設計が割れているときだけ見直しを1席当てる（割れていることを機械が言える形で決める必要があり、効きの根拠がまだ無い）。設計の判断を含む依頼を、人が確認する側にする
  - decided_by: 利用者

- A18 依存のライセンスと既知の脆弱性を見る検査を CI に足す。実装のときに時間を測り、5分に収まればマージを止める側に、収まらなければ裏で回す側に置く。これは CI の構成で、利用者から見える製品の振る舞いではないので IR に書かない
  - why: 依存の変更で人を止めないと決めたので（A11）、足さなければ気づくのが人の事後の確認だけになる
  - decided_by: 利用者（推奨を採用）

- A19 パスの一覧はプロジェクトごとのファイル `.kotowari/confirm-paths` に置き、1行に1つ、git のパスの書き方で書く。skill には手順だけを書く。このファイルが無いプロジェクトでは、自動マージに任せず、プルリクエストで止まる。このファイル自身は、一覧に書かれていなくても、手順の側で必ず当たりとして扱う。線の手順を書いた skill の元を持つリポジトリは、その元のパスを一覧に書く
  - why: 一覧を skill の中に書くと、ほかのプロジェクトでは skill を書き換えないと使えない。本体の設定ファイルに書く手は、本体に何も足さない決定（A9）と合わない。一覧の行を消す変更は一覧のファイルに触れるので、ファイル自身を必ず当たりにすれば線をすり抜けない。動いている skill はリポジトリの外に入れたものなので、手順の側からは元のパスを知れない
  - decided_by: 利用者（代決を承認）。最後の2文は主セッションが A16 から導いた。見直しのラウンドでは「skill も手順の側で必ず当たりにする」と示したが、手順が元のパスを知れないとわかり、一覧に書く形に改めて、次の見直しのラウンドで示した

- A20 線の判定は、どの依頼でも、マージ先との分かれ目のコミットから枝の先頭までの差分をぜんぶ調べる。マージ先は、プルリクエストの向き先の枝で、決めていなければリポジトリの既定の枝とする。ファイルを移す変更は、元のパスと先のパスの両方を数える
  - why: 仕様の置き場を一覧から外したので（A16）、承認のコミットを基点にする理由が無くなった。基点が1つなら、調べられずに通る区間が無い
  - decided_by: 利用者（推奨を採用）。マージ先の定義と、移す変更の数え方は、主セッションが仕様のレビューの指摘から足し、見直しのラウンドで利用者に示した

- A21 承認のあとに整合のフェーズが仕様や判断の記録へ書き足した具体化では止めない。仕様について人が出るのは、整合のフェーズが人の判断が要ると返したものが残っているとき、または実装役が承認済みの要求を変える・消す必要があると返したとき。測って決めた具体化は、判断の1行として事後の報告に載せる
  - why: パスでは具体化と仕様の変更を見分けられない。見分けは、いまある整合のフェーズの決まりがすでに持っている
  - decided_by: 利用者（推奨を採用）

- A22 人が仕様を承認してコミットした（またはコミットしてよいと言った）時点を、実装を始めてよい合図として扱い、同じ流れで実装を始める。後回しにしたいときは人がそう言う
  - why: 承認のあとに人が実装を呼ぶ形だと、依頼ごとに手で起こす場面が1回残る
  - decided_by: 利用者（推奨を採用）

- A23 cycle はプルリクエストを作ったあと、必須の検査の結果まで見届ける。落ちた検査は指摘の1つとして指摘のファイルに入れ、いまある修正の往復と止まり方（同じ指摘が2回続けて残ったら前提を疑い、それでも進まなければ終わる）に従う。それでも通らなければ人に渡す
  - why: プルリクエストを作ったところで終えると、検査が落ちた依頼が、人が気づくまで止まったままになる
  - decided_by: 利用者（推奨を採用）

- A24 人なしでマージまで通すのは、cycle が回す依頼と iterate が回す小さい作業とする。主セッションが直接編集する変更は、コミットするところまでで、いまと変えない
  - why: cycle だけにすると、小さい作業が今と同じ場所で人を待つ
  - decided_by: 利用者（推奨を採用）

- A25 判断の1行は、プルリクエストの本文に書き、cycle の最後の報告にも同じものを出す
  - why: 最後の報告にだけ出すと、セッションを閉じたあと読み返せない
  - decided_by: 利用者（代決を承認）

- A26 一覧に当たって止まったときは、自動マージを有効にせずプルリクエストを開いたままにし、当たったパスの一覧とプルリクエストの場所を人に見せる。人は差分を読み、よければ自分でマージする
  - why: 変更の要約まで付けると、要約を読んで承認し、差分そのものを読まずに通す形になりうる
  - decided_by: 利用者（代決を承認）

- A27 計画を書く工程の skill は今回無くす。計画の形を検査するコマンドは今回は残し、消すかどうかは別の依頼にする
  - why: コマンドを消すのは、公開しているコマンドが減る互換性を壊す変更で、工程の変更と分けて決められる
  - decided_by: 利用者（推奨を採用）

- A28 自動マージを使えるようにするリポジトリの設定は人が有効にし、工程はリポジトリの設定を変えない。使えないプロジェクトでは、cycle はプルリクエストを作るところ（または枝を出すところ）で止まり、人がマージする。工程は自動マージが使えるかを見て、使えなければそう報告する
  - why: リポジトリの設定は、通す基準の一部で、A15 の物差しの根っこにあたる
  - decided_by: 利用者（推奨を採用）

- A29 今回の変更は2つの依頼に分ける。工程の振る舞いを変えるものと、CI に依存の検査を足すもの（A18）
  - why: 互いに依らず、後者は工程の skill に触れない
  - decided_by: 利用者（代決を承認）

- A30 出戻りの記録は消さない。寿命は、ループを作る話題で決める
  - why: 何件あれば読めるかが、まだ分からない
  - decided_by: 利用者（代決を承認）

- A31 マージされたあと、工程は手元の作業用のディレクトリと枝だけ片付ける。ホスティングの側の枝はリポジトリの設定に任せ、工程は外にあるものを消さない
  - why: 外にあるものを消すのは戻せない操作で、A3 の (1) にあたる
  - decided_by: 利用者（代決を承認）

- A32 人の判断を待つ指摘が開いたまま残っているときは、出どころ（整合のフェーズ、レビュー、人が残すと決めたもの）を問わず、プルリクエストは作り、自動マージにはせず、残ったものを人に見せる。一覧に当たったときと同じ止まり方にする
  - why: 止まり方が1つなら、人が見る場所も1つになる。出どころを整合のフェーズに限ると、レビューが残した判断待ちがあってもマージされる
  - decided_by: 利用者（代決を承認）。出どころを問わない形に広げたのは主セッションで、見直しのラウンドで利用者に示した

- A33 cycle は、壁打ちが足した・変えた要求の ID と仕様の置き場を、壁打ちから直接受け取り、あとから始めるときや再開のときは、枝の差分のうち仕様の置き場の部分から数え直す。再開は状態を新しく持たずに決める。実装の途中なら、git の履歴と、扱う要求のうちまだ印の付いたテストが無いもの（読んで確かめる種類の要求は除く）を手がかりに実装役が残りを決め、作業メモがあればそれも読む。プルリクエストを作ったあとなら、プルリクエストがあるか、自動マージを頼んであるか、検査の状態、マージ済みかを、ホスティングの側から読む。テストのコマンドはプロジェクトの指示か、その言語の標準の道具で決め、どちらでも決まらなければ人に聞く。順番と触るファイルは実装役が決める
  - why: 計画が運んでいた4つの役目（cycle の入力、再開の手がかり、テストのコマンド、順番と触るファイル）の行き先を決めないと、計画の段を外したあと仕様が黙る。まだテストの無い要求は、本体がそのまま答えられる
  - rejected: 実装役に作業メモを必ず書かせ、それを cycle の入力と再開の手がかりにする（承認しないだけで、計画を書く段が実質的に戻ってくる）

- A39 cycle は、プルリクエストの枝へコミットを足すたびに線を調べ直す。自動マージを頼んだあとは、枝へ足す前に頼みを取り消し、足したあとの先頭で条件（収束、線に当たらない、人の確認が要る場合に当たらない）を確かめ直してから頼み直す。条件が1つでも崩れたとき、検査が通らず人に渡すときも、頼みを取り消す
  - why: 線を調べるのが1回だけだと、自動マージを有効にしたあとに cycle が足した直しが、調べられずにマージされる。検査が落ちたときの直しは、検査の定義に触れやすい。頼みが生きたまま直しを足すと、その直しをレビューする前に検査が通ってマージされうる

  - why: 人が確認するプルリクエストも、検査が通っていなければ確認できない。線は毎回、差分の全体で決まる（A20）ので、検査の定義への変更を戻せば、マージされる差分はそれに触れていない
