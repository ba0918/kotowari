# 壁打ちの記録: IR に無い、利用者から見える面の検査

## Context

IR に書かれないまま実装された機能を、今の kotowari は機械で見つけられない。テストの無い新しいコードは差分の変異テストで、印の無いテストは test_without_id で止まるが、近い既存の要求の ID で印を付けたテスト、工程を通らない変更、変異テストを回さないプロジェクトでは抜ける。
根は、利用者から見える振る舞いの一覧を kotowari が持たず、IR に無い振る舞いが増えても数えて比べられないことにある。
案 A として、プロジェクトが利用者から見える面（CLI のサブコマンドとフラグ、設定の鍵、HTTP のルートなど）をコードから取り出す規則を設定に書き、取り出した面が IR に出てくるかを kotowari が確かめる検査を決める。規則は印の検査の "tests.rules" と同じ ast-grep の規則を使う。

Position: 承認済み（2026-09-27）。第3ラウンドまでで A1〜A14 を決めて木が尽きた。IR を書く段で決定に無かった細部を A15〜A22 として、敵対的レビューと照合レビューの指摘を第4ラウンドで A23〜A25 として決めた（A21 は A24 で改めた）（2026-09-27）。IR は docs/ir/core/surface.md と surface-unspecified.md（新設）ほか。

## Agreements

- A1 利用者から見える面は、設定の "surface.files"（探すファイルの glob）と "surface.rules"（ast-grep の規則のファイル）で取り出す。規則に当たった節1つが面1つで、"$NAME" で捕まえた文字列が面の名前、規則の id が面の種類になる
  - why: "tests.rules" と同じ作りにすると、規則の書き方を1つ覚えれば済み、言語を選ばない
  - decided_by: 利用者（推奨を採用）

- A2 面の名前が、IR のどこかの要求の文、決定表のセル、シナリオのステップに、二重引用符かバッククォートで囲んだ中身として完全に一致して出てくれば、その面は IR にあるとする
  - why: コードに何も書き足さず、IR の側はふだんの書き方の決まり（具体的な値は二重引用符）どおりに書けば通る。名前が出てくるだけで通り、中身の正しさは見ない
  - rejected: 面の定義のそばにテストと同じ印を書かせる。どの要求が面を決めるかは正確に分かるが、コードに書く手間が増え、関係の薄い ID を付ける穴が残る
  - decided_by: 利用者（推奨を採用）

- A3 IR に出てこない面は誤りにし、"surface.rules" を書いたプロジェクトでだけ検査する。指摘の種類の名前は surface_without_spec のような形にする
  - why: 狙いは関門なので注意では意味が薄い。規則を書かないプロジェクトには何も起きない
  - decided_by: 利用者（推奨を採用）

- A4 まだ IR にしていない面の一覧のファイルを置けるようにし、1件ごとに理由を必須にして、一覧に載った面は誤りにしない。外した件数は出力の最後に必ず出す
  - why: 既存のプロジェクトで最初から大量の誤りが出ても導入できるようにする。変異テストの等価の一覧と同じ作りで、一覧に頼った量が毎回見える。一覧を減らす作業は kotowari-adopt が拾う
  - decided_by: 利用者（推奨を採用）

- A5 面の規則は同梱せず、スキルの reference に書き方の例（clap のフラグとサブコマンドなど）を載せる。kotowari 自身の設定にも規則を書き、自分の CLI の面で使う
  - why: 面の形はフレームワークごとに違う。自分の CLI で動かすと、判定の甘さと厳しさをこの仕様の中で確かめられる
  - decided_by: 利用者（推奨を採用）

- A6 まだ IR にしていない面の一覧は、設定の "surface.unspecified" が指す YAML のファイルに置き、1件は kind、name、why の3つで why を必須にする。形の壊れた件は誤りにし、その面がコードから消えたか IR に出てくるようになって要らなくなった件は注意にする
  - why: 変異テストの等価の一覧（equivalent_invalid は誤り、equivalent_stale は注意）と同じ扱いにする
  - decided_by: 利用者（推奨を採用）

- A7 IR に出てこない面の指摘は、面が見つかったコードのファイルと行を場所にし、detail を「種類 名前」にする。同じ種類と名前の面が何か所にあっても、最初の1か所に1件だけ出す
  - why: kotowari 自身でも同じフラグが2つの match の腕に出てくる（"--format" が 334 行目と 350 行目）。同じ面を何度も数えると指摘が膨らむ
  - decided_by: 利用者（推奨を採用）

- A8 面の名前は、前後が同じ引用符で囲まれていれば1組だけ外し、それ以上は kotowari が整えない。形を変えたいときは、ast-grep の規則の transform で規則を書く人が整える
  - why: clap の derive のようにフィールド名から名前が作られる面もあるが、kotowari が "--" を補うような決め打ちをすると、設定の鍵や HTTP のルートのような CLI 以外の面で困る。transform で頭に "--" を付けられるかは確かめていない（実装で確かめ、できなければ壁打ちに戻す）
  - decided_by: 利用者（推奨を採用）

- A9 kotowari 自身の設定には、サブコマンド（COMMANDS の中の文字列）と、"--" で始まる match の腕のフラグの2つの規則を書く。指摘の種類の名前は REQ-core-125 がコードと突き合わせているので外す
  - why: 利用者から見える CLI の面はこの2つ。既に機械で突き合わせているものを二重にしない
  - decided_by: 利用者（推奨を採用）

- A10 "kotowari status" に面の数（全部、IR にある数、一覧に載っている数）を出し、"kotowari list" には出さない
  - why: IR に無い面は誤りなので complete はそれで false になる。数は一覧に頼った量を見えるようにするために出す
  - decided_by: 利用者（推奨を採用）

- A11 kotowari スキルの references に面の検査の書き方の新しい文書 "surface.md" を足し、"config.md" に設定の鍵を、"findings.md" に指摘の種類を足す。kotowari-adopt には、導入で話題の面を要求にしたら一覧からその面の件を外すことと、規則を最初に書いたときに出る IR に無い面はすべて一覧に載せて話題ごとに減らすことを書く
  - why: 面の検査は書き方も直し方も印とは別の場面になる。一覧を減らす作業は導入の流れに乗せる
  - decided_by: 利用者（推奨を採用）

- A12 "surface.rules" があって "surface.files" が空のときと、"surface.files" があって "surface.rules" が空のときは、設定の誤りとして停止する。規則のファイルが無い、読めない、形が壊れているときは "tests.rules" と同じ扱いで停止する
  - why: 何もせずに通すと、検査しているつもりで何もしていない状態に気づけない
  - decided_by: 利用者（推奨を採用）

- A13 後回しの要求の文に出てくる面の名前も、IR にあると数える
  - why: 後回しは仕様を決めてまだ作らないことで、仕様には書いてある。作ってあるのに後回しのままというずれは、この検査の範囲の外
  - decided_by: 利用者（推奨を採用）

- A14 面は check が検査し、status が数を出す。list、query、plan、mutants は面を読まない
  - why: status の complete は check の誤りの数で決まるので、面の誤りもそこに入る
  - decided_by: 利用者（推奨を採用）

- A15 指摘の種類の名前は、IR に無い面を surface_without_spec、未記載の面の一覧の形の誤った1件を surface_unspecified_invalid、要らなくなった1件を surface_unspecified_stale にする
  - why: 面に関わる種類の頭を "surface_" に揃え、一覧の2種類は等価の一覧の equivalent_invalid と equivalent_stale に倣う
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A16 未記載の面の一覧で外した件数は、"surface.rules" が空でないときだけ check の出力に出す。JSON は最上位の "surface" に "unspecified" の鍵1つ、text は最後の1行 "surface: unspecified=数" とし、指摘や数が0でも出す。数えるのは IR に無く、一覧の形の正しい1件に一致した面で、単位は種類と名前の組とする
  - why: 規則を書かないプロジェクトには何も起きない（A3）。ガイドの集計はいつも出すが、それには倣わない。text の形は mutants の最後の行に倣う
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A17 status の "surface" の群は total、specified、unspecified の3つの鍵を持ち、群はいつも出して規則が空なら3つとも0にする。一覧に載っていて IR にもある面は specified に数える
  - why: 一覧に頼った量を見えるようにする（A10）。IR にある面は一覧の有無にかかわらず仕様にある
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A18 IR にあるかの判定では前後の空白を除かず完全に一致したときだけ IR にあるとし、二重引用符は行の左から対にし、バッククォートは二重引用符の外のものだけを対にする。決定表の見出しの行のセルも数え、性質の文、問題の記録の本文、用語集、"- how_to_verify:" の行は数えない
  - why: A2 が挙げた要求の文、決定表のセル、シナリオのステップに合わせ、対の取り方は用語の検査と同じにする
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A19 同じ種類と名前の面が何か所にもあるとき、最初の1か所は面のファイルのパスのバイト順、次に行の小さい順で決める。"$NAME" を捕まえない当たりは面にしない。引用符はテストの名前と同じく、一重引用符、二重引用符、バッククォートのどれかが前後で揃っていれば1組だけ外す
  - why: 並べ方と名前の扱いを既存の指摘の並べ方とテストの名前に揃える
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A20 面の規則と面のファイルの読み方は "tests.rules" と "tests.files" に揃える。規則の "files" と "ignores" を当て、"severity: off" の規則も当て、走査と読めないファイルでの停止は "tests.files" と同じにする。読めない面のファイルには unparsable_file を出し、同じパスにテストのファイルとして出したときは重ねて出さない
  - why: 規則の書き方と読み方を1つ覚えれば済むようにする（A1）
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A21 設定の鍵の組み合わせの誤り（規則だけ、またはファイルだけ）は設定を読むどのコマンドでも停止し、規則のファイルと未記載の面の一覧のファイルの誤りで停止するのは check と status だけにする。"surface.rules" が空のときは "surface.unspecified" の鍵があっても一覧を読まない
  - superseded_by: [A24（一覧だけがあるときも停止する）](./2026-09-27-surface-check.md#A24)
  - why: 面を読むのは check と status だけ（A14）。読まない一覧の誤りでほかのコマンドを止めない
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A22 未記載の面の一覧の読み方は等価の一覧に揃える。同じ内容の1件が2つあることは検査せず、一致は "kind" と "name" の完全一致で空白を除かない。形の誤った1件の detail は書かれたままの "kind" と "name" を半角空白1つで区切り、無い値は空の文字列にする。置き場が無いか読めないときは読めないファイル、UTF-8 でないときは UTF-8 でないファイル、YAML でないか最上位が並びでないときは設定の誤り（詳細にパス）を理由に停止する
  - why: 等価の一覧と同じ作りにする（A6）
  - decided_by: 利用者（IR を書く段で決めた細部をまとめて採用）

- A23 面のファイルのうち、tree-sitter で木にして構文の誤りに unparsable_file を出すのは、拡張子から決まる言語が面の規則のどれかの language と同じファイルだけにする。ほかの面のファイルは木にしない
  - why: "surface.files" を広く書いたときに、関係の無い文書や別の言語のファイルで誤りが出ないようにする（敵対的レビューの指摘）
  - decided_by: 利用者（推奨を採用）

- A24 "surface.rules" があって "surface.files" が空のとき、"surface.files" があって "surface.rules" が空のとき、"surface.unspecified" があって "surface.rules" が空のときは、設定の誤りとして設定を読むどのコマンドでも停止する。面の規則のファイルと未記載の面の一覧のファイルの誤りで停止するのは check と status だけにする
  - why: 一覧だけが書かれて黙って読まれないと、鍵の書き誤りに気づけない（敵対的レビューの指摘）。検査しているつもりで何もしていない状態を作らない点は A12 と同じ。面を読むのは check と status だけ（A14）
  - decided_by: 利用者（推奨を採用）

- A25 用語集で、面を「API」「インターフェース」「エンドポイント」とは呼ばず、面の規則をテストを見つける問い合わせと別のものとして「問い合わせ」とは呼ばず、未記載の面の一覧を「許可リスト」「除外リスト」とは呼ばない
  - why: ありがちな呼び方と混ざるのを防ぐ（照合レビューで決定の無いまま書いていたと分かった）
  - decided_by: 利用者（推奨を採用）
