# 全体像の一覧ページを読める形にする

## Context

全体像（kotowari overview）の一覧ページは、各全体像の題名と冒頭の結論のカードを、文書の名前のバイト順に縦に並べるだけである（[REQ-view-005](../../ir/view/rendering.md)）。
利用者が初めて実物を見て、ページが増えると一覧が「きつい」と判断した。題名は日本語なので名前のバイト順は読む側には順不同に見え、見出し・件数・まとまりも無く、各ページの状態（見直していない節、未決・予定）も一覧から分からない。
全体像は話題ごとに増えていく（[A18](./2026-10-02-whole-picture.md#A18)）ので、一覧で迷うと全体像の価値が落ちる。このリポジトリでの利用が始まる前に決める。

Position: 利用者が kemi で承認した（2026-10-05、コメントなし）。照合は3回で打ち切り、3回目の残り4件は既にある決定の出典の足し忘れで、出典を足して直したことも承認の材料に含めて示した。次は kotowari-plan。

## Agreements

第1ラウンド（2026-10-05）

- A1 この壁打ちは、一覧のページと、ページ間の移動だけを扱う。狭い画面で flow の箱が重なること、flow の1列に箱を縦に置いたときに順番か並列か分からないこと、元データの YAML が読めないときの誤りの場所が "(yaml)" としか出ないことは扱わない（[U1](#U1)）。
  - why: 利用者が「きつい」と言ったのは一覧で迷うことで、残りの3つは部品の描き方と元データの検査の話であり、決める論点が別である
  - decided_by: 利用者（推奨を採用）
- A2 一覧のページは、読みたいページを探す入口であり、一覧そのものが製品の地図として機能のまとまりと順番を見せる場所とする。見直しが要るページや未決が残るページに気づかせることは補助として添える。
  - why: 読み手は壁打ちをした本人だけで（[A3](./2026-10-02-whole-picture.md#A3)）、「結局この製品は何だったか」を掴み直す入口として使うのがいちばん効く
  - decided_by: 利用者（推奨を採用）
- A3 一覧が扱うページの数に上限を置かない。ページが数十から百を超えても迷わない形にする。
  - why: ページの数は製品の規模で決まり、kakoi のような製品では非常に多くなりうる（利用者の言葉）
  - rejected: 30ページ程度までを想定し、超えたら改めて決める（規模を前もって絞れない）
  - decided_by: 利用者

第2ラウンド（2026-10-05）

- A4 一覧は全体像のページを階層に束ねて見せる。階層は全体像の単位（[A18](./2026-10-02-whole-picture.md#A18)〜[A20](./2026-10-02-whole-picture.md#A20)）の上にかぶせるもので、ページを分け直したりまとめ直したりしない。階層の深さは仕様で制限しない。群を分けるのはその群が大きくなってからにする、という決まりを kotowari のスキルに書く。
  - why: ページの数に上限が無い（[A3](#A3)）。1段で束ねるだけでは、群が増えると群の見出しの並びが今の縦並びと同じきつさになる。1段は階層の特別な場合なので、小さい製品は1段のままでよい
  - rejected: 1段で束ねるだけ（群が増えたときに一段上で同じ問題が起きる）
  - decided_by: 利用者（推奨を採用）
- A5 1つの全体像のページは、階層の中のちょうど1か所に属する。複数の群に重ねて置かない。
  - why: 重ねると一覧の件数が合わず、直す場所も一意に決まらない。1つの IR の文書が多くても1つの全体像に属する（[A19](./2026-10-02-whole-picture.md#A19)）のと同じ考え方である。横のつながりは別に扱う
  - decided_by: 利用者（推奨を採用）

  - why: 1ページに全部あれば、ページ内検索で全ページの題名と結論を探せる。群ごとにページを分けると、探すために群を当てて開くか、検索を自前で作ることになる
