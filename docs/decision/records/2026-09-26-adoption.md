# 壁打ちの記録: 既存プロジェクトへの kotowari の導入

## Context

既存のプロジェクトに途中から kotowari を入れると、旧仕様・判断の記録・実装とテストの3つが食い違っていたり欠けていたりして、どれを IR にするかが決まらない。
remote-merge での導入では、移行の判断 54 件を1つの記録（remote-merge の "docs/decision/records/2026-09-25-spec-migration.md"）で最初に決め切ろうとし、52 件が推奨の採用だった。FLAGS.md は 0 件、既存テスト 2,821 件に対して印は 174 個。"tests.files" は "tests/contract/**/*.rs" に絞られ、その中の "#[test]" は 146、外は 2,680（2026-09-26 の数え）。
全部を導入の時点で決めようとすると面談が膨らみ、推奨の丸呑みになる。導入を手順として助ける方法を kotowari 側で決める。
出発点の案: 話題ごとに旧資料と実装を突き合わせて仕分け（一致は追認、未実装は後回しか捨てる、食い違いと欠けは FLAG）、次に触る話題から段階的に入れ、既存テストに一括で印を付けない。本体（kotowari の CLI）は当面変えない。

Position: 承認済み（2026-09-26）。9ラウンド（A1〜A40）で木は尽きた。A3、A6、A11、A14、A15、A16、A17、A22 は後の決定で改めた。敵対的レビューの指摘は第7ラウンドで、照合レビューの指摘は第8と第9ラウンドで決め、照合は3回目で指摘0件になった。IR は docs/ir/core/adoption.md（新設）と docs/ir/core/CONTEXT.md の旧資料の行。実装は plan → cycle

## Agreements

- A1 導入の手順は新しい工程の skill "kotowari-adopt" として作る。承認の手順は kotowari-brainstorm の手順を名指しして使う
  - why: kotowari-brainstorm は木を尽くすまで終わらず妥協しないが、導入は決めないものを FLAG に残して先へ進むのが要で、同じ skill に入れるとどちらかの規則が骨抜きになる。人に聞く場面のある手順は工程の skill の役目で、kotowari スキルは書き方の辞書
  - rejected: kotowari スキルの reference に導入の場面を足す。人に聞く手順を辞書の側に持ち込むことになる
  - decided_by: 利用者（推奨を採用）

- A2 1回の導入で扱うのは話題1つで、どれにするかは人が選ぶ。既定は次に変更する予定の機能。全体の棚卸しはせず、触らない話題は旧資料のまま置く
  - why: 全部を導入の時点で決めようとすると面談が膨らみ、推奨の丸呑みになる（remote-merge で 54 件中 52 件）
  - decided_by: 利用者（推奨を採用）

- A3 旧資料と現行の実装が一致する振る舞いは、その回の記録に「旧資料と現行の実装が一致しているので、見直さずにそのまま仕様とする」決定を1つ書き、人には一覧を1回見せて承認を得て、要求はその決定を出典にする。一覧から外された項目は食い違いとして扱う（A6）
  - superseded_by: [A21（追認は行ごとに決定を書く）](./2026-09-26-adoption.md#A21)
  - why: 利用者が期待する結果そのものが空白期間で記憶から消えていて、項目ごとに期待を聞いても答えが出ない（利用者の言葉）。2つの出所の一致を固める危険は、全部を見直すために導入が止まる損より小さい
  - decided_by: 利用者（推奨を採用。期待が曖昧という理由は利用者の言葉）

- A4 実装にだけある振る舞いは、利用者から見えてそれを確かめるテストがあるものは A3 の一覧に旧資料なしと示して載せ、利用者から見えるがテストが無いものは FLAG の gap にし、利用者から見えない内部の振る舞いは IR にしない
  - why: 見えてテストもある振る舞いは、誰かが意図して守ってきた証拠がある。テストの無いものは誰も決めても確かめてもいないので、欠けとして見える所に残す
  - decided_by: 利用者（推奨を採用）

- A5 旧資料にだけある振る舞いは、一覧で作る予定があるかだけを人に聞き、あるものは後回しにする決定を記録に書いて "- deferred:" の要求にし、無いものは記録の Rejected に旧資料にあったが作らないと書く
  - why: 作らないものを黙って消さず、作るものは ID と形の検査を保ったままテストを求めずに置ける
  - decided_by: 利用者（推奨を採用）

- A6 旧資料と実装が食い違うもの（A3 の一覧から外されたものを含む）はその場で決めず FLAG の contradiction にし、記録に「次の食い違いは決めずに FLAG に残す」決定を書いてそれを FLAG の出典にする。旧資料の場所は決定の本文かリンクで示す。FLAG はその機能を壁打ちするときに回収する
  - superseded_by: [A22（食い違いは FLAG ごとに決定を書く）](./2026-09-26-adoption.md#A22)
  - why: 旧資料は判断の記録の置き場の外にあり、そのまま出典にすると source_invalid になる（reference の記述。実測はしていない）。決めることを導入から切り離し、機能を触るときに回す
  - decided_by: 利用者（推奨を採用）

- A7 この件で kotowari 本体（CLI）は変えない
  - why: A3〜A6 は出典、後回し、FLAG という今ある部品で書ける。旧資料を直接出典にしたくなるのが本体を変える一番の理由だが、A3 と A6 の決定を経れば避けられる
  - decided_by: 利用者（推奨を採用）

- A8 既に IR がある話題にも adopt を使う。既存の要求を旧資料の側に入れて A3〜A6 と同じ仕分けをし、実装と一致する要求はそのまま残し、食い違う要求は書き換えずに FLAG の contradiction にしてその ID を "- related:" に入れる
  - why: 導入済みでも切り方が怪しい IR がある（remote-merge、利用者の言葉）。要求を勝手に書き換えると、元の決定との関係が見えなくなる
  - decided_by: 利用者（推奨を採用）

- A9 A3 の一覧は行ごとに旧資料の記述、実装の振る舞い、根拠のテストの場所（無ければなし）を並べ、人は違和感のある行だけを外し、迷った行は残して追認する。記録の "decided_by" は「利用者（現状追認の一覧を承認）」とする
  - why: 期待が曖昧な人に項目ごとの判断を求めても答えは出ない。中身を一つずつ判断したふりをせず、決定の重みを記録が正直に示せば、後で読む人が見誤らない

  - why: すべてを動かして確かめるのは導入の費用として重い。読み違えの可能性は ambiguity として見える所に残す

  - why: adopt の成果物を IR と記録に限り、コードに触る作業は実装の工程に任せる

  - why: 入口で振り分けないと導入が brainstorm として回り、A1 で分けた意味が無くなる。FLAG の回収は brainstorm の通常の依頼として来る

- A21 旧資料と現行の実装が一致する振る舞いは、一覧の行ごとに「旧資料と現行の実装が一致しているので、見直さずにそのまま仕様とする」決定を1つずつ記録に書き、人には一覧を1回見せて承認を得る。各決定の "decided_by" は「利用者（現状追認の一覧を承認）」とし、要求はその行の決定を出典にする。一覧から外された行は食い違いとして扱う（A22）

  - decided_by: 利用者（推奨を採用）

  - decided_by: 利用者（推奨を採用）

- A25 adopt はテストに印を付けず、テストを消さず、移さない。承認の後に、根拠のテストが要求を十分に確かめるかを審査して十分なものだけに印を付ける作業、細部をなぞるだけのテストを削除の候補として人がまとめて消すかを決める作業、印を付けるテストを "tests.files" の範囲に入れる作業（中に移すか "tests.files" を広げるかはプロジェクトの既存の設定に従う）を1つの依頼文にまとめて人に渡し、どの工程で回すかは kotowari-using-workflow が決める。依頼文はファイルに残さない。印を付けるテストは "tests.files" が指す範囲に置き、adopt の skill は "tests.files" の外のテストは kotowari の対象外で印が無くても誤りにならないと案内する
  - why: A14 の内訳の件数（例えば根拠 40、細部 250）では kotowari-iterate の小さな作業を超えることがあり、件数に応じて plan と cycle に回すかを入口が決めるほうが合う。候補は一覧と内訳から出し直せるので、ファイルに残さなくてよい。A11、A15、A17 の理由（adopt の成果物は IR と記録に限る、git で戻せる、見えないテストが誤りにならない理由を示す）は変わらない
  - decided_by: 利用者（推奨を採用）

- A26 旧資料の用語は振る舞いと同じく仕分け、旧資料の定義と実装やテストでの使われ方が一致するものは1語に1つの追認の決定を出典にして CONTEXT.md に載せ、読み方が割れるものは FLAG の ambiguity にする
  - why: 要求の文でバッククォートで囲む用語は CONTEXT.md に無いと unknown_term になり、扱いを決めずには IR を書けない
  - decided_by: 利用者（推奨を採用）

- A27 adopt は最初に対象のリポジトリに ".kotowari/config.yaml" があるかを確かめ、無ければ kotowari スキルの references/config.md の準備の手順を先に行う。準備の中身は adopt に書かず場所を名指しする。adopt の skill は、FLAG が残る間は "kotowari status" の complete が false になり、それが回収待ちの一覧として狙いどおりであることを書く
  - why: 準備の手順を二か所に持つと食い違う。complete が false のままなのを壊れていると読まれないようにする

- A28 旧資料、コード、テストを読んで仕分けるのは主セッションで、1回で読み切れない大きさなら別の agent に読ませず、話題を小さく割ることを人に提案する
  - why: kotowari は利用者が費用をかけられない前提で、理由の無い委譲の席を足さない。読み切れない大きさは A2 の話題の単位が大きすぎる合図

- A29 人に聞くのは、話題と範囲と旧資料の確認（A19、A23）、一覧の1ラウンド、承認の3回とする。一覧のラウンドでは追認の候補の行に違和感のあるものの印を、旧資料にだけある行に作る予定の有無を答えてもらい、FLAG にする行とテストの内訳は見せるだけにする。答えを受けて IR と記録を書き、承認は kotowari-brainstorm の承認の手順で1回行い、人が読む記録の差分が一覧の最終版になる

  - decided_by: 利用者（推奨を採用）

- A30 話題の既存の IR の要求は、旧資料のほかの記述とは別に扱う。実装と一致すれば残し、食い違えば書き換えずにその ID を "- related:" に入れた contradiction の FLAG にし、実装がまだ無ければ一覧で作る予定を聞いて、あればその要求に後回しにする決定を出典にした "- deferred:" の行を足し、無ければ要求を消さずに contradiction の FLAG にする
  - why: 既存の IR も旧資料に含めたため、一致した要求が追認の候補にもそのまま残す行にも当たり、行き先が割れた（敵対的レビューの指摘）。消すと A8 の書き換えないに反する
  - decided_by: 利用者（推奨を採用）

- A31 FLAG は kind（contradiction、gap、ambiguity）を問わず、1つの FLAG に1つの「この件は決めずに FLAG に残す」決定を記録に書いてその FLAG の出典にする。旧資料と実装が食い違うもの（A21 の一覧から外された行を含む）の kind は contradiction にする。旧資料の場所は決定の本文かリンクで示す。FLAG はその機能を壁打ちするときに回収する
  - why: A22 は contradiction の FLAG だけを決めていて、gap と ambiguity の FLAG の出典が決まっていなかった（敵対的レビューの指摘）。食い違いの kind を contradiction にする点は A22 から引き継ぐ（照合レビューで、A31 への書き直しで落としていたと分かり戻した）。FLAG ごとに決定が分かれていないと照合できない点は A22 と同じ
  - decided_by: 利用者（推奨を採用）

- A32 旧資料なしと示した追認の候補（A4）も、人が外さなければ行ごとの追認の決定を出典にした要求になり、人が一覧で外せば人の期待と実装の食い違いとして contradiction の FLAG にする
