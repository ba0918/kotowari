# 壁打ちの記録: 変異テストの取り込み

## Context

`kotowari check` は「要求と具体例に印のあるテストがあるか」までを機械で見る（[REQ-085](../../ir/coverage.md#REQ-085)、[REQ-137](../../ir/coverage.md#REQ-137)）。しかし、そのテストが実装を縛っているかは見ていない。テストが何も assert していなくても、印があれば指摘は0件になる。
変異テスト（実装に小さな変更を入れ、テストが落ちるかを見る手法）はこの「縛る力」を実測する。[A1（scenario-tests）](./2026-09-17-scenario-tests.md#A1) でこの話題を別の記録に切ると決めていたので、ここで扱う。
過去の実験では cargo-mutants（Rust の変異テストの道具）を手で回し、見逃し（変異を入れてもテストが全部通ったもの）を LLM の調査役が「等価」「未検査」「欠陥の疑い」に分けた。実行の形（nightly の cargo と内容ハッシュでの再ビルド判定、`-j 1`、メモリ上限つきの systemd サービス、居残った子プロセスを殺す見張り）はそのとき固めた。ただし道具も結果もリポジトリの追跡外にあり、今の main に対する計測は無い（2026-09-17 の実測: `cargo mutants --list --no-config` は 804 件の変異を挙げる。実行はしていない）。
決めたいのは、変異テストを kotowari の何として取り込むか（check の指摘、別のコマンド、手順書だけ）、見逃しを要求にどう結び付けるか、等価の判断をどこに残すか、いつ走らせるか。

Position: A1〜A58 は承認済み（2026-09-17、kemi）。計画のレビューで見つかった2点を A59、A60 として足した（同日）。A59 と A60 も承認済み（同日、kemi）。次は cycle（計画は docs/plans/mutants.md）。

実走の観測（2026-09-17、cargo-mutants 27.1.0、`src/record_form.rs` だけ、メモリ上限つきのサービス、nightly と内容ハッシュの判定、`-j 1 --no-config`）: 変異23件、44秒、捕まえた23、見逃し0。全件のログに再コンパイルの行がある。結果の置き場 `mutants.out/` の `outcomes.json` は変異ごとに、名前（`src/record_form.rs:12:5: replace check_record_forms with ()` の形）、ファイル、関数名と範囲、変異の範囲、置き換えの内容、種類、結果（CaughtMutant など）、ログと差分のパスを持つ。落ちたテストの名前は `outcomes.json` に無く、ログの中の `test 名前 ... FAILED` の行にだけある。`cargo test` は最初に失敗したテストの実行ファイルで止まるので、その一覧は落ちるはずのテストの一部でしかない。
差分だけの実走の観測（2026-09-17、同じ走らせ方に `--in-diff` を足した）: 具体例ごとのテスト対応の実装の差分（`git diff baacead..HEAD -- src`、128行）に入る変異は16件。ビルドとテストの基準の実行を含めて26秒。捕まえた12、ビルド不能4、見逃し0。
差分にソースが無いときの観測（2026-09-17）: 文書だけの差分を `--in-diff` に渡すと、cargo-mutants は「Diff changes no Rust source files」と出して終了コード0で終わり、結果のファイルを作らない。結果のファイルが無い場面は、フックのスクリプトの側で扱う必要がある。差分のファイルが空のときも同じで、「Diff file is empty」と出して終了コード0で終わり、結果のファイルを作らない（同日の実測）。

## Agreements

- A1 変異テストの結果のファイルを入力として読み、指摘に変える機能を kotowari に足す。変異テストの実行は kotowari の外に置く。「見逃しが0件」という基準は IR の要求にせず、リリース前に人が見る確認の項目にする
  - why: 「テストが変異を捕まえる」は検証の対象がテスト自身で、製品の振る舞いではない（[A17（scenario-tests）](./2026-09-17-scenario-tests.md#A17) で外した具体例と同じ形）。結果のファイルを読んで指摘を出すことは製品の振る舞いで、入力のファイルを置けばテストできる。実行を外に置けば kotowari は Rust 専用にならず、実行時間とメモリの問題も抱えない
  - rejected: 手順書とスクリプトだけにして本体を変えない（見逃しと要求の対応が人の手に残る）。kotowari が変異テストを起動する（実行時間とメモリの問題を本体が抱える）
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A27](#A27)（「人が見る確認の項目にする」の部分だけ）

- A2 見逃し（変異を入れてもテストが全部通ったもの）は要求に結び付けず、場所（ファイル、行、関数）と変異の内容で出す。補助として、同じ関数の中で捕まえた変異を落としたテストの印から、関係しそうな要求を候補として並べる
  - why: 見逃しは落ちたテストが0本なので、テストの印から要求へ辿る道が無い。実装の側の印や関数と要求の対応表は、人が維持する新しい対応で、ずれても検査できない
  - rejected: 実装の側に印を置く。関数と要求の対応表を持つ
  - decided_by: 利用者（推奨を採用。候補の出し方は実走でログの形を確かめてから確定する）
  - superseded_by: [A7](#A7)（候補を並べる部分だけ。要求に結び付けない本体は生きている）

- A3 IR は新しい話題の文書に書く。`docs/ir/coverage.md` には足さない
  - why: coverage.md は要求とテストの対応を扱う。今回はテストと実装の対応で、責務が別
  - decided_by: 利用者（推奨を採用）

- A4 変異テストの実行の手順（nightly の cargo と内容ハッシュでの再ビルド判定、`-j 1`、メモリ上限つきの systemd サービス、居残った子プロセスを殺す見張り）は、リポジトリのスクリプト1本に置き、IR の要求にしない。kotowari のスキルの手順書には走らせる時機だけを書く
  - why: 実行の手順は製品の観測できる振る舞いではなく、この環境（WSL、cargo）に固有の運用
  - decided_by: 利用者（推奨を採用）

- A5 見逃しの分類は「等価」（変異しても振る舞いが変わらない）、「未検査」（テストが見ていない）、「欠陥の疑い」（元のコードがおかしい）の3つ。「未検査」は、要求がその変異を区別できるほど具体的かを先に確かめ、曖昧なら IR へ戻し、具体的ならテストを足す。用語集に「変異」「見逃し」「等価」を足す
  - why: 過去の実験で使って回った語彙で、構想メモ（docs/spec/concept.md の「ミューテーションテストで見逃された変更があった場合」）の手順と合う。テストを先に足すと、曖昧な要求を実装の今の振る舞いで固定してしまう
  - decided_by: 利用者（推奨を採用）

- A6 初版が読む入力は cargo-mutants の `outcomes.json` そのまま。kotowari 独自の中立なファイル形式と変換スクリプトは作らない
  - why: 結果を作る道具が今は1つで、中立なファイル形式は想像で決める契約になり、変換スクリプトは誰にも検査されない。実物の形式なら結果のファイルを置くだけでテストできる
  - rejected: kotowari 独自の中立なファイル形式を決め、道具ごとの変換スクリプトを外に置く
  - decided_by: 利用者（推奨を採用）

- A7 初版では、見逃しに「関係しそうな要求の候補」を付けない。見逃しは場所（ファイル、行、関数）と置き換えの内容だけで出す
  - why: 落ちたテストの名前は `outcomes.json` に無く、ログの `test 名前 ... FAILED` の行にしか無い。その文面は Rust のテスト実行器の表示で契約ではなく、`cargo test` が最初に失敗した実行ファイルで止まるので一覧も一部でしかない（Context の実走の観測）
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A56](#A56)（場所のうち関数を外した）

- A8 結果を読むのは `kotowari check` ではなく別のコマンド（仮の名前 `kotowari mutants <結果のパス>`）。出力は check の指摘と同じ形（text / json、ファイルと行と種類）で、見逃しがあれば終了コード1
  - why: check は push の前に毎回0件を要求されるが、変異テストは十数分かかり毎回は回せない。古い結果のファイルを check が読むと、ずれた行を指したまま push を止める。入力を引数にすれば、どの結果を読んだかが明示できる
  - rejected: check に混ぜる（設定の鍵で結果のファイルを指す）
  - decided_by: 利用者（推奨を採用）

- A9 等価などの分類は kotowari の側のファイル1つに「変異、分類、理由」の一覧で持ち、理由は必須。変異テストは常に除外なしで走らせる。kotowari は一覧に載った見逃しを指摘から外し、一覧にあって結果に現れない行には注意を出す
  - why: cargo-mutants の除外設定（`.cargo/mutants.toml`）は、除外した変異を測らず、理由はコメントで誰も検査しない。道具の設定に判断を置くと道具を替えたときに失う
  - rejected: `.cargo/mutants.toml` の `exclude_re` と理由のコメントに置く
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A20](#A20)（注意を出す条件だけ。一覧を kotowari の側に持つ本体は生きている）

- A10 走らせるのはリリースの前と、cycle が収束した後の後始末として主セッションが手で。push の前のフックと cycle の中には入れない。全体の実行時間はスクリプトを作った後に基準値として1回測る
  - why: push の前には遅すぎる。cycle の中に置くと1周ごとにレビュー役が全体を読み直す費用を払う（構想メモ docs/spec/concept.md の実験003の学び）
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A25](#A25)、[A26](#A26)（手で走らせる部分。cycle の中に入れない部分は生きている）

- A11 見逃しは誤り（error）、時間切れは注意（notice）。ビルド不能と捕まえた変異には何も出さない
  - why: 時間切れは無限ループになる変異で多く出る。テストが捕まえたとは言い切れないが、壊れていることは観測できている
  - decided_by: 利用者（推奨を採用）

- A12 変異テストの道具に依存しないつくりにする。今は Rust と cargo-mutants だけだが、道具に固有の語と形を kotowari の要求と指摘に漏らさない
  - why: kotowari 自体は言語を限らない道具で、結果を作る道具は替わりうる
  - decided_by: 利用者（第2ラウンドへの回答で利用者が足した）

- A13 kotowari の中に、道具を知らない「変異の結果」の形を1つ持つ（ファイル、行、関数名（あれば）、変更の説明（道具が出した文のまま）、結果の4値: 捕まえた、見逃した、時間切れ、ビルド不能）。IR の要求と指摘はこの形の語だけで書く。道具ごとの読み取りは、その道具の結果のファイルをこの形に写す部品で、写し方は IR の決定表に書く
  - why: [A12](#A12)。道具を足すときに既存の要求が変わらず、部品と決定表の行の追加で済む。5つの項目は変異テストという手法が持つ情報で、道具に固有ではない（他の道具の実物の出力は未確認）
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A56](#A56)（関数名を持つ部分だけ）

- A14 どの道具の結果かはコマンドのオプションで必ず指定する（`--tool cargo-mutants`）。省略は引数の誤り。値は今は1つ
  - why: 既定値を cargo-mutants にすると Rust の前提が焼き付く。中身からの自動判別は道具が増えたときに誤判定の場面を生む
  - rejected: 既定値を置く。ファイルの中身から判別する
  - decided_by: 利用者（推奨を採用）

- A15 等価の一覧の1件は「ファイル、変更の説明、変異が入る行の元の文面（前後の空白を除く）」で変異を同定する。kotowari は結果の行番号で今のソースのその行を読み、文面を比べる。同じファイルに同じ文面の行が複数あり同じ変更が入る場合は、どれにも効くことを認める
  - why: 行番号は直すたびにずれる。行番号を外した名前は重なる（2026-09-17 の実測: 804 件のうち 382 件が他と重なる）。文面で取れば、行が動いただけでは外れず、その行を書き換えたときだけ外れて判断のし直しに倒れる
  - rejected: 行番号で同定する。ファイルと関数と説明だけで同定する
  - decided_by: 利用者（推奨を採用）

- A16 一覧の置き場は `.kotowari/config.yaml` の鍵で指す。既定は無く、鍵が無ければ一覧なしで動く。形は YAML の一覧で、1件がファイル、変更の説明、行の文面、分類、理由を持つ。理由が空の行は誤り
  - why: 数十から百件の機械的な一覧で、人が読む判断の記録とは性質が違う
  - rejected: Markdown の判断の記録に混ぜる
  - decided_by: 利用者（推奨を採用）

- A17 一覧に書ける分類は「等価」だけ。「未検査」と「欠陥の疑い」は一覧で指摘を消せない。3分類（A5）は調べるときの語彙として手順書に残す
  - why: 直すべき状態を一覧で黙らせられると先送りの置き場になる。見逃しを抱えて出すかは人が件数と中身を見て決める（A1）
  - decided_by: 利用者（推奨を採用）

- A18 コードを直すたびに人手の専用の対応が要る仕組みにしない
  - why: 形だけになる可能性が上がる
  - decided_by: 利用者（第3ラウンドへの回答で利用者が足した）

- A19 cycle の後の実走は main との差分に入る変異だけ（cargo-mutants の `--in-diff`）。全体の実走はリリースの前だけ
  - why: 後始末が十数分かかると省かれるようになる。2026-09-17 の実測で23件が44秒
  - decided_by: 利用者（推奨を採用）

- A20 等価の一覧の1件に注意を出すのは、その「行の文面」がそのファイルのどこにも無くなったとき。結果に現れるかどうかでは判定しない。注意は終了コードを変えない
  - why: 差分だけの実走では結果に入るのが一部の変異だけで、結果に対して判定すると一覧のほとんどが誤って古いと言われる。ソースに対する判定は結果が全体でも一部でも同じに動き、道具にも依存しない
  - decided_by: 利用者（推奨を採用）

- A21 一覧の手入れ（新しい見逃しを3分類で調べる、外れた行の判断のし直し、古い行の削除）は主セッションと安い調査役の LLM が後始末の手順で行う。人に専用の作業を作らない。人が見るのは普段の差分のレビューに混ざる一覧の変更だけ
  - why: [A18](#A18)。過去の実験で分類を安いモデルの調査役に出して回った
  - decided_by: 利用者（推奨を採用）

- A22 等価を見つけたら、一覧に書く前に、コードを単純にして変異そのものを無くせないかを先に見る（到達しない分岐や使われない値を消す）。手順書の文言で、kotowari の機能にはしない
  - why: 一覧が育たなければ手入れも減る。過去の実験で到達不能コードの除去で等価が1件消えた
  - decided_by: 利用者（推奨を採用）

- A23 A4 のスクリプト1本に、実行（メモリ上限と見張りつき）、続けて `kotowari mutants` を叩くところまでを入れる。引数で差分だけか全体かを選ぶ
  - why: 手順が1コマンドなら省かれにくく、結果のファイルを毎回その場で作るので古い結果を読ませる余地が無い
  - decided_by: 利用者（推奨を採用）

- A24 目指す形は、人は特別に意識しなくてよく、LLM に対しては強固なガードレールとして働くこと
  - why: not recorded
  - decided_by: 利用者（第4ラウンドへの回答で利用者が足した）

- A25 この記録で「ガードレール」と呼ぶのは、LLM が必ず通る関門で機械が終了コードで止めるものだけ。手順書やスキルの文言は数えない。差分だけの実走（A19）を push の前のフック（lefthook の pre-push）に入れ、リモートの main との差分に入る変異に見逃しが1件でも残れば push を止める
  - why: [A24](#A24)。手順書は LLM が飛ばせる。2026-09-17 の実測で、1つの機能の差分（変異16件）が26秒で、push の前に入れても遅くない
  - decided_by: 利用者（推奨を採用）

- A26 タグを push するときは、同じ pre-push のフックで全体の実走に切り替える
  - why: git にタグを打つ瞬間のフックは無いが、pre-push は push される対象がタグかを受け取れる。リリースはタグの push を必ず通るので、LLM がリリースの手順を飛ばしても止まる。十数分はリリースのときだけ払う（lefthook での見分け方は計画の段で確かめる）
  - decided_by: 利用者（推奨を採用）

- A27 「見逃しが0件（等価の一覧に載った分を除く）」はフックが終了コードで強制する。IR の要求にはしない
  - why: [A24](#A24)。人が見る確認の項目のままだと人が意識しないといけない。IR に書くのは `kotowari mutants` が結果を読んで指摘を出す振る舞いまでで、0件の強制は今の push の前の check 0件と同じ位置づけのフックの設定
  - decided_by: 利用者（推奨を採用）

- A28 等価の申告への歯止めは3段。（1）`kotowari mutants` は出力の最後に、等価として外した件数を必ず出す。（2）一覧に1件足す前に、別の文脈の LLM にその変異を落とすテストを書かせる。落とせたらそのテストを採用し、落とせなかった試みを理由に書く（手順書の文言）。（3）一覧の変更は人の普段の差分のレビューに混ざる。等価の件数の上限は置かない
  - why: 等価が本当かは機械で判定できない。一覧に頼った量が毎回見えれば、増え方の異常に気づける。上限の数字には根拠を持てない
  - rejected: 等価の件数に上限を置く
  - decided_by: 利用者（推奨を採用）

- A29 関門の抜け道のうち、ソースの `#[mutants::skip]`（スクリプトがソースを探し、あれば失敗で止める）、cargo-mutants の除外設定（スクリプトは常に設定を読まないオプションで走らせる）、古い結果や作った結果（A23。スクリプトが毎回その場で作る）の3つをスクリプトで塞ぐ。フックを無視する push（`--no-verify`）は塞がない
  - why: `#[mutants::skip]` は cargo-mutants に固有なので、kotowari 本体でなくスクリプトの側に置く（A12）。`--no-verify` は今あるフックすべてに共通で、この記録の範囲の外

- A30 用語集に足す語は5つ。「変異」（変異テストの道具が実装に入れる、1か所の小さな変更）、「変異の結果」（変異1件について、ファイル、行、関数名、変更の説明、結果の4値を持つもの）、「見逃し」（結果が「見逃した」の変異。その変異を入れてもテストが全部通った）、「等価」（変異を入れても観測できる振る舞いが変わらない、という人か LLM の判断）、「等価の一覧」（設定の鍵が指す YAML のファイル）。同じ意味で「ミューテーション」「生存」「ミュータント」を使わない
