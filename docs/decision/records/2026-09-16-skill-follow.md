# 壁打ちの進捗: スキルを本体の変更に追従させる

目的: kotowari 本体は 2026-09-16 に、IR の置き場を再帰で読む形（ir-tree の記録 A1〜A21）、注意の severity "notice"（notice の記録 A1〜A2）、行数の既定 200（同 A5）に変わった。スキル `kotowari` の references と SKILL.md、スキルの仕様（docs/spec/kotowari-skill.md）はまだ古い形（置き場の直下、ID は3桁、警告、版 0.1.0 の固定）を書いている。利用者の方針（版はタグに追従、スキルは上限の数字を持たず指摘の種類で拾う、分割の単位は責務）を合わせて反映する。

Position: 1ラウンド。利用者の方針は会話で決まっているので、反映の仕方だけを決めた（2026-09-16）

## Agreements
- A1 SKILL.md は対象の版を固定しない。最初の手順は `kotowari --version` で道具の有無を確かめるだけにし、コマンドが無いか出力から版が読めないときだけ止まる。references の先頭には版の写しでなく改訂日を書く。理由: 本体はローカルにしか無く常に最新で、固定は不一致で止まる摩擦にしかならない。リリースで版がタグとして公開されたら追従の書き方を決める（利用者、2026-09-16）
- A2 スキルは上限の数字（行数、要求の数）を書き方の指針に持たない。指針は指摘の種類名（too_many_lines、too_many_requirements）で書き、本体の既定が変わってもスキルを変えなくてよい形にする。数字が残るのは config.md の設定の雛形だけ（setup が既定と同じ値を書く約束のため）で、そこには本体の既定の写しであることを書く（利用者）
- A3 too_many_lines と too_many_requirements の対処は「文書を分割する」ではない。分割の単位は責務であり、注意は責務の混在を疑う合図。混在していれば範囲の行で説明できる単位に分け、していなければ理由を判断の記録に書いて残す。行数や件数を理由に切らない。承認の提示では注意の件数でなく残す理由を見せる（利用者のフィードバック。kakoi-net の要件定義で、責務が同じ内容が行数を理由に切られた実例から）
- A4 ir-form.md を ir-tree の記録に合わせて改める: 置き場の再帰（A1、A13）、どの階層にも置ける CONTEXT.md と FLAGS.md（A8）、用語集の連鎖と連鎖の中の duplicate_term（A3、A4）、文書名の参照の2形と条件（A5、A14、A17、A18、A21）、ID の3桁以上（A6、A11）、README.md を置かない（A7）、粒度の目安（A9）、ディレクトリ名は参照で指せる文字にする（A12）、detail はファイル名（A19）。除外の一覧から「IR の置き場のサブディレクトリ」を外す
- A5 スキルの全文とスキルの仕様の「警告」を「注意」に改め、severity は "notice" と書く（notice の記録 A1、A2 に追従）
- A6 反映はメインセッションが書き、調査役1体の照合（references と本体の IR の食い違い、スキルの仕様との食い違い）で確かめる。フルレビューは行わない（軽量の作業として利用者が指示）
