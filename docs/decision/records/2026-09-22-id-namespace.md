# 壁打ちの記録: ID の名前空間とドメインごとの IR

## Context

mds（Markdown スキーマの検証と抽出の道具）を kotowari の monorepo へ取り込み、`src/ir.rs` の自前パーサを mds のエンジンに置き換える。取り込みの前に、2 つの製品の仕様 IR を同じ木に置けるようにする必要がある。

障害が 2 つあった。どちらも実測で確かめた。

1 つ目は ID の衝突。mds の IR の ID 86 個のうち 84 個が kotowari 側と重なる（REQ 52/52、TBL 10/10、PROP 5/7、EX 17/17）。`ID` の名前空間はリポジトリ全体で大域で、[REQ-032](../../ir/ir-items.md#REQ-032) の重複検出が 84 件出る。ディレクトリを分けても解けない。

2 つ目は`用語`の衝突。両方の`用語集`で 7 語（題名・項目・文・指摘・停止・コードブロック・基準のディレクトリ）が重なり、意味はすべて違う。うち 4 語は mds のスキーマ言語のキーワード（`title:`、`item:`、`statement:`、`codeblock:`）の和訳で、言い換えると仕様の散文と利用者が書く YAML の対応が切れる。

こちらは実測で解けた。[REQ-041](../../ir/terms.md#REQ-041) の`連鎖`は「文書のあるディレクトリから IR の置き場の根まで」なので、根に`用語集`を置かず各ドメインのディレクトリに置けば連鎖は重ならない。実際に `docs/ir/core/` と `docs/ir/markdown-schema/` に分けて `kotowari check` を走らせ、duplicate_term 0 件・unknown_term 0 件を確かめた。仕様変更は要らない。対照として根に `CONTEXT.md` を戻すと duplicate_term が 52 件出る。

残るのは ID だけ。この記録はそれを決める。

Position: 承認済み（2026-09-22）。利用者が案 A（両方のドメインに名前を付ける）を選び、ドメインをまたぐ参照と指摘の種類を確認した。IR は [ir-references.md](../../ir/ir-references.md)、[findings.md](../../ir/findings.md)、[CONTEXT.md](../../ir/CONTEXT.md)。実装はこの記録の後。

## Agreements

- A1 `ID` の形に任意の名前を入れ、"REQ-"、"TBL-"、"PROP-"、"EX-"、"FLAG-" のいずれかに、省いてよい「名前と "-"」を続け、その後に 3 桁以上の数字を置く形にする。名前は小文字の英字で始まり、以降は小文字の英数字と "-" だけを使う
  - why: 84 個の ID 衝突を帯の割り当てでなく構造で解く。番号の帯は規約でしかなく、次に要求を足すときに帯を覚えていないと再び衝突する。名前があればどの ID を見ても所属が分かり、LLM が文脈なしに読める
  - rejected: mds の ID を空き帯（REQ-501 以降など）へ振り直す（書き換え量は名前付きと同じで、将来の衝突が残る）。ディレクトリの位置だけで ID の名前空間を分け、ID の文字は変えない（`印`は ID の文字しか持たないので、どのドメインを指すか決まらない）
  - decided_by: 利用者

- A2 名前は必須にしない。`ID` に名前が無い形（"REQ-001"）は有効のまま残す
  - why: kotowari は配布される道具で、スキルの setup は利用者側に単一製品の IR を作る。必須にすると配布先の利用者全員が製品名入りの ID を書く羽目になる。テストの試験データ 650 箇所も、合成した利用者側の文書なので名前を持たない
  - decided_by: 利用者（推奨を採用）

- A3 `ID` に名前があるとき、その名前は文書の置き場の第 1 階層と一致する。一致しないとき kotowari は新しい種類の`誤り`を出す
  - why: A2 で名前を任意にしたので、名前の正しさを見る者が要る。一致を検査すれば「ドメインの取り違え」と「文書の置き違い」の両方が機械的に捕まり、規約が不変条件になる
  - rejected: 一致を検査せず規約に任せる（暗黙の約束が増える。kotowari の流儀に合わない）
  - decided_by: 利用者（推奨を採用）

- A4 A3 の`誤り`は新しい種類にする。既存の invalid_id を使い回さない
  - why: invalid_id は [REQ-114](../../ir/ir-references.md#REQ-114) の「"@id" の値が EX の`ID`の形でない」で、detail は値。名前の不一致を混ぜると、出力から原因が読めなくなる。kotowari は`指摘`の種類を細かく分ける流儀で、今 40 種類ある
  - decided_by: 利用者（推奨を採用）

- A5 IR の置き場の直下にある文書（第 1 階層を持たない文書）の名前付き `ID` は、一致する相手が無いので A3 の`誤り`にする
  - why: 名前は置き場の階層を指すものなので、指す先が無ければ不一致と同じ。単一製品の利用者は名前を使わないので影響しない
  - decided_by: 推奨（利用者の確認済みの方針から導いた）

- A6 ドメインをまたぐ `ID` の参照を許す。別のドメインの `ID` を指しても`誤り`にしない
  - why: 今回は 2 つの製品が同じ木に並ぶだけで、相互参照の需要がまだ分かっていない。禁止は後から足せるが、一度禁止してから解くのは難しい。今の [REQ-054](../../ir/ir-references.md#REQ-054) の参照解決は大域なので、実装の変更も要らない
  - rejected: 禁止する（新しい要求と`指摘`の種類がもう 1 つ増える）。片方向だけ許す（規則が一つ複雑になる）
  - decided_by: 利用者（推奨を採用）

- A7 `用語`の衝突は、ドメインごとのディレクトリに`用語集`を置き、IR の置き場の根に`用語集`を置かないことで解く。`連鎖`の規則は変えない
  - why: 実測で duplicate_term 0 件・unknown_term 0 件を確かめた。仕様変更が要らず、[REQ-041](../../ir/terms.md#REQ-041) の`連鎖`が既に意図どおり働く
  - rejected: `連鎖`を「下が上を隠す」に変える（今の duplicate_term が捕まえている「うっかり再定義」を失う）。mds 側の 7 語を言い換える（4 語はスキーマ言語のキーワードの和訳で、仕様と YAML の対応が切れる）
  - decided_by: 利用者

- A8 kotowari 自身の IR を `docs/ir/core/` へ移し、その `ID` に "core" の名前を付ける。mds の IR は `docs/ir/schema/` へ置き、"schema" の名前を付ける
  - why: A3 の一致の検査が働くには、どちらのドメインも名前を持つ必要がある。名前は`印`に多数回現れるので短い方がよい（kotowari 側 1002 箇所、mds 側 424 箇所）
  - rejected: kotowari 側を名前なしのまま残す（「名前なし = core」という暗黙の既定ができ、A3 の検査が core に効かない）
  - decided_by: 利用者

- A9 テストの試験データの `ID` には名前を付けない
  - why: 試験データは利用者側の IR を模した合成文書で、kotowari の要求を指していない。A2 で名前を任意にしたのでそのまま通る。`印`とコメントの`ID` だけが kotowari の実 IR を指す
  - decided_by: 推奨（A2 から導いた）
