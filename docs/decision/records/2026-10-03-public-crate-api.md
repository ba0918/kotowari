# 公開クレートとライブラリAPIの再構成

## Context

利用者は、core と markdown-schema の内部に責務が集中していると考え、分離を求めている。
将来のクレート公開に向け、利用者が用途に合うクレートとAPIを選べる構成を決める。
現状の実装と依存関係を調査し、利用用途と互換性の方針を確認してから仕様と実装計画を定める。

Position: Q22承認済み。再構成を先行し、overviewは別計画で新構成に載せる。D1に基づく具体設計と仕様草案のレビュー・判断照合を終え、仕様承認待ち。承認後に実装計画へ進む。公開も実装もまだ行わない。

## Agreements

- A1 将来のクレート公開を前提に、責務の分離と利用者が迷わない公開APIを設計する。
  - why: 現在のクレート内部に責務が集中しており、使いやすい形で提供するために再構成したいという利用者の要望による。
  - decided_by: 利用者の初回依頼

- A2 公開ライブラリは、別のRustアプリからkotowariの検査・問い合わせを呼び出す用途と、kotowariとは独立したMarkdownスキーマ検証の用途を前提とする。
  - why: 公開API設計の優先対象として利用者が選択した。
  - decided_by: 利用者の第1ラウンドQ1回答
- A3 IR解析結果を利用するエディタ連携や独自ツールの用途も視野に入れる。
  - why: 利用者が将来の利用用途として挙げた。今回提供するAPIの具体的な範囲は後続ラウンドで決める。
  - decided_by: 利用者の第1ラウンドQ1回答
- A4 現在提供しているバイナリのCLIインターフェースを維持し、既存Rust APIと内部構造の破壊的変更を許容する。
  - why: 現状はバイナリのみを提供しており、既存ライブラリ利用者向けの互換性維持は必要ない。
  - decided_by: 利用者の第1ラウンドQ2回答
- A5 今回の計画は、再構成、APIドキュメント、利用例、パッケージ検証、バージョン管理方針を含め、実際の公開作業は別作業とする。
  - why: 利用者が公開準備の範囲について推奨案を採用した。
  - decided_by: 利用者の第1ラウンドQ3回答
- A6 文字列などのメモリ上の入力を受け取る検査APIと、ディレクトリを指定して利用するAPIの両方を提供する。複数文書の検査は、内容と論理的なパスの組を受け取れる形にする。
  - why: ファイルを保存せずに生成文書や未保存テキストを検査する用途と、既存プロジェクトを検査する用途を支援する。
  - decided_by: 利用者の第2ラウンドQ4回答（推奨を採用）
- A7 ライブラリは指摘の種類・重要度・位置と問い合わせ結果をRustの型で返し、表示方法は呼び出し側が決める。CLIはその結果をテキストまたはJSONに整形する。
  - why: 呼び出し側が表示文字列を解析せずに結果を扱えるようにする。
  - decided_by: 利用者の第2ラウンドQ5回答（推奨を採用）
- A8 検査対象に問題が見つかった結果と、読み込み失敗などで検査を完了できなかった失敗を区別する。
  - why: 呼び出し側が検査結果と実行失敗を別々に処理できるようにする。
  - decided_by: 利用者の第2ラウンドQ5回答（推奨を採用）
- A9 両バイナリのコマンド・引数・終了コード・出力の既存契約を維持し、既存の設定・IR・スキーマの受け付けと検査結果の意味を維持する。
  - why: 内部再構成によって既存CLI利用者の入力や処理を壊さないため。
  - decided_by: 利用者の第2ラウンドQ6回答（推奨を採用）
- A10 kotowariライブラリは check・list・query・status・plan・mutants・changes に相当する操作をすべて提供し、CLI引数ではなく各操作に必要な型付き入力を受け取る。
  - why: 別のRustアプリが既存機能をCLI経由にせず呼び出せるようにする。
  - decided_by: 利用者の第3ラウンドQ7回答（推奨を採用）
- A11 メモリ上の計算・検査と、ファイル探索・Git操作・HTTP取得をクレート境界で分離し、CLIは専用パッケージに置く。メモリ上の検査だけを使う利用者に環境操作とCLI用の依存を要求しない。
  - why: 不要な依存を避け、依存方向をコンパイラで制約するため。クレート数とリリース管理の手間の増加を受け入れる。
  - decided_by: 利用者の第3ラウンドQ8回答（推奨を採用）
- A12 IRの項目・参照関係・位置情報を読み取り専用で取得するAPIを今回提供する。構文違反のある文書でも、取得できた項目と指摘を参照できる形にする。
  - why: IR解析結果を利用するエディタ連携や独自ツールの用途を支援する。
  - decided_by: 利用者の第3ラウンドQ9回答（推奨を採用）
- A13 Markdown解析ライブラリ固有の構文木と内部検索エンジンの型を公開契約に含めない。
  - why: 外部利用者が内部実装の型に依存することを避ける。
  - decided_by: 利用者の第3ラウンドQ9回答（推奨を採用）
- A14 利用者向けライブラリのパッケージ名を kotowari、CLI専用パッケージ名を kotowari-cli とする。実行コマンド名 kotowari は維持し、ソースからのインストール手順のパッケージ指定は変更する。
  - why: ライブラリ利用者が cargo add kotowari から始められるようにする。
  - decided_by: 利用者の第4ラウンドQ10回答（推奨を採用）
- A15 kotowari系とMarkdownスキーマ系は独立したバージョン系列とし、各系列内のクレートは同じバージョンに揃える。
  - why: 汎用Markdownスキーマの版をkotowari固有の変更から独立させ、系列内のリリース管理を簡単にする。
  - decided_by: 利用者の第4ラウンドQ11回答（推奨を採用）
- A16 依存先として公開する下位クレートも、公開APIの互換性管理の対象とする。
  - why: 下位クレートに直接依存する利用者にも、公開APIの変更方針を明確にする。
  - decided_by: 利用者の第4ラウンドQ11回答（推奨を採用）
- A17 Markdownスキーマのファイル・URL読み込みを専用のI/Oクレートで提供する。既存CLIのファイル探索・HTTP取得・キャッシュ処理を移し、CLIと外部アプリが共用する。
  - why: 文字列から検査する利用者の依存を増やさず、CLI相当の読み込み処理を外部アプリでも再利用できるようにする。
  - decided_by: 利用者の第4ラウンドQ12回答（推奨を採用）
- A18 一回で結果を得るAPIと、読み込み済みデータを複数操作で再利用するAPIを提供する。再利用中はファイルを暗黙に読み直さず、変更の反映には明示的な再読み込みを必要とする。
  - why: 簡単な呼び出しと、同じ入力に対する複数操作の両方を支援する。
  - decided_by: 利用者の第5ラウンドQ13回答（推奨を採用）
- A19 読み込み済みデータの提供によって、すべての操作に全ファイルの読み込みを要求しない。list/query がガイドを読まない既存動作を維持する。
  - why: 操作ごとの読み込み範囲の違いを保ち、従来不要だったファイルの問題で操作が失敗することを避ける。
  - decided_by: 利用者の第5ラウンドQ13回答（推奨を採用）
- A20 Markdownからの値抽出の通常の入口は、文書を検証し違反がない場合に値を抽出する。違反のある文書について指摘と取得可能な値を返す明示的な別APIも提供する。
  - why: 利用者が検証済みの値と部分的な抽出結果を区別できるようにする。CLIの既存動作は維持する。
  - decided_by: 利用者の第5ラウンドQ14回答（推奨を採用）
- A21 解析済みのスキーマと文書を再利用できるようにする。
  - why: 同じ内容の検証・抽出を行うたびに再解析する必要をなくす。
  - decided_by: 利用者の第5ラウンドQ14回答（推奨を採用）
- A22 同期APIを基本とし、高水準操作をawaitできる任意のTokio対応を初回公開の範囲に含める。同期処理をspawn_blockingで実行し、検査ロジックを共用する。純粋な検査クレートにTokioを依存させない。
  - why: 非同期アプリからの利用を支援しつつ、同期の検査処理と既存I/O処理を再利用する。
  - decided_by: 利用者のQ15再提案への回答（Aを採用）
- A23 Tokio対応では処理の同時実行数を制限する。
  - why: 多数の呼び出しで実行スレッドが増え続けることを避ける。
  - decided_by: 利用者のQ15再提案への回答（Aを採用）
- A24 非同期の待機をキャンセルしても、実行開始済みの同期処理の停止は保証しない。Git実行・HTTP取得・計算・キャッシュ書込みが継続し得ることを公開APIの契約に明示する。
  - why: spawn_blockingの実行開始後の処理はabortで停止できず、待機の中止と処理の停止を区別する必要がある。
  - decided_by: 利用者のQ15再提案への回答（Aを採用）
- A25 計算層は kotowari-core と kotowari-source-analysis に分離する。core はIR解析・出典検査・テスト対応判定・変異結果検査・変更照合などの純粋な計算を責務別モジュールとして持ち、source-analysis はソース文字列からテスト・公開要素を発見する。
  - why: IRだけを扱う利用者にast-grep依存を要求せず、単独クレート化の効果がまだ明確でない計算はモジュールで責務を分ける。
  - decided_by: 利用者の第6ラウンドQ16回答（推奨を採用）
- A26 ast-grep依存は kotowari-source-analysis に閉じ込める。テスト対応判定は発見済みの事実を受け取り、ソース解析を呼ばない。
  - why: ソース解析とIRに対する判定の依存方向を分ける。
  - decided_by: 利用者の第6ラウンドQ16回答（推奨を採用）
- A27 Tokio対応は kotowari とスキーマI/Oクレートの既定で無効な tokio feature で提供する。CLIは同期APIを使う。
  - why: 非同期操作のために利用者が選ぶパッケージを増やさず、同期利用者にはTokio依存を要求しない。
  - decided_by: 利用者の第6ラウンドQ17回答（推奨を採用）
- A28 今回の計画には、公開順序の手順書、公開しないパッケージ検証の手順、既存の版管理・バイナリ配布スクリプトの分割対応を含める。
  - why: 再構成後も既存のバイナリ配布を継続でき、将来の公開手順とパッケージを事前検証できるようにする。
  - decided_by: 利用者の第6ラウンドQ18回答（推奨を採用）
- A29 メモリ入力は、必要な情報が未提供の場合と、提供された情報が空の場合を区別する。必要な入力が未提供なら検査の完了を報告せず不足を返す。IR解析だけのAPIはIRだけで利用できる。
  - why: 検査に必要な情報の欠落を、対象が存在しないことや検査成功として扱わないため。
  - decided_by: 利用者の第7ラウンドQ19回答（推奨を採用）
- A30 非同期の同時実行数は非同期実行用オブジェクトごとに制限する。既定値は1とし、利用者は正の整数で変更できる。
  - why: 制限の範囲を明示し、利用者が実行環境に合わせて調整できるようにする。
  - decided_by: 利用者の第7ラウンドQ20回答（推奨を採用）
- A31 非同期実行用オブジェクトを複製した場合、複製同士は同じ実行枠を共有する。
  - why: オブジェクトの複製によって意図した同時実行数の制限を迂回しないため。
  - decided_by: 利用者の第7ラウンドQ20回答（推奨を採用）
- A32 実行枠を待つ間にキャンセルされた処理は投入しない。投入後は、呼び出し側が待機をやめても処理完了まで実行枠を保持する。
  - why: 待機キャンセルを繰り返すことで実際の同時実行数が上限を超えることを防ぐ。
  - decided_by: 利用者の第7ラウンドQ20回答（推奨を採用）
- A33 今回は既存7操作の再構成を先行し、overviewの実装は別計画で新構成に載せる。overviewの機能仕様と、kotowari-overview がcoreとmarkdown-viewに依存してcoreはoverviewを知らない関係を維持し、検査結果の統合先だけをルートCLIから新しい kotowari ライブラリへ変更する。
  - why: 未実装の新機能を再構成に混ぜず、CLIと外部アプリが同じ高水準操作を使う構成に揃える。
  - decided_by: 利用者のQ22回答（推奨を採用）
- A34 今回の対象パッケージは kotowari、kotowari-core、kotowari-source-analysis、kotowari-cli、kotowari-markdown-schema、kotowari-markdown-schema-io、kotowari-mds の7つとする。前4つはkotowari系、後3つはMarkdownスキーマ系に属する。CLIはルートの kotowari-cli と crates/kotowari-mds に置き、他のライブラリは同名の crates/ 配下に置く。
  - why: A14・A25で決まった入口と境界を具体的なパッケージ名にする。mdsのインストール対象を実行コマンド名と一致させる。
  - decided_by: 設計担当（D1の具体的命名・配置の委任）
- A35 workspace内の通常依存は、kotowari-cli から kotowari、kotowari から core と source-analysis、source-analysis から core、core から markdown-schema、markdown-schema-io から markdown-schema、kotowari-mds から markdown-schema-io と markdown-schema の方向とする。coreのIR・出典・テスト対応・変異・変更照合・計画書・読み取り結果は責務別モジュールとし、設定読込・ファイル探索・Git取得・表示を置かない。外部依存は既存のものを移し、Tokio以外の新規依存は追加確認する。
  - why: A11・A25・A26の依存分離を具体化し、計算を上位の環境操作から独立させる。
  - decided_by: 設計担当（D1の配置の委任）
- A36 kotowari の入口を Project::new とし、呼出開始位置と任意の設定ファイル指定を ProjectOptions で渡す。check・list・query・status・plan・mutants・changes をメソッドとして提供し、必要な下位の入力型・結果型を同じ型のまま再公開する。Project はカレントディレクトリを変更せず、CLIが現在位置を渡す。既存の設定探索・相対パス解決の意味は保つ。
  - why: A7・A10・A14を、単一の依存追加から使える入口に具体化する。
  - decided_by: 設計担当（D1のAPI設計の委任）
- A37 Project::read は list/query 用の不変の ReadModel、Project::inspect は check/status 用の不変の Inspection を返す。ReadModel は list/query を、Inspection は check/status と読み取り結果への参照を提供する。これらのメソッドは追加I/Oを行わない。簡便な7操作のメソッドは呼出ごとに必要な入力を新しく読む。保持期間は所有値を利用者が破棄するまでとし、ディスクへの保存や自動監視はしない。読み込み中のファイル群が同時点の内容である保証は追加しない。
  - why: A18・A19の再利用と操作別読込範囲を両立する。
  - decided_by: 設計担当（D1の型設計の委任）
- A38 core の ir::parse は SourceText の論理パスと文字列を受け取り、IrDocument の取得できた項目・参照・指摘を返す。項目はID欠落や不正なID文字列を理由に解析結果から除かず、元の文書の1始まりの行と、存在する場合の終端行を読み取り専用で返す。list/queryの既存の掲載条件は変えない。文字列にないIDや位置は補わない。
  - why: A12の部分解析結果を既存のCLI用一覧とは独立したAPIとして具体化する。
  - decided_by: 設計担当（D1の型設計の委任）
- A39 core の ReadInputs はIR・判断の記録・ADR・発見済みテスト情報、CheckInputs はそれらに検査設定で有効なガイド・面・照合記録の入力を加えたものとする。ReadModel::build と Inspection::build は設定と型付き入力を受ける。入力群の未提供と提供済みの空集合を区別し、必須の未提供は InputMissing、空集合は通常の検査規則で判定する。無効な任意機能の入力は不要とし、メモリ入力からファイルを自動取得しない。
  - why: A6・A29を、入力欠落による偽の検査完了を防ぐ構築手順に具体化する。
  - decided_by: 設計担当（D1の型設計の委任）
- A40 公開する失敗型は種類をプログラムで判別でき、std::error::Error と Display を実装する。文書の指摘は正常に完了した検査結果に含め、実行できない失敗は Result の Err にする。入力不足、設定・入力形式不正、未知の問い合わせID、読込・Git失敗、内部対応不能を区別し、CLIはそれらを既存の停止理由へ写す。指摘と結果の公開フィールドは読み取り専用にし、将来拡張する種類のenumは non_exhaustive とする。CLIのJSON構造は表示側で維持し、全内部モデルのSerialize/Deserializeを公開契約にはしない。
  - why: A7・A8・A9・A16を、文字列解析やCLI出力型への依存が不要なAPIに具体化する。
  - decided_by: 設計担当（D1の型設計の委任）
- A41 source-analysis の Analyzer は既存の組込み規則と文字列で渡す追加規則を読み、SourceTextから発見済みテスト・印・面と指摘を返す。規則の解釈と未対応言語の扱いは既存仕様を保ち、ファイル取得と対応判定は行わない。changes::evaluate の Comparison 入力と識別値計算はcoreが所有し、Git取得側がその同じ型を構築する。計画書検査と変異結果検査はIRの読み込みを要求しない。
  - why: A10・A25・A26の境界で既存モデルと計算を再利用し、Gitやソース解析への逆依存をなくす。
  - decided_by: 設計担当（D1の型設計の委任）
- A42 markdown-schema の通常入口は Schema::parse、Document::parse、validate、extract_validated、extract_partial とし、frontmatter_schema と resolve_schema も維持する。Schemaは意味検証を通した不変の型にし、外からのフィールド変更や未検証の直接Deserializeで検証を迂回できない形にする。ValidationOptions の既定はスキーマの open を尊重し、明示的な緩和指定との論理和を使う。
  - why: A20・A21の再利用可能な検証・抽出を、検証の迂回やopen設定の取り違えが起きない手順に具体化する。
  - decided_by: 設計担当（D1の型設計の委任）
- A43 extract_validated は検証済みの値を表す ValidatedValues か文書の指摘を返し、extract_partial は指摘と取得可能なJSON値を持つ PartialExtraction を返す。両方のJSON値は既存の serde_json::Value を使う。CLIの values と ast --schema は部分抽出の値を使い、文書の違反による既存の終了コード・出力を変えない。ast_json と extract_typed_partial は既存のAST JSONと型付き抽出JSONを提供し、markdown::mdast::Node や regex::Captures は公開しない。
