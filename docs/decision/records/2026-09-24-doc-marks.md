# 壁打ちの記録: 人間向け文書の印

## Context

IR から人間向けの使い方の文書を機械的に写すと、情報が足りず読みにくいうえに二重管理になる。そこで文書は IR を読んで人（か LLM）が書き、節ごとに説明している IR の項目の ID を印として持たせる方向を試した（2026-09-24、status・check・mutants・テストの印の4本。利用者は「読める内容になった」と評価）。
IR を直すたびに文書全体を見直すとトークンが枯れるので、印を使って見直すべき節だけを機械的に絞り込みたい。
障害が2つある: [P1（records）](./records.md#P1) は人間向けの文書の生成（render）と影響範囲の追跡（trace）を作らないと決めている。kotowari は今どのファイルも書かない（読むだけ）。

Position: 承認待ち（2026-09-24）。6ラウンド（A1〜A28）で木は尽き、IR を書く段の細部を照合レビューの指摘から A29〜A35 で足した。IR は docs/ir/core/guides.md（新設）と config、findings、list、output、status、cli、cli-environment、finding-order、query の各文書と CONTEXT.md。実装は plan → cycle

## Agreements

- A1 この仕組みの対象の文書を「ガイド」と呼ぶ。利用者向けの使い方の文書で、IR、決定の記録、実装計画、skill はガイドに含めない
  - why: "文書" は IR の側で「IR の文書」の意味に使っていて、同じ語だと取り違える
  - decided_by: 利用者（推奨を採用）

- A2 見直すべき節は、IR を変えた時点に限らずいつでも絞り込めるようにする。ガイドの印に項目の指紋を書き、"kotowari check" が今の IR の指紋と照合して、古い節がある間は指摘を出し続ける。指紋は読み取りのコマンドの出力に載せ、見直した人か LLM が印に書き写す。kotowari はファイルを書かない
  - why: 変更の中だけで絞る形では、その変更でガイドを直し忘れると後から気づく手段が無い。手順の順守を当てにせず機械で確かめる、という kotowari の方針と揃う。書き写しにすれば kotowari が初めてファイルを書くコマンドを持たずに済む
  - rejected: 指紋を持たず、IR を変えた変更の差分から直した項目の ID を取って絞る（直し忘れが残る）
  - decided_by: 利用者（推奨を採用。「cli 経由で放置されてるドキュメントがいつでも検出できるのはいい」）

- A3 ガイドの印の照合は [P1（records）](./records.md#P1) の render にも trace にも当たらず、P1 は変えない。kotowari はガイドを生成せず、印と今の IR を照らすだけで、変更から影響を辿るのではない（[REQ-core-142](../../ir/core/equivalents.md#REQ-core-142) の equivalent_stale と同じ種類の検査）
  - why: 厳密には render ではない（利用者）。利用者は render を作ること自体も否定していない（「別に作ったっていい」）が、この仕組みには要らないので P1 を解く判断はしない
  - decided_by: 利用者

- A4 ガイドの置き場は設定の "guides.files" に glob の一覧で書く。"tests.files" と同じ形で、鍵が無ければガイドは0件で、ガイドの検査は何もしない
  - why: テストの置き場と同じ書き方なら覚えることが増えない。ガイドを持たないプロジェクト（このリポジトリを含む）に影響しない
  - decided_by: 利用者（推奨を採用）

- A5 ガイドの印は HTML コメントの中にテストの印と同じ "@kotowari[" の形で書き、1件は "ID:指紋" で、コンマで並べる（例 `<!-- @kotowari[REQ-core-165:3fa9c2e1, EX-core-259:77b0d1aa] -->`）
  - why: HTML コメントは描画したガイドに出ないので読者が戸惑わない（試作で確認した懸念）。テストの印と見た目が揃う。1件ごとに指紋を持つので、どの項目が変わったかが分かる
  - decided_by: 利用者（推奨を採用）

- A6 指紋は、"kotowari query" の "body" と同じ範囲の行（[TBL-core-027](../../ir/core/query.md#TBL-core-027)）から取る。正規化はせず、見出しの名前は含めない
  - why: 本文の切り出しを新しく作らずに済む。名前を変えただけで古い扱いにするとうるさい
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A27](#A27)

- A7 指紋は、その行を "\n" でつないだ文字列の SHA-256 の先頭の16進8桁（小文字）
  - why: アルゴリズムを固定しないと、Rust の版を上げただけで値が変わりうる（標準の DefaultHasher はそう文書化されている）。8桁は書き写しやすさを優先した長さで、1プロジェクト数百件の項目では偶然の一致を気にしなくてよい
  - decided_by: 利用者（推奨を採用）

- A8 古い節は guide_stale の注意として出す。注意なので "kotowari status" の complete を妨げない
  - why: complete は誤り0と問題の記録0だけで決まる（[A9（query-status）](./2026-09-20-query-status.md#A9)）のを保つ。注意は check と status の数に残り続けるので、放置されたガイドはいつでも見える
  - rejected: 誤りにする（ガイドが遅れているだけで CI が落ちる）
  - decided_by: 利用者（推奨を採用）

- A9 ガイドの印は、CommonMark で読んだときの HTML コメントの中だけから読む。コードブロックとコードスパンの中は読まない。Markdown の読み方は mds のエンジンに揃える
  - why: 印の書き方を説明するガイド（試作の「テストに印を付ける」）は例をコードブロックに書くので、ファイルの中の "@kotowari[" を全部拾うと例が印として読まれる
  - decided_by: 利用者（推奨を採用）

- A10 ガイドの印が壊れているとき（中が空、閉じ括弧が無い、":指紋" が無い、指紋が16進8桁の小文字でない）は invalid_marker の誤りを出す
  - why: テストの印と同じ扱い。形の合わない入力を黙って飛ばさない（[P2（records）](./records.md#P2)）
  - decided_by: 利用者（推奨を採用）

- A11 ガイドの印の ID が IR に無いときは guide_stale の注意を出す
  - why: 項目を消したならその節は古い。unresolved_reference の誤りにすると、IR から項目を消しただけで CI が落ち、A8 と食い違う
  - rejected: テストの印と同じ unresolved_reference の誤り
  - decided_by: 利用者（推奨を採用）

- A12 kotowari は印が受け持つ範囲（節）を決めない。guide_stale は印の行を指すだけで、印の細かさ（1つの印に ID が数個まで、を目安にする）は kotowari の skill の書き方の決まりにする
  - why: 試作では症状ひとつの節は ID 1〜4個で回り、横断する節では 7〜11個に膨らんだ。細かく割るのは書き方の問題で、機械で止めるほどではない
  - decided_by: 利用者（推奨を採用）

- A13 印の付け忘れは kotowari で検査しない。ガイドを書くときと見直すときに、節の内容に対応する項目を query で確かめて印に足す手順を skill に書く
  - why: ガイドの文章がどの項目を説明しているかは機械に判定できない
  - decided_by: 利用者（推奨を採用）

- A14 "kotowari list" の1件に "fingerprint" の鍵を足し、query の1件も持つ。guide_stale の detail は "ID 書かれていた指紋 今の指紋" で、項目が IR に無いときの今の指紋は "-"
  - why: 注意の1行だけで、どの ID を何に書き換えるかまで分かる。query は list の1件を詳しくしたもの（[A4（query-status）](./2026-09-20-query-status.md#A4)）
  - decided_by: 利用者（推奨を採用）

- A15 1つのファイルが "guides.files" と "tests.files" の両方に当たるとき、kotowari は設定の誤りを理由に停止し、詳細に重なったファイルの相対パスを出す
  - why: 問い合わせの無い言語ではファイルの中の "@kotowari[" を全部拾うので、ガイドの印がテストの印として読まれる。片方を黙って優先しない（[P2（records）](./records.md#P2)）
  - decided_by: 利用者（推奨を採用）

- A16 ガイドのファイルの読み方の失敗は "tests.files" と同じに扱う（glob として読めない要素は設定の誤り、読めないファイル・UTF-8 でないファイル・先の無いシンボリックリンクは停止、何にも当たらない glob は誤りにしない）
  - why: 置き場ごとに規則が違うと覚えにくい
  - decided_by: 利用者（推奨を採用）

- A17 "kotowari check" の JSON の最上位と "kotowari status" に "guides" の群を足し、読んだガイドの数（files）と印の中の ID の数（marks）を出す
  - why: "tests" と同じく、glob の誤りでガイドが0件になっても黙らない
  - decided_by: 利用者（推奨を採用）

- A18 kotowari の skill にガイドを書く・見直す場面（印の細かさの目安と、印を足す・指紋を書き写す手順）を足すことも今回の範囲に入れる
  - why: A12 と A13 が決まりと手順を skill に置くと決めた
  - decided_by: 利用者（推奨を採用）

- A19 試作のガイドをこのリポジトリに入れて "guides.files" を設定することは今回の範囲に入れない。仕組みができてから別の作業で、頁の構成もそのときに調整する
  - why: 今回作るのは仕組みだけ。構成は後から調整すればよい（利用者）
  - decided_by: 利用者（推奨を採用）

- A20 印の ID と同じ ID の項目が IR に2つ以上あるときは、どれかの項目の指紋と一致すれば古くないとする
  - why: query は同じ ID の項目を全部返す（[A6（query-status）](./2026-09-20-query-status.md#A6)）。重なり自体は duplicate_id の誤りで止まるので注意を重ねない
  - decided_by: 利用者（推奨を採用）

- A21 用語集に「ガイド」（"guides.files" に当たる利用者向けの使い方の文書）、「ガイドの印」（ガイドの HTML コメントの中の "@kotowari[ID:指紋, …]"。テストの印と区別する）、「指紋」（項目の本文の行から取る16進8桁の値）を足す
  - why: A1 の取り違えを避ける理由と同じ。テストの「印」と同じ語で呼ぶと、どちらの規則の話か分からない
  - decided_by: 利用者（推奨を採用）

- A22 "kotowari status" はガイドを読み、"kotowari list" と "kotowari query" はガイドを読まず、ガイドの置き場と読み込みでは停止しない
  - why: status は check と同じ検査をし、A17 で guides の群を出す。list の fingerprint は IR だけから決まり、ガイドは要らない
  - decided_by: 利用者（推奨を採用）

- A23 ガイドの印の1件は、コンマで区切った1件ごとに前後の空白を除き、最初の ":" で ID と指紋に分けてそれぞれの前後の空白を除く。":" の前が ID の形でない（空を含む）ときは invalid_marker の誤りにする。同じ ID の1件が2つ以上あっても1件ずつ扱う
  - why: 括弧の内側や ":" の前後の空白で誤りにする理由は無い。A11 が注意にしたのは IR に項目が無い場合で、形そのものが壊れているのは書き間違いなので誤りで止める
  - decided_by: 利用者（推奨を採用）

- A24 "guides.files" が IR や判断の記録の置き場と重なっても停止せず、両方として読む。用語集の「ガイドに IR などを含めない」は置き場の想定の説明で、kotowari は区別しない
  - why: テストの置き場との重なりを止めた理由（印の書き方の衝突）が IR と判断の記録には無く、両方として読んでも害が無い
  - decided_by: 利用者（推奨を採用）

- A25 ガイドの印を読む範囲は HTML のコメントの "<!--" から "-->" までの中で、"<!--" で始まる HTML ブロックの "-->" より後の文字は読まない。読まないコードは CommonMark のコードブロック（字下げの形とフェンスの形）とコードスパン
  - why: CommonMark の HTML ブロックは "-->" を含む行の終わりまで続くので、ブロックで判定するとコメントの外の文字まで読む。用語集のコードブロックはフェンスの形だけで、CommonMark として読むガイドとは食い違う
  - decided_by: 利用者（推奨を採用）

- A26 指紋の行には行の終わりの文字（"\r\n" の "\r" を含む）を入れない
  - why: 入れると同じ内容でも checkout の改行の形で指紋が変わる。等価の一覧の文面も "\r" を含めない（[REQ-core-141](../../ir/core/equivalents.md#REQ-core-141)）
  - decided_by: 利用者（推奨を採用）

- A27 指紋は、項目では query の body の行から "- source:" の行を除いた並び、シナリオではステップの行だけの並びから取る（A6 を改める）
  - why: 出典は brainstorm のたびに足され、そのたびに注意が出るとうるさい。シナリオの名前を変えただけで古くなるのは、要求の見出しの名前を除いた A6 と揃わない
  - decided_by: 利用者（推奨を採用）

- A28 ガイドとテストの置き場が重なるファイルが2つ以上あるときは、停止の詳細にパスのバイト順で最初の1つを出す
  - why: 停止の詳細は1行。直して実行し直せば次が出る
  - decided_by: 利用者（推奨を採用）

- A29 ガイドの走査と除外（隠しディレクトリ、ディレクトリのシンボリックリンク、ディレクトリでも通常のファイルでもないもの）は "tests.files" と同じにする
  - why: A16 の「読み方の失敗を tests.files と同じにする」と同じ理由で、置き場ごとに規則を変えない。照合レビューが A4 と A16 だけでは走査と除外まで言っていないと指摘した
  - decided_by: IR を書く段で推奨を採用（照合レビューの指摘から。承認で利用者が確かめる）

- A30 1つの HTML のコメントの中と1行の中にあるガイドの印はすべて拾う
  - why: テストの印の「1行に複数の印」（[A57（records）](./records.md#A57)）と揃える
  - decided_by: IR を書く段で推奨を採用（照合レビューの指摘から。承認で利用者が確かめる）

- A31 形の誤ったガイドの印は、1つの印につき invalid_marker を1件出し、その印の中のどの1件も照合しない。中が空か区切りだけのとき、始まりと同じ行に "]" が無いときも形の誤りで、detail はその行の文字にする
  - why: テストの印と同じ扱い（A10）。テストの印も閉じ括弧を同じ行に求め、detail を行の文字にする（[REQ-core-072](../../ir/core/test-markers.md#REQ-core-072)）。壊れた印の一部だけを照合すると、どの1件が読まれたかが書き手に分からない
  - decided_by: IR を書く段で推奨を採用（照合レビューの指摘から。承認で利用者が確かめる）

- A32 ガイドへの指摘（invalid_marker と guide_stale）の path はガイドの基準のディレクトリからの相対パス、line はそのガイドの印の始まりの行にする
  - why: A12 の「印の行を指す」を path と line の形にしたもの。ほかの指摘の path と同じ基準
  - decided_by: IR を書く段で推奨を採用（照合レビューの指摘から。承認で利用者が確かめる）

- A33 指紋の SHA-256 は、行をつないだ文字列の UTF-8 のバイト列から取る
  - why: IR の文書は UTF-8 で読む。バイト列を決めないと値が決まらない
  - decided_by: IR を書く段で推奨を採用（照合レビューの指摘から。承認で利用者が確かめる）

- A34 同じ ID が2か所以上にあって guide_stale を出すとき、detail の今の指紋は [REQ-core-032](../../ir/core/findings.md#REQ-core-032) の1つ目の項目の指紋にする
  - why: A20 は一致の判定だけを決めていて、出す値が1つに決まらない。duplicate_id と同じ「1つ目」に揃える
  - decided_by: IR を書く段で推奨を採用（照合レビューの指摘から。承認で利用者が確かめる）

- A35 "guides" の "marks" は形の正しいガイドの印の1件の数で、"files" はテストのファイルと同じ数え方（パスごとに1回、複数の glob に当たっても1回、シンボリックリンクと実体は別のパス）にする。"--format text" の check には出さない
  - why: A31 で形の誤った印は照合しないので、照合した数と揃える。数え方と text の扱いは "tests" と揃える
  - decided_by: IR を書く段で推奨を採用（照合レビューの指摘から。承認で利用者が確かめる）

## Rejected
