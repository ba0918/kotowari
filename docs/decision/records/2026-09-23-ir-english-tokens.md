# 壁打ちの記録: IR の型の語を英語にする

## Context

判断の記録は、補足の行の名前と検査の切り替えになる見出しを英語に固定し、値は言語を問わない形にした（[A26（record-form）](./2026-09-17-record-form.md#A26)）。一方で IR は、節の見出し（`## 要求`、`## 具体例` など）、項目の欄の名前（`- 種類:`、`- 出典:` など）、用語集の題名と列の名前、問題の記録の見出しがまだ日本語で、利用者の言語に依存している。

これらの語は kotowari のスキーマ（`.mds/schemas/` の3つ。本体に埋め込まれる）と kotowari-core の写しのコードで決まっていて、このリポジトリの IR 40 文書、テスト、skill の references が使っている。IR の型の語も英語に揃えるかどうかと、揃え方を決める。

Position: 第1ラウンドで範囲、語、移行を決めた（A1〜A3）。第2ラウンドで曖昧語の既定と kotowari スキルの言語を決めた（A4、A5）。第3ラウンドで references の表の見出しを決めた（A6）。木は尽きた。IR の中で型の語を名指しする文を英語の語に直した（見出しと欄そのものは、今の kotowari が読める日本語のまま、実装でエンジンと一緒に切り替える）。照合の1回目で挙がった4件のうち2件を A7 と A8 で決め、3回目の照合で裏付けの無い項目は0件になった。承認待ち（2026-09-23）。

## Agreements

- A1 IR の型の語を英語にする。型の語は、節の見出し、項目の欄の名前、用語集の題名と列の名前、問題の記録の節の見出し。要求の文、項目の名前、用語、表の中身、欄の値の自由文は言語を問わない
  - why: 利用者の言語に依存しないため。判断の記録は同じ線引きで型の語を英語にしてある（[A26（record-form）](./2026-09-17-record-form.md#A26)）のに、IR だけ日本語なのは揃っていない
  - decided_by: 利用者（推奨を採用）

- A2 英語の語は判断の記録の表記に合わせ、見出しは頭だけ大文字、欄の名前は小文字で2語なら `_` でつなぐ。`## 要求` → `## Requirements`、`## 決定表` → `## Decision tables`、`## 性質` → `## Properties`、`## 具体例` → `## Examples`、`- 種類:` → `- kind:`、`- 出典:` → `- source:`、`- 検証:` → `- verification:`、`- 定義:` → `- definition:`、`- 確かめ方:` → `- how_to_verify:`、`- 関係:` → `- related:`、`# 用語集` → `# Glossary`、列の `用語`・`意味`・`出典` → `Term`・`Meaning`・`Source`、`## 問題の記録` → `## Flags`
  - why: `source` はシナリオのタグ `@source` と、`how_to_verify` は `kotowari list` の JSON の鍵と、`Examples` は ID の接頭辞 `EX-` と揃う
  - decided_by: 利用者（推奨を採用）

- A3 日本語の型の語は受け付けず、一度に切り替える。このリポジトリの IR、テスト、fixture、skill の references、README も同じ変更で書き換える
  - why: 使っているのは作者だけで、移行の期間を持つ費用を払う理由が無い（[A89（ir-engine）](./2026-09-22-ir-engine.md#A89) と同じ判断）
  - decided_by: 利用者（推奨を採用）

- A4 曖昧語の既定（`vague_words` の「適切に」「必要に応じて」「通常は」「など」）は変えず、設定で上書きできることを README に書く
  - why: 曖昧語は本文の言語の話で、型の語ではない。既定に英語の語を足すのは検査の振る舞いを変えるので、足すなら英語で本文を書く利用者が出てから別に決める
  - rejected: 既定に英語の曖昧語を足す。英語の利用者は最初から守られるが、日本語の本文にも英語の語の照合が走り、どの語を曖昧とみなすかを今決める手間がかかる
  - decided_by: 利用者（推奨を採用）

- A5 kotowari スキル（`skills/kotowari/` の SKILL.md と references）の本文を英語にする。工程の skill と同じ言語に揃える
  - why: kotowari スキルだけ日本語なのは統一感が無く、英語のほうがトークンも少し少ない（利用者の言葉）。references は IR の型の語を説明するので、A1〜A3 の書き換えと同じ変更で一度に行えば2度書き換えずに済む
  - decided_by: 利用者

- A6 kotowari スキルの `references/findings.md` で、このリポジトリのテストが目印にする表の1列目の見出しを、指摘の種類の表は `Kind`、停止の文言の表は `Message` にする。ほかの列の見出しは英語で自由に訳してよい
  - why: A5 で references を英語にすると、日本語の列名「種類」「文言」を目印にしたテストの約束が成り立たなくなる。`Kind` は JSON の `kind` と A2 の `- kind:` に揃い、停止の文言は標準エラーの1行目の文字なので `Message` にする
  - decided_by: 利用者（推奨を採用）

- A7 kotowari のスキーマ（`.mds/schemas/` の `ir.yaml`、`context.yaml`、`flags.yaml`）と本体のコードも、A2 の英語の語で節、欄、題名、表のヘッダを宣言する。指摘の detail に欄の名前が入るもの（missing_field の detail など）は英語の名前になる
  - why: IR の型の語はスキーマの宣言で決まり、detail はその宣言の名前を写すので、A2 と A3 を実現すればそうなる。IR の項目がスキーマの宣言や detail の値を名指ししているので、決定として書いておく
  - decided_by: 主セッション（A2 と A3 の帰結。照合レビューで出典が要ると分かった）

- A8 `kotowari list` の `type` は、`- kind:` の行が無ければ null にする（今の振る舞いの追認）
  - why: `verification` と `how_to_verify` は行が無ければ null と決めてある（[A18（read-commands）](./2026-09-19-read-commands.md#A18)）のに、`type` だけ決めていなかった。照合レビューで裏付けの無い値として挙がった
  - decided_by: 主セッション（今の振る舞いと、同じ表の他の鍵に揃えた追認）
