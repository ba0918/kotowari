# 壁打ちの記録: 計画書の形を mds で検査する

## Context

kotowari-plan が書く計画書（`docs/plans/`）の形は、`agent/skills/kotowari-plan/references/step-template.md` が決めている。今は plan の Finishing 1 で、書いた本人がこの雛形と見比べて散文で自己点検するだけで、機械の検査が無い。

このリポジトリには Markdown の形をスキーマで検査する `kotowari-mds` があり、工程も ba0918 から切り出した（[A1（workflow-split）](./2026-09-23-workflow-split.md#A1)）のに、自分の工程の成果物を自分の道具で検査していない。計画書をスキーマで検査するかどうか、するならどう組むかを決める。複数モデルのレビューの件（[review-panel](./2026-09-24-review-panel.md)）と同じ席で壁打ちする。

Position: 第1ラウンドで範囲と置き場を決めた（A1〜A4）。利用者の言葉で書式の方向を決めた（A5）。第2ラウンドでスキーマの指し方、書式、落ちたときの扱いを決めた（A6〜A8）。第3ラウンドで利用者が出した同梱の案を第4ラウンドで決め（A9）、A2 と A6 を改めた。第5ラウンドでコマンド、指摘、frontmatter、雛形の守り方、置き場を決めた（A10〜A14）。第6ラウンドで `kotowari plan` の細部を決めた（A15〜A18）。IR を書く前に見つかった中身の縛り方を第7ラウンドで決めた（A19〜A21）。IR を書き、独立したレビューで見つかった未決を第8ラウンドで決めた（A23〜A29）。照合レビューで出典の無い箇所を A30〜A34 で埋め、A7 と A25 の書き写しの誤りを直した。照合を3回行い、3回目に残った2件は出典の書き漏らしで、照合役が名指しした決定（A10、A15）を足した。承認待ち。

## Agreements

- A1 この件と複数モデルのレビューの件は、壁打ちを同じ席で行い、判断の記録と後で作る計画をそれぞれ1つずつに分ける
  - why: 2つは互いに依存せず、plan に渡す条件が「成果物が1つ（ブランチが1つ）」だから
  - decided_by: 利用者（推奨を採用）

- A2 この件のために新しい IR は作らず、決めたことは判断の記録と工程の skill の本文に書く。mds に足りない機能が見つかったときだけ、その機能を `docs/ir/schema/` の要求として足す
  - why: 工程の skill の変更は [A6（workflow-split）](./2026-09-23-workflow-split.md#A6) と同じ扱いにする。mds の機能は製品の振る舞いなので IR が持つ
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A9](#A9)

- A3 スキーマで検査するのは計画書の形だけにする。決まった節があること、各ステップに全部の欄があること、`Shown by` の種類が test、check、artifact、external のどれかであること。要求の ID が実在するかは今までどおり `kotowari query` で確かめ、欄の中身の良し悪しは自己点検とレビューに残す
  - why: 中身の良し悪し（Done when が他人に観測できるか、など）は機械で決まらない。ID の実在は既に別の道具が確かめている
  - decided_by: 利用者（推奨を採用）

- A4 検査は plan の工程が Finishing で、承認を求める前に回す。lefthook には載せない
  - why: 計画書はマージの後に消える。kotowari を使う他のプロジェクトに mds が入っているとは限らない
  - decided_by: 利用者（推奨を採用）

- A5 これから kotowari-plan が書く計画書は、書式を mds で検査しやすい形に変えてよい
  - why: 今の `step-template.md` の形（深さ2の `Step N — …` の繰り返し、地の文のラベル、`Shown by` の頭の語）は今の mds では検査できない（`節` は名前の完全一致で照合し、欄として読むのは一覧の `- 名前: 値` の行だけで、`enum` は値全体との一致）。汎用のエンジンである mds を計画書の都合で広げるより、書式を寄せるほうが安い
  - rejected: mds に節名の正規表現や節の順序の検査を足す。mds は汎用のエンジンで、kotowari の都合を持ち込まない
  - decided_by: 利用者（「今後 kotowari-plan で作られるものを mds に都合がいい書式にしても問題ない」）

- A6 plan の工程は計画書を書くたびに、自分の skill の `references/` にあるスキーマをプロジェクトの `.kotowari/schemas/plan.yaml` へ写して上書きし、計画書は frontmatter の `$schema` でそれを相対パスで指す。写したスキーマは計画書と一緒にコミットする
  - why: URL で指すとキャッシュに期限が無く（[REQ-schema-013](../../ir/schema/schema-resolution.md#REQ-schema-013)）、skill を更新しても古いスキーマが使われ続ける。skill の置き場の絶対パスは人によって違う。毎回上書きすればスキーマは常に今の skill と揃い、コミットすれば同じ検査を後からやり直せる
  - rejected: GitHub の URL で指す。キャッシュに期限が無いので skill の更新に追従しない
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A9](#A9)

- A7 計画書の形は、題名の後に計画全体の節（Goal、Specification、Approach and why、Scope of change、Step order and prerequisites、Verification map、Left to the implementer、Stop conditions、任意の Test command、Out of scope）と `## Steps` を置き、各ステップを `## Steps` の下の `### S<番号>: <作るもの>` の項目にする。ステップの欄は `- Purpose:`、`- Specification:`、`- Prerequisites:`、`- May change:`、`- Done when:`、`- Shown by:`、`- Left to the implementer:`、`- Stop and hand back if:` の一覧の行にして順序も縛り、`Shown by` の値は test、check、artifact、external のどれかの語で始まり、その語の後は空白か値の終わりである。節の並び順は検査しない
  - why: 今の mds のまま書ける形にする（A5）。節の並び順を検査する仕組みは mds に無く、そのために mds を広げない。この形が実際に通るかはスキーマを書いた段階で、正しい計画書と壊した計画書を食わせて確かめ、通らなければこの決定に戻る
  - decided_by: 利用者（推奨を採用）

- A8 検査の終了コードが1なら、plan の工程は指摘を自分で直して0になるまで回す。2（停止）なら理由を人に見せて止まる
  - why: 形の直しは判断ではないので、人に聞く理由が無い
  - decided_by: 利用者（推奨を採用）

- A9 計画書のスキーマは、IR、用語集、問題の記録のスキーマと同じく kotowari の本体に同梱し、本体が計画書の形を検査する。計画書は `$schema` でスキーマを指さず、プロジェクトにスキーマを写さない。本体の機能になるので、その検査は `docs/ir/core/` の要求として書く。skill の版と本体の版がずれて検査に落ちたときは、本体のスキーマに合わせて計画書を直す
  - why: 本体は既に3つのスキーマを `include_str!` で同梱し（`crates/kotowari-core/src/schema.rs`）、工程が作る判断の記録の形も本体が検査しているので、kotowari が提供する機能として説明がつく。plan の工程は既に `kotowari query` を使うので、本体がある前提にでき、mds が入っているかを問わなくてよい。計画書は完了すれば消すので常に利用者の手元の本体のスキーマで書かれ、過去の計画書を検査し直す機会はほとんど無い
  - rejected: skill の `references/` のスキーマをプロジェクトの `.kotowari/schemas/` へ写して `$schema` で指す（A6）。写す手順とコミットするファイルが増え、mds が入っていない環境の扱いも別に要る
  - decided_by: 利用者（同梱の案と、版がずれたら計画書を直すのは利用者の言葉）

- A10 計画書の検査は新しいコマンド `kotowari plan <path>` で行う。位置引数は計画書のファイル1つで、`--format` を受ける
  - why: `check` は位置引数を受けず（[REQ-core-004](../../ir/core/cli.md#REQ-core-004)）、ファイルを1つ受けて読むコマンドには `mutants` の前例がある
  - rejected: `check` に計画書の置き場の設定を足し、IR と一緒に検査する。pre-commit で自動で回るが、計画書の指摘が `status` の完了の判定に響き、その回の指摘だけを扱う規則（[A13（workflow-split）](./2026-09-23-workflow-split.md#A13)）とも絡んで広がりすぎる
  - decided_by: 利用者（推奨を採用）

- A11 計画書の形の指摘は新しい種類を1つだけ作って出し、mds が出した種類と詳細はその指摘の詳細に入れる。重さは誤りで、終了コードは今の決定表のとおり（0、1、2）
  - why: mds の種類をそのまま kotowari の種類として並べると、skill の `findings.md` の表と、それを本体と突き合わせるテスト（[REQ-core-125](../../ir/core/skill-references.md#REQ-core-125)）の対象が増える。計画書を直すのは LLM で、詳細を読めれば足りる
  - decided_by: 利用者（推奨を採用）

- A12 計画書には frontmatter を置かない。`kotowari plan` は同梱のスキーマで読む
  - why: スキーマを文書から指す必要が無くなった（A9）
  - decided_by: 利用者（推奨を採用）

- A13 kotowari-plan の skill の `references/` に例の計画書を1つのファイルとして置き、それが同梱のスキーマを通ることをリポジトリのテストで確かめる。この検査は skill の references と本体の一致の要求として `docs/ir/core/skill-references.md` に足す。`step-template.md` は欄の説明とその例へのリンクにする
  - why: 本体と skill が同じリポジトリにあるうちは、雛形と同梱のスキーマのずれをテストで先に見つけられる。[REQ-core-125](../../ir/core/skill-references.md#REQ-core-125) と同じ形の前例がある
  - decided_by: 利用者（推奨を採用）

- A14 同梱するスキーマは、他の3つと同じくこのリポジトリの `.kotowari/schemas/plan.yaml` に置き、本体はそこから取り込む
  - why: 置き場と取り込み方を既存の3つと揃える
  - decided_by: 利用者（推奨を採用）

- A15 `kotowari plan` が受けるオプションは `--format`、`--help`、`--version` だけにし、`--config` は引数の誤りとして停止する
  - why: `plan` は設定を読まない。受けて黙って無視すると、付けた人が効いていると誤解する
  - decided_by: 利用者（推奨を採用）

- A16 `kotowari plan` の引数と読めないときの扱いは `mutants` と揃える。位置引数がちょうど1つでなければ引数の誤りで停止し、パスはカレントディレクトリからの相対で読み、ファイルが無い・ディレクトリ・読めないときは読めないファイル、UTF-8 でなければ UTF-8 でないファイルを理由に停止する。新しい停止の理由は作らない
  - why: ファイルを1つ受けて読むコマンドの前例（[REQ-core-149](../../ir/core/cli.md#REQ-core-149)）に揃えれば、決めることが増えない
  - decided_by: 利用者（推奨を採用）

- A17 `kotowari plan` の JSON の最上位は `findings` と `counts` の2つにし、指摘の鍵は今の指摘の鍵（kind、severity、path、line、detail）をそのまま使う。path は `mutants` の結果のファイルと同じ扱いにする
  - why: `check` の `files`、`lines`、`tests` は IR とテストのファイルを読んだ量で、計画書1つには当たらない
  - decided_by: 利用者（推奨を採用）

- A18 計画書の形の指摘の種類は `invalid_plan` とし、detail は「mds の種類: mds の詳細」の形、line は mds が出した行をそのまま使う
  - why: A11 で種類を1つにしたので、何が悪いかは detail で伝える
  - decided_by: 利用者（推奨を採用）

- A19 計画全体の節の下には文、箇条書き、表、コードブロックのどれを置いてもよい。ステップの項目の下には8つの欄の行だけを置き、それ以外の行は指摘にする
  - why: Verification map は表、Approach は散文が書きやすい。ステップは実装役が読む契約なので形を固める
  - decided_by: 利用者（推奨を採用）

- A20 必須の節はちょうど1つずつ、Test command だけ0個か1個とする。`## Steps` にはステップが1つ以上あり、各ステップの8つの欄は決まった順で1回ずつ書く
  - why: 計画書の各部分が欠けず重ならないことを形で保つ
  - decided_by: 利用者（推奨を採用）

- A21 ステップの番号は `S` の後に数字が続く形だけを見て、連番かどうかは検査しない
  - why: 番号の飛びは中身の問題で、検査する理由が無い
  - decided_by: 利用者（推奨を採用）

- A22 `## Steps` の節にはステップの項目だけを置き、最初のステップより前に空でない行を置かない
  - why: A7 は `## Steps` を計画全体の節と別に挙げ、A19 はステップの形を固めるとした。`## Steps` の直下に散文を許すと、ステップの外に実装役への指示が紛れる
  - decided_by: 主セッション（A7 と A19 から導いた。承認のときに利用者へ示す）

- A23 計画書のスキーマは1行ずつ読む（"reading: line"）。欄の値は1行に書く
  - why: 既定の段落の読み方では、欄の直後に空行なしで続く行が欄の値に吸われ、空行の後の字下げした行は継続段落として指摘にならず、ステップの下にほかの行を置かない（A19）が成り立たない。IR の3つのスキーマも "reading: line" で揃っている
  - decided_by: 利用者（推奨を採用）

- A24 ステップの見出しは `### S` と数字の後に `:` があることだけを見て、名前が空か、`:` の後に空白が無いかは検査しない
  - why: mds は見出しを最初の `:` で分けて両側の空白を除くだけで、名前の側を検査しない。検査するには mds を広げることになり、A5 で棄てた方向になる
  - decided_by: 利用者（推奨を採用）

- A25 計画全体の節には、番号付きの一覧、題名と最初の節の間の行、`### ` とそれより深い見出しを置けない。`- ` の箇条書きの子の一覧は置ける
  - why: mds に番号付きの一覧の規則の種類が無く、宣言できない。要約は Goal に書けばよい。箇条書きの子の一覧はスキーマで宣言できる
  - decided_by: 利用者（推奨を採用）

- A26 `kotowari plan` の出力の "path" は、計画書のファイルの基準のディレクトリからの相対パスとし、基準の外なら "../" を含める。`./a.md` や絶対パスで渡されても正規化して同じ形で出す
  - why: 設定ファイルの停止の詳細（基準の外なら "../" を含める）と揃える。A17 が前例に挙げた mutants の "path" は変異の結果の中の値で、前例にならなかった
  - decided_by: 利用者（推奨を採用）

- A27 計画書の先頭の frontmatter は、中身を問わず読まずに飛ばし、指摘にも停止にもしない。「置かない」（A12）は skill の書き方の決まりとして残す
  - why: mds は先頭の frontmatter を中身を見ずに飛ばす。kotowari の除外にも「題名より前の空でない行」がある
  - decided_by: 利用者（推奨を採用）

- A28 欄の行の一覧の記号は `-`、`*`、`+` のどれでもよい
  - why: mds は3つの記号を同じ規則の種類として読む
  - decided_by: 利用者（推奨を採用）

- A29 同じ番号のステップが2つあっても検査しない。mds が重複を自分で指摘するなら、スキーマを書くときの実測でこの決定に戻る
  - why: 番号の飛び（A21）と同じく中身の問題とみる
  - decided_by: 利用者（推奨を採用）

- A30 引数が無いときと1つ目の位置引数が無いときの停止の詳細は "expected command: check, list, mutants, plan, query or status" にする
  - why: コマンドを足すたびに、この詳細に挙げるコマンドを改めてきた（[A18（query-status）](./2026-09-20-query-status.md#A18)）。A10 で plan を足したので、バイト順の並びに plan を入れる
  - decided_by: 主セッション（A10 に伴う直し。承認のときに利用者へ示す）

- A31 計画書の題名はちょうど1つとし、A7 に挙げた節のほかの `## ` の節は置けない
  - why: A7 は計画書の形を節の列挙で決めた。mds のスキーマは既定で閉じた世界で、宣言しない節と2つ目の題名は指摘になる
  - decided_by: 主セッション（A7 と、Q9 で示した書式から導いた。承認のときに利用者へ示す）

- A32 `kotowari plan` は計画書のファイルだけを読み、設定ファイル、IR、判断の記録、テストのファイルを読まない
  - why: 計画書1つの形を同梱のスキーマで検査するだけで（A9、A10）、`check` と一緒に検査する案は棄てた（A10）。設定を読まないことは A15 で決めた
  - decided_by: 主セッション（A9、A10、A15 から導いた。承認のときに利用者へ示す）

- A33 mds が行を持たない指摘を出したとき、`invalid_plan` の line は null にする。`counts` の中身は `check` と同じく種類ごとの指摘の数にする
  - why: 行を持たない指摘の line を null にするのは `check` の指摘の鍵の決まりと同じ。A17 で指摘の鍵をそのまま使うとしたので、数え方も揃える
  - decided_by: 主セッション（A17、A18 から導いた。承認のときに利用者へ示す）

- A34 A13 の例の計画書のファイル名は `plan-example.md` にする
  - why: 置き場は A13 で決めた。名前は中身が分かれば足りる
  - decided_by: 主セッション（承認のときに利用者へ示す）

- A35 `docs/ir/core/plan.md` に行数の上限の注意（too_many_lines）が出ても分けない
  - why: 読み直した結果、文書の要求はすべて範囲の文の「kotowari plan が計画書を1つ読み、同梱のスキーマで形を検査する」に収まり、責務は混ざっていない。行の多くは REQ-core-192 の条件ごとの具体例で、分けると形の要求と反例が別の文書に離れる
  - decided_by: 主セッション（承認のときに利用者へ示す）
