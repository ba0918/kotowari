# テストより先にコミットする仕様を check で止めない

## Context

仕様の承認のコミットは実装より先で、そのとき新しい要求には必ず requirement_without_test が出る。kotowari を使う別のプロジェクトでは、pre-commit に `kotowari check` を入れると、この承認のコミットが止まる事例が何度か起きた。kotowari 自身は [A19](./2026-09-17-decision-log.md#A19) で、lefthook.yml の jq にテスト側の指摘の種類を直書きして避けているが、その知識は kotowari 本体に無く、他のプロジェクトに伝わらず、種類が増えると古くなる。そこで、どの指摘をコミットで止めないかを kotowari の側で持つ仕組みを決める。途中から導入するプロジェクトのための段階（level）は、実際の需要が無いので扱わない。

Position: 第1〜第3ラウンドを推奨どおりに決めた（A1〜A11）。照合で出典の無い点が見つかり A12 を足した（承認で確かめる）。照合は3回目で裏付けの無い項目が0件になった。利用者が承認した（2026-10-06）。

## Agreements

- A1 仕組みは `kotowari check` のオプションにする。付けたときだけ、テスト側の指摘を終了コードの判定に数えない。
  - why: フックはオプションを付けて check を呼ぶだけで済み、どの指摘がテスト側かを各プロジェクトの jq に持たせなくてよい
  - rejected: 指摘の JSON に分類のフィールドを足す（絞り込みはフックが書くことになる）、設定ファイルに書く（設定は1つなので pre-push と CI まで緩む）
  - decided_by: 利用者（推奨を採用）
- A2 テスト側の指摘は「テストのファイルが原因の指摘」とする。requirement_without_test、scenario_without_test、test_without_id と、テストのファイルで出た invalid_marker、unparsable_file、unresolved_reference。ガイドの印と面のファイルから出た指摘は含めない。
  - why: A19 の jq は unparsable_file と invalid_marker を種類ごと外しており、面のファイル（プロダクトのコード）が読めないときとガイドの印の形の誤りまで素通りさせていた。原因をテストのファイルに限れば、仕様の先行コミットと TDD の途中のコミットが通り、それ以外は止まる
  - decided_by: 利用者（推奨を採用）
- A3 テストのファイルと面のファイルの両方に当たるファイルが読めないときの unparsable_file は、テスト側の指摘に数えない（オプションを付けても止める）。
  - why: どちらの側としても読めないなら、プロダクトのコードが壊れているのと同じ
  - decided_by: 利用者（推奨を採用）
- A4 オプションを付けても、テスト側の指摘は出力から除かず、severity も error のまま出す。変わるのは終了コードの判定だけとする。
  - why: 注意に格下げすると、同じ指摘の意味が呼び方で変わり、status や読む側と食い違う。見えなくなると未完の量が分からなくなる
  - rejected: 注意に格下げする、出力から除く
  - decided_by: 利用者（推奨を採用）
- A5 オプションは check だけが受ける。status の complete は変えない。changes にも足さない。
  - why: 止めるかどうかを決めるのはゲートに使う check の終了コードだけ。changes はもともとコミットのフックで走らせない（[change-conformance のガイド](../../guides/change-conformance.ja.md)）
  - decided_by: 利用者（推奨を採用）
- A6 オプションの名前は `--allow-test-findings` とする。
  - why: 指摘は出したままなので、無視（skip、ignore）より許す（allow）が中身に合う
  - decided_by: 利用者（推奨を採用）
- A7 フックの組み方（pre-commit はオプション付き、pre-push と CI はオプション無し）を、check のガイドの「フックに入れる」の節、kotowari スキルの check の場面、kotowari-adopt の導入の案内に書く。
  - why: 他のプロジェクトでは仕組みがあっても組み方を知らなければ同じ事故が起きる
  - decided_by: 利用者（推奨を採用）
- A8 kotowari 自身の lefthook.yml の pre-commit を、jq の絞り込みをやめて `--allow-test-findings` に切り替える。これはフックの設定で、利用者から見える製品の振る舞いではないので IR に書かない。
  - why: 種類の直書きを残すと A2 と食い違い、古くなる
  - decided_by: 利用者（推奨を採用）
- A9 テスト側の指摘の範囲は、IR の決定表に種類と条件を1行ずつ並べて定める。テストのファイルから出る指摘の種類を将来足すときは、その種類を決める壁打ちでこの表にも行を足す。
  - why: 「原因がテストのファイルの指摘」という一般の文だけでは、どの種類が入るかが読み手で割れ、テストで確かめる範囲も定まらない。表ならずれが IR の差分としてレビューで見える
  - rejected: 一般の文だけで定める
  - decided_by: 利用者（推奨を採用）
- A10 用語「誤り」を「severity が "error" の指摘。終了コードを1にする。ただし `--allow-test-findings` を付けた check では、テスト側の指摘は終了コードに数えない」に改める。「注意」の定義は変えない。
  - why: 今の定義「終了コードを1にする指摘」のままだと、オプションを付けたときだけテスト側の指摘が注意に見え、A4 の「呼び方で意味を変えない」と食い違う。誤りかどうかを指摘そのものの性質で決め、終了コードとの関係を例外つきで書く
  - rejected: 定義を変えず、オプション付きのときのテスト側の指摘を誤りでも注意でもないものにする（同じ種類の指摘の呼び名がオプションで変わる）
  - decided_by: 利用者（推奨を採用）
- A11 用語「テスト側の指摘」を用語集に足す。意味は「テストのファイルが原因の誤り。範囲は決定表で定める」。
  - why: 要求の文と決定表の名前で使い、「テストに関係する指摘のすべて」と読まれると A2 と割れる
  - decided_by: 利用者（推奨を採用）
- A12 `--allow-test-findings` は値を取らない。check でないコマンドに付けたときは、ほかの受けないオプションと同じく引数の誤りとして停止する。
  - why: A1 の「付けたときだけ」効くオプションで、値で切り替える中身が無い。check だけが受ける（A5）ので、ほかのコマンドでは [records.md の A60](./records.md#A60) の知らないオプションと同じ扱いになる
  - decided_by: 主セッション（A1 と A5 から導いた。照合で出典が無いと指摘されて書き足した。承認で確かめる）
