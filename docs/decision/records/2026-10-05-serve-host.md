# serve が受け付ける Host

## Context

"kotowari overview serve" は "127.0.0.1" だけで待ち受けるが、リクエストの Host ヘッダーを確かめない（[whole-picture A59](./2026-10-02-whole-picture.md#A59) は配る範囲だけを決めた）。
悪意のあるサイトが自分のドメインの名前を 127.0.0.1 に向け直すと（DNS リバインディング）、利用者のブラウザはそのサイトと同じ生まれのページとして serve の応答を読ませてしまい、全体像のページ（仕様の中身）が外へ読み出されうる。

Position: 利用者が第1ラウンドの推奨を採用した（2026-10-05）。木は尽きた。

## Agreements

第1ラウンド（2026-10-05）

- A1 serve は、Host ヘッダーの値が "127.0.0.1:<ポート>" か "localhost:<ポート>"（ポートは待ち受けているもの、名前の英字の大小は問わない）のリクエストだけに答える。
  - why: 出力する URL は "127.0.0.1" だが、手で "localhost" と打つ人もいる。どちらも手元の名前で、外のサイトの名前を通さないことが目的に足りる
  - rejected: "127.0.0.1:<ポート>" だけ（手で localhost を打つと開けない）
  - decided_by: 利用者（推奨を採用）
- A2 A1 に当たらないリクエスト（Host ヘッダーが無いものを含む）には、本文の無い 403 を返す。ファイルがあるかどうかを確かめる前に返し、リクエストごとに何も出力しない。
  - why: 同じ応答にすれば、置き場にどんなファイルがあるかも外に漏れない。無い場合と違う場合を分ける理由が無い
  - rejected: 無ければ 400、違えば 403（決まりが1つ増えるだけで、守るものは変わらない）
  - decided_by: 利用者（推奨を採用）
- A3 この変更（判断の記録、IR の要求と具体例の日英の両側、テストと実装、CHANGELOG）は、手順書と cycle を回さず主セッションが直接直して1本の PR にし、照合記録は実装側を主セッション、レビュー側を別の席が書く。
  - why: 要求1つと数十行の変更で、手順書と cycle の費用に見合わない
  - decided_by: Claude（利用者の「残りも対応しましょう」の指示のもとで決めた）
