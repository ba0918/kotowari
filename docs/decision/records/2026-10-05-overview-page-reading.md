# 全体像の文書のページを読みやすくする

## Context

全体像の一覧は目次で階層にし、見た目も整えた（[2026-10-05-overview-index.md](./2026-10-05-overview-index.md)）。残ったのは文書のページの側で、節が多い長いページでは今どこを読んでいるか、ほかの節へどう移るかが分からない。
一覧の壁打ちで別に決めるとした、狭い画面での flow の箱の重なり、flow の縦並びの意味、元データの YAML が読めないときの誤りの場所（[U1](./2026-10-05-overview-index.md#U1)）もここで決める。
利用者からは、明るい配色とダークの切り替えも議題に入れるよう求められた。今の配色は OS とブラウザの設定に従って自動で決まり、どのページにもスクリプトを入れない（[REQ-view-018](../../ir/view/navigation.md#REQ-view-018)）。

Position: 承認済み（2026-10-05）。実装のレビューで見つかった REQ-view-006 との食い違いを A19 で直した。

## Agreements

- A1 節のアウトラインは文書のページにだけ描き、一覧のページには描かない。
  - why: 一覧は目次そのものを描いており、左にもう一度並べると同じものの繰り返しになる
  - decided_by: 利用者（推奨を採用）
- A2 アウトラインに並べるのは文書の "## " の節の見出しだけとし、"### " 以下の見出しは並べない。
  - why: 節は古いかどうかを持つ単位で、深い見出しまで並べると長くなりアウトラインの役目がぼやける
  - decided_by: 利用者（推奨を採用）
- A3 アウトラインには、冒頭（lead と、lead に続く冒頭の部品）への項目を入れない。
  - why: 冒頭は題名のすぐ下にあり、ページの頭に戻れば見える
  - decided_by: 利用者（推奨を採用）
- A4 文書に節が1つ以上あればアウトラインを描き、節の数でしきい値を作らない。
  - why: しきい値は根拠の無い数になり、規則を増やすだけである
  - decided_by: 利用者（推奨を採用）
- A5 アウトラインの項目のうち古いとされた節の項目には、節の見出しの近くの印（[REQ-view-009](../../ir/view/rendering.md#REQ-view-009)）と同じ意味の印を付ける。
  - why: 長いページで見直しが要る節を探すことが、アウトラインのいちばんの使いどころである
  - decided_by: 利用者（推奨を採用）
- A6 スクロールに合わせて今読んでいる節をアウトラインで強調することはしない。
  - why: スクロールに合わせた強調にはスクリプトが要り、どのページにもスクリプトを入れない決まり（[REQ-view-018](../../ir/view/navigation.md#REQ-view-018)）に反する
  - decided_by: 利用者（推奨を採用）
- A7 アウトラインは同じ目次の群のほかの文書へのリンクを持たず、そのリンクは今の位置（最後の節の後、[REQ-view-020](../../ir/view/navigation.md#REQ-view-020)）のまま変えない。
  - why: アウトラインはそのページの中を移るものに絞る
  - decided_by: 利用者（推奨を採用）
- A8 flow の1つの列に縦に並べた箱は、同じ段階に並ぶもの（並列）を意味する。順番は列から列への左から右の流れだけで表し、それが読めるように、列を1つの囲みで描き、矢印は列と列の間にだけ置く。
  - why: 今は列の中の縦並びが順番か並列か見分けられず、意味がどこにも決まっていなかった
  - decided_by: 利用者（推奨を採用）
- A9 狭い画面では、flow の列を上から下に積み、列と列の間の矢印を下向きにする。
  - why: 今の flow は列を横に詰めるため、幅が足りないと箱が重なる
  - decided_by: 利用者（推奨を採用）
- A10 部品の中身が YAML として読めないとき、overview_part_invalid の "line" を、YAML の読み取りが誤りの位置として返した行を元データのファイルの行に直したものにし、detail は今までどおり種類の名前と "(yaml)" とする。位置が返らないときは今までどおりフェンスの開始の行とする。
  - why: 今はフェンスの開始の行と "(yaml)" しか出ず、長い部品では直す場所を探せない。detail に検査のライブラリが作る文を入れない決まりは保つ
  - decided_by: 利用者（推奨を採用）
- A11 ローカライズ（このリポジトリ自身の文書の多言語化と、kotowari が利用者の多言語の IR、ガイド、全体像を扱えるようにすること）は、この壁打ちでは扱わない（[U1](#U1)）。
  - why: どちらを先にするか、置き場の切り方、訳の古さの検出はそれぞれ大きい論点で、文書のページの読みやすさとは決める論点が別である
  - decided_by: 利用者（推奨を採用）
- A12 広い画面では、アウトラインを本文の左に置き、本文をスクロールしても見え続けるようにする。
  - why: 節が多い長いページでも、今どこにいるかとほかの節へ移る手段がいつも見えていてほしい（利用者の言葉「アウトラインを常に出せるなら長文のページが出てきても読みやすい」）
  - decided_by: 利用者
- A13 狭い画面では、アウトラインを題名の下、冒頭の lead より上に置き、スクロールに追従させない。
  - why: 狭い画面で左に固定すると本文の幅を食う
  - decided_by: 利用者（推奨を採用）
- A14 アウトラインの項目の文字は節の見出しの文字そのままとし、古い節の印は文字の後に付ける。
  - why: 節の見出しと別の文字にすると、どの節か対応が取れなくなる
  - decided_by: 利用者（推奨を採用）
- A15 アウトラインの見え方（広い画面で見え続けること、狭い画面での置き場所）と、狭い画面での flow の積み方は、人が広い幅と狭い幅で描いたページを見て確かめる。
  - why: 画面の幅とスクロールで変わる見え方は、view が返す文字列の単体テストでは確かめられない
  - decided_by: 利用者（推奨を採用）
- A16 目次の YAML が読めないときの誤りは変えず、"line" は null のままとする。
  - why: 目次の指摘はいつも "line" を null にする決まり（[REQ-core-027](../../ir/core/findings.md#REQ-core-027)）があり、目次は短いファイルで場所はすぐ見つかる
  - decided_by: 利用者（推奨を採用）

- A17 アウトラインの項目は、節が文書のページに出てくる順（元データに書いた順）に並べる。
  - why: 並べ替えると本文の上から下の順とずれる
  - decided_by: 利用者（推奨を採用）
- A18 文書のページの節の見出しの並びを「アウトライン」と呼び、「目次」とは呼ばない。
  - why: 「目次」は一覧の並びと入れ子を決める YAML（overview.toc）の名前に使っており、同じ語にするとどちらの話か分からなくなる
  - decided_by: 利用者（推奨を採用）

- A19 文書のページでは、題名の後に、アウトラインを描くときはアウトラインを描き、その後に冒頭の lead の部品を描く。lead が題名の直後に来るのは、アウトラインを描かないときだけとする。
  - why: 題名の直後に lead を描くとした要求（[REQ-view-006](../../ir/view/rendering.md#REQ-view-006)）が、アウトラインを題名の下、lead より上に置く A13 と食い違っていた。壁打ちで既存の要求を読み落としていた
  - decided_by: 利用者（推奨を採用）

## Delegated

- D1 節へのリンクの場所（id）の具体的な形は実装に任せる。満たすのは、1つのページの中で重ならないこと（同じ見出しの節が2つあっても別の場所になる）、同じ`描画の入力`から同じ値になること（[REQ-view-004](../../ir/view/rendering.md#REQ-view-004)）、アウトラインの項目を選ぶとその節へ移れることだけである。
  - why: 形を決めても読み手にとっての違いが無く、守るべき性質だけを決めれば足りる
  - decided_by: 利用者（推奨を採用）
- D2 「広い画面」と「狭い画面」の境目の幅、アウトラインと flow の具体的な見た目（列の囲みの描き方、矢印の形、印の形）は実装に任せる。
  - why: 見た目の細部は実物を見て整えるもので、A15 の人の確認で足りる
  - decided_by: 利用者（推奨を採用）

## Undecided

- U1 ローカライズをどう進めるか。このリポジトリ自身の文書（ガイド、紹介ページ、README）と、kotowari が利用者の多言語の文書を扱うことのどちらから始めるか、言語ごとの置き場（"<lang>/..." のようにディレクトリを切るか、ほかの方式か）、訳の古さの検出。利用者が挙げた別の方式は deepseek-harness のもので、同じディレクトリに "foo.md"、"foo.zh.md"、両側の blob hash を持つ一致の記録 "foo.i18n.yaml" の3つを置き、言語のディレクトリを作らず、hash と見出しや表などの構造の一致を機械で検査し、意味が同じかはレビューで確かめる。
  - decides: 利用者（ローカライズの壁打ちで決める）
  - related: A11
- U2 明るい配色とダークを読み手が切り替えられるようにするか。言語の切り替えと同じく読み手が表示を切り替える仕組みで、スクリプトを入れない決まり（[REQ-view-018](../../ir/view/navigation.md#REQ-view-018)）を変えるかと一緒に決める。決まるまでは OS とブラウザの設定に従う。
  - decides: 利用者（ローカライズの壁打ちで一緒に決める）
  - related: A11
