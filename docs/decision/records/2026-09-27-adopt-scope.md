# 壁打ちの記録: 導入で要件にする範囲と行の粒度

## Context

remote-merge で kotowari-adopt を「rollback」の話題で回したところ、追認の候補が32行になった（2026-09-27）。
実際の保存と復元の処理を見るために確認した範囲の外のファイル（保存の側の backup_store.rs や merge_flow.rs など）まで読み、その中で見つけた振る舞いまで行にしたため、候補のおよそ半分がバックアップを取る側の振る舞いだった。また、1つの規則の文言の違い（スキップの理由の文言）が別々の行になっていた。
今の仕様（[REQ-core-215 の元の決定 A23（導入）](./2026-09-26-adoption.md#A23)）は範囲のコードファイルとテストファイルを確かめることを決めているが、読む範囲と要件にする範囲を分けておらず、行の粒度も決めていない。

Position: 承認済み（2026-09-27）。第1ラウンドで A1〜A5 を決めて木が尽きた。IR は docs/ir/core/adoption-scope.md（2026-09-27）。

## Agreements

- A1 話題の範囲は利用者の入口（利用者が触るコマンドやサブコマンド、画面の操作）で決め、範囲の確認のラウンドでコードファイルとテストファイルに加えて話題の入口を人に確かめる。行にするのは、その入口から観測できる振る舞いだけとし、同じコードを共有していても別の入口から観測される振る舞いは範囲の外とする
  - why: コードは入口の間で共有されるので、ファイルで範囲を切ると別の入口の振る舞いまで行になる（remote-merge の rollback で保存の側の振る舞いが候補の半分になった）
  - decided_by: 利用者（推奨を採用）

- A2 理解のために範囲の外のファイルを読んでよいが、そこで見つけた範囲の外の振る舞いは行にせず記録にも書かない。一覧のラウンドでは範囲の外で見つかった振る舞いの件数と、次の話題の候補の名前だけを見せる
  - why: 保存と復元の処理を見るために読む範囲を広げるのは要るが、読んだものを全部要件にすると話題が膨らむ。見つけたことは次の話題の手がかりとして残す
  - decided_by: 利用者（推奨を採用）

- A3 一覧の1行は要求1つの候補とし、同じ規則で値や文言だけが違うもの（スキップの理由の文言など）は1行にまとめて決定表で書く候補にする。一覧の実装の振る舞いの欄に表の中身を短く並べる
  - why: 1つの規則の文言の違いが別々の行になり、行が膨らんだ
  - decided_by: 利用者（推奨を採用）

- A4 要求の候補の数が設定の limits.requirements を超えたら、入口が混ざっていないかを見直す。混ざっていれば一覧のラウンドの中で話題を分けることを提案して人に今回の側を選んでもらい、混ざっていなければ数を理由に分けず、IR を書く段で責務ごとに文書を分ける
  - why: 分ける単位は数ではなく責務で、数は混ざりを疑う合図にとどめる。分ける提案を一覧のラウンドの中で行えば人に聞く回数は増えない
  - decided_by: 利用者（推奨を採用）

- A5 範囲と行の作り方を責務として "docs/ir/core/adoption-scope.md" に分け、REQ-core-215 をそこへ移して書き直し、行の粒度と範囲の外の扱いの要求を置く
  - why: "docs/ir/core/adoption.md" の要求が limits.requirements と同じ10件に達している
  - decided_by: 利用者（推奨を採用）
