# 壁打ちの記録: レビューに別のモデルの席を足す

## Context

kotowari-review は、観点（quality と、要るときだけ conformance）ごとに別コンテキストのレビュー役を立てる。どの席も同じ系統のモデルで動く。別の系統のモデルに同じプロンプトを投げると、見落としの傾向が違うため精度が上がることを、利用者は以前の agentic-workflow で経験している。

一方で、そのときは codex や opencode に投げた先で利用枠（クォータ）が尽きていて、レビューが回らない事故が起きた。利用者は費用に敏感で（[A12（workflow-split）](./2026-09-23-workflow-split.md#A12)）、余裕があれば複数のモデル、無ければ1つ、とその都度制御したい。別のモデルの席をどう足し、落ちたときどう扱い、席の数を誰がどこで決めるかを決める。計画書の検査の件（[plan-schema](./2026-09-24-plan-schema.md)）と同じ席で壁打ちする。

Position: 第1ラウンドで置き場と範囲を決めた（A1〜A4）。第2ラウンドで起動、書き換えの扱い、時間の上限、上書き、統合を決めた（A5〜A9）。第3ラウンドで席に渡す観点と付けるレビューの範囲を決めた（A10、A11）。木を歩き終えた。IR は作らない（A1）。計画の独立したレビューで見つかった未決を第9ラウンドで決めた（A12〜A14）。

## Agreements

- A1 この件のために新しい IR は作らず、決めたことは判断の記録と kotowari-review（と、それを呼ぶ工程の skill）の本文に書く
  - why: 工程の skill の変更は [A6（workflow-split）](./2026-09-23-workflow-split.md#A6) と同じ扱いにする。記録と計画の分け方は [A1（plan-schema）](./2026-09-24-plan-schema.md#A1)
  - decided_by: 利用者（推奨を採用）

- A2 既定の席の一覧は、利用者スコープで常に読まれる指示ファイルに数行で書く。書いていなければ席は1つにする。kotowari-review は「その一覧があれば従う」とだけ書き、ba0918 の skill を名指ししない
  - why: 使えるモデルは利用者の契約で決まり、リポジトリで決まらない。`.kotowari/config.yaml` は未知の鍵で停止するうえ（`deny_unknown_fields`）、リポジトリで共有される。ba0918-delegation の実行役の表に置くと、kotowari の工程が agentic-workflow に依存する（[A1（workflow-split）](./2026-09-23-workflow-split.md#A1)、[A3（workflow-split）](./2026-09-23-workflow-split.md#A3)）。モデルがどのみち読むものに乗せれば、新しい仕組みが要らない
  - rejected: 専用のファイル（例 `~/.config/kotowari/review.yaml`）を決めてモデルに読ませる。置き場ははっきりするが、読みに行く手順が1つ増える
  - decided_by: 利用者（推奨を採用）

- A3 別のモデルの席を付けるのは full review だけにし、diff review には付けない
  - why: diff review は修正のループで何度も回り、席を足すと費用が回数分かかる（[A12（workflow-split）](./2026-09-23-workflow-split.md#A12)）。モデルごとの見落としの差が効くのは全体を見る full review だと見込む（未計測の推測）
  - decided_by: 利用者（推奨を採用）

- A4 任意の席が1回落ちたら試し直さず欠席とし、終端報告にどの席がなぜ（利用枠切れ、時間切れ、起動の失敗）欠席したかを残す。必須の席が落ちたときは、今の「委譲し直しても成功しなければ ending 3」の規則のままにする
  - why: 利用枠は数分では戻らないので、試し直しは待ち時間を増やすだけになる
  - decided_by: 利用者（推奨を採用）

- A5 任意の席の一覧には、席ごとに起動の手段（実行するコマンド、または呼び出す skill）を書く。kotowari-review はその手段に quality の席と同じプロンプトを渡し、返った JSON を読むだけで、特定のツールや skill を名指ししない
  - why: 利用者の環境では、別のモデルを起動する skill を用意し、それをレビューとして呼ぶ skill を置くことがある。コマンドに限ると、その形を受けられない
  - decided_by: 利用者（推奨を採用し、skill でもよいとしたのは利用者の言葉）

- A6 任意の席の起動の前後で呼び出し側が `git status` を取り、差があればその席の指摘を捨てて欠席とし、終端報告に書き換えがあったことを残す。書き換えは戻さず人に見せる。一覧の手段は読み取り専用で動くように書く約束にする
  - why: レビュー役は編集しないのが今の契約で、外のツールの sandbox の設定はこちらから保証できない
  - decided_by: 利用者（推奨を採用）

- A7 時間の上限は、一覧の行に書かれているときだけ効かせる。書かれていなければ起動の手段が終わるのを待つ
  - why: 利用枠切れはたいていすぐエラーで終わり、固まるのは稀と見込む（未計測）。既定の値を置く根拠が無い
  - decided_by: 利用者（推奨を採用）

- A8 席の数は strength と同じく、人の一言（「今回は1席で」「全席で」など）か呼び出し側の1行の理由で実行ごとに上書きでき、無ければ一覧のとおりにする。cycle は人が最初に言った席の指定を full review に引き継ぐ
  - why: 余裕があれば複数のモデル、無ければ1つ、とその都度制御したい
  - decided_by: 利用者（推奨を採用）

- A9 複数の席の指摘は今の「呼び出し側が統合し、重複を除く」でまとめ、finding の JSON の形は変えない。終端報告には出席した席と欠席した席だけを載せる
  - why: kotowari の指摘は oracle で裁くので、何席が同じことを言ったかで重みを変えない
  - rejected: どの席が出したかを指摘ごとに持たせ、合意を信号にする。finding-schema の変更が要り、裁き方と合わない
  - decided_by: 利用者（推奨を採用）

- A10 任意の席に渡すのは quality の観点のプロンプトだけにし、conformance の席には別のモデルを付けない
  - why: conformance は仕様との照合で、機械の検査や読み比べで足りる部分が多い。モデルごとの見落としの差が効くのは対象そのものを見る quality と見込む（未計測）。席を2倍にしない（[A12（workflow-split）](./2026-09-23-workflow-split.md#A12)）
  - decided_by: 利用者（推奨を採用）

- A11 別のモデルの席は kotowari-review が立てるレビューにだけ付け、人が review を直接呼んだときも同じ規則で付ける。plan と brainstorm が Finishing で立てる敵対的なレビューと、brainstorm の照合レビューには付けない
  - why: その2つは kotowari-review ではなく、各工程が1席で立てるもの。広げるならそのときに別に決める
  - decided_by: 利用者（推奨を採用）

- A12 任意の席は1つずつ順に起動し、その前後の `git status` の差をその席のものとする
  - why: 同時に起動すると差をどの席に帰すかが決まらず、書き換えた席の指摘を捨てる A6 が成り立たない。時間は延びるが費用は変わらない
  - decided_by: 利用者（推奨を採用）

- A13 任意の席の書き換えが見つかったら、security の指摘と同じくループ全体を止め、書き換わったファイルを人に見せる。戻して続けるか、そのまま続けるかは人の返事で決める
  - why: 書き換わった worktree のまま fixer が直し始めると、誰の変更か分からないものがコミットに混ざる。A6 の「人に見せる」の時を「その場で」と決める
  - decided_by: 利用者（推奨を採用）

- A14 起動の手段が終わっても、出力が finding の JSON として読めなければ、その席を「出力を読めない」を理由に欠席とし、試し直さない
  - why: A4 が挙げた欠席の理由（利用枠切れ、時間切れ、起動の失敗）のどれにも当たらない終わり方がある。読めない出力を指摘として扱う手段は無い
  - decided_by: 利用者（推奨を採用）
