# TODO.md の残りを決めて片付ける

## Context

2026-10-06 のコード衛生の点検（PR #24）で TODO.md に残った「判断待ち」5件と「記録のみ」の各件を、利用者が「目標0なので、決めて対応する」として一度に決めることにした。各件は、仕様（IR）を直すもの、IR を変えずにコードか文書を直すもの、理由を付けて見送るもののどれかに分ける。「後でやる」の1件（紹介ページのガイドへのリンク）は、ガイドを英語と日本語の対にした後のリリースが前提なので今回の範囲に入れない。

Position: 第1ラウンドで全17問を推奨どおりに決めた（A1〜A16）。IR を改訂し、照合を3回行って裏付けの無い項目は0件になった。第2ラウンドで CHANGELOG の言語を決めた（A17。IR ではない）。利用者が承認した（2026-10-06）。

## Agreements

- A1 mds は URL のスキーマをキャッシュに書けないとき（ディレクトリを作れないときと書けないとき）、誤りにも指摘にもせず、取得した内容で検査を続ける。
  - why: キャッシュは取得を省くためのもので、取得した内容は手元にある。止めると読み取り専用の環境で検査が使えなくなる
  - decided_by: 利用者（推奨を採用）
- A2 view は `block` の Markdown の参照リンクを、同じ `block` の中にある参照の定義だけで解決する。別の `block` にある定義では解決せず、参照は文字のまま出る。
  - why: view が使う `markdown` クレートには外から定義を渡す口が無く、文書全体から定義を集める仕組みを新しく要する。塊をまたいで参照を書く利用者がいる根拠も無い
  - rejected: 文書の全部の定義を各塊に渡す、塊をまたぐ参照を誤りにする
  - decided_by: 利用者（推奨を採用）
- A3 "tests.files"、"guides.files"、"surface.files"、"overview.files" の要素のうち "/" で始まるものは、絶対パスの値として設定の誤りにする。
  - why: "/" で始まる glob は基準のディレクトリからの相対パスに当たらず、これまで何にも当たっていない。拒んでも動いていた設定は壊れない
  - decided_by: 利用者（推奨を採用）
- A4 "changes.records" と "overview.files" の glob が波括弧の中で名指しした隠しディレクトリは、パスの成分による名指しに数えず、入らない。
  - why: 数えるには波括弧の展開を自前で持つ必要がある。既定の値はパスの成分で名指ししており、困る利用者がいない
  - decided_by: 利用者（推奨を採用）
- A5 "kotowari overview build" と "kotowari overview serve" が置き場の下のファイルを列挙できないときも、置き場の誤り（location error）で止め、詳細にそのパスと OS の誤りの文を置く。
  - why: 置き場の作成・書き込み・削除の失敗はすべて置き場の誤りで、列挙だけが読めないファイルになっていたのは揃っていなかっただけ
  - decided_by: 利用者（推奨を採用）
- A6 mds は題名より前にある深さ3の見出しを、題名の無い文書のものも含めて前置部の外として扱い、開いた世界では前置部を宣言していても未宣言の構造として許す。
  - why: 仕様が黙っていた今の振る舞いを書く。題名の無い文書には missing_title が別に立つので実害は無い
  - decided_by: 利用者（推奨を採用）
- A7 "## " の直下で最初の "### " より前にある行のうち、箇条書きの行と、スキーマが宣言した表の行は、unknown_line にしない。
  - why: 節の直下に置く箇条書きと宣言済みの表は形の検査が別に受け持つ。REQ-core-174 の出典に、この除外を支える決定が無かったので書く
  - decided_by: 利用者（推奨を採用）
- A8 kotowari-core の ir.yaml、context.yaml、flags.yaml から、どこにも読まれない題名の `extract: title` を外す。題名の宣言は残す。
  - why: 読んでいた `MapContext.title` は既に消え、取り出した値を使う箇所が無い。題名の検査は宣言が受け持つので結果は変わらない
  - decided_by: 利用者（推奨を採用）
- A9 kotowari-markdown-schema-io に文書を読む入口（BOM の除去と UTF-8 の判定）を公開し、mds の `ast` はそれを使う。
  - why: 同じ読み方の規則を2か所に持たない。公開 API の追加で、壊れる変更ではない
  - decided_by: 利用者（推奨を採用）
- A10 CHANGELOG.md の `## [0.3.0]` の前の余分な空行を今回の変更で直す。
  - why: 照合記録を書く変更に乗せれば、単独で記録を作らずに済む
  - decided_by: 利用者（推奨を採用）
- A17 根の CHANGELOG.md と crates/kotowari-markdown-schema/CHANGELOG.md を英語で書く。過去の版の節も英語に直し、PROJECT.md のリリースの節にその決まりを書く。IR ではない（製品の振る舞いではなく、リポジトリの文書の言語の決まり）。
  - why: 公開する文書は英語を先に置くことにしたのに、変更履歴だけが日本語だった。版ごとに言語が混ざると読みにくく、GitHub Release の本文はその版の節から切り出される
  - rejected: これからの版だけ英語にする（ファイルの中で言語が混ざる）
  - decided_by: 利用者（推奨を採用）

## Rejected

- A11 スキルの ir-form.md に、題名より前の `### FLAG-nnn` も読まれると書き足すこと。
  - why: スキルは問題の記録を書く場所を案内しているだけで、エンジンがそれより広く読めても利用者に害は無い
  - decided_by: 利用者（推奨を採用）
- A12 `reading: line` の文書の読み取りの回数を減らすこと。
  - why: 影響を測っておらず、遅いという報告も無い
  - decided_by: 利用者（推奨を採用）
- A13 メモリの入口が返す写せない指摘（MappingError）のために `InputError` に種類を足すこと。
  - why: 利用者の入力からその失敗に届く経路が見つかっておらず、作る者のいない失敗をテストで確かめられない。`InputError` は `#[non_exhaustive]` なので、必要になれば壊さずに足せる
  - decided_by: 利用者（推奨を採用）
- A14 kotowari-core の `cargo_mutants::read_outcomes`、`mutants::normalize_source_path`、`SourceContext::check_source` の `String` の誤りを型にすること。
  - why: 呼び出し元は crate の中だけで、型を変えると公開 API を壊す
  - decided_by: 利用者（推奨を採用）
- A15 1回の `check` で基準のディレクトリを鍵ごとに走査する回数をまとめること。
  - why: 2026-10-06 の実測で、全体の走査1回が約 0.03 秒、`check` 全体が 1.6〜2.3 秒で、まとめても実行のばらつきの中に収まる
  - decided_by: 利用者（推奨を採用）
- A16 `changes` が読む blob の範囲を "/" の境界で選び直すこと。
  - why: TODO.md の記録が誤っていた。`git_snapshot.rs` は `PathBuf` の `Path::starts_with` で比べており、パスの成分ごとに比べるので `docs/irx/` は `docs/ir` に当たらない
  - decided_by: 利用者（推奨を採用）
