# 壁打ちの記録: IR の読み取りを markdown-schema のエンジンに置き換える

## Context

`crates/kotowari-core/src/ir.rs`（1658 行）は Markdown を自前で読み、IR の文書の形を検査して`項目`を組み立てている。同じ workspace に、宣言したスキーマで Markdown を検証し値を抽出する `kotowari-markdown-schema` が入った（[取り込みの経緯](./2026-09-22-id-namespace.md)）。この自前の読み取りをそのエンジンに置き換える。

取り込みまでの5工程は済んでいる。ID に置き場の名前が入り、IR は `docs/ir/core/` と `docs/ir/schema/` の2つのドメインに分かれ、workspace になり、1回の `kotowari check` が 42 文書・要求 218 件を指摘0件で通る。

`.mds/schemas/ir.yaml` は最初から kotowari の`項目`の構造を抽出するように書かれている。実測で `requirements[].{id,name,line,kind,sources,verification,text}`、`properties`、`tables`、`title`、`scope` が出る。条件付き規則（`種類` が algorithm のとき `定義` が必須）と `enum`（`種類` と `検証` の値）も宣言で表現されている。

論点は「どの指摘をどちらの層が出すか」だった。9ラウンドで木は尽きた。置き換えのために `kotowari-markdown-schema` へ足す機能が4つ出たので、工程を2つに分ける。

Position: 承認済み（2026-09-22）。9ラウンド（A1〜A35）。仕様は [docs/spec/ir-engine.md](../../spec/ir-engine.md)。実装は plan → cycle を2本。

## Agreements

- A1 話題ごとの文書・用語集・問題の記録の形の検査と`項目`の抽出は `kotowari-markdown-schema` に任せ、kotowari は Markdown を読まない。gherkin の塊の中身（タグとシナリオの組み立て）は kotowari に残す
  - why: エンジンは gherkin を1つの塊として扱い、宣言した正規表現で行の形だけを見る。タグとステップの構造は抽出に出ない（実測）
  - decided_by: 利用者（推奨を採用）

- A2 利用者が見る`指摘`の種類の名前は kotowari のものを保つ。エンジンの`指摘`を kotowari の種類へ写す対応表を仕様に置く
  - why: 配布したスキルの `findings.md` と、利用者の運用（種類ごとの対処と担当）が今の名前に依存している
  - decided_by: 利用者（推奨を採用）

- A3 エンジンにあって kotowari に対応の無い`指摘`は、意味が最も近い既存の種類へ写す。新しい種類は足さない。kotowari にあってエンジンが出せないものは kotowari の層に残す
  - why: 種類が増えると配布したスキルの表と利用者の運用が変わる
  - decided_by: 利用者（推奨を採用）

- A4 行数と要求の数の上限は kotowari に残す
  - why: 文書の形ではなく IR の運用上の制限。スキーマ言語に行数の上限は無い（`docs/ir/schema/schema-language.md` に該当なしを確認）
  - decided_by: 利用者（推奨を採用）

- A5 利用者から見える振る舞いを変えない。`指摘`の種類・detail・行・出る順は今のまま。変わるものが見つかったら1件ずつ決める
  - why: 置き換えは実装の入れ替えで、仕様の変更ではない
  - decided_by: 利用者（推奨を採用）

- A6 gherkin の絶対の行は、コードブロックに行番号の抽出を宣言して塊の開始行を得て、そこから kotowari が数える
  - why: gherkin の行の`指摘`（invalid_gherkin_line、missing_tag、unknown_tag、`@id` の invalid_id、scenario_without_test）の行を今と同じにできる
  - decided_by: 利用者（推奨を採用）

- A7 用語表の行ごとの行番号を `kotowari-markdown-schema` の機能として足す
  - why: 利用者の言葉で「markdown-schema の基本機能として提供しても問題ないはず」。今の抽出は行のオブジェクトの並びを返すが行番号を持たず、duplicate_term と invalid_glossary_row の行を出せない
  - rejected: 用語集だけ kotowari の行ベースの読み取りを残す（A1 の例外を増やす）。表の開始行から数えて導く（不正な行が抽出から落ちると数がずれる）
  - decided_by: 利用者

- A8 IR の文書にスキーマの宣言を書かせない。kotowari が文書の種類に応じてスキーマを選ぶ。`docs/ir/schema/` の 10 文書からも外す
  - why: 42 文書への追記と「足し忘れの検出」を恒久的に抱えない。`kotowari check` が同じエンジンと同じスキーマを使うなら、エンジンの CLI 単体での検査は重複
  - rejected: 全文書に宣言を足し、宣言の無い文書を検出する検査を足す
  - decided_by: 利用者（推奨を採用）

- A9 エンジンの`停止`は kotowari の`停止`の理由を1つ足して写す。スキーマは kotowari が自分で持つので、スキーマが読めない・壊れているのは利用者の入力の問題ではない。利用者の入力で起きる`停止`は今のまま
  - why: 利用者が直せない不具合と、利用者が直せる入力の誤りを混ぜない
  - decided_by: 利用者（推奨を採用）

- A10 対応表は `docs/ir/core/findings.md` に新しい決定表として置く
  - why: `指摘`の種類と detail を定める表の隣に置くと、写し先と detail の形を一緒に読める

- A11 表の`抽出`が導かれる値を含むとき、行ごとのオブジェクトにその鍵を足す。`項目`が既に持っている仕組みを`表`に広げる
  - why: 今は表の開始行が最上位に配列で出るだけで、行ごとの`指摘`の行を出せない
  - decided_by: 利用者（推奨を採用）

- A12 導かれる値を要素ごとに入れるのは`表`だけに広げる
  - why: `箇条書き`と`コードブロック`は要素が文字列で、行番号を足すには要素をオブジェクトに変える必要があり別の判断になる。`項目`は既に持っている
  - decided_by: 利用者（推奨を採用）

- A13 表の行番号はそのデータ行そのもの。ヘッダの行と区切りの行は数えない

  - decided_by: 利用者（推奨を採用）

- A14 工程を2つに分ける。エンジンへの機能追加を先に独立して終わらせ、そのあと kotowari の置き換え

  - decided_by: 利用者（推奨を採用）

- A15 仕様書は1本。判断の記録も1本

  - decided_by: 利用者（推奨を採用）

- A16 繰り返す表は表ごとの配列の中に行のオブジェクトが並び、その中に行番号が入る
  - why: 「`出現回数`の範囲も宣言したときは配列の配列にする」という既にある流儀に合わせる
  - decided_by: 利用者（推奨を採用）

- A17 行のオブジェクトの鍵が表の列の名前と衝突したら`停止`する
  - why: 宣言の誤り。「導かれる値に受けない語は`停止`にする」と同じ流儀
  - decided_by: 利用者（推奨を採用）

- A18 `IrDocument` と `Item` の型は残し、エンジンの抽出結果から組み立てる
  - why: 文書をまたぐ検査と `list`・`query`・`status` がこの型に依存している。型を消すと置き換えの範囲が製品全体に広がる
  - decided_by: 利用者（推奨を採用）

- A19 置き換えの証拠は、今のテストと `kotowari check` の指摘0件、`kotowari status` の数が不変であること
  - why: A5 で振る舞いを変えないと決めたので、既存のテストがそのままオラクルになる
  - decided_by: 利用者（推奨を採用）

- A20 抽出結果から型へ写せない値は起きない前提にする。起きたらスキーマと型の食い違いで、A9 の`停止`の理由に含める
  - why: スキーマが `enum` と必須を宣言しているので、エンジンの検証を通った文書は必ず写せる

  - why: 利用者の言葉で「mds 自体が行番号を持てるのが自然」。性能の懸念は無い。行番号は mdast の位置情報から取っており、パースの時点で計算済みで、欠けたフィールドに`項目`の行を付けるのは既に手元にある値を使うだけ（`document.rs` の実装を確認）
  - rejected: kotowari が抽出の構造から判定してエンジンの`指摘`を捨てる。行が無くなることを受け入れる（A5 に反する）
  - decided_by: 利用者

- A22 スキーマの必須と条件付きの宣言は残す。A21 によりエンジンの`指摘`をそのまま使うので、kotowari 側に同じ判定を持たず、宣言は1か所のまま
  - why: 判定が2か所に分かれると、片方だけ直したときに食い違う
  - decided_by: 利用者（推奨を採用）

- A23 閉じないコードブロックの`指摘`は kotowari に残す
  - why: エンジンは検出しない（実測）。Markdown のパーサは閉じないフェンスを文書の終わりまで伸ばす。生の行を読むので A1 の2つ目の例外になる

- A24 用語集の2つの`指摘`はエンジンの`指摘`を写すだけにする。表が無い場合と、列の数が合わない行の場合を分けて写す。duplicate_term は文書をまたぐので kotowari に残り、行は A11 で足す行番号から取る
  - why: A21 と A11 でエンジンが行を出せるようになるので、kotowari が数え直す必要が無い
  - decided_by: 利用者（推奨を採用）

- A25 エンジンの`指摘`の行は1つの規則にする。違反したノードがあるならそのノードの開始行、欠落ならそれを含むノードの開始行
  - why: kotowari が種類ごとに求める2通りの行（`項目`の見出しの行、その行）がこの1つの規則で出る。表の行の列の数が合わない`指摘`が今ヘッダの行を指しているのは、この規則で該当の行に変わる
  - decided_by: 利用者（推奨を採用）

- A26 CLI のバイナリの名前の変更は別の仕様として切り出す。この工程ではやらない
  - why: CLI の名前は IR のエンジンの置き換えとは別の関心。A15 で仕様書を1本にすると決めた前提が崩れる。配布も保留で急がない
  - rejected: この仕様に含める。先に別の工程でやる
  - decided_by: 利用者（推奨を採用）

- A27 エンジンの`指摘`に、宣言されたノードの名前を構造として足す。kotowari は種類とノードの名前の組で自分の種類へ写す
  - why: detail の文言はエンジンの仕様のどこにも定めていない（`指摘`を5つの要素で表すとだけ定めている）。文言に依存すると、言い換えたときに kotowari が黙って壊れる。エンジンは`指摘`を作る時点でフィールドの名前を持っている
  - rejected: detail の文言を仕様で固定して kotowari が読む（人向けの英文を機械の契約にする）。kotowari が抽出の構造から判定する（判定が2か所に分かれる）
  - decided_by: 利用者（推奨を採用）

- A28 対応表には、写し先の無い`指摘`も「今のスキーマでは発生しない」と書いて残す。発生したら kotowari は`停止`する
  - why: 黙って捨てると、将来スキーマに宣言を足したときに検査が静かに緩む
  - decided_by: 利用者（推奨を採用）

- A29 エンジンの`指摘`に、その`指摘`が指す行の生の文字を足す。エンジンは「何がどこで」を構造で返し、文言は呼ぶ側が組み立てる
  - why: kotowari は detail に「読んだ行の文字そのまま（字下げと末尾の空白を含み、再構成しない）」を入れると定めている。エンジンの detail は見出しの名前だけで生の行を持たない（実測）
  - rejected: kotowari が生の行を読む（A1 の例外が3つになり「Markdown を読まない」が形だけになる）
  - decided_by: 利用者（推奨を採用）

- A30 スキーマから`出典`の書式のパターンを外す。`出典`の検査は kotowari が6条件で担う
  - why: 同じ入力にエンジンの書式の`指摘`と kotowari の`出典`の`指摘`が二重に出る（実測）。A22 の「宣言は1か所」に沿う
  - rejected: パターンを残して写す（2件出る）。残して kotowari の層で捨てる（宣言が機能しない）
  - decided_by: 利用者（推奨を採用）

- A31 対応表は「エンジンの種類とノードの名前 → kotowari の種類」の3列にする。名前が同じで意味が違う行にはその旨を書く
  - why: エンジンの invalid_id は`項目`の見出しの ID、kotowari の invalid_id は gherkin のタグの値で、同じ名前が別物を指す（実測）
  - decided_by: 利用者（推奨を採用）

- A32 エンジンの機能追加を1つの工程にまとめる。内容は A11・A21・A27・A29・A37 の5つ
  - why: どれも「`指摘`と`抽出`に位置と文脈を足す」という一つの関心で、どれもエンジンの中で閉じて検証できる
  - decided_by: 利用者（推奨を採用）

- A33 エンジンが出して kotowari が今出さない3件を受け入れて、kotowari の新しい`指摘`にする。宣言外の素の文、gherkin でないコードブロック、用語集の題名の誤り
  - why: どれも kotowari が今`除外`として黙って読み飛ばしている実の抜け。kotowari 自身の 42 文書は既に指摘0件で通る（実測）
  - rejected: スキーマの宣言を緩めて発生させない（置き換えが純粋な入れ替えになるがスキーマが IR の形を語る力が落ちる）。kotowari の層で捨てる
  - decided_by: 利用者（推奨を採用）

- A34 A33 で`指摘`の種類が増えるので、kotowari の版を上げる
  - why: 利用者の IR に今まで出なかった`誤り`が出るようになる。意味の変わる変更
  - decided_by: 推奨（A33 と釣り合わせて導いた）

- A35 A33 の3件には、それぞれ確かめるテストを置く
  - why: A19 の「既存のテストがオラクル」は振る舞いが変わらない部分にだけ効く。新しく出る`指摘`はそれを見るテストが無い

- A36 スキーマをバイナリに埋め込む。`include_str!` で3つの YAML をコンパイル時に取り込み、実行時にスキーマのファイルを読まない
  - why: [REQ-core-090](../../ir/core/form-contract.md#REQ-core-090)（`IR`の形を宣言したスキーマのファイルを読んではならない）が現にある。埋め込めばこの禁止が文のまま成り立ち、廃止しなくて済む。[REQ-core-089](../../ir/core/form-contract.md#REQ-core-089)（コードに固定した1つの形で`IR`を読む）も、宣言が Rust から YAML に変わるだけで実質成り立つ。配布先にスキーマをどう用意するかという問いも消える。形を設定で変えられるようにする案は [R9](./records.md#R9) で既に却下されているので、差し替えを許す理由も無い
  - rejected: ファイルから読み、REQ-core-090 を廃止して改訂に記録する
  - decided_by: 利用者（推奨を採用）

- A37 エンジンに`文`の行ごとの`抽出`を足す。A12 で`表`だけに限った境界を広げる
  - why: `ir.rs` が`文`を行ごとに生の文字で持っている（「detail の元になるので生の行（字下げを含む）を持つ」とコメントにある）。エンジンの今の`抽出`は`継続段落`を1つの文字列に繋げて開始行だけを返すので（実測）、unknown_term・vague_word・unclosed_backtick の「その行」と detail を復元できない
  - rejected: これら3つの検査を kotowari に残して生の行を読む（A1 の例外が3つになり「Markdown を読まない」が形だけになる）。行と detail が変わることを受け入れる（A5 に反する）
  - decided_by: 利用者（推奨を採用）
  - related: `出典` の行はフィールド行に行番号の`抽出`を宣言すれば出る（実測。エンジンの改修は要らない）

- A38 置き換えの証拠を、`kotowari check --format json` の出力全体の差分が A33 の3件だけであることにする。`kotowari status` の数の不変はやめる
  - why: A33 で`指摘`の種類が増えれば IR に要求が増えて数が変わるので、A19 の数の不変は A33 と両立しない。出力全体の差分なら detail と出る順も同時に見える
  - decided_by: 利用者（推奨を採用）

- A39 A33 の3件は kotowari の新しい`指摘`の種類として名前・detail・重大度を仕様で決める。`skills/kotowari/references/findings.md`、[TBL-core-008](../../ir/core/findings.md#TBL-core-008)、[用語集](../../ir/core/CONTEXT.md)の`除外`の列挙の更新を範囲に入れる
  - why: [REQ-core-125](../../ir/core/skill-references.md#REQ-core-125) がスキルの表の1列目とコードが出す種類の集合の一致をテストで固定している。[REQ-core-120](../../ir/core/cli-environment.md#REQ-core-120) が「`除外`に列挙していない入力を、`停止`も`指摘`もせずに読み飛ばしてはならない」と定めるので、`除外`の列挙から外す作業が要る
  - decided_by: 利用者（推奨を採用）
  - related: A3 の「新しい種類は足さない」はエンジンの`指摘`の写し方の規則で、kotowari が新しく見るようになった場面には及ばない。A33 の3件はこの区別に当たる

- A40 対応表を5列にする。エンジンの種類、ノードの名前、kotowari の種類、写した後の "line" の扱い、detail の材料
  - why: [REQ-core-027](../../ir/core/finding-order.md#REQ-core-027) が9種類の "line" を null と定めており、detail の材料も種類ごとに違う（文書名、行の名前、見出しの文字）。3列では書けない
  - decided_by: 利用者（推奨を採用）
