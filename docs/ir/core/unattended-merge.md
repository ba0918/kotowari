# Merging without waiting for a person

English | [日本語](unattended-merge.ja.md)

Covers how the workflow skills carry one request from the approval of its specification to the merge without waiting for a person: what the cycle takes as input now that no plan is written, the line that decides whether a person confirms the merge, how the merge is made, and what is recorded of the run.

## Requirements

### REQ-core-364: From approval to implementation

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A4, docs/decision/records/2026-11-24-unattended-merge.md#A22, docs/decision/records/2026-11-24-unattended-merge.md#A24, docs/decision/records/2026-11-24-unattended-merge.md#A27, docs/decision/records/2026-11-24-unattended-merge.md#A33, docs/decision/records/2026-11-24-unattended-merge.md#A37, docs/decision/records/2026-11-24-merge-flow-fixes.md#A1, docs/decision/records/2026-11-24-merge-flow-fixes.md#A4, docs/decision/records/2026-11-24-merge-flow-fixes.md#A7, docs/decision/records/2026-11-24-merge-flow-fixes.md#A8, docs/decision/records/2026-11-24-merge-flow-fixes.md#A9, docs/decision/records/2026-11-24-merge-flow-fixes.md#A11, docs/decision/records/2026-11-24-merge-flow-fixes-consistency.md#A9, docs/decision/records/2026-11-24-merge-flow-fixes-consistency.md#A11, docs/decision/records/2026-11-24-merge-flow-fixes-consistency.md#A12
- verification: review
- how_to_verify: Read "agent/skills/kotowari-brainstorm/", "agent/skills/kotowari-cycle/", "agent/skills/kotowari-implement/", "agent/skills/kotowari-iterate/" and "agent/skills/kotowari-using-workflow/", and confirm that all of the following are written. There is no station that writes a plan and no approval of one, and "agent/skills/kotowari-plan/" does not exist. When the person has committed the approved specification, or said it may be committed, the brainstorm goes on to the cycle in the same flow, unless the person says to put it off. The brainstorm cuts a new branch from the head of the merge target in the main working tree and commits the specification on it; after the approval, before the cycle starts, the main working tree is put back on the branch it was on when the brainstorm began and the new branch is checked out in a working directory of its own. When the person said the specification may be committed rather than committing it, the brainstorm commits it on the new branch, and while an approved file is not committed on the new branch it does not put the main working tree back: it tells the person which files and stops. When the main working tree cannot be switched, the brainstorm stops and tells the person. A brainstorm that resumes after the cycle handed the work back writes in that working directory. The cycle receives from the brainstorm the place of the specification and the IDs of the requirements the brainstorm added or changed, and it receives the merge target, which is the default branch of the repository when none was decided; when none was decided and the default branch cannot be read, the cycle asks the person and does not guess. The first full review, the first run of the consistency phase and the line read from the commit where the branch parted from that merge target, and the pull request points at it; the later diff reviews and the run of the consistency phase after the fixes keep the ranges they have (REQ-core-359). A small task that goes on with a branch an earlier run already reviewed reads from where that run ended. At a start that received the place of a specification, and neither at a resume nor for a small task without a specification, the cycle confirms that its working directory holds no uncommitted change in the place of the specification or in the place of decision records, and that the check of kotowari reports no error on the side of the specification on a document the branch changed or on an ID the cycle received; when either does not hold it says the specification is not approved and stops. At its start the cycle creates the findings file of the branch and writes into it the IDs and the merge target it received, an empty list of IDs included; a later request on the same branch adds its IDs. A resume is a start that brings no request; a start that brings a request to a branch whose findings file is already there is a later request, not a resume: it confirms the specification as above, and it begins again from implementation, its consistency phase run and its full review reading from the commit where the branch parted from the merge target, the small task above apart, which reads from where the earlier run ended. The cycle reads the pull requests of the branch first, confirms the specification next, and only then creates or changes the findings file. A resume reads both from the file, and only when the file has no record of the IDs does it count them again from the part of the diff of the branch that lies in the place of the specification. The cycle removes the IDs under deferral before handing them to the implementer. The cycle creates no new file for resuming. A resume during implementation is decided by the implementer from the git history and from which of those requirements, other than the ones verified by review, still have no marked test, and reads the working notes of the implementer when there are any. A resume after the pull request was created reads from the hosting service whether the pull request exists, whether merging by itself was asked for, the state of the checks, and whether it was merged. The name of a branch is not used again after its request ended: when a start that received a new request finds a merged or closed pull request under the name of the branch on the hosting service, the cycle stops and asks for a new branch name. When the pull request of the branch is open and its head is not on the local branch, the cycle stops and tells the person. When the hosting service cannot be read at the start, the cycle goes on without these two checks, makes them before it pushes the branch when the hosting service can be read then, and says in its final report which checks could not be made. The test command comes from the instructions of the project or the standard tool of the language, and when neither settles it the person is asked. When the implementer returns that a check command cannot succeed as it is written, the cycle asks the person and delegates again with the answer. The implementer decides the order and the files to touch, and writes working notes only when it judges them necessary; the notes are not committed and no person reads them

kotowari-cycle always starts a request that has a specification from the approval of that specification without waiting for a person, taking the place of the specification and the `ID` of each `requirement` the brainstorm added or changed as its input, with no station that writes a `plan` in between.

### REQ-core-365: The line is judged from paths with git

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A3, docs/decision/records/2026-11-24-unattended-merge.md#A9, docs/decision/records/2026-11-24-unattended-merge.md#A16, docs/decision/records/2026-11-24-unattended-merge.md#A19, docs/decision/records/2026-11-24-unattended-merge.md#A20, docs/decision/records/2026-11-24-unattended-merge.md#A39, docs/decision/records/2026-11-24-unattended-merge.md#A44, docs/decision/records/2026-11-24-unattended-merge-consistency.md#A5, docs/decision/records/2026-11-24-merge-flow-fixes.md#A1, docs/decision/records/2026-11-24-merge-flow-fixes.md#A6
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and confirm that all of the following are written. The line between a change a person confirms and a change that merges without one is judged by git alone: the paths of the files changed between the commit where the branch parted from the merge target and the head of the branch are matched against the pathspecs written one per line in ".kotowari/confirm-paths". The merge target is the one the cycle received (REQ-core-364), and the pull request points at it. The pathspecs are read from both the list at the head of the merge target and the list at the head of the branch, and a hit under either is a hit. Each line is read with the blanks around it and a carriage return at its end taken off, and is matched on its own, so a line that excludes paths takes no hit away from another line. A file that was moved counts under both its old path and its new path. What a project writes in the file is the definitions of its checks (CI, hooks, the scripts that run checks, the configuration of mutation tests, of static analysis and of tool versions); the places of the specification and of decision records are not written there. A repository that holds the source of the skill text with this procedure writes the path of that source there too. ".kotowari/confirm-paths" itself always counts as a hit, whether or not it is written in the file. When the file does not exist, the result is the same as a hit. The result has two values only, hit or no hit, and no LLM judges it. When a command of the procedure fails, the result is a hit with no paths, and the cycle reports the failure with its error output, not as paths that were hit. The line is judged again each time the cycle adds commits to the branch of the pull request, always over the whole diff, so a hit that a later change takes out of the diff is no longer a hit. No command of kotowari is used for it

kotowari-cycle always judges, with git alone and again each time it adds commits to the branch, whether the diff from the commit where the branch parted from the merge target touches a path listed in ".kotowari/confirm-paths" or the file itself.

### REQ-core-366: Merging without waiting for a person

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A1, docs/decision/records/2026-11-24-unattended-merge.md#A12, docs/decision/records/2026-11-24-unattended-merge.md#A23, docs/decision/records/2026-11-24-unattended-merge.md#A24, docs/decision/records/2026-11-24-unattended-merge.md#A28, docs/decision/records/2026-11-24-unattended-merge.md#A35, docs/decision/records/2026-11-24-unattended-merge.md#A39, docs/decision/records/2026-11-24-unattended-merge.md#A41, docs/decision/records/2026-11-24-unattended-merge.md#A43, docs/decision/records/2026-11-24-unattended-merge.md#A44, docs/decision/records/2026-11-24-unattended-merge-consistency.md#A1, docs/decision/records/2026-11-24-unattended-merge-consistency.md#A8, docs/decision/records/2026-11-24-merge-flow-fixes.md#A10, docs/decision/records/2026-11-24-merge-flow-fixes-consistency.md#A7, docs/decision/records/2026-11-24-merge-flow-fixes-consistency.md#A8, docs/decision/records/2026-11-24-merge-flow-fixes-consistency.md#A10
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and "agent/skills/kotowari-iterate/" and confirm that all of the following are written. Only a run that reached the converged ending goes on to a merge; a run that reached any other ending (the round-trip limit, no progress, a hand-back) reports to the person as before and asks for no merge. When the run converged, the line is not hit and nothing of REQ-core-367 holds, the cycle creates a pull request and asks the hosting service to merge it by itself once the required checks pass; the cycle never performs the merge. It asks for this only when it has confirmed that the repository allows such merging, that the merge target requires one or more checks, that the merge target requires no approving review, and that the pull request points at the merge target the cycle received; when one of these does not hold or cannot be confirmed, it stops at the pull request, reports that merging by itself is not available, and the person merges; on a host where it cannot create a pull request it stops after pushing the branch. The cycle never changes a setting of the repository. After asking, it withdraws the request before it adds a commit to the branch, and asks again only after confirming for the new head that the run converged, the line is not hit and nothing of REQ-core-367 holds; it also withdraws the request when one of these stops holding and when it hands the pull request to the person. When it cannot read from the hosting service whether a request stands, it does not push to the branch: it stops and tells the person, except on a host where it cannot create a pull request, where no request can stand. After creating the pull request it watches the required checks to their result, in a run that stops at the pull request too. Every run that creates a pull request confirms whether the merge target requires checks; where it does, required checks that have not reported yet are not read as a failure: the cycle reads again until they appear. When a read of the required checks fails, whether the merge target requires checks is not confirmed, whatever another read returned: the cycle watches the checks that show and then hands the pull request to the person with that failure. After the checks passed, while the request to merge stands, the cycle waits for the merge; it reads the hosting service as not merging only when the request is gone or the state is one that waiting does not change, such as a conflict or a branch behind its target. A required check that failed is put in the findings file as a finding and follows the existing fixing round trips and the existing endings, and when the checks still do not pass the cycle hands the pull request to the person. The watch ends when the cycle sees the pull request merged, when it hands the pull request to the person after failed checks, when the checks passed and the hosting service reports that it does not merge, which the cycle hands to the person with the reason, when the checks passed in a run that stops at the pull request, when the pull request was closed without being merged, which the cycle reports to the person, when it hands the pull request to the person because it could not confirm whether the merge target requires checks, or at once when the merge target requires no check; the cycle has no time limit of its own for the watch. A small task run through kotowari-iterate merges the same way. A change the main session edits directly ends at the commit, as before

kotowari-cycle always, when the run converged, the line is not hit and no decision of a person is left, creates a pull request, asks the hosting service to merge it once the required checks pass, and watches those checks to their result without waiting for a person.

### REQ-core-367: When a person confirms

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A3, docs/decision/records/2026-11-24-unattended-merge.md#A12, docs/decision/records/2026-11-24-unattended-merge.md#A15, docs/decision/records/2026-11-24-unattended-merge.md#A19, docs/decision/records/2026-11-24-unattended-merge.md#A21, docs/decision/records/2026-11-24-unattended-merge.md#A26, docs/decision/records/2026-11-24-unattended-merge.md#A31, docs/decision/records/2026-11-24-unattended-merge.md#A32, docs/decision/records/2026-11-24-unattended-merge.md#A39, docs/decision/records/2026-11-24-unattended-merge.md#A44, docs/decision/records/2026-11-24-unattended-merge.md#A46, docs/decision/records/2026-11-24-unattended-merge-consistency.md#A5, docs/decision/records/2026-11-24-merge-flow-fixes.md#A12, docs/decision/records/2026-11-24-merge-flow-fixes.md#A10
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and confirm that all of the following are written. Of the runs that converged, a person confirms the merge in these three cases only: the line of REQ-core-365 is hit; a finding is still open as awaiting the judgment of a person, whatever raised it (the consistency phase or a review); the consistency phase revised an approved requirement after showing by a contradiction or a reproduction that it was wrong. In each case the cycle creates the pull request, does not ask for it to be merged by itself, leaves it open, and shows the person where the pull request is and what caused the stop: the paths that were hit (or, when the procedure of the line failed, that failure), the open findings, or the revised requirements. It shows this as soon as the pull request is created, before the watch. It adds no summary of the change. On a host where it cannot create a pull request it stops after pushing the branch and shows the cause in its final report. In the third case the consistency phase does not stop its work; only the request to merge is withheld. When the implementer returned that an approved requirement has to be changed or deleted, the existing stop conditions of the workflow apply, a person comes in, and nothing is merged. An operation that cannot be undone (a release, publishing, a tag, a deletion of something outside the local machine) stays with the person under the existing stop rules. A concretisation the consistency phase added to the specification or to a decision record after approval is not a reason to stop

kotowari-cycle always, when the line is hit, a `finding` awaiting the judgment of a person is left, or the `consistency phase` revised an approved `requirement`, leaves the pull request open without asking for it to be merged and shows the person the pull request and what caused the stop, and when the implementer returns that an approved `requirement` has to be changed or deleted, stops by the existing stop conditions of the workflow without merging.

### REQ-core-368: What does not wait for a person

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A5, docs/decision/records/2026-11-24-unattended-merge.md#A10, docs/decision/records/2026-11-24-unattended-merge.md#A11, docs/decision/records/2026-11-24-unattended-merge.md#A15, docs/decision/records/2026-11-24-unattended-merge.md#A17, docs/decision/records/2026-11-24-unattended-merge.md#A25, docs/decision/records/2026-11-24-unattended-merge.md#A41, docs/decision/records/2026-11-24-merge-flow-fixes.md#A2, docs/decision/records/2026-11-24-merge-flow-fixes.md#A3, docs/decision/records/2026-11-24-merge-flow-fixes.md#A5, docs/decision/records/2026-11-24-unattended-merge-consistency.md#A4
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/", "agent/skills/kotowari-implement/" and "agent/skills/kotowari-review/" and confirm that all of the following are written. Among the findings of a review, three kinds keep a run from converging: a mistake that running something shows, a security finding whose proposed action is a fix, and a proposal to delete verification the diff added because it does not meet the evidence conditions; the stops of REQ-core-367 are apart from this. A finding whose oracle was replaced with all existing checks passing counts as shown by running when the reviewer ran the oracle it proposed before the replacement and saw it fail. A proposal to delete verification the diff added because it does not meet the evidence conditions is fixed without having been seen failing. A security finding whose proposed action is a fix does not pause the run: it goes to the fixer whether or not its oracle was seen failing, the existing ending for no progress hands it to the person when it cannot be fixed, and what was fixed is left as a decision line. A security finding that asks for the judgment of a person stays open under REQ-core-367, and one that is only recorded stays recorded. A change that deletes a test, adds a suppression of a check, or adds or changes a dependency is not sent to a person for that reason. Readability and choices of structure are decided by the implementer and are neither a reason to stop nor a reason to add a review seat. Each decision the implementer made by itself, a dependency it added included, is written as one line holding what was decided, why, and the evidence; the lines go in the body of the pull request and, the same, in the final report of the cycle. A gap from the intent that running cannot show is counted as a hole in the specification, a rework on the side of the brainstorm

kotowari-cycle always lets, among the findings of a review, only a mistake that running something shows, a security `finding` proposing a fix, or a proposal to delete verification the diff added that does not meet the evidence conditions keep a run from converging, never pauses for a person on such a security `finding`, and leaves each decision the implementer made by itself as one line of what, why and evidence in the body of the pull request and in its final report.

### REQ-core-369: What the record of a run holds

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A6, docs/decision/records/2026-11-24-unattended-merge.md#A13, docs/decision/records/2026-11-24-unattended-merge.md#A14, docs/decision/records/2026-11-24-unattended-merge.md#A30, docs/decision/records/2026-11-24-unattended-merge.md#A31, docs/decision/records/2026-11-24-unattended-merge.md#A40, docs/decision/records/2026-11-24-unattended-merge.md#A43, docs/decision/records/2026-11-24-unattended-merge.md#A45, docs/decision/records/2026-11-24-unattended-merge.md#A47, docs/decision/records/2026-11-24-merge-flow-fixes.md#A4, docs/decision/records/2026-11-24-merge-flow-fixes-consistency.md#A13
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and the finding schema under "agent/skills/kotowari-review/" and confirm that all of the following are written. The cycle writes no new record file; it adds five things to the findings file it already writes for each branch: the IDs it received; the merge target it received; the result of the line with the paths that were hit; the name of the branch of the earlier request this request fixes, written only when the request says it is a fix of an earlier request and left empty otherwise; and which ending the run reached with its reason, a hand-back to an earlier station and a stop for a person included. Cost is not recorded. The findings file is not committed, is kept outside the working directory that is cleaned up, and is never deleted by the workflow. The findings file of a run that ended in a merge is not read as a resume by a later run on a branch of the same name. The cycle cleans up only when it saw the merge itself: it removes the local working directory and the local branch after confirming the findings file is outside the working directory, leaves them and reports when the working directory holds uncommitted changes other than the working notes of the implementer, and deletes nothing on the hosting service. A run the person merges later is not cleaned up by the cycle

kotowari-cycle always keeps, in the findings file it already writes for the branch, the `ID` of each `requirement` it received, the merge target it received, the result of the line, the earlier request a fix belongs to, and the ending with its reason, and after a merge it saw removes only the local working directory and the local branch.
