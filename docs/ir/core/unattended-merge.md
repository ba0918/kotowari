# Merging without waiting for a person

English | [日本語](unattended-merge.ja.md)

Covers how the workflow skills carry one request from the approval of its specification to the merge without waiting for a person: what the cycle takes as input now that no plan is written, the line that decides whether a person confirms the merge, how the merge is made, and what is recorded of the run.

## Requirements

### REQ-core-364: From approval to implementation

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A4, docs/decision/records/2026-11-24-unattended-merge.md#A22, docs/decision/records/2026-11-24-unattended-merge.md#A24, docs/decision/records/2026-11-24-unattended-merge.md#A27, docs/decision/records/2026-11-24-unattended-merge.md#A33, docs/decision/records/2026-11-24-unattended-merge.md#A37
- verification: review
- how_to_verify: Read "agent/skills/kotowari-brainstorm/", "agent/skills/kotowari-cycle/", "agent/skills/kotowari-implement/", "agent/skills/kotowari-iterate/" and "agent/skills/kotowari-using-workflow/", and confirm that all of the following are written. There is no station that writes a plan and no approval of one, and "agent/skills/kotowari-plan/" does not exist. When the person has committed the approved specification, or said it may be committed, the brainstorm goes on to the cycle in the same flow, unless the person says to put it off. The cycle receives from the brainstorm the place of the specification and the IDs of the requirements the brainstorm added or changed; when it starts later or resumes, it counts them again from the part of the diff of the branch that lies in the place of the specification. The cycle removes the IDs under deferral before handing them to the implementer. The cycle keeps no new state for resuming. A resume during implementation is decided by the implementer from the git history and from which of those requirements, other than the ones verified by review, still have no marked test, and reads the working notes of the implementer when there are any. A resume after the pull request was created reads from the hosting service whether the pull request exists, whether merging by itself was asked for, the state of the checks, and whether it was merged. The test command comes from the instructions of the project or the standard tool of the language, and when neither settles it the person is asked. The implementer decides the order and the files to touch, and writes working notes only when it judges them necessary; the notes are not committed and no person reads them

kotowari-cycle always starts a request that has a specification from the approval of that specification without waiting for a person, taking the place of the specification and the `ID` of each `requirement` the brainstorm added or changed as its input, with no station that writes a `plan` in between.

### REQ-core-365: The line is judged from paths with git

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A3, docs/decision/records/2026-11-24-unattended-merge.md#A9, docs/decision/records/2026-11-24-unattended-merge.md#A16, docs/decision/records/2026-11-24-unattended-merge.md#A19, docs/decision/records/2026-11-24-unattended-merge.md#A20, docs/decision/records/2026-11-24-unattended-merge.md#A39, docs/decision/records/2026-11-24-unattended-merge.md#A44
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and confirm that all of the following are written. The line between a change a person confirms and a change that merges without one is judged by git alone: the paths of the files changed between the commit where the branch parted from the merge target and the head of the branch are matched against the pathspecs written one per line in ".kotowari/confirm-paths". The merge target is the branch the pull request points at, and the default branch of the repository when none was decided. A file that was moved counts under both its old path and its new path. What a project writes in the file is the definitions of its checks (CI, hooks, the scripts that run checks, the configuration of mutation tests, of static analysis and of tool versions); the places of the specification and of decision records are not written there. A repository that holds the source of the skill text with this procedure writes the path of that source there too. ".kotowari/confirm-paths" itself always counts as a hit, whether or not it is written in the file. When the file does not exist, the result is the same as a hit. The result has two values only, hit or no hit, and no LLM judges it. The line is judged again each time the cycle adds commits to the branch of the pull request, always over the whole diff, so a hit that a later change takes out of the diff is no longer a hit. No command of kotowari is used for it

kotowari-cycle always judges, with git alone and again each time it adds commits to the branch, whether the diff from the commit where the branch parted from the merge target touches a path listed in ".kotowari/confirm-paths" or the file itself.

### REQ-core-366: Merging without waiting for a person

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A1, docs/decision/records/2026-11-24-unattended-merge.md#A12, docs/decision/records/2026-11-24-unattended-merge.md#A23, docs/decision/records/2026-11-24-unattended-merge.md#A24, docs/decision/records/2026-11-24-unattended-merge.md#A28, docs/decision/records/2026-11-24-unattended-merge.md#A35, docs/decision/records/2026-11-24-unattended-merge.md#A39, docs/decision/records/2026-11-24-unattended-merge.md#A41, docs/decision/records/2026-11-24-unattended-merge.md#A43, docs/decision/records/2026-11-24-unattended-merge.md#A44, docs/decision/records/2026-11-24-unattended-merge-consistency.md#A1
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and "agent/skills/kotowari-iterate/" and confirm that all of the following are written. Only a run that reached the converged ending goes on to a merge; a run that reached any other ending (the round-trip limit, no progress, a hand-back) reports to the person as before and asks for no merge. When the run converged, the line is not hit and nothing of REQ-core-367 holds, the cycle creates a pull request and asks the hosting service to merge it by itself once the required checks pass; the cycle never performs the merge. It asks for this only when it has confirmed both that the repository allows such merging and that the merge target requires one or more checks; when either is absent or cannot be confirmed, it stops at the pull request, reports that merging by itself is not available, and the person merges; on a host where it cannot create a pull request it stops after pushing the branch. The cycle never changes a setting of the repository. After asking, it withdraws the request before it adds a commit to the branch, and asks again only after confirming for the new head that the run converged, the line is not hit and nothing of REQ-core-367 holds; it also withdraws the request when one of these stops holding and when it hands the pull request to the person. After creating the pull request it watches the required checks to their result, in a run that stops at the pull request too. A required check that failed is put in the findings file as a finding and follows the existing fixing round trips and the existing endings, and when the checks still do not pass the cycle hands the pull request to the person. The watch ends when the cycle sees the pull request merged, when it hands the pull request to the person after failed checks, when the checks passed and the hosting service reports that it does not merge, which the cycle hands to the person with the reason, when the checks passed in a run that stops at the pull request, or at once when the merge target requires no check; the cycle has no time limit of its own for the watch. A small task run through kotowari-iterate merges the same way. A change the main session edits directly ends at the commit, as before

kotowari-cycle always, when the run converged, the line is not hit and no decision of a person is left, creates a pull request, asks the hosting service to merge it once the required checks pass, and watches those checks to their result without waiting for a person.

### REQ-core-367: When a person confirms

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A3, docs/decision/records/2026-11-24-unattended-merge.md#A12, docs/decision/records/2026-11-24-unattended-merge.md#A15, docs/decision/records/2026-11-24-unattended-merge.md#A19, docs/decision/records/2026-11-24-unattended-merge.md#A21, docs/decision/records/2026-11-24-unattended-merge.md#A26, docs/decision/records/2026-11-24-unattended-merge.md#A31, docs/decision/records/2026-11-24-unattended-merge.md#A32, docs/decision/records/2026-11-24-unattended-merge.md#A39, docs/decision/records/2026-11-24-unattended-merge.md#A44, docs/decision/records/2026-11-24-unattended-merge.md#A46
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and confirm that all of the following are written. Of the runs that converged, a person confirms the merge in these three cases only: the line of REQ-core-365 is hit; a finding is still open as awaiting the judgment of a person, whatever raised it (the consistency phase, a review, or a finding the person chose to leave); the consistency phase revised an approved requirement after showing by a contradiction or a reproduction that it was wrong. In each case the cycle creates the pull request, does not ask for it to be merged by itself, leaves it open, and shows the person where the pull request is and what caused the stop: the paths that were hit, the open findings, or the revised requirements. It adds no summary of the change. On a host where it cannot create a pull request it stops after pushing the branch and shows the cause in its final report. In the third case the consistency phase does not stop its work; only the request to merge is withheld. When the implementer returned that an approved requirement has to be changed or deleted, the existing stop conditions of the workflow apply, a person comes in, and nothing is merged. An operation that cannot be undone (a release, publishing, a tag, a deletion of something outside the local machine) stays with the person under the existing stop rules. A concretisation the consistency phase added to the specification or to a decision record after approval is not a reason to stop

kotowari-cycle always, when the line is hit, a `finding` awaiting the judgment of a person is left, or the `consistency phase` revised an approved `requirement`, leaves the pull request open without asking for it to be merged and shows the person the pull request and what caused the stop, and when the implementer returns that an approved `requirement` has to be changed or deleted, stops by the existing stop conditions of the workflow without merging.

### REQ-core-368: What does not wait for a person

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A5, docs/decision/records/2026-11-24-unattended-merge.md#A10, docs/decision/records/2026-11-24-unattended-merge.md#A11, docs/decision/records/2026-11-24-unattended-merge.md#A15, docs/decision/records/2026-11-24-unattended-merge.md#A17, docs/decision/records/2026-11-24-unattended-merge.md#A25, docs/decision/records/2026-11-24-unattended-merge.md#A41
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/", "agent/skills/kotowari-implement/" and "agent/skills/kotowari-review/" and confirm that all of the following are written. Among the findings of a review, only a mistake that running something shows keeps a run from converging; the stops of REQ-core-367 are apart from this. A change that deletes a test, adds a suppression of a check, or adds or changes a dependency is not sent to a person for that reason. Readability and choices of structure are decided by the implementer and are neither a reason to stop nor a reason to add a review seat. Each decision the implementer made by itself, a dependency it added included, is written as one line holding what was decided, why, and the evidence; the lines go in the body of the pull request and, the same, in the final report of the cycle. A gap from the intent that running cannot show is counted as a hole in the specification, a rework on the side of the brainstorm

kotowari-cycle always lets, among the findings of a review, only a mistake that running something shows keep a run from converging, and leaves each decision the implementer made by itself as one line of what, why and evidence in the body of the pull request and in its final report.

### REQ-core-369: What the record of a run holds

- kind: ubiquitous
- source: docs/decision/records/2026-11-24-unattended-merge.md#A6, docs/decision/records/2026-11-24-unattended-merge.md#A13, docs/decision/records/2026-11-24-unattended-merge.md#A14, docs/decision/records/2026-11-24-unattended-merge.md#A30, docs/decision/records/2026-11-24-unattended-merge.md#A31, docs/decision/records/2026-11-24-unattended-merge.md#A40, docs/decision/records/2026-11-24-unattended-merge.md#A43, docs/decision/records/2026-11-24-unattended-merge.md#A45, docs/decision/records/2026-11-24-unattended-merge.md#A47
- verification: review
- how_to_verify: Read "agent/skills/kotowari-cycle/" and the finding schema under "agent/skills/kotowari-review/" and confirm that all of the following are written. The cycle writes no new record file; it adds three things to the findings file it already writes for each branch: the result of the line with the paths that were hit; the name of the branch of the earlier request this request fixes, written only when the request says it is a fix of an earlier request and left empty otherwise; and which ending the run reached with its reason, a hand-back to an earlier station and a stop for a person included. Cost is not recorded. The findings file is not committed, is kept outside the working directory that is cleaned up, and is never deleted by the workflow. The findings file of a run that ended in a merge is not read as a resume by a later run on a branch of the same name. The cycle cleans up only when it saw the merge itself: it removes the local working directory and the local branch after confirming the findings file is outside the working directory, leaves them and reports when the working directory holds uncommitted changes other than the working notes of the implementer, and deletes nothing on the hosting service. A run the person merges later is not cleaned up by the cycle

kotowari-cycle always keeps, in the findings file it already writes for the branch, the result of the line, the earlier request a fix belongs to, and the ending with its reason, and after a merge it saw removes only the local working directory and the local branch.
