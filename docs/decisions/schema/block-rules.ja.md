# 見出しの下の行の規則

[English](block-rules.md) | 日本語

見出しや前置部の下に並ぶ行を、フィールド行、文、箇条書き、表、コードブロックのどれとして読むかと、それぞれの行にスキーマが課せる制約を扱う。題名・節・項目という見出しの骨格は[文書の骨格](document-structure.ja.md)で決める。

## 一覧の行は、宣言した名前と一致すればフィールド行、一致しなければ箇条書きとして読む

状態: 実装済み

### 問題

一覧の行の中には「名前と値」の形をしたものがある。これをいつフィールド行として読み、いつ普通の箇条書きとして読むかを決める必要がある。また Markdown では、一覧のマーカー "-"、"*"、"+" はどれも同じ一覧で、書き手がどれを使うかで意味が変わると驚きになる。

### 決めたこと

一覧の行は、次の順に読み分ける。

| 順 | 行の形 | 読み方 |
|---|---|---|
| 1 | マーカーに「名前と値」が続き、名前がスキーマの宣言と一致する | フィールド行 |
| 2 | マーカーに続くが、1 に当たらない | 箇条書き |
| 3 | 数字と "." か ")" の区切りで始まる | どの規則種別にも属さない（[数字で始まる一覧の行は、箇条書きにしない](#数字で始まる一覧の行は箇条書きにしない)） |

マーカー "-"、"*"、"+" は同じに扱う。どれを使っても、同じ行は同じ規則種別として読む。

### 確認すること

- C-schema-block-1 スキーマが宣言した名前の「名前と値」の行はフィールド行として読まれ、宣言していない名前の「名前と値」の行は箇条書きとして読まれて、箇条書きの規則の照合と数に入る
- C-schema-block-2 一覧のマーカーが "-"、"*"、"+" のどれであっても、行ごとに混ぜても、同じ行は同じ規則種別として読まれ、同じ指摘になる（性質）

## 数字で始まる一覧の行は、箇条書きにしない

状態: 実装済み

### 問題

数字で始まる順序付きの一覧の行を、箇条書きとして読むかどうかを決める必要がある。区切りに "." だけを認めるか、")" も認めるかも決める。理由は、")" の区切りについてのもののほかは残っていない。

### 決めたこと

数字と区切りで始まる一覧の行は、箇条書きとして扱わない。どの規則種別にも属さず、閉じた世界（[既定は閉じた世界にし、宣言していない見出しと行を指摘にする](closed-world.ja.md#既定は閉じた世界にし宣言していない見出しと行を指摘にする)）では undeclared_line の指摘にする。

区切りは、CommonMark のとおり "." と ")" のどちらも認める。段落で読んでも行で読んでも、mds は CommonMark に合わせて "1)" を順序付きの一覧の行として読んでいる。

### 見送った案

- ")" の区切りの行を一覧の行として読まず、文にする。段落で読むときの CommonMark の読み方と、行で読むときの読み方が分かれる。

### 確認すること

- C-schema-block-3 数字と "." か ")" で始まる一覧の行は、箇条書きの規則の照合にも、箇条書きの数にも、箇条書きの抽出にも入らず、閉じた世界では undeclared_line の指摘になる

## フィールド行の値に、正規表現と許可リストを課せる

状態: 実装済み

### 問題

フィールド行の値の形を、スキーマで縛れるようにしたい。値を区切り文字で区切って複数の要素として書くフィールド行では、どの単位で照合するかも決める必要がある。理由は残っていない。

### 決めたこと

フィールド行の値に、正規表現と許可リストを課せる。正規表現に合わない値は field_pattern_mismatch、許可リストに無い値は field_enum_invalid の指摘にする。

区切り文字を宣言したフィールド行では、区切った要素ごとに、前後の空白を取り除いてから照合する。区切った結果が空の要素も照合の対象にする。

### 確認すること

- C-schema-block-4 フィールド行の値が正規表現に合わなければ field_pattern_mismatch、許可リストに無ければ field_enum_invalid の指摘になる
- C-schema-block-5 区切り文字を宣言したフィールド行は、区切った要素ごとに前後の空白を除いて照合され、空の要素も照合と値の対象に残る

## 文と箇条書きの行に正規表現を課し、文には許可リストも課せる

状態: 実装済み

### 問題

文と箇条書きの行の形も、スキーマで縛れるようにしたい。理由は残っていない。

### 決めたこと

文に正規表現と許可リストを課せる。正規表現を満たさない文は statement_pattern_mismatch、許可リストに無い文は statement_enum_invalid の指摘にする。

箇条書きの行に正規表現を課せる。満たさない行は bullet_pattern_mismatch の指摘にする。照合は、元のマーカーの行の、マーカーを除いた部分にだけ行う。継続段落と、マーカーの行に空行を挟まずに続く行には照合しない。

### 確認すること

- C-schema-block-6 文が正規表現に合わなければ statement_pattern_mismatch、許可リストに無ければ statement_enum_invalid の指摘になる
- C-schema-block-7 箇条書きの行が正規表現に合わなければ bullet_pattern_mismatch の指摘になり、照合はマーカーの行のマーカーを除いた部分だけに行われ、継続段落と、マーカーの行に続く行は照合されない

## フィールド行の並び順は、強制を宣言したときだけ照合する

状態: 実装済み

### 問題

フィールド行を決まった順に並べさせたい書式と、順を問わない書式の両方がある。理由は残っていない。

### 決めたこと

フィールド行の並び順は、既定では順不同にする。スキーマで並び順の強制を宣言したときは、スキーマに書いた順で現れることを求め、その順で現れないフィールド行を field_order_mismatch の指摘にする。

### 確認すること

- C-schema-block-8 並び順の強制を宣言したスキーマでは、スキーマに書いた順で現れないフィールド行が field_order_mismatch の指摘になり、書いた順に並んだフィールド行には指摘が出ない

## 見出しの下の行は、スキーマが選ぶ読み方（段落か行）で読む

状態: 実装済み

### 問題

mds は公開済みで、見出しの下の行を CommonMark の段落として読む。これを既定のまま変えると、mds の利用者の結果が変わる。

一方で、kotowari が仕様の文書に求めていた文は1行ずつで、CommonMark の段落とは別の読み方だった。段落として読むと、フィールド行のすぐ次の行が値に吸われて的外れな指摘が出たり、引用や HTML の行が文にも指摘にもならずに黙って消えたりした。kotowari が生の行を自分で読み直すことは、「kotowari は Markdown を読まない」という決まりに反する。

そこで、既定の読み方は変えず、要る読み方をスキーマの宣言で選べるようにする。宣言は "open" と同じ最上位の設定として読め、読み方を足すときに鍵を増やさずに済む形にする。

### 決めたこと

スキーマの最上位の "reading" で、見出しと前置部の下の行の読み方を選ぶ。"paragraph"（段落で読む）が既定で、CommonMark の読み方である。"line"（行で読む）は、一覧の行でも表の行でもない空でない行を1行ずつ文にする。"reading" が受ける値は[読み方は段落を既定にし、行で読む読み方をスキーマで選べる](schema-language.ja.md#読み方は段落を既定にし行で読む読み方をスキーマで選べる)で決める。

どちらの読み方でも、一覧の行そのものの読み分けは[一覧の行は、宣言した名前と一致すればフィールド行、一致しなければ箇条書きとして読む](#一覧の行は宣言した名前と一致すればフィールド行一致しなければ箇条書きとして読む)のとおりで、子の一覧は[箇条書きの子の一覧は、宣言した子の規則に照らす](#箇条書きの子の一覧は宣言した子の規則に照らす)のとおりである。

| 行の形 | "paragraph" | "line" |
|---|---|---|
| CommonMark の ATX 見出しの行（[見出しと表は、どちらの読み方でも CommonMark と GFM のとおりに読む](#見出しと表はどちらの読み方でも-commonmark-と-gfm-のとおりに読む)） | 見出し | 見出し |
| それ以外の "#" で始まる行（"#foo"、7つ以上の "#" の行） | 文 | 文 |
| 文の次の、"===" か "---" だけの行 | 前の行とあわせて1つの見出し | 前の行も、その行も文 |
| 空行で区切らずに続く、一覧でも表でもない複数の行 | まとめて1つの文 | 1行ずつ文 |
| 一覧の行の直後に空行なしで続く、一覧の行でない行 | 直前の一覧の行の一部（フィールド行なら値に入る） | 文 |
| 一覧の行の後に空行を挟み、字下げして続く、一覧の行でない行 | 継続段落 | 文 |
| 一覧の行の後に字下げして続く一覧の行 | 一覧の行 | 一覧の行 |
| 引用、水平線、HTML、画像の行 | 引用、水平線、HTML のブロックは、"open: true" を宣言しないノードの中では undeclared_line（[段落で読むとき、"open: true" を宣言しないノードの中の引用、HTML のブロック、水平線は指摘にする](#段落で読むときopen-true-を宣言しないノードの中の引用html-のブロック水平線は指摘にする)）。画像の行は文に数えず、指摘にもしない | 文 |
| 一覧の行の後でない所で、空行の後に4つ以上の空白で字下げした行 | 字下げのコードブロック | 文（フェンスの開始の行は次の行のとおり） |
| "```" か "~~~" のフェンスで囲んだブロック | コードブロック | コードブロック（開始の行の字下げの深さを問わない） |
| GFM の表（見出しの行と区切りの行を持つ並び。縦棒で始まらなくてもよい。終わりは GFM のとおり） | 表 | 表 |
| 区切りの行を持たず表にならない、縦棒で始まる行 | 文 | 文 |

段落で読むときの続く行と継続段落の扱いは[段落で読むとき、一覧の行に続く行と継続段落は、その一覧の行の一部にする](#段落で読むとき一覧の行に続く行と継続段落はその一覧の行の一部にする)、文の数え方は[段落で読むとき、空行で区切った段落を1つの文として数える](#段落で読むとき空行で区切った段落を1つの文として数える)で決める。

### 見送った案

- kotowari が生の行を読んで、文を補う。「kotowari は Markdown を読まない」に反する。
- エンジンの既定の読み方を、行単位に変える。mds の利用者の結果が変わる。

### 確認すること

- C-schema-block-9 "reading: line" のスキーマでは、フィールド行の直後に空行を挟まずに続く行も、一覧の行の後に空行を挟んで字下げした行も文になり、一覧の行の値に入らない（"kotowari-mds values --format json" でフィールド行の値はその行の値だけになり、次の行は文の要素として出る）
- C-schema-block-10 "reading: line" のスキーマでは、引用、水平線、HTML、画像だけの行が、それぞれ文として読まれる
- C-schema-block-11 "reading: line" のスキーマでは、文の次の "---" や "===" だけの行で見出しを作らず、空行の後に4つの空白で字下げした行で字下げのコードブロックを作らず、どれも文になる
- C-schema-block-12 区切りの行を持たない "| a | b |" のような縦棒の行は、"reading: paragraph" でも "reading: line" でも文になる
- C-schema-block-13 一覧の行の入れ子は、どちらの読み方でも同じに読まれ、"reading: line" でも、字下げした一覧の行は文でなく一覧の行のままである
- C-schema-block-14 "```" か "~~~" のフェンスで囲んだブロックは、一覧のマーカーの行で開いたものも含めて、どちらの読み方でも同じコードブロックとして読まれる

## 段落で読むとき、一覧の行に続く行と継続段落は、その一覧の行の一部にする

状態: 実装済み

### 問題

段落で読むときは CommonMark の読み方を既定として残す（[見出しの下の行は、スキーマが選ぶ読み方（段落か行）で読む](#見出しの下の行はスキーマが選ぶ読み方段落か行で読む)）。CommonMark では、一覧の行に続く行や、空行を挟んで字下げした段落は、その一覧の項目に属する。これを文として数えるか、一覧の行の一部とするかを決める必要がある。

### 決めたこと

段落で読む間は、一覧の行の直後に空行を挟まずに続く行を、その一覧の行の一部として読む。フィールド行なら値に入る。一覧の行の後に空行を挟んで字下げして続く段落は、継続段落として、直前の一覧の行の一部として読む。どちらも文には数えず、閉じた世界でも指摘にしない。

行で読む間は、継続段落を作らない。

### 確認すること

- C-schema-block-15 "reading" を書かないスキーマでは、フィールド行の次に空行を挟まず続く行はその値に入り、空行を挟んで字下げした継続段落は直前の一覧の行に付き、どちらも文に数えられず、閉じた世界でも指摘にならない（"kotowari-mds check --format json" で指摘が1件も出ない）

## 段落で読むとき、空行で区切った段落を1つの文として数える

状態: 実装済み

### 問題

段落で読むときの文の数え方を決める必要がある。CommonMark では、空行で区切らずに続く複数の行は1つの段落で、引用、水平線、HTML、画像は段落ではない。mds の既定の読み方はこれに合わせて残す。決めた中身そのものの理由は残っていない。

### 決めたこと

段落で読む間は、空行で区切った段落を1つの文として数える。画像だけの行は文に数えず、閉じた世界でも指摘にしない。引用、水平線、HTML のブロックの扱いは、[段落で読むとき、"open: true" を宣言しないノードの中の引用、HTML のブロック、水平線は指摘にする](#段落で読むときopen-true-を宣言しないノードの中の引用html-のブロック水平線は指摘にする)で決めている。

### 確認すること

- C-schema-block-16 段落で読むと、空行で区切らずに続く複数の行は1つの文として数えられ、画像だけの行は、文に数えられず、閉じた世界でも指摘にならない

## 見出しと表は、どちらの読み方でも CommonMark と GFM のとおりに読む

状態: 実装済み

### 問題

mds は kotowari に縛られない汎用のエンジンで、kotowari は mds に依存するが、逆の依存は無い。行で読む読み方を足したとき、見出しの条件を kotowari の以前の読み方（"#" の直後に空白があり、"#" の数に上限が無い）に合わせていたので、"####### x" や行頭に空白のある "## x" が、読み方によって違う読まれ方になっていた。表も、段落で読むと表になるのに、行で読むと文になるものがあった。

### 決めたこと

見出しは、どちらの読み方でも、CommonMark の ATX 見出しの行だけにする。行頭の空白が3つまでで、"#" が1〜6個あり、その後が空白か行末の行である。"#" だけの行も見出しになる。"#foo" と、7つ以上の "#" の行は文になる。

表は、どちらの読み方でも GFM の表にする。見出しの行と区切りの行を持つ並びで、縦棒で始まらなくてもよい。表の終わりも GFM のとおりにする。

### 見送った案

- kotowari の以前の読み方と同じ条件（"#" の直後に空白、"#" の数に上限なし）を、行で読むときだけ使う。mds に kotowari 固有の読み方を持ち込むことになる。

### 確認すること

- C-schema-block-17 行頭に空白が2つある "  ## x" と "#" だけの行は見出しとして、"####### y" と "#z" の行は文として読まれ、"reading: paragraph" と "reading: line" で "kotowari-mds check --format json" の出力が一致する。"reading: line" では、4つの空白で字下げした "## y" の行は文になる
- C-schema-block-18 "a | b" と "--- | ---" のように縦棒で始まらない GFM の表や、見出しの行か区切りの行に縦棒の欠けた GFM の表は、"reading: line" でも表として読まれ、抽出される

## 行で読むとき、フェンスの開始の行は字下げの深さを問わない

状態: 実装済み

### 問題

行で読むときは、字下げのコードブロックを作らない。一覧の行も、続く行を吸わない。そのため、一覧の下に字下げして書いたフェンスは、字下げの深さを問わないことでしかコードブロックにならない。CommonMark に合わせて字下げを3つまでにすると、字下げしたフェンスの開始と閉じの行とその中身が、1行ずつ文になる。

### 決めたこと

"reading: line" のとき、"```" か "~~~" のフェンスの開始の行は、字下げの深さを問わずフェンスの開始として読み、そのブロックをコードブロックにする。"reading: paragraph" の読み方は変えない。

### 見送った案

- CommonMark と同じく、字下げが3つまでの行だけをフェンスの開始にする。一覧の下のフェンスが壊れ、誤りに気づきにくい。

### 確認すること

- C-schema-block-19 "reading: line" のスキーマで、文の後に空行を挟み、4つの空白で字下げした "```" の行で囲んだブロックは、コードブロックとして読まれ、フェンスの行とその中の行は文の要素として出ない

## 箇条書きの子の一覧は、宣言した子の規則に照らす

状態: 実装済み

### 問題

箇条書きの下に、字下げした子の一覧を書く書式がある。検査の既定は閉じた世界で、書式を固定するのが目的なので、宣言していない子の行を黙って通すと目的を果たさない。理由は、閉じた世界の理由のほかは残っていない。

### 決めたこと

箇条書きに子の一覧があるとき、スキーマが宣言した子の規則 "children" に照らす。子の規則を宣言していない箇条書きやフィールド行の子の行は、閉じた世界の決まり（[既定は閉じた世界にし、宣言していない見出しと行を指摘にする](closed-world.ja.md#既定は閉じた世界にし宣言していない見出しと行を指摘にする)）のとおり、指摘にする。

子の規則には、フィールド行と箇条書きを宣言できる。子の箇条書きは、さらに子の規則を持てる。子の行の読み分けは、一覧の行の読み分け（[一覧の行は、宣言した名前と一致すればフィールド行、一致しなければ箇条書きとして読む](#一覧の行は宣言した名前と一致すればフィールド行一致しなければ箇条書きとして読む)）と同じで、特定の名前を特別扱いしない。

子の箇条書きに抽出を宣言したスキーマは、停止にする。子のフィールド行の抽出の値の置き場は[値は、配置パスが指す場所に、ドットで区切った名前の入れ子で置く](extraction.ja.md#値は配置パスが指す場所にドットで区切った名前の入れ子で置く)のとおりである。

### 確認すること

- C-schema-block-20 子の規則を宣言していない箇条書きやフィールド行の下にある子の行（子の一覧、字下げして続く表やコードブロック）は、undeclared_line の指摘になる
- C-schema-block-21 子の規則にフィールド行と箇条書きを宣言でき、子の箇条書きはさらに子の規則を持て、子の行は親の数に入らずに親の子として読まれ、宣言していない名前の子の行は子の箇条書きとして照合される
- C-schema-block-22 子の箇条書きに抽出を宣言したスキーマは、停止になる

## 表のヘッダは、宣言したときだけ照合する

- C-schema-block-24 "header" を宣言した表の規則では、ヘッダが宣言と合わない表に table_header_mismatch の指摘が出る

## 表の列数は文書のヘッダ行に合わせ、余ったセルは捨てる

状態: 実装済み

### 問題

GFM の表の定めでは、ヘッダより多いセルは捨てる。mds はこれと違って、余ったセルのある行を指摘にしていた。

また、列数をスキーマが宣言したヘッダで照合すると、文書のヘッダ行が宣言と違う表では、1つの原因（ヘッダの行）から、データ行の数だけ指摘が連鎖する。データ行は自分の表のヘッダとは合っている。余ったセルを捨てるのは、行を文書のヘッダに合わせて読むことなので、宣言したヘッダの列数で比べ直すと、捨てたセルで指摘することになり、両立しない。

### 決めたこと

表の列数の照合は、スキーマが宣言したヘッダではなく、文書のヘッダ行の列数を基準にする。

セルが文書のヘッダ行より多いデータ行は、ヘッダの宣言に依らず、余ったセルを捨てて指摘にしない。セルが文書のヘッダ行より少ないデータ行は、指摘にする。

文書のヘッダ行が宣言と違う表では、ヘッダの食い違いの指摘を1件だけ出し、データ行ごとの列数の指摘は出さない。

### 見送った案

- 宣言したヘッダの列数でも、データ行を照合する。ヘッダを直したあとに検査し直せば、同じ行が分かる。

### 確認すること

- C-schema-block-25 3つのセルのヘッダの表で、4つのセルのデータ行には指摘が出ず、その行の抽出の値は先頭の3つのセルだけを持ち、2つのセルのデータ行には、その行を指す指摘が1件出る
- C-schema-block-26 文書のヘッダ行が宣言と違う表では、ヘッダの食い違いの指摘が1件だけ出て、文書のヘッダ行と列数の合うデータ行には指摘が出ない

## 表の規則は、"select: first" でヘッダの合う最初の表だけを選べる

状態: 実装済み

### 問題

同じ置き場に、ヘッダの合う表と合わない表が並ぶ書式がある（題名の後に用語の表を置き、ほかの表も置ける、など）。抽出の値には表のヘッダ行の文字が入らないので、値を読む側では、どの表がヘッダの合う表かを見分けられない。それでも、検査の既定（ヘッダの合わない表は指摘）は変えない。

"select" は、ヘッダを持たない表の規則では「ヘッダが合う」が決まらない。"select" の値の範囲を決めておかないと、実装の型の選び方で、知らない値が停止になるか無視されるかが変わる。"reading" の知らない値と同じ扱いにする。

### 決めたこと

表の規則が "header" と一緒に "select: first" を宣言したとき、その規則を置いたノードの中で、ヘッダが宣言と合う最初の表だけを、その規則の表として検査と抽出に使う。ほかの表は、ヘッダが合っても合わなくても、宣言していない表として扱う。

"select" を書かない表の規則は、今までどおり、ヘッダの合わない表を形の違反の指摘にする。

"header" なしで "select" を書いたスキーマと、"select" に "first" 以外の値を書いたスキーマは、停止にする。

### 確認すること

- C-schema-block-27 "header" と "select: first" を宣言した表の規則では、ヘッダの合う最初の表のデータ行だけが抽出され、ほかの表は宣言していない表の指摘になってヘッダの形の違反の指摘は出ず、規則を置いたノードが繰り返し現れるときは出現ごとに1つの表が選ばれる
- C-schema-block-28 "header" を書かずに "select: first" を宣言したスキーマと、"select: last" のように "first" 以外の値を書いたスキーマでは、"kotowari-mds check" の終了コードが 2 になる

## コードブロックの言語は宣言したときだけ照合し、行の照合は行頭の空白を除いて行う

状態: 実装済み

### 問題

コードブロックの言語と、中の行の形を、スキーマで縛れるようにしたい。理由は残っていない。

### 決めたこと

コードブロックの規則に、言語と、行ごとの正規表現を宣言できる。言語を宣言したときだけ言語を照合し、合わなければ codeblock_lang_mismatch の指摘にする。

行ごとの正規表現は、行頭の空白を取り除いてから照合し、取り除いた結果が空の行は照合しない。合わない行は codeblock_line_mismatch の指摘にする。

### 確認すること

- C-schema-block-29 言語を宣言したコードブロックの規則では、言語の違うコードブロックに codeblock_lang_mismatch の指摘が出る
- C-schema-block-30 行ごとの正規表現を宣言したコードブロックの規則では、行頭の空白を除いた行が照合され、空の行は照合されず、合わない行に codeblock_line_mismatch の指摘が出る

## 表とコードブロックの規則は、項目にも節と同じに宣言できる

状態: 実装済み

### 問題

見出しの下に表を持つ決定表のような項目を、検査できるようにしたい。節には表とコードブロックを宣言できて、項目には宣言できないのは、非対称である。

### 決めたこと

項目にも、表とコードブロックの規則を宣言できる。規則の中身、既定の出現回数、指摘の種類は、節に宣言したときと同じにする。どの規則種別をどこに置けるかの全体は[規則種別は9つにし、それぞれ置ける場所を決める](schema-language.ja.md#規則種別は9つにしそれぞれ置ける場所を決める)で決める。

### 確認すること

- C-schema-block-31 項目に宣言した表とコードブロックは宣言していない行の指摘にならず、項目の表のヘッダが宣言と合わなければ、節と同じく table_header_mismatch の指摘になる

## 箇条書きの正規表現は、一覧の項目の先頭の段落を1行につないだ文字と照合する

状態: 提案

### 問題

箇条書きの正規表現は、マーカーの行の、マーカーを除いた部分とだけ照合する。行を折り返して書いた箇条書きでは、正規表現も名前付きキャプチャも、2行目からの文字を見ない。フィールド行の値には、空行を挟まずに続く行も入るので、箇条書きとフィールド行で読み方がそろわない。kotowari の決定の文書は、確認することの行から名前付きキャプチャで ID と名前を切り出すので、折り返した行の名前が欠ける。

### 決めたこと

箇条書きの正規表現と、その名前付きキャプチャ（[名前付きキャプチャは、題名と箇条書きの of の鍵の値に group で書く](extraction.ja.md#名前付きキャプチャは題名と箇条書きの-of-の鍵の値に-group-で書く)）は、一覧の項目の先頭の段落と照合する。照合する文字は、先頭の段落の各行の前後の空白を除き、行の区切りを空白1つにしてつないだもので、マーカーを含めない。継続段落と子の一覧は照合しない。

### 見送った案

- 以前の決定: 箇条書きの照合は、マーカーの行のマーカーを除いた部分にだけ行い、マーカーの行に空行を挟まずに続く行には照合しない（[文と箇条書きの行に正規表現を課し、文には許可リストも課せる](#文と箇条書きの行に正規表現を課し文には許可リストも課せる)の決めたことの2段目）。折り返した箇条書きの残りの文字を、正規表現とキャプチャが見ないので、やめた。
- マーカーの行だけの照合を残し、折り返した名前は mds を使う側（kotowari）がつなぐ。使う側が一覧の項目を読み直すことになる。

### 確認すること

- C-schema-block-32 "reading" を書かないスキーマで、マーカーの行 "- a b" に空行を挟まずに "  c" の行が続く箇条書きは、正規表現 "^a b c$" に合って指摘が出ず、正規表現 "^a b$" には合わずに bullet_pattern_mismatch になる
- C-schema-block-33 先頭の段落が "a" で、空行を挟んで字下げした継続段落 "b" と子の一覧 "- c" を持つ箇条書きは、正規表現 "^a$" に合い、指摘が出ない

## 段落で読むとき、"open: true" を宣言しないノードの中の引用、HTML のブロック、水平線は指摘にする

状態: 実装済み

### 問題

段落で読むとき、引用、HTML のブロック、水平線は、文に数えず、閉じた世界でも指摘にしない。書式を固定するための閉じた世界の中で、これらは検査されずに黙って通る。kotowari が決定の文書を読むのに使っていた自前の読み取りは、状態の行の場所と「未決」の節で、これらを誤りにしていた。

### 決めたこと

段落で読むとき、"open: true"（[前置部・節・項目・箇条書きの子は、"open: true" を宣言すると、規則の無いブロックを受ける](schema-language.ja.md#前置部節項目箇条書きの子はopen-true-を宣言すると規則の無いブロックを受ける)）を宣言しないノードの中の引用、HTML のブロック、水平線は、undeclared_line の指摘にする。"open: true" を宣言したノードの中では、指摘にしない。開いた世界で許す、宣言していない構造の内側では、ほかの行と同じく許す（[開いた世界は、宣言していない構造とその内側だけを許す](closed-world.ja.md#開いた世界は宣言していない構造とその内側だけを許す)）。

画像だけの段落、リンクの参照定義、HTML のコメントだけのブロックは、どのノードの中でも、文に数えず、指摘にもしない。HTML のコメントは、文書を書く人やツールのための書き込み（kotowari のマーカーも HTML のコメントに書く）で、文書の中身ではないためである。

行で読むときの読み方（引用、水平線、HTML、画像の行を文にする）は、[見出しの下の行は、スキーマが選ぶ読み方（段落か行）で読む](#見出しの下の行はスキーマが選ぶ読み方段落か行で読む)のとおりで、この決定は変えない。

### 見送った案

- 以前の決定: 段落で読むとき、引用、水平線、HTML、画像だけの行は、文に数えず、閉じた世界でも指摘にしない（[段落で読むとき、空行で区切った段落を1つの文として数える](#段落で読むとき空行で区切った段落を1つの文として数える)の決めたことの2文目と、[見出しの下の行は、スキーマが選ぶ読み方（段落か行）で読む](#見出しの下の行はスキーマが選ぶ読み方段落か行で読む)の表の「引用、水平線、HTML、画像の行」の行の "paragraph" の列）。宣言していないものが閉じた世界で黙って通るので、引用、HTML のブロック、水平線について、やめた。

### 確認すること

- C-schema-block-34 "reading" を書かないスキーマで、"open" を書かない節の中の引用、HTML のブロック、水平線には、それぞれの開始の行に undeclared_line の指摘が出る
- C-schema-block-35 "reading" を書かないスキーマで、"open" を書かない節の中の画像だけの段落とリンクの参照定義には、指摘が出ない
- C-schema-block-36 "open: true" を宣言した節の中の引用、HTML のブロック、水平線には、指摘が出ない
- C-schema-block-37 スキーマの最上位に "open: true" を書いても、宣言した節の中の引用には undeclared_line の指摘が出る
- C-schema-block-41 "reading" を書かないスキーマで、"open" を書かない節の中の HTML のコメントだけのブロックには、指摘が出ない

## 閉じないフェンスは、どのスキーマでも unclosed_codeblock の指摘にする

状態: 提案

### 問題

"```" か "~~~" で開いたフェンスが閉じられずに文書が終わると、CommonMark は文書の終わりまでをコードブロックの中身にする。その後の見出しと行は中身になり、検査されない。mds には、これを表す指摘の種類が無く、文書はスキーマを満たしたものとして通る。kotowari は、決定の文書の閉じないコードブロックを、自前のコードで探して誤りにしていた。

### 決めたこと

フェンスで開いたコードブロックが閉じられずに文書が終わるときは、unclosed_codeblock の指摘を出す。指摘の行はフェンスの開始の行にし、生の行はその行の文字にする。

この指摘は、どのスキーマでも出す。閉じた世界でも開いた世界でも、"open: true" を宣言したノードの中でも、宣言していない構造の中でも、一覧の項目の中で開いたフェンスでも出す。段落で読むときも行で読むときも出す。行で読むときは、[行で読むとき、フェンスの開始の行は字下げの深さを問わない](#行で読むときフェンスの開始の行は字下げの深さを問わない)のとおりに開いたフェンスが、閉じる行の無いまま文書の終わりに届いたものを指摘にする。

### 確認すること

- C-schema-block-38 スキーマを満たした段落の後に "```" で開いて閉じない文書では、"kotowari-mds check --format json" に、開始の行の行番号と生の行を持つ unclosed_codeblock の指摘が出て、終了コードは 1 になる
- C-schema-block-39 一覧の項目の中で字下げして開き、閉じないフェンスにも、"open: true" のスキーマでも、"reading: line" のスキーマでも、unclosed_codeblock の指摘が出る
- C-schema-block-40 閉じたフェンスだけを持つ文書には、unclosed_codeblock の指摘が出ない
