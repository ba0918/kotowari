# ライブラリの入口

[English](library.md) | 日本語

ファイルを読まない純粋なライブラリ `kotowari-markdown-schema` が公開する入口と、読み書きをどこが受け持つかを扱う。検証と抽出の入口の振る舞いは[「検証と値の抽出」の話題](library-extraction.ja.md)で、ファイルと URL からの読み込みは[「読み込みのライブラリ」の話題](library-io.ja.md)で決める。

## 依存するクレートは、決めた入口だけで参照の読み取りから抽出までを通せる

状態: 実装済み

### 問題

kotowari は、mds を CLI として起動するのではなく、クレートとして使う。利用者に2つ目のバイナリの導入を求めずに済み、版のずれがコンパイルのときに分かるからである。ただ、依存するクレートが仕様に書いていない公開項目に頼ると、仕様と実装を機械で突き合わせることが、その境界だけ抜けてしまう。

また、下位のクレートに直接依存する利用者にも、公開 API をどう変えていくかの方針をはっきりさせたい。

### 決めたこと

`kotowari-markdown-schema` は、次の入口を公開する。

| 入口 | 何をするか |
|---|---|
| `frontmatter_schema` | 文書の文字列から "$schema" の参照を読み、参照か、参照が無いことを返す |
| `resolve_schema` | 文書の位置と参照から、スキーマの位置（ファイルのパスか URL）を決める |
| `Schema::parse` | スキーマの YAML を解析する（[スキーマは意味の検査を通したものだけを返し、解析済みのものを繰り返し使える](library-extraction.ja.md#スキーマは意味の検査を通したものだけを返し解析済みのものを繰り返し使える)） |
| `Document::parse` | 文書の文字列を読み、文書の構造を返す |
| `validate` | スキーマと文書を `ValidationOptions` に従って検証し、指摘の並びを返す（[ライブラリの検証は、スキーマの open を打ち消さない](library-extraction.ja.md#ライブラリの検証はスキーマの-open-を打ち消さない)） |
| `extract_validated` | 検証し、違反が無いときだけ値を返す（[値の抽出の通常の入口は、違反の無い文書からだけ値を返す](library-extraction.ja.md#値の抽出の通常の入口は違反の無い文書からだけ値を返す)） |
| `extract_partial` | 指摘と、取れた値を返す（同上） |
| `ast_json` | 素の構文木の JSON を作る（[CLI の values と ast --schema は、違反のある文書でも今までどおり値を出す](library-extraction.ja.md#cli-の-values-と-ast---schema-は違反のある文書でも今までどおり値を出す)） |
| `extract_typed_partial` | 型付きの抽出の JSON を作る（同上） |

公開した入口と、その入出力の型は、すべて互換性を管理する対象にする。公開している項目を「実装の都合なので、いつ変わってもよい」とは扱わない。

### 見送った案

- 以前の決定: 依存するクレートが契約として当てにしてよい入口だけを列挙し、列挙に無い公開項目は、いつ変わってもよい実装の都合とする。下位のクレートも公開 API の互換性を管理する対象にすると決めたので、公開したものはすべて契約として扱い、内部の実装は公開しない（[内部の実装の型を、公開の署名に出さない](#内部の実装の型を公開の署名に出さない)）ことにした。
- kotowari から mds の CLI を起動して、出力の JSON を読む。利用者に mds の導入を求めることになり、版のずれが実行のときにしか分からない。性能の差は、測って無視できる程度だった。

### 確認すること

- C-schema-lib-1 スキーマを宣言した文書の文字列から、公開の入口だけを順に呼んで、"$schema" の参照、スキーマの位置、指摘の並び、抽出の値、素の構文木の JSON が得られる

## 内部の実装の型を、公開の署名に出さない

状態: 実装済み

### 問題

Markdown の解析の道具が持つ構文木の型や、内部の検索の道具の型を公開すると、外の利用者が内部の実装の型に頼ることになる。

指摘の欄は、すでに crate の中だけにしてあり、外から要るのは読む口だけである。それなのに指摘を作る関数が公開されていると、検証を通らない作り方が公開に残る。

### 決めたこと

公開の署名に、`markdown::mdast::Node` と `regex::Captures` を含めない。抽出の値と構文木の JSON は、既存の抽出の約束どおり `serde_json::Value` で渡す。

指摘（`Finding`）を作る関数（`new`、`at`、`maybe_at`、`of_node`、`of_rule`）は crate の中だけにし、外には指摘を読む口だけを公開する。

### 確認すること

- C-schema-lib-2 （読んで確認）`kotowari-markdown-schema` の公開の署名に、`markdown::mdast::Node` と `regex::Captures` が出てこない
- C-schema-lib-3 （読んで確認）指摘を作る関数は、crate の外から呼べない
- C-schema-lib-4 `validate` が返した指摘から、公開の読む口で、指摘の種類、行、詳細を読める

## ライブラリはファイルを読まず、URL のスキーマも取得しない

状態: 実装済み

### 問題

スキーマの言語、検査、抽出の核は、kotowari の中から使い回せるように、CLI のフレームワークに依存しない別のクレートに置く。

メモリの上の検査だけを使う利用者に、ファイルの探索や HTTP の取得のための依存を求めたくない。依存の向きをコンパイラで縛るためでもある。そのためにクレートの数とリリースの手間が増えることは、受け入れた。

### 決めたこと

`kotowari-markdown-schema` は、文書とスキーマのファイルを読まず、URL のスキーマも取得しない。`resolve_schema` は、スキーマの位置（ファイルのパスか URL）を決めるところまでを行う。読み書きは、呼び出し側か、ファイルと URL から読む別のクレート（[スキーマと文書の読み込みは、別のクレートに置いて CLI と外のアプリで共用する](library-io.ja.md#スキーマと文書の読み込みは別のクレートに置いて-cli-と外のアプリで共用する)）が受け持つ。

### 確認すること

- C-schema-lib-5 URL のスキーマを宣言した文書では、`resolve_schema` が URL を返し、取得は行われない
- C-schema-lib-6 （読んで確認）`kotowari-markdown-schema` は、ファイルを読むコードも、HTTP で取得するための依存も持たない
