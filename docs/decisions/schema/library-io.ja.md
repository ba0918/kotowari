# スキーマと文書を読み込むライブラリ

[English](library-io.md) | 日本語

ファイルと URL からスキーマと文書を読む別のクレート `kotowari-markdown-schema-io` の入口と、既存の CLI の読み込みの規則をそのまま使い回すことを扱う。ファイルを読まない純粋なライブラリの側は[「ライブラリの入口」の話題](library.ja.md)で、読み込んだあとの検証と抽出は[「検証と値の抽出」の話題](library-extraction.ja.md)で決める。

## スキーマと文書の読み込みは、別のクレートに置いて CLI と外のアプリで共用する

状態: 実装済み

### 問題

文字列から検査する利用者の依存は増やしたくない（[ライブラリはファイルを読まず、URL のスキーマも取得しない](library.ja.md#ライブラリはファイルを読まずurl-のスキーマも取得しない)）。一方で、CLI がしているのと同じ読み込みを、外のアプリでも使い回せるようにしたい。

内部を作り直しても、既存の CLI のコマンド、引数、終了コード、出力の約束と、スキーマの受け付け方は壊さない。CLI の利用者の入力や処理を壊さないためである。

読み込みの入口は、複数のプロジェクトを同じプロセスで扱えるものにする。入口がプロセスのカレントディレクトリを書き換えると、同じプロセスのほかの処理が読む位置まで変わる。

### 決めたこと

ファイルと URL からスキーマと文書を読む処理は、`kotowari-markdown-schema-io` に置く。既存の CLI のファイルの探索、URL の解決、キャッシュ、取得の上限とタイムアウトの規則を、そのままこのクレートに移す（規則は[「CLI と結果の出し方」](cli.ja.md#ディレクトリの検査はschema-を持つ文書だけを検査し-で始まるディレクトリとシンボリックリンクを辿らない)と[「スキーマの解決」](schema-resolution.ja.md)の話題で決める）。キャッシュの場所と寿命も既存のままにする。mds の CLI も、外のアプリも、このクレートを使う。

`SchemaLoader` の読み込みは、プロセスのカレントディレクトリを変えない。

入口は `SchemaLoader::new` で、`LoaderOptions` で作業開始位置と、任意のキャッシュ基準を受ける。作業開始位置とキャッシュ基準の扱いは、kotowari のライブラリの入口と共通で、「ライブラリ入力のパス」の話題で決める。

`load` は、読み込んだスキーマと文書の組を返し、その組は検証と抽出に繰り返し使える。`check` は1つのファイルかディレクトリの検査の結果を、`extract_validated` と `extract_partial` はそれぞれの抽出の結果を返す（2つの違いは[値の抽出の通常の入口は、違反の無い文書からだけ値を返す](library-extraction.ja.md#値の抽出の通常の入口は違反の無い文書からだけ値を返す)で決める）。

### 確認すること

- C-schema-io-1 `SchemaLoader` で `load` したスキーマと文書の組で検証と抽出を繰り返せ、`SchemaLoader` の `check`、`extract_validated`、`extract_partial` に同じ文書のパスを渡しても、同じ文書の結果が返る
- C-schema-io-2 `SchemaLoader` の `check` がディレクトリから選ぶ文書は、mds の `check` が同じディレクトリから選ぶ文書と同じになる
- C-schema-io-8 `SchemaLoader` の `load` を呼んでも、プロセスのカレントディレクトリは変わらない

## 文書だけを読む入口を公開し、mds の ast もそれを使う

状態: 実装済み

### 問題

文書を読むときの規則（先頭の BOM の扱いと、UTF-8 かどうかの判定）を、2か所に持ちたくない。入口を足すのは公開 API の追加で、壊れる変更ではない。

### 決めたこと

`read_document` は、文書を `load` と同じ読み方で読み、先頭の UTF-8 の BOM を除いた文字列を返す。スキーマは解かない。UTF-8 として読めない文書は、読めない失敗にする。

mds の `ast` は、この入口で文書を読む。

### 確認すること

- C-schema-io-3 `read_document` は、先頭の BOM を除いた文字列を返し、UTF-8 でない文書には読めない失敗を返す
- C-schema-io-4 （読んで確認）mds の `ast` は、文書を `read_document` で読む

## 読み込みの失敗は、文書の指摘と分けて返す

状態: 実装済み

### 問題

呼び出し側が、文書に問題が見つかった検査の結果と、読み込めずに検査を終えられなかった失敗とを、別々に扱えるようにしたい。

### 決めたこと

文書の検査を終えて見つかった指摘は、検査の結果として返す。検査を終えられない失敗（例えば、スキーマが見つからない、スキーマが壊れている、文書を読めない）は、`Result` の `Err` として、種類を見分けられる形で返す。失敗の型は `std::error::Error` と `Display` を実装する。

### 確認すること

- C-schema-io-5 スキーマが見つからない、スキーマが壊れている、文書が読めない、のどのときも、`load` と `check` は検査の結果ではなく、種類を見分けられる失敗を返す

## Tokio の feature を選んだ呼び出しにも、同期と同じ結果を返す

状態: 実装済み

### 問題

非同期のアプリからも使えるようにしたい。そのとき、同期の検査と、既存の読み込みの処理は使い回したい。

非同期のために利用者が選ぶパッケージは増やさず、同期で使う利用者には Tokio への依存を求めない。

### 決めたこと

`kotowari-markdown-schema-io` は、既定で無効な `tokio` feature で `AsyncSchemaLoader` を提供する。`AsyncSchemaLoader` は同期の読み込みの処理を使い回し、同じ入力には、同期の `SchemaLoader` と同じ値、指摘、失敗の種類を返す。ファイルを読まない `kotowari-markdown-schema` は Tokio に依存しない。CLI は同期の API を使う。

同時に動かす数の上限、複製したオブジェクトどうしの実行枠、待機を取り消したときに始まった処理が止まらないこと、どのランタイムの上で動くかは、kotowari の非同期の入口と共通で、「任意の Tokio 対応」の話題で決める。

### 見送った案

- 同期の API と、非同期のアプリから呼ぶ利用例だけを出す。利用者は、高水準の操作を await できる Tokio 対応まで出す案を選んだ。
- HTTP の取得の待ちを非同期の I/O で作り直し、始まった処理を途中で止める仕組みも足す。利用者は、同期の処理を使い回して非同期のアプリから呼べるようにする案を選んだ。

### 確認すること

- C-schema-io-6 `tokio` feature を有効にすると、`AsyncSchemaLoader` の `load`、`check`、`extract_validated`、`extract_partial` が、Tokio の上で、同期の `SchemaLoader` と同じ値、指摘、失敗の種類を返す
- C-schema-io-7 （読んで確認）`tokio` feature は既定で無効で、`kotowari-markdown-schema` は Tokio に依存しない
