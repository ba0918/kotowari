# スキーマ言語の骨格

[English](schema-language.md) | 日本語

スキーマがどの規則種別を持つか、出現回数と条件付き規則をどう書くか、見出しの下の行をどの読み方で読むかを扱う。文書がスキーマをどう指すかは[「スキーマの解決」の話題](schema-resolution.ja.md)で決める。

## スキーマは YAML で書き、題名・前置部・節・文書の直下の項目を根に置く

状態: 実装済み

### 問題

スキーマは型付きで読める形で書きたい。対象にする文書の形は、見出しが3段（題名、節、項目）あれば足りる。任意の深さの入れ子は、規則と抽出の両方を複雑にする。

項目を節の下にしか宣言できないと、節を挟まずに項目を並べる文書の形を検査できない。

### 決めたこと

スキーマは YAML のマッピングとして書く。根のノードは、題名、前置部、節、文書の直下の項目の4つにする。

文書の直下の項目は "document.items" に、節の下の "items" と同じ形の規則の一覧で宣言する。これを宣言したスキーマでは、前置部は最初の "## " か "### " の見出しの手前で終わる。宣言したときとしないときに文書の見出しをどう読むかは、[スキーマは、節を挟まない文書の直下の項目を "document.items" に宣言できる](document-structure.ja.md#スキーマは節を挟まない文書の直下の項目を-documentitems-に宣言できる)と[文書の直下の項目を宣言しないスキーマでは、最初の節より前の深さ3の見出しを、前置部を宣言したか閉じた世界のときだけ指摘にする](document-structure.ja.md#文書の直下の項目を宣言しないスキーマでは最初の節より前の深さ3の見出しを前置部を宣言したか閉じた世界のときだけ指摘にする)で決める。

### 見送った案

- スキーマを Markdown のルール行で書く。機械で検査できる形に落とすと独自の書き方になる。YAML のほうが型付きで読める。

### 確認すること

- C-schema-lang-1 題名、前置部、節と、その下の規則種別を宣言した YAML のスキーマが、そのとおりに読み込まれる

## 規則種別は10にし、それぞれ置ける場所を決める

状態: 実装済み

### 問題

見出しの下に表を持つ決定表のような項目を検査できるようにしたい。節には表やコードブロックを宣言できて項目にはできないのは非対称である。

ほかの規則種別とその置ける場所を決めた理由は残っていない。

### 決めたこと

スキーマの木の1要素をノードと呼び、検証と抽出の単位にする。ノードの種類（規則種別）は、次の10にする。

| 規則種別 | 何を検証するか | 置ける場所 |
|---|---|---|
| 題名 | 深さ1の見出し | スキーマの根 |
| 前置部 | 題名の後、最初の節より前の部分。文書の直下の項目を宣言したときは、最初の節か項目より前の部分 | スキーマの根 |
| 節 | 深さ2の見出し | スキーマの根 |
| 項目 | 深さ3の見出し | 節の下、スキーマの根（文書の直下の項目） |
| フィールド行 | 名前と値の形の一覧の行 | 前置部、節、項目、箇条書きの子 |
| 文 | 一覧でも表でもない空でない行 | 前置部、節、項目 |
| 箇条書き | フィールド行でない一覧の行 | 前置部、節、項目、箇条書きの子 |
| 表 | Markdown の表 | 前置部、節、項目 |
| コードブロック | フェンスで囲んだブロック | 前置部、節、項目 |
| 小見出し（"subheading"） | 深さ4以上の見出し | 前置部、節、項目 |

項目に宣言した表とコードブロックは、規則の中身、既定の出現回数、誤りの種類を、節に宣言したときと同じにする。前置部そのものが抽出を宣言しないことは、[前置部には、その内側のノードに規則と抽出を宣言する](document-structure.ja.md#前置部にはその内側のノードに規則と抽出を宣言する)で決める。

## スキーマに知らないキーや形に合わない値があれば、検査せずに停止する

状態: 実装済み

### 問題

読めない、壊れている、形に合わない入力を黙って飛ばすと、検査していない文書が通ったように見える。

### 決めたこと

スキーマに、規則種別が受けないキーがあるとき、mds は検査を行わずに停止する。YAML として読めないスキーマと、値が規則種別の形に合わないスキーマも、同じく停止する。停止をどう知らせるか（終了コードと停止の理由の名前）は、[停止の理由は5つにする](cli.ja.md#停止の理由は5つにする)で決める。

### 確認すること

- C-schema-lang-3 規則種別が受けないキーのあるスキーマは、箇条書きの下のキーも含めて、スキーマの誤りとして読み込まれない
- C-schema-lang-4 YAML として読めないスキーマと、値が規則種別の形に合わない（例えば、型が違う、正規表現として読めない、条件付き規則に比べ方が1つだけ書かれていない）スキーマは、スキーマの誤りとして読み込まれない

## 読み方は段落を既定にし、行で読む読み方をスキーマで選べる

状態: 実装済み

### 問題

mds は公開済みで、既定の読み方を変えると、mds の利用者の結果が変わる。一方で、見出しの下の行を1行ずつ文として数える文書の形も、mds の外で生の行を読まずに検査したい。

読み方の宣言は、"open" と同じ最上位の設定として読め、読み方を足すときに鍵を増やさずに済む形にしたい。受けない値の扱いは、[知らないキー](#スキーマに知らないキーや形に合わない値があれば検査せずに停止する)と同じにする。

### 決めたこと

スキーマの最上位の "reading" の鍵を、読み方の宣言として受ける。値は "paragraph"（CommonMark の段落として読む）と "line"（1行ずつ読む）の2つだけを受け、鍵を書かないときは "paragraph" として読む。"paragraph" と "line" のどちらでもない値のスキーマは停止する。

それぞれの読み方で、見出しの下の行をどう読み分けるかは、[見出しの下の行は、スキーマが選ぶ読み方（段落か行）で読む](block-rules.ja.md#見出しの下の行はスキーマが選ぶ読み方段落か行で読む)で決める。

### 見送った案

- エンジンの既定の読み方を行単位に変える。mds の利用者の結果が変わる。
- mds を使う側（kotowari）が生の行を読んで、文を補う。kotowari は Markdown を自分で読まない、という決まりに反する。

### 確認すること

- C-schema-lang-5 "reading" を書かないスキーマと、それに "reading: paragraph" だけを足したスキーマは、同じ文書に対して、check でも values でも同じ出力を返し、空行を挟まずに続く2行の段落を1つの文と数える
- C-schema-lang-6 "reading" の値が "paragraph" でも "line" でもないスキーマ（例えば "reading: word"）は、check が停止する

## 出現回数は5つの書き方で宣言する

状態: 実装済み

### 問題

理由は残っていない。

### 決めたこと

出現回数は、ノードが現れてよい個数の下限と上限とし、次の5つの書き方で宣言する。

| 書き方 | 意味 |
|---|---|
| 既定（何も書かない） | ちょうど1個 |
| 必須の宣言を偽にする | 0個か1個 |
| 下限だけを書く | その数以上 |
| 上限だけを書く | 0個からその数まで |
| 下限と上限を書く | その範囲 |

範囲の宣言は、必須の宣言を上書きする。下限を満たさないときは repeat_min_not_met、上限を超えるときは repeat_max_exceeded の指摘にする。

### 確認すること

- C-schema-lang-7 出現回数を書かないノードが文書に無ければ、欠落の指摘が出る
- C-schema-lang-8 必須の宣言を偽にしたノードは、無くても指摘が出ず、2個あれば repeat_max_exceeded の指摘が出る
- C-schema-lang-9 下限を書いたノードが下限に満たなければ repeat_min_not_met、上限を書いたノードが上限を超えれば repeat_max_exceeded の指摘が出る。上限だけを書いたノードは、無くても repeat_min_not_met の指摘が出ない
- C-schema-lang-10 下限と上限を同じ数で書いた出現回数は、スキーマの誤りにならない

## 出現回数の範囲を宣言したノードは、1件でも配列で抽出する

状態: 実装済み

### 問題

理由は残っていない。

### 決めたこと

出現回数の範囲を宣言したノードの抽出は、値が1件でも配列になる。範囲を宣言しないノードの抽出は、単一の値になる。この対応が当たるのは、区切り文字を宣言しないフィールド行、文、節、項目、題名、コードブロックである。

箇条書きと表、区切り文字を宣言したフィールド行の抽出の形は、[要素ごとに宣言した表が繰り返すときは表ごとの段を作り、それ以外は1つの配列につなぐ](extraction.ja.md#要素ごとに宣言した表が繰り返すときは表ごとの段を作りそれ以外は1つの配列につなぐ)と[区切り文字を宣言したフィールド行は、出現回数に関わらず配列にする](extraction.ja.md#区切り文字を宣言したフィールド行は出現回数に関わらず配列にする)で決める。

### 確認すること

- C-schema-lang-11 出現回数の範囲を宣言したフィールド行や節は、1件でも配列で抽出され、範囲を宣言しないフィールド行は単一の値で抽出される

## 条件付き規則は、条件が真の間だけ添えた制約を効かせる

状態: 実装済み

### 問題

理由は残っていない。

### 決めたこと

条件付き規則 "when" は、"required"、"pattern"、"enum" のどれにでも添えられ、条件が真の間だけ、その制約を効かせる。偽の間は効かせない。比べ方は、等しい（"eq"）と等しくない（"ne"）の2つで、右辺はリテラルの文字列だけを受ける。

条件が参照するフィールド行は、同じノードの下だけから探す。見つからないときは、等しい条件を偽、等しくない条件を真として扱う。

### 確認すること

- C-schema-lang-12 条件が真のときだけ、"when" を添えた制約が効く（必須のフィールド行が欠けると欠落の指摘が出る）。偽のときは効かず、"when" は添えた制約のほかの照合を止めない
- C-schema-lang-13 条件が参照するフィールド行は、同じノードの下（箇条書きの子なら、兄弟のフィールド行）から探され、見つからないときは "eq" の条件が偽、"ne" の条件が真になる

## 節と項目の規則は、見出しを名前の一覧か正規表現で選ぶ

状態: 実装済み

### 問題

節の規則は、1つの名前と等しい見出しだけを選ぶ。項目の規則は1つの節に1つだけで、どの深さ3の見出しにも "ID: 名前" の形を求める。そのため、次の形の文書を宣言できない。

- 同じ節を、2つの言語の綴り（"未決" と "Open"）のどちらでも書ける文書
- 節の見出しの文字が文書ごとに自由で、どの深さ2の見出しも同じ規則で読む文書
- 1つの節の下に、名前で見分ける複数の項目（"### 問題" と "### 決めたこと"）を並べる文書。項目の規則が1つなので見分けられず、"ID: 名前" の形でない見出しは invalid_id になる

kotowari の決定の文書は、この3つをすべて持ち、宣言できなかった。

### 決めたこと

節の規則と項目の規則は、見出しを次のどれかで選ぶ。

| 書き方 | 選ぶ見出し |
|---|---|
| "name" に文字列か、文字列の一覧を書く | 見出しの文字が、そのどれかと等しい見出し |
| "pattern" に正規表現を書く | 見出しの文字の中に、正規表現に合う所がある見出し。"pattern: """ は、どの見出しにも合う |
| 項目の規則に "name" も "pattern" も書かない（ID の規則） | それより前の規則が選ばなかった、すべての深さ3の見出し |

1つの見出しは、宣言した順で、それを選ぶ最初の規則のものになる。見出しの文字は、[節は、見出しの文字で見分ける](document-structure.ja.md#節は見出しの文字で見分ける)のとおりに読む。ID の規則が選んだ見出しの読み方は、[名前も正規表現も持たない項目の規則が選んだ見出しだけを、":" の前の ID と後の名前に分けて読む](document-structure.ja.md#名前も正規表現も持たない項目の規則が選んだ見出しだけを-の前の-id-と後の名前に分けて読む)で決める。

どの節の規則にも選ばれない深さ2の見出しは、undeclared_heading の指摘にする。項目の規則の一覧に ID の規則が無ければ、どの項目の規則にも選ばれない深さ3の見出しを undeclared_heading の指摘にし、その下の行も、ブロックごとに undeclared_line の指摘にする（[項目を宣言していない節の中の、深さ3の見出しは指摘にする](document-structure.ja.md#項目を宣言していない節の中の深さ3の見出しは指摘にする)と同じ扱い）。

### 見送った案

- 以前の決定: 節は、スキーマが宣言した1つの名前と等しいかで見分け、宣言した名前と一致しない節を指摘にする（[節は、見出しの文字で見分ける](document-structure.ja.md#節は見出しの文字で見分ける)の決めたことの1文目）。同じ節を2つの綴りで書く文書と、見出しの文字が自由な節を宣言できないので、やめた。
- 正規表現の選び方だけを持ち、綴りの候補を "^(問題|Problem)$" のように書く。指摘が、ノードの名前として正規表現を持つことになる。
- 規則に、指摘に出す名前を別に書くキー "label" を持たせる。名前の一覧の最初の名前が、変わらないノードの名前になるので、要らない。

### 確認すること

- C-schema-lang-14 "name: [未決, Open]" の節の規則を宣言したスキーマでは、"## 未決" の節も "## Open" の節も指摘にならない
- C-schema-lang-15 名前の規則の後に "pattern: """ の節の規則を宣言したスキーマでは、名前の規則に合わないどの深さ2の見出しの節も undeclared_heading にならず、"pattern" の規則の節として検査される
- C-schema-lang-16 1つの見出しに合う規則が2つあるときは、宣言した順で先の規則がその見出しを選ぶ（"pattern: """ の規則を "name: 未決" の規則より前に宣言すると、"## 未決" は "pattern" の規則の節として数えられ、"name: 未決" の規則には欠落の指摘が出る）
- C-schema-lang-17 項目の規則の一覧が名前の規則と正規表現の規則だけのとき、どれにも合わない深さ3の見出しは、":" の有無に関わらず invalid_id にならずに undeclared_heading になり、その下の段落と箇条書きも、それぞれ undeclared_line になる

## 項目の規則は "items" に一覧で書き、"item" のキーは受けない

状態: 実装済み

### 問題

項目の規則は、節の下の "item" と、文書の直下の "document.item" に、1つだけ書ける。1つの節に、名前で見分ける複数の項目（[節と項目の規則は、見出しを名前の一覧か正規表現で選ぶ](#節と項目の規則は見出しを名前の一覧か正規表現で選ぶ)）を宣言するには、規則の一覧が要る。

### 決めたこと

項目の規則は、節の下では "items" に、文書の直下では "document.items" に、規則の一覧として書く。

"item" と "document.item" のキーは受けない。書いたスキーマは、[スキーマに知らないキーや形に合わない値があれば、検査せずに停止する](#スキーマに知らないキーや形に合わない値があれば検査せずに停止する)のとおり、検査せずに停止する。

"name" も "pattern" も持たない規則1つだけの一覧（"items: [X]"）は、"item: X" と書いた規則と同じに読む。

### 見送った案

- 以前の決定: 項目の規則は、節の下の "item" と文書の直下の "document.item" に1つだけ書く（[スキーマは YAML で書き、題名・前置部・節・文書の直下の項目を根に置く](#スキーマは-yaml-で書き題名前置部節文書の直下の項目を根に置く)の決めたことの2段目）。1つの節に複数の項目の規則を書けないので、やめた。
- 1つの規則と規則の一覧の両方を受ける。同じことに書き方が2つできる。今あるスキーマの書き換えは、"item: X" を "items: [X]" にするだけで済む。

### 確認すること

- C-schema-lang-18 節の下に "items"、文書の直下に "document.items" を書いたスキーマは読み込まれ、節の下に "item" か、文書の直下に "document.item" を書いたスキーマは、スキーマの誤りとして読み込まれない
- C-schema-lang-19 "item: X" を "items: [X]" に書き換えたスキーマは、同じ文書に、書き換える前と同じ指摘と同じ抽出の値を返す

## 前置部・節・項目・箇条書きの子は、"open: true" を宣言すると、規則の無いブロックを受ける

状態: 実装済み

### 問題

宣言済みの前置部・節・項目の中では、規則の無いブロックは、開いた世界でも指摘になる。自由な文章を書く項目や、箇条書きの行の下にコードブロックや入れ子の一覧を書ける形は、ブロックの種類ごとに規則を宣言しても書き切れない。順序付きリストには規則種別が無いので、宣言する手段も無い。

### 決めたこと

前置部、節、項目と、箇条書きの子の規則（"children"）に、"open: true" を宣言できる。"open: true" を宣言したノードは、そのノードに規則の無い種類のブロックを、その中身ごと受け、指摘にしない。

"open: true" を宣言したノードでも、そのノードに宣言した規則は、すべての制約を保つ。深さ4以上の見出しは受けない（[深さ4以上の見出しは、それを含む前置部・節・項目の行として読み、"subheading" を宣言しなければ指摘にする](document-structure.ja.md#深さ4以上の見出しはそれを含む前置部節項目の行として読みsubheading-を宣言しなければ指摘にする)）。深さ2と深さ3の見出しの扱いも変えない。

"open: true" は、ノードが自分の中身として宣言するもので、スキーマの最上位の "open" と `check` の `--open`（[開いた世界は、宣言していない構造とその内側だけを許す](closed-world.ja.md#開いた世界は宣言していない構造とその内側だけを許す)）とは別のものである。"open" を書かないノードは、規則の無いブロックを指摘にする。

### 見送った案

- 以前の決定: 宣言済みの前置部・節・項目の中に足した、宣言していない構造と行は、開いた世界でも許さない（[開いた世界は、宣言していない構造とその内側だけを許す](closed-world.ja.md#開いた世界は宣言していない構造とその内側だけを許す)の決めたことの2段目の1つ目）。ノードが自分で中身を受けると宣言する手段が無く、自由な文章の項目を宣言できないので、"open: true" を宣言したノードには当てない。
- 順序付きリストの規則と、子の規則の下に置く前置部と同じ形の入れ物を足す。1つで済む "open" に対して、3つの追加になる。
- ノードの "open" が、深さ4以上の見出しも受ける。深さ4以上の見出しを受けながら、順序付きリストを指摘にしたいノードを宣言できない。指摘にならない順序付きリストは、箇条書きとして読まれないまま黙って通る。

### 確認すること

- C-schema-lang-20 "open: true" を宣言した項目では、規則の無い段落、順序付きリスト、表、コードブロック、引用が指摘にならず、"open" を書かない同じ形の項目では、それぞれ undeclared_line になる
- C-schema-lang-21 "open: true" を宣言した項目に宣言した箇条書きの規則の正規表現に合わない行は、bullet_pattern_mismatch になる
- C-schema-lang-22 箇条書きの子の規則に "open: true" を宣言すると、箇条書きの行の下の子の一覧、表、コードブロックが undeclared_line にならない
- C-schema-lang-23 "open: true" を宣言した項目の中でも、深さ4以上の見出しは、"subheading" を宣言しなければ heading_level_mismatch になる
- C-schema-lang-24 1つの項目に "open: true" を宣言しても、"open" を書かないほかの項目の中の規則の無いブロックは undeclared_line になる

## 深さ4以上の見出しの規則 "subheading" を、前置部・節・項目に宣言できる

状態: 実装済み

### 問題

深さ4以上の見出しには規則種別が無く、どこにあっても指摘になる。項目の中に小見出しを置く形の文書を、宣言する手段が無い。kotowari の決定の文書は、決定の節の中に深さ4以上の見出しを置くことを許す形で、宣言できなかった。

### 決めたこと

規則種別に、深さ4以上の見出しの規則 "subheading" を加える。"subheading" は前置部、節、項目に宣言できる。出現回数（[出現回数は5つの書き方で宣言する](#出現回数は5つの書き方で宣言する)）と正規表現を書け、抽出は書けない。

規則種別とその置ける場所の表（[規則種別は10にし、それぞれ置ける場所を決める](#規則種別は10にしそれぞれ置ける場所を決める)）は、次の1行を加えた10の規則種別になる。

| 規則種別 | 何を検証するか | 置ける場所 |
|---|---|---|
| 小見出し（"subheading"） | 深さ4以上の見出し | 前置部、節、項目 |

"subheading" は、深さ4以上の見出しの行を数えて照らす規則で、その下の行を持つノードではない。深さ4以上の見出しをどのノードの中の行として読むかは、[深さ4以上の見出しは、それを含む前置部・節・項目の行として読み、"subheading" を宣言しなければ指摘にする](document-structure.ja.md#深さ4以上の見出しはそれを含む前置部節項目の行として読みsubheading-を宣言しなければ指摘にする)で決める。

### 見送った案

- 以前の決定: 規則種別は9つで、深さ4以上の見出しの規則を持たない（[規則種別は10にし、それぞれ置ける場所を決める](#規則種別は10にしそれぞれ置ける場所を決める)）。項目の中の小見出しを宣言できないので、やめた。

### 確認すること

- C-schema-lang-25 （読んで確認）`crates/kotowari-markdown-schema/src/schema.rs` の公開する構造体が、9つの規則種別に小見出しを加えた10の規則種別と1対1で対応し、"subheading" の構造体を置けるのが前置部、節、項目だけである
- C-schema-lang-26 項目に "subheading: { repeat: { min: 1, max: 1 } }" を宣言したスキーマでは、深さ4以上の見出しが無い項目に repeat_min_not_met が、2つある項目に repeat_max_exceeded が出る
- C-schema-lang-27 "subheading" に "extract" を書いたスキーマは、スキーマの誤りとして読み込まれない
