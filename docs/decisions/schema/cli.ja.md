# CLI と結果の出し方

[English](cli.md) | 日本語

mds の CLI `kotowari-mds` が受けるコマンド、終了コード、出力の形、指摘の形、検査を行えないときの停止をどう知らせるかを扱う。宣言していない見出しと行の扱いと `--open` は[「閉じた世界と開いた世界」の話題](closed-world.ja.md)で、CLI と同じ読み込みを外のアプリで使う入口は[スキーマと文書の読み込みは、別のクレートに置いて CLI と外のアプリで共用する](library-io.ja.md#スキーマと文書の読み込みは別のクレートに置いて-cli-と外のアプリで共用する)で決める。スキーマの書き方は[「スキーマ言語の骨格」](schema-language.ja.md)、文書の構造の読み方は[「文書の骨格」](document-structure.ja.md)と[「見出しの下の行の規則」](block-rules.ja.md)、値の抽出の形は[「抽出と素の構文木」](extraction.ja.md)、"$schema" の解き方は[「スキーマの解決」](schema-resolution.ja.md)の話題で決める。どの入力で検査を行えなくなるかはそれぞれの話題で決め、この話題では、そのときの停止の知らせ方を決める。

## mds の CLI は kotowari-mds の名前で、check、ast、values、--version を受ける

状態: 実装済み

### 問題

mds は、文書の frontmatter の "$schema" が指す YAML のスキーマで Markdown の文書を検査し、値を抽出する CLI である。LLM が書いた Markdown の書式を、機械的に固定できるようにするのが目的である。

CLI のバイナリの名前は、短い "mds" にすると、Rust のクレートの公開先で他者が公開済みの名前とぶつかり、配布できない。受けるコマンドを検査、構文木、抽出、版の4つにした理由は残っていない。

### 決めたこと

CLI のバイナリの名前は `kotowari-mds` にする。文章の中で製品の略称を "mds" と書くことは変えない。

`kotowari-mds` は、検査の `check`、素の構文木の `ast`、抽出の `values`、版を出す `--version` の4つを受ける。`ast` が出す素の構文木は[ast は、検査とは別に、文書の素の構文木を JSON で出す](extraction.ja.md#ast-は検査とは別に文書の素の構文木を-json-で出す)で決める。`ast` に `--schema` を付けたときは、素の構文木ではなく型付きの値を出す（[ast --schema は、values --format json と同じ値に、スキーマの name を type として添える](#ast---schema-はvalues---format-json-と同じ値にスキーマの-name-を-type-として添える)）。

### 見送った案

- kotowari のサブコマンド "kotowari mds" にする。mds の CLI を使うのは kotowari を使わない人で（kotowari は mds をライブラリとして呼ぶ）、仕様の道具ごと入れさせることになる。mds と kotowari で分けた版も、CLI の上では kotowari の版になる。

### 確認すること

- C-schema-cli-1 `kotowari-mds --version` は版を出し、終了コード 0 で終わる

## ast --schema は、values --format json と同じ値に、スキーマの name を type として添える

状態: 実装済み

### 問題

`ast --schema` は、抽出の値に型の名前を添えたものとして作られていて、`values` と別の組み立て方を持たない。同じと決めておけば、抽出の規則がそのまま `ast --schema` にも効く。スキーマの最上位の "name" は、`ast --schema` の "type" にしか使われていない。何のための鍵かを決めておかないと分からない。

### 決めたこと

`kotowari-mds ast` に `--schema` を付けたとき、mds は文書が宣言したスキーマで `kotowari-mds values --format json` と同じ値を組み立て、JSON で出す。スキーマが最上位の "name" を宣言していれば、根の "type" の鍵にその値を置く。"name" を宣言しないときは "type" を置かず、出力は `values --format json` と同じになる。

"name" は文字列の型の名前として受け、`ast --schema` の "type" にだけ使う。`check` と `values` の結果は変えない。

### 確認すること

- C-schema-cli-3 "name" を宣言したスキーマでは、`ast --schema` の出力は `values --format json` の値に、根の "type" が "name" の値の鍵を足したものになり、"name" を宣言しないスキーマでは、2つの出力は同じ値で "type" の鍵を持たない
- C-schema-cli-4 "name" を宣言したスキーマでも、`values` の出力に "type" の鍵は入らない

## 終了コードは、指摘が無ければ 0、あれば 1、検査を行えなければ 2 にする

状態: 実装済み

### 問題

「書式が違う」と「検査できなかった」は、呼び出し側にとって別の事象である。同じ終了コードにすると区別できない。

### 決めたこと

終了コードは、上から順に当てはめて決める。

| 順 | 条件 | 終了コード |
|---|---|---|
| 1 | 検査を行えなかった（[停止の理由](#停止の理由は5つにする)のいずれかに当たった） | 2 |
| 2 | 1 に当たらず、指摘が1件以上ある | 1 |
| 3 | 1 にも 2 にも当たらない | 0 |

### 確認すること

- C-schema-cli-5 スキーマをすべて満たす文書の `check` は終了コード 0 で何も出力せず、指摘のある文書では 1、停止したときは 2 で終わる

## 出力の形は、--format で text と json から選ぶ

状態: 実装済み

### 問題

mds の第一の利用者は LLM なので、構造化された形が基本になる。一方で、人が手で叩く場面もある。`ast` だけが `json` しか受けない理由は残っていない。

### 決めたこと

出力の形は `--format` で受け、人間向けの `text` と機械向けの `json` の2つから選ばせる。`ast` は `json` だけを受け、`--format text` を与えたときは引数の誤りで停止する（[停止の理由は5つにする](#停止の理由は5つにする)）。

### 確認すること

- C-schema-cli-6 `check` と `values` は、人間向けの text と、`--format json` を付けたときの JSON の2つの形で結果を出す

## values の text 出力は、入れ子ごとに空白2つで字下げし、配列の要素に1からの番号を付ける

状態: 実装済み

### 問題

人間向けの出力でも、形が決まっていないとテストが書けない。今の振る舞いを、そのまま決まりにした。

### 決めたこと

`values` の `text` の出力では、入れ子が1段深くなるごとに空白2つで字下げし、配列の要素には1から始まる番号と "." を付ける。

### 確認すること

- C-schema-cli-7 `values --format text` の出力では、入れ子の鍵の行が親の鍵の行より空白2つ深く字下げされ、配列の要素が "1." から始まる番号で並び、要素の中の配列も "1." から番号を付けて1段深く字下げされる

## 指摘は、種類、深刻度、文書のパス、行番号、詳細を持つ

状態: 実装済み

### 問題

指摘は、機械が種類で分岐でき、人が位置をたどれる必要がある。そのための最小の組を決める。

### 決めたこと

1件の指摘は、種類、深刻度、文書のパス、行番号、詳細を持つ。行を持たない指摘では、行番号を省く（行の決め方は[指摘の行は、違反したノードの開始行か、欠落ならそれを含むノードの開始行にする](#指摘の行は違反したノードの開始行か欠落ならそれを含むノードの開始行にする)）。さらに、ノードの名前、生の行、規則種別を添える（下の3つの決定）。

指摘の種類は、何を見つけるかで次の5つに分類する。

| 分類 | 何を見つけるか |
|---|---|
| 題名 | 題名が無い、2つ以上ある、正規表現に合わない |
| 欠落 | 必須のノードが無い |
| 形の違反 | 値が正規表現や許可リストに合わない、見出しの深さが合わない、項目の ID の形が合わない、フィールド行の並び順が合わない、表のヘッダが合わない、コードブロックの言語が合わない |
| 出現回数 | 出現回数の下限を下回る、上限を超える |
| 閉じた世界 | 宣言していない見出しと行がある |

個々の指摘の種類と、それぞれが出る条件は、[「文書の骨格」](document-structure.ja.md)、[「見出しの下の行の規則」](block-rules.ja.md)、[「スキーマ言語の骨格」](schema-language.ja.md#出現回数は5つの書き方で宣言する)、[「閉じた世界と開いた世界」](closed-world.ja.md)の話題で決める。

### 確認すること

- C-schema-cli-8 `check --format json` の指摘は、種類、深刻度、文書のパス、行番号、詳細を持つ

## 指摘の行は、違反したノードの開始行か、欠落ならそれを含むノードの開始行にする

状態: 実装済み

### 問題

指摘が指す行を、ノードの種類ごとに別々に決めると、呼ぶ側が種類ごとに読み分けることになる。mds 自身が行番号を持てるのが自然で、行番号は文書を解析した時点で計算済みなので、性能の懸念も無い。

### 決めたこと

指摘の行番号は、1つの規則で決める。違反したノードがあるなら、そのノードの開始行にする。ノードの欠落なら、それを含むノードの開始行にする。含むノードに行が無いとき（例えば、文書の題名の欠落）は、行番号を省く。ノードの中の要素（例えば、表のデータ行）が違反したときは、その要素の行にする。

### 見送った案

- 呼ぶ側が、抽出の構造から行を判定し、mds の指摘を捨てる。判定が2か所に分かれる。
- 行が無くなることを受け入れる。利用者から見える指摘の行が変わる。

### 確認すること

- C-schema-cli-9 指摘の行番号は、違反したノードの開始行（例えば、宣言していない節の見出しの行、形に合わないフィールド行、上限を超えた2つ目のフィールド行）、欠落ならそれを含むノードの開始行（必須のフィールド行が欠けた項目の見出しの行）、表のデータ行の違反ならその行になる
- C-schema-cli-10 含むノードに行が無い指摘（例えば、題名の欠落と、必須の節の欠落）は、行番号を持たない

## 指摘に、宣言したノードの名前を構造として持たせる

状態: 実装済み

### 問題

指摘の詳細の文言は、仕様のどこにも定めていない。呼ぶ側が、どのフィールド行や節の指摘かを詳細の文言から読むと、文言を言い換えたときに黙って壊れる。mds は指摘を作る時点で、宣言したノードの名前を持っている。

### 決めたこと

指摘に、スキーマが宣言したノードの名前を、構造として持たせる。宣言上の名前を持つのは節とフィールド行だけなので、名前はその2つの指摘にだけ付け、題名のように宣言上の名前を持たないノードの指摘には付けない。

### 見送った案

- 詳細の文言を仕様で固定し、呼ぶ側がそれを読む。人向けの英文を、機械の契約にすることになる。
- 呼ぶ側が抽出の構造から判定する。判定が2か所に分かれる。

### 確認すること

- C-schema-cli-11 フィールド行と節の指摘はスキーマが宣言した名前を持ち、題名と表の指摘はノードの名前を持たない

## 名前の一覧で選ぶ節と項目の規則の指摘は、その一覧の最初の名前をノードの名前に持つ

状態: 提案

### 問題

指摘にノードの名前を持たせるのは、節とフィールド行だけである。項目を名前で選べるようになると（[節と項目の規則は、見出しを名前の一覧か正規表現で選ぶ](schema-language.ja.md#節と項目の規則は見出しを名前の一覧か正規表現で選ぶ)）、項目の出現回数の指摘は、どの名前の項目が足りないかを、詳細の英文のほかに持たない。名前の一覧で選ぶ規則では、一覧のどの名前を指摘に出すかも決める必要がある。

### 決めたこと

名前の一覧（"name"）で選ぶ節と項目の規則の指摘は、その一覧の最初の名前を、ノードの名前として持つ。"name" が文字列1つのときは、その名前を持つ。正規表現（"pattern"）で選ぶ規則と、"name" も "pattern" も持たない項目の規則の指摘は、ノードの名前を持たない。フィールド行の指摘は宣言した名前を持ち、題名と表の指摘はノードの名前を持たない。

### 見送った案

- 以前の決定: ノードの名前は、節とフィールド行の指摘にだけ付ける（[指摘に、宣言したノードの名前を構造として持たせる](#指摘に宣言したノードの名前を構造として持たせる)の決めたことの2文目）。名前で選ぶ項目の指摘が、どの項目かを構造として持たないので、名前で選ぶ項目にも付ける。

### 確認すること

- C-schema-cli-30 "name: [問題, Problem]" の項目の規則に合う項目が無い節では、`repeat_min_not_met` の指摘が、ノードの名前として "問題" を持つ（`check --format json` の出力でも同じ）
- C-schema-cli-31 "pattern" で選ぶ節の規則の指摘（例えば、上限を超えた `repeat_max_exceeded`）は、ノードの名前を持たない

## 指摘に、指す行の文字をそのまま持たせる

状態: 実装済み

### 問題

呼ぶ側は、指摘を人に見せるとき、読んだ行の文字をそのまま（字下げと末尾の空白を含め、組み立て直さずに）出したい。詳細の文言は見出しの名前だけで、行の文字を持っていない。

### 決めたこと

行番号を持つ指摘には、その指摘が指す行の文字を、生の行としてそのまま持たせる。行番号を持たない指摘では省く。mds は「何がどこで」を構造で返し、文言は呼ぶ側が組み立てる。

### 見送った案

- 呼ぶ側が文書の行を読む。呼ぶ側は Markdown を読まず、読むのは mds に任せる、という分担が形だけになる。

### 確認すること

- C-schema-cli-12 行番号を持つ指摘の生の行は、文書のその行と一文字も違わず、行番号を持たない指摘は生の行を持たない

## 出現回数の指摘に、数えたノードの規則種別を持たせる

状態: 実装済み

### 問題

節とフィールド行のほかの指摘にはノードの名前が付かない。出現回数の下限と上限の指摘は、どのノードを数えたかの手がかりが、種類にも名前にも無い。詳細の英文を読ませたくない。

### 決めたこと

出現回数の下限（`repeat_min_not_met`）と上限（`repeat_max_exceeded`）の指摘に、数えたノードの規則種別を持たせる。宣言していない行の指摘に付ける種別は、[宣言していない行の指摘に、その行をどう読んだかの種別を持たせる](closed-world.ja.md#宣言していない行の指摘にその行をどう読んだかの種別を持たせる)で決める。ほかの指摘には付けない。

### 確認すること

- C-schema-cli-13 節か項目の文に出現回数の下限を宣言したスキーマで、文の無い節か項目の `repeat_min_not_met` の指摘は、規則種別として文を持つ（`check --format json` の出力でも同じ）

## 検査を行えないときは、部分的な結果を出さずに停止する

状態: 実装済み

### 問題

読めない、壊れている、形に合わない入力を黙って飛ばすと、検査していない文書が通ったように見える。スキーマを解決できない以上、検査の結果は出せず、部分的な結果を出すと通ったように見える。

"$schema" には文書の側が任意のファイルを書ける。スキーマとして読めないファイルを指したとき、パーサの説明はそのファイルの中身を引用するので、説明をそのまま流すと、読める任意のファイルの断片が標準エラーへ出る。これを防ぐ決まりを決めた理由は、記録に残っていない。

### 決めたこと

読めない、壊れている、形に合わない入力を、黙って飛ばさない。スキーマを解決できないときと、frontmatter が壊れているときは、`check`、`values`、`ast --schema` のどれも、部分的な結果を出さずに停止する（終了コード 2）。どの入力で停止するかは、[「スキーマの解決」](schema-resolution.ja.md#frontmatter-が壊れているかスキーマを指していない文書は検査せずに停止する)と[「スキーマ言語の骨格」](schema-language.ja.md#スキーマに知らないキーや形に合わない値があれば検査せずに停止する)の話題と、下の[停止の理由は5つにする](#停止の理由は5つにする)で決める。

停止するときは、停止の理由の名前に説明を添えた1行だけを標準エラーに出し、それまでに集めた指摘は1件も出さない。ディレクトリの検査の途中で停止の理由に当たったときも、全体を停止する。

停止の説明が複数の行にわたるときも、1行目だけを出し、"$schema" が指したファイルの中身を、2行目より後の行まで標準エラーへ流さない。

### 確認すること

- C-schema-cli-14 "$schema" の無い文書、参照先のスキーマが無い文書、frontmatter が壊れた文書には、`check`、`values`、`ast --schema` のどれも終了コード 2 で停止する
- C-schema-cli-15 停止するとき、標準エラーには1行だけを出し、標準出力に指摘を1件も出さない
- C-schema-cli-16 ディレクトリの検査で、1つの文書が停止の理由に当たると、検査は全体が終了コード 2 で停止し、ほかの文書の指摘も出さない
- C-schema-cli-29 "$schema" がスキーマとして読めない複数行のファイルを指して停止したとき、標準エラーは1行だけで、そのファイルの2行目より後の中身を含まない

## 停止の理由は5つにする

状態: 実装済み

### 問題

停止の理由の分け方と名前を決める。それぞれの理由に当てる条件を決めた理由は残っていない。

### 決めたこと

停止の理由は次の5つにする。停止の1行には、この理由の名前と説明を並べる。

| 理由 | いつ |
|---|---|
| `schema_not_found`（スキーマが見つからない） | 参照先のスキーマが無い。URL のスキーマの取得に失敗した（応答が 4MiB を超えたとき、取得全体が10秒を超えたときを含む。取得の決まりは[URL のスキーマを取得できないときと、取得が上限を超えたときは停止する](schema-resolution.ja.md#url-のスキーマを取得できないときと取得が上限を超えたときは停止する)で決める） |
| `schema_invalid`（スキーマが形に合わない） | [配置パスが衝突する](#配置パスが衝突するスキーマは文書を読まずに停止する)、["name" を宣言したスキーマで根の "type" に値を置く](#name-を宣言したスキーマで根の-type-に値を置くと停止する)、[同じ名前を2度宣言する](#同じ置き場の同じ名前と表のヘッダの同じ列の名前を2度宣言すると停止する)、[配置パスに空の名前がある](#配置パスのドットで区切った名前が空なら停止する)。"reading" に "paragraph" でも "line" でもない値を書いた（[読み方は段落を既定にし、行で読む読み方をスキーマで選べる](schema-language.ja.md#読み方は段落を既定にし行で読む読み方をスキーマで選べる)）。表の規則に "header" なしで "select" を書いた、"select" の値が "first" でない（[表の規則は、"select: first" でヘッダの合う最初の表だけを選べる](block-rules.ja.md#表の規則はselect-first-でヘッダの合う最初の表だけを選べる)） |
| `frontmatter_invalid`（frontmatter が壊れている） | frontmatter が壊れた YAML か、YAML のマッピングでない。"$schema" の値が空か空白だけである。"$schema" の値が文字列でない |
| `unreadable_file`（文書が読めない） | 文書のファイルを読めない |
| `argument_error`（引数の誤り） | 受けない `--format` の値、知らないフラグ、[同じオプションを2回渡した](#同じオプションを2回渡すと引数の誤りで停止する)、`ast` に `--format text` を与えた |

### 確認すること

- C-schema-cli-17 表のそれぞれの条件に当たる入力では、終了コード 2 で停止し、標準エラーにその理由の名前が出る（参照先の無いスキーマや取得できない URL は `schema_not_found`、"header" なしの "select" は `schema_invalid`、壊れた frontmatter と空の "$schema" は `frontmatter_invalid`、読めない文書は `unreadable_file`、知らないフラグと `ast --format text` は `argument_error`）

## 配置パスが衝突するスキーマは、文書を読まずに停止する

状態: 実装済み

### 問題

抽出の値を置く配置パスが、同じ置き場の中で重なると、値が黙って上書きされて消える。この判定はスキーマの宣言どうしの比較だけでできるので、文書を見る必要がない。一方で、ドット区切りの入れ子は正当な書き方で、最初の名前だけで判定すると誤って弾く。親子が重なる組だけが本当の衝突である。

### 決めたこと

同じ置き場の中で配置パスが衝突するスキーマは、スキーマを読んだ時点で `schema_invalid` の停止にし、文書の値を出さない。同じパスどうしと、一方が他方の手前の段にあたるもの（"a" と "a.b"）は衝突にする。途中まで同じで先が分かれるもの（"a.b" と "a.c"）は衝突にしない。

判定は、要素オブジェクトの中と、要素オブジェクトの外（例えば、節の直下）のどちらでも行う。抽出の値を配置パスの入れ子に置くことは[値は、配置パスが指す場所に、ドットで区切った名前の入れ子で置く](extraction.ja.md#値は配置パスが指す場所にドットで区切った名前の入れ子で置く)で、要素オブジェクトの "value" と "of" の鍵は[抽出は、path・value・of を持つ1つの入れ子で宣言する](extraction.ja.md#抽出はpathvalueof-を持つ1つの入れ子で宣言する)で決める。要素オブジェクトの中では、内側の配置パスと、要素の値の "value" の鍵と、導かれる値の "of" の鍵を、同じ置き場のパスとして数える。

### 確認すること

- C-schema-cli-18 要素オブジェクトの中で内側の配置パスと "value" か "of" の鍵が重なるスキーマや、2つの節の直下に同じパスか "a" と "a.b" を宣言したスキーマでは、`values` が `schema_invalid` で停止し、文書の値を出さない
- C-schema-cli-19 "a.b" と "a.c" のように先が分かれる配置パスは、要素オブジェクトの中でも外でも停止しない

## name を宣言したスキーマで、根の type に値を置くと停止する

状態: 実装済み

### 問題

型付きの抽出（`ast --schema`）は根の "type" の鍵に "name" を置くので、同じ鍵に抽出の値を置くと、"name" が黙って消える。配置パスの衝突と同じ形で止めれば、出力の形を変えずに済む。

### 決めたこと

"name" を宣言したスキーマで、文書の値の根に置く配置パスが "type" か "type." で始まるものは、`schema_invalid` の停止にする。停止の説明は、型付きの抽出が "name" を置く鍵と衝突する、という言い方にする。"name" を宣言しないスキーマでは、"type" に値を置いてよい。

### 見送った案

- 出力の形を変え、"name" を抽出の値と別の鍵に分ける（抽出の値を1段下に置く、など）。`ast --schema` の出力を読む側が壊れる。
- "name" を宣言しないスキーマでも "type" を禁じる。`values` には "type" が出ないので、衝突しないスキーマまで止めることになる。

### 確認すること

- C-schema-cli-20 "name" を宣言したスキーマで、題名の配置パスを "type" か "type.title" にすると `values` が `schema_invalid` で停止し、"name" を宣言しない同じスキーマでは停止せず "type" に題名の値を置く

## 同じ置き場の同じ名前と、表のヘッダの同じ列の名前を、2度宣言すると停止する

状態: 実装済み

### 問題

同じ置き場に同じ名前の節かフィールド行を2度宣言すると、検査は1つ目の宣言だけを使い、抽出は両方の宣言を使う。2つ目の宣言の正規表現は黙って効かず、抽出には検査を通っていない値が入る。表のヘッダに同じ列の名前を2度書くと、抽出で後の列の値が前の列の値を黙って上書きし、前の列の値が消える。どちらの宣言が効くかを決めるより、書けなくするほうが誤りに気づける。

### 決めたこと

同じ置き場に同じ名前の節、または同じ名前のフィールド行を2度宣言したスキーマは、`schema_invalid` の停止にする。表のヘッダに同じ列の名前を2度書いたスキーマも、`schema_invalid` の停止にする。

### 見送った案

- 2つ目以降の宣言を無視する。書いた規則が黙って効かない。
- 表で、後の列が前の列を上書きする今の振る舞いを決まりにする。値が黙って消える。

### 確認すること

- C-schema-cli-21 同じ名前の節を2つ宣言したスキーマ、前置部に同じ名前のフィールド行を2つ宣言したスキーマ、表のヘッダに同じ列の名前を2つ書いたスキーマでは、`check` が `schema_invalid` で停止する

## 配置パスの、ドットで区切った名前が空なら停止する

状態: 実装済み

### 問題

空の名前を含む配置パスは、空文字列の JSON の鍵を作り、ドット区切りの名前として意味を持たない。書き間違いに、すぐ気づけるようにしたい。

### 決めたこと

配置パスをドットで区切った名前は、どれも空であってはならない。空の名前を含む配置パス（空文字列、"a..b"、".a"、"a."）を書いたスキーマは、`schema_invalid` の停止にする。

### 確認すること

- C-schema-cli-22 配置パスに、空文字列、"a..b"、".a"、"a." を書いたスキーマは、`schema_invalid` で停止する

## 停止の説明の文言は約束せず、問題の欄の名前と、期待した型か受け付ける語を含める

状態: 実装済み

### 問題

停止の説明の文言を約束にすると、言い回しを手直しするたびにテストが壊れる。中身だけを決めれば、テストはその中身を確かめられる。

### 決めたこと

停止の説明の文言そのものは約束しない。スキーマか frontmatter の値の型や語が違って停止するとき、説明には、問題のあった欄の名前と、期待した型か受け付ける語の一覧を含める。

### 見送った案

- 今の文言を、そのまま約束にする。

### 確認すること

- C-schema-cli-24 "$schema" の値が数値の文書、"reading" の値が "foo" のスキーマ、"open" や "extract" の値の型が違うスキーマ、ノードが受けない "of" の語を書いたスキーマでは、停止の説明に、その欄の名前と、期待した型か受け付ける語（"reading" なら "paragraph" と "line"）が含まれる

## ディレクトリの検査は、$schema を持つ文書だけを検査し、. で始まるディレクトリとシンボリックリンクを辿らない

状態: 実装済み

### 問題

ディレクトリを対象に検査するとき、どの文書を対象にするかを決める。"$schema" を持つ文書だけを選ぶことと、"." で始まるディレクトリを辿らないことの理由は残っていない。

シンボリックリンクを辿ると、同じ文書を二重に読む経路と、検査の対象に指定した置き場の外へ出る経路ができる。

### 決めたこと

`check` の対象がディレクトリのとき、その配下の文書のうち、frontmatter に "$schema" を持つものだけを集めて検査する。"$schema" を持たない文書は対象外にする。"$schema" はあるが値が空か空白だけの文書は、宣言と見なさず、frontmatter が壊れているとして全体を停止する。

名前が "." で始まるディレクトリの下は辿らない。スキーマとキャッシュを置く ".kotowari/" も、これで辿らない。

シンボリックリンクは辿らない。配下にある文書へのシンボリックリンクも、検査の対象にしない。

### 確認すること

- C-schema-cli-25 ディレクトリの `check` は、"$schema" を持つ文書の指摘だけを出し、"$schema" を持たない文書は指摘も停止も出さない
- C-schema-cli-26 ディレクトリの `check` は、名前が "." で始まるディレクトリの下の文書を検査しない
- C-schema-cli-28 ディレクトリの `check` は、置き場の外にある違反のある文書へのシンボリックリンクを辿らず、その文書の指摘を出さない

## values と ast --schema は、検査の合否と関係なく値を組み立てる

状態: 実装済み

### 問題

理由は残っていない。

### 決めたこと

`values` と `ast --schema` は、検査の合否と関係なく、スキーマの抽出の規則に沿って文書から値を組み立てる。文書の違反を理由に、終了コードと出力を変えない。ただし、スキーマを解決できないときは停止する（[検査を行えないときは、部分的な結果を出さずに停止する](#検査を行えないときは部分的な結果を出さずに停止する)）。`--open` は `check` にだけ付き、`values` と `ast` には効かない。

ライブラリの側でこの振る舞いをどの入口で支えるかは、[CLI の values と ast --schema は、違反のある文書でも今までどおり値を出す](library-extraction.ja.md#cli-の-values-と-ast---schema-は違反のある文書でも今までどおり値を出す)で決める。

### 確認すること

- C-schema-cli-27 読める文書に違反（例えば、2つ目の題名）があっても、`values` は取れる値を出力し、終了コード 0 で終わる
