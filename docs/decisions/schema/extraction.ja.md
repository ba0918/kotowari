# 抽出と素の構文木

[English](extraction.md) | 日本語

スキーマが宣言した抽出から値を組み立てる振る舞いと、検査とは別に素の構文木を出す振る舞いを扱う。抽出した値をライブラリから取り出す入口は[「ライブラリの検証と値の抽出」](library-extraction.ja.md)の話題の[CLI の values と ast --schema は、違反のある文書でも今までどおり値を出す](library-extraction.ja.md#cli-の-values-と-ast---schema-は違反のある文書でも今までどおり値を出す)で、出現回数の範囲で値が配列になることは[出現回数の範囲を宣言したノードは、1件でも配列で抽出する](schema-language.ja.md#出現回数の範囲を宣言したノードは1件でも配列で抽出する)で、どの行がフィールド行・文・箇条書きになるかは[「見出しの下の行の規則」](block-rules.ja.md)の話題で、配置パスどうしの衝突と停止の理由は[配置パスが衝突するスキーマは、文書を読まずに停止する](cli.ja.md#配置パスが衝突するスキーマは文書を読まずに停止する)と[停止の理由は5つにする](cli.ja.md#停止の理由は5つにする)で決める。

## 抽出した値は文字列のまま出し、型を変換しない

状態: 実装済み

### 問題

文書から取り出した値を日付や数値に変換すると、値をどう解釈するかを mds が利用者に代わって決めてしまう。文字列なら、どの利用者にも共通に使える。

### 決めたこと

文書から取り出した抽出の値は、文字列として出す。日付や数値に見える値でも型を変換しない。

文書の文字ではなく位置から導く値（導かれる値の行番号と要素の最後の行）は、この決まりの外にする。決め方は[導かれる値は5つの語にし、語ごとに宣言できるノードを限る](#導かれる値は5つの語にし語ごとに宣言できるノードを限る)で決める。

### 見送った案

- 抽出した値を日付や数値へ型変換する。利用者の解釈を固定してしまい、文字列が共通分母になる。

### 確認すること

- C-schema-extract-1 数や日付に見える値を含むどんな文書でも、抽出した値の葉はすべて文字列である

## 値は、配置パスが指す場所に、ドットで区切った名前の入れ子で置く

状態: 実装済み

### 問題

抽出した値をどこに置くかは、スキーマに書いた配置パスで決める。ドット区切りで入れ子に置くことの理由は残っていない。

### 決めたこと

mds は、抽出した値を、配置パスのドットで区切った名前に沿った入れ子に置く。`values` と `ast --schema` は、この入れ子の形で値を出す（`ast --schema` の形は[ast --schema は、values --format json と同じ値に、スキーマの name を type として添える](cli.ja.md#ast---schema-はvalues---format-json-と同じ値にスキーマの-name-を-type-として添える)で決める）。

配置パスの区切った名前が空のスキーマの停止は[配置パスの、ドットで区切った名前が空なら停止する](cli.ja.md#配置パスのドットで区切った名前が空なら停止する)で、配置パスどうしが重なるスキーマの停止は[配置パスが衝突するスキーマは、文書を読まずに停止する](cli.ja.md#配置パスが衝突するスキーマは文書を読まずに停止する)で決める。

### 確認すること

- C-schema-extract-2 ドットを含む配置パスを宣言すると、`kotowari-mds values --format json` の値は、ドットで区切った名前の入れ子として出る

## 抽出の対象が文書に無いときは、その配置パスのキーを出さない

状態: 実装済み

### 問題

抽出を宣言したノードが文書に無いとき、出力をどうするかを決める必要がある。理由は残っていない。

### 決めたこと

抽出の対象のノードが文書に無いとき、mds はその配置パスのキーを出力に出さない。

### 確認すること

- C-schema-extract-4 抽出を宣言したノード（フィールド行、箇条書き、表のどれでも、繰り返すかどうかに関わらず）が文書に無いと、その配置パスのキーが出力に無い

## 抽出は、path・value・of を持つ1つの入れ子で宣言する

状態: 実装済み

### 問題

抽出の宣言は、以前は1つのリストに、値を置く場所（絶対の配置パス）と、要素の中の鍵（相対の配置パス）を並べていた。どちらなのかは、導かれる値の宣言が無いことという、書かれていない手がかりで見分けていた。置き場の数の規則もリストの形の中に居場所が無く、置き場が0個だと出力が黙って空になり、2個だと同じ内容が複製された。間違えやすいのは、宣言の書き方が直感的でないからだ、という利用者の指摘から、置き場0個・2個を停止で弾くのではなく、書けない形にすることにした。

要素の値に名前の無い暗黙の場所を与えると、導かれる値と同じ階層で名前を取り合う。要素の値にも宣言した鍵を与えると、取り合いそのものが無くなる。導かれる値だけが欲しい（セルは要らない）という宣言は正当な意図で、置き場が必ずあるので結果も予測どおりになる。

短い書式は、宣言の22件のうち13件がこの形で、それ自体は曖昧でない。名前付きキャプチャは要素の値を正規表現で切り出すもので、要素から導く別の値ではない。名前付きキャプチャを題名にだけ宣言できるようにした理由は残っていない。

### 決めたこと

ノードの抽出は、1つの入れ子で宣言する。`path` に配置パスをちょうど1つ、`value` に要素の値を置く鍵を、`of` に導かれる値の鍵と語の対応を書く。`value` を書かずに `of` だけを書いてよく、そのときの要素は導かれる値の鍵だけを持つ。`path` の無い宣言と、書式の並びで書いた宣言は、スキーマが形に合わない停止にする。

短い書式 `extract: <名前>` は、`{ path: <名前> }` の略記として読む。

名前付きキャプチャ `group` は、`of` の下ではなく `path` と並べて書き、題名にだけ宣言できる。`group` を宣言した題名の抽出は、題名の正規表現の、その名前付きキャプチャが捕まえた文字を値にする。題名の外のノードに `group` を宣言したスキーマと、題名に正規表現が無いか、正規表現が指定の名前付きキャプチャを含まないスキーマは停止にする。

### 見送った案

- 抽出を書式の並びのままにし、置き場がちょうど1つであることを `schema_invalid` で強制する。置き場と要素の中の鍵が同じリストに並ぶ読みにくさが残る。

### 確認すること

- C-schema-extract-5 `path` を書かない抽出か、書式の並びで書いた抽出を宣言したスキーマでは、`values` が停止し、終了コードは 2 である
- C-schema-extract-6 `value` を書かず `of` だけを書いた抽出の要素のオブジェクトは、導かれる値の鍵と、内側のノードが宣言した配置パスだけを持つ
- C-schema-extract-7 短い書式 `extract: <名前>` は、`path` だけを書いた宣言と同じに読まれる
- C-schema-extract-8 題名の抽出に `group` を宣言すると、題名の正規表現の名前付きキャプチャが捕まえた文字が値になる
- C-schema-extract-9 題名の外のノードに `group` を宣言したスキーマと、`group` を宣言した題名に正規表現が無いか、その名前付きキャプチャを含まないスキーマは、停止する

## value か導かれる値を宣言したときだけ、要素ごとのオブジェクトを組み立てる

状態: 実装済み

### 問題

導かれる値を1つも宣言していない抽出の出力が、変わる理由は無い。一方で、要素の集まりを持つノードは、どれも同じ書き方で要素の値と導かれる値を取り出せるようにしたい。ノードごとに、何を1つの要素にし、生の行がどの行を指すかを一表で決めておかないと、宣言したときの形が定まらない。

### 決めたこと

どのノードでも、`value` も導かれる値も宣言しなければ、下の表の略記の形をそのまま出し、要素に分けない。どちらかを宣言すれば、要素の単位ごとに1つのオブジェクトを組み立て、要素の値を `value` の鍵に、導かれる値を `of` の鍵に置く。分けないノードでも、宣言すれば配置パスの下にオブジェクトが1つできる。

| ノード | 要素の単位（`value` か導かれる値を宣言したとき） | 値 | 生の行と行番号が指す行 |
|---|---|---|---|
| 題名 | 分けない | 見出しの文字列。`group` を宣言したときは名前付きキャプチャが捕まえた文字 | 題名の見出しの行 |
| フィールド行 | 分けない | 名前の後の値の文字列。区切り文字を宣言したときは区切った文字列の配列 | そのフィールド行の行 |
| 文 | 導かれる値を宣言したときだけ行。宣言しなければ分けない | 分けないときは本文の文字列。行に分けたときは前後の空白を取り除いた行の文字 | その行 |
| 節 | 分けない | 文と箇条書きの行だけをつないだ本文の文字列。フィールド行、表、コードブロック、項目は含めない | 節の見出しの行 |
| 項目 | 項目 | 見出しと本文を改行でつないだ文字列。見出しは ID と名前だけにする。本文にはフィールド行、文、箇条書きを含め、表とコードブロックは含めない。宣言したフィールド行はその行と継続段落を入れて子の箇条書きを入れず、宣言していない行は子の行まで入れる | 項目の見出しの行 |
| 箇条書き | 行 | マーカーから始まる元の行（継続段落と子の箇条書きの行を含む）。略記の形では、その文字列の配列 | その行のマーカーの行 |
| 表 | データ行 | データ行の値。鍵は[表の行の鍵は、header の宣言か列の位置から取り、文書のヘッダ行の文字を使わない](#表の行の鍵はheader-の宣言か列の位置から取り文書のヘッダ行の文字を使わない)で決める。略記の形では行の配列 | そのデータ行の行 |
| コードブロック | ブロック | ブロック全体の文字列 | フェンスの開始行 |

値の行の取り方とつなぎ方は[値の行は、文書の元の行のまま使う](#値の行は文書の元の行のまま使う)で決める。表の行のセルのうち、文書のヘッダ行より多いものの扱いは[表の列数は文書のヘッダ行に合わせ、余ったセルは捨てる](block-rules.ja.md#表の列数は文書のヘッダ行に合わせ余ったセルは捨てる)で決める。

### 確認すること

- C-schema-extract-10 略記の `extract: text` と `extract: rows` だけを宣言すると、文の値は1つの文字列に、表の値は行の並びになり、要素ごとのオブジェクトはできない
- C-schema-extract-11 `value` か導かれる値を宣言すると、表はデータ行ごと、箇条書きは行ごと、コードブロックはブロックごとに1つのオブジェクトになり、分けないフィールド行は配置パスの下に1つのオブジェクトになる。要素の値は `value` の鍵に、導かれる値は `of` の鍵に入る
- C-schema-extract-12 箇条書きの値は、元のマーカーとその後の空白を保った元の行で、継続段落と子の箇条書きの行を字下げのまま含む
- C-schema-extract-13 節の値は、文と箇条書きの行だけをつないだ本文で、フィールド行、表、コードブロック、項目を含まない
- C-schema-extract-14 項目の略記の値は、見出しの ID と名前と、本文を改行でつないだ文字列で、本文に表とコードブロックを含まない
- C-schema-extract-15 項目の本文には、宣言したフィールド行はその行と継続段落だけが入って子の箇条書きの行は入らず、宣言していない一覧の行は子の箇条書きの行まで入る
- C-schema-extract-16 コードブロックの要素の値は、ブロックの中身全体の文字列である

## 項目の内側に抽出があれば、項目は内側の配置パスを鍵にしたオブジェクトにする

状態: 実装済み

### 問題

文書をまたいで検査する側が、項目を構造のある値として読めるようにしたい。鍵をスキーマを書く人が決めれば、書式を変えても配置パスを保つ限り、値を使う側のコードは変わらない。文書の語（見出しやフィールド行の名前）を鍵にすると、見出しを言い換えただけで出力の約束が壊れる。利用者は、特定の使い先に固定されない汎用のエンジンとして使えることを条件に、この形を採った。

### 決めたこと

項目の内側のノードが抽出を宣言している間、mds は項目ごとに1つのオブジェクトを組み立て、内側の配置パスを、そのオブジェクトの中の相対パスとして解く。鍵は内側の配置パスで決め、文書の見出しやフィールド行の名前は出力の鍵にしない。

内側に抽出が無く、項目の抽出が `value` も導かれる値も宣言していなければ、オブジェクトを組み立てず、略記の形（見出しと本文をつないだ文字列）にする。

### 見送った案

- 宣言したフィールドの名前を、そのまま鍵にする。Markdown の語が出力の約束になり、書式を変えると使う側が壊れる。

### 確認すること

- C-schema-extract-17 項目の内側のノードが抽出を宣言すると、項目の抽出が `path` だけでも、項目ごとに内側の配置パスを鍵にしたオブジェクトができ、見出しやフィールド行の名前が違う文書でも鍵は同じになる
- C-schema-extract-18 項目の内側に抽出が無く、項目の抽出が `value` も導かれる値も宣言していなければ、項目の値は見出しと本文をつないだ文字列のままである

## 項目自身が抽出を宣言しないまま、内側にだけ抽出を宣言したスキーマは停止する

状態: 実装済み

### 問題

項目の内側の値は、[項目の内側に抽出があれば、項目は内側の配置パスを鍵にしたオブジェクトにする](#項目の内側に抽出があれば項目は内側の配置パスを鍵にしたオブジェクトにする)のとおり項目のオブジェクトの中に置く。項目自身に抽出が無いと、内側の値を置く場所が無い。理由は残っていない。

### 決めたこと

項目の内側のフィールド行、文、箇条書き、表、コードブロックが抽出を宣言し、その項目自身が抽出を宣言していないとき、mds はスキーマが形に合わない停止（`schema_invalid`）にする。箇条書きの子のフィールド行も、項目の内側に数える。

### 確認すること

- C-schema-extract-19 項目自身は抽出を宣言せず、項目の中のフィールド行、表、コードブロックにだけ抽出を宣言したスキーマは、`schema_invalid` で停止する。項目が抽出を宣言していれば、同じ内側の宣言で停止しない
- C-schema-extract-20 項目の中の箇条書きの子のフィールド行（入れ子が深くても）にだけ抽出を宣言したスキーマも、`schema_invalid` で停止する

## 導かれる値は5つの語にし、語ごとに宣言できるノードを限る

状態: 実装済み

### 問題

位置の情報は、文書から取り出した値ではなく、エンジンが導くものである。文字列にすると、使う側が必ず解析し直す手間だけが残る。要る利用者だけが宣言するので、要らない利用者の出力は変わらない。

生の行を暗黙の鍵で必ず持たせると、その名前を仕様が決めないまま実装が決めることになり、宣言した導かれる値と名前を取り合う（行番号を宣言すると生の行が黙って上書きされた）。語の1つにすれば、要るときだけ名前を付けて取り出せる。生の行を宣言できる範囲を行番号と違えると、その差を覚える必要が出るので、同じにする。項目の見出しの ID と名前を項目にだけ宣言できるようにした理由は残っていない。

### 決めたこと

導かれる値は、行番号 `line`、項目の見出しの ID `id`、項目の見出しの名前 `name`、生の行 `raw`、要素の最後の行 `end` の5つにする。ほかの語を宣言したスキーマは停止にする。

行番号と要素の最後の行は JSON の数値で出す。

`line` と `raw` はどのノードにも宣言できる。`id` と `name` は項目にだけ宣言でき、項目の外のノードに宣言したスキーマは停止にする。`end` は項目と節にだけ宣言でき、ほかのノードに宣言したスキーマは停止にする。

行番号と生の行が指す行は、[value か導かれる値を宣言したときだけ、要素ごとのオブジェクトを組み立てる](#value-か導かれる値を宣言したときだけ要素ごとのオブジェクトを組み立てる)の表のとおりにする。表の行は、ヘッダの行と区切りの行を数えず、そのデータ行を指す。生の行は、その行の文字を字下げと末尾の空白を含めてそのまま出し、組み立て直さない。

### 見送った案

- フラグで、すべての値を値と行番号の組に包む。使う側が2つの形を扱うことになる。

### 確認すること

- C-schema-extract-21 `line` と `end` の値は、JSON の数値で出る
- C-schema-extract-22 5つのどれでもない語を導かれる値に宣言したスキーマでは、`values` が停止し、終了コードは 2 である
- C-schema-extract-23 `id` か `name` を項目の外のノードに宣言したスキーマは、停止する
- C-schema-extract-24 `end` を項目と節の外のノード（例えば表）に宣言したスキーマでは、`values` が `schema_invalid` で停止する
- C-schema-extract-25 `line` と `raw` は、題名では見出しの行、表ではそのデータ行、フィールド行ではその行、コードブロックではフェンスの開始行を指す
- C-schema-extract-26 `raw` は、見出しや行の文字を、字下げ・末尾の空白・インラインの記法の記号を含めて書いたとおりに出す

## 要素の最後の行は、次の同じ深さか浅い見出しの手前の行にする

状態: 実装済み

### 問題

抽出の結果には、項目がどこで終わるかが無かった。項目の本文の範囲を切り出すには、その終わりの行が要る。

### 決めたこと

項目と節の `end` は、その見出しの後で次に現れる、同じ深さかそれより浅い見出しの手前の行の行番号にする。そのような見出しが無ければ、文書の最後の行の行番号にする。範囲の末尾の空行も、最後の行に含める。

### 確認すること

- C-schema-extract-27 項目と節の `end` は、次の同じ深さか浅い見出しの手前の行（間に空行があればその空行）で、後ろに見出しが無ければ文書の最後の行である

## 文に導かれる値を宣言すると行ごとの要素にし、要素の値は前後の空白を取り除く

状態: 実装済み

### 問題

kotowari は、文の行ごとに指摘の行と内容を出すために、行ごとの行番号と元の文字を必要とした。それまでの抽出は、続く行を1つの文字列につなぎ、開始行だけを返していたので、それを復元できなかった。

文の行の値を元の行そのものにすると、要素の値と生の行が同じものを指し、どちらを使うかが毎回の問いになる。分ければ、語の照合には要素の値、指摘の内容には生の行と、用途で選べる。値が1行なので、字下げを取っても行どうしの関係は崩れない。

### 決めたこと

文に導かれる値を宣言すると、文の行ごとに1つの要素を作る。空行を挟んで続く段落の行も、同じ並びに入る。一覧の行の継続段落は、文の要素に入らない。

行の要素の値は、前後の空白を取り除いた行の文字にする。元の行は生の行で取る。

### 見送った案

- 行ごとの生の行を要する検査を kotowari に残し、kotowari が Markdown を読む。Markdown を読まないという方針の例外が増え、方針が形だけになる。
- 行と指摘の内容が変わることを受け入れる。利用者から見える振る舞いを変えないという方針に反する。

### 確認すること

- C-schema-extract-28 文に導かれる値を宣言すると、行の数と同じ数の要素が出て、空行を挟んで続く段落の行も並びに入り、一覧の行の継続段落は入らない
- C-schema-extract-29 文の行の要素の値は前後の空白を取り除いた文字で、同じ行の生の行は字下げと末尾の空白を含む

## 表の行の鍵は、header の宣言か列の位置から取り、文書のヘッダ行の文字を使わない

状態: 実装済み

### 問題

Markdown の表のヘッダ行のセルは、空でも、同じ名前が重なってもよい。そこから鍵を作ると、値が黙って消える（空のヘッダの表で1列目の値が失われ、同じ名前の列が2つあると片方が消えた）。`header` を宣言しても、照合の指摘は出るが、抽出は文書の側の文字で続いていた。鍵の出どころをスキーマと位置に限れば、この経路は検出するものではなく、起こりえないものになる。この案の出どころは利用者である。

位置しか意味が無いなら配列が素直で、鍵の衝突という考え自体が消える。鍵が宣言の側から来る以上、列の数の基準も宣言の側に置かないと、余った列の鍵をどこから取るかがまた文書の側に戻る。

### 決めたこと

表の行の鍵は、スキーマが `header` を宣言したときはその名前、宣言しないときは列の位置にする。列の位置で取るときは、行を配列にする。どちらの場合も、文書のヘッダ行の文字を鍵に使わない。この決まりは、略記の形でも要素ごとのオブジェクトでも同じに効く。

`header` の名前の数と文書の列の数が違うときは、宣言した名前の数を正とする。文書の列が足りなければその鍵を省き、多ければ余りを捨てる。

### 見送った案

- 導かれる値を使う表に `header` の宣言を必須にする。表ごとに列の名前も数も違う表（決定表）は `header` を宣言できず、導かれる値を一切使えなくなる。
- 常に列の位置を鍵にする。用語集の表は列を名前で読んでいる。
- 文書のヘッダ行から鍵を取り、空のセル・重なった列の名前・導かれる値との衝突を検出して、指摘か停止にする。検出止まりで、間違えやすさそのものが残る。
- 位置と名前を結ぶ対応を、スキーマに別に宣言する。`header` の宣言がそのままその対応なので、別の仕組みは重複になる。

### 確認すること

- C-schema-extract-30 `header` を宣言した表の行は宣言した名前を鍵にしたオブジェクトに、宣言しない表の行は列の位置の配列になり、ヘッダのセルが空でも同じ名前の列が2つあっても、列の値は1つも失われない
- C-schema-extract-31 `header` の名前より文書の列が少なければ足りない列の鍵が省かれ、多ければ余った列の値が捨てられる

## 要素ごとに宣言した表が繰り返すときは表ごとの段を作り、それ以外は1つの配列につなぐ

状態: 実装済み

### 問題

配置パスは値を置く場所で、表が繰り返すなら置き場が複数になるのが素直である。これは、出現回数の範囲も宣言したときは配列の配列にする、という既にある流儀にも合う。要素の形そのものは、繰り返すかどうかで変えない。それ以外の表と箇条書きを1つの配列につなぐ理由は残っていない。

### 決めたこと

`value` か導かれる値を宣言した表に出現回数の範囲も宣言したときは、配置パスの直下に表ごとの段を作り、その中に行のオブジェクトを並べる。それ以外の表と箇条書きは、同じ置き場に複数現れても、文書に現れた順に1つの配列へつなぐ。

### 確認すること

- C-schema-extract-32 `value` か導かれる値と出現回数の範囲を宣言した表が2つあると、配置パスの直下は表ごとの段になり、行ごとの行番号はその表のデータ行を指す
- C-schema-extract-33 略記の形の表は、出現回数の範囲を宣言していても、同じ置き場の表の行を現れた順に1つの配列へつなぐ

## 区切り文字を宣言したフィールド行は、出現回数に関わらず配列にする

状態: 実装済み

### 問題

区切り文字を宣言したフィールド行の値を、どの形で出すかを決める必要がある。理由は残っていない。

### 決めたこと

区切り文字を宣言したフィールド行は、出現回数の宣言に関わらず、区切った文字列の配列へ抽出する。出現回数の範囲も宣言したときは、配列の配列にする。`value` か導かれる値も宣言したときは、この配列を `value` の鍵の下に置く。

区切るのは、継続段落を含めない値（空行を挟まずに続く行を含む）だけにする。継続段落は区切らず、区切った末尾の要素に付ける。

### 確認すること

- C-schema-extract-34 区切り文字を宣言したフィールド行の値は配列になり、出現回数の範囲も宣言すると配列の配列になる
- C-schema-extract-35 空行を挟まずに続く行は区切る対象に入り、継続段落は区切られずに区切った末尾の要素に付く
- C-schema-extract-36 区切り文字と `value` を宣言したフィールド行では、区切った配列が `value` の鍵の下に入る

## 値の行は、文書の元の行のまま使う

状態: 実装済み

### 問題

複数の行にわたる値の字下げと空行が崩れていた。段落の1行目だけ字下げが消え、2行目からは残り、段落どうしの間の空行は消える。箇条書き、フィールド行、文、節、項目のどれも同じ崩れ方をした。誰かが決めた規則ではなく、段落を切り出す位置の誤りだった。

箇条書きの要素を組み立て直すと、書き手が置いた空白や記法が失われ、抽出した値から元の行に戻せなくなる。これを箇条書きの1行目だけでなく値の全体で成り立たせ、場所ごとに扱いが変わる形を残さない。フィールド行の名前やマーカーの前の字下げは値ではない。範囲の元の行から含めない行を抜いた形にすれば、部分の種類ごとのつなぎ方の規則が要らない。それまでは、文どうしだけ空行、ほかは改行、継続段落どうしは空行と、場所ごとに違っていた。マーカーだけの行の後の lead 段落と継続段落の間には、元の文書で必ず空行があり、この規則がそれを残すので、形ごとの規則は要らない。

### 決めたこと

値に入る行は、文書の元の行のまま使う。字下げと、値の途中の行の末尾の空白を残し、値の末尾の空白と空行を除く。

値が始まる位置はノードごとに決める。箇条書きはその行のマーカーから（マーカーの後の空白も含める）、フィールド行は名前の後のコロンと空白の後から、文は段落の最初の空白でない文字から始める。2行目からは行の先頭から取る。

複数の部分から成る値（箇条書きの lead 段落・継続段落・子の箇条書き、フィールド行の lead 段落と継続段落、文の並び、節の本文、項目の本文）は、含める部分の間に元の文書で空行があれば空行1つで、無ければ改行1つでつなぐ。含めない部分の行は抜き、抜いた跡と、元の文書で続いていた空行は、空行1つにまとめる。空白だけの行は空行として扱う。マーカーだけの行の後の lead 段落と継続段落の間も、この決まりのとおり元の空行が残る。

行に分けた文の要素の値は、この決まりの外で、[文に導かれる値を宣言すると行ごとの要素にし、要素の値は前後の空白を取り除く](#文に導かれる値を宣言すると行ごとの要素にし要素の値は前後の空白を取り除く)のとおりにする。

### 見送った案

- 一覧の中身の字下げを、すべての行から除く。元の行に戻せるという決まりとぶつかり、子の箇条書きの行だけ字下げを残す例外が要る。
- 部分ごとに切り出して、改行1つでつなぐ（直す前のやり方）。部分の中には空行が残り、部分の間では消える。
- どの形でも、lead 段落と継続段落を改行1つでつなぐ。元の段落の区切りが値から消える。

### 確認すること

- C-schema-extract-37 複数の行にわたる値は、2行目からの字下げと、途中の行の末尾の空白を元のまま持つ
- C-schema-extract-38 フィールド行の値は名前の後の空白の後から始まり、箇条書きの値はマーカーから始まる
- C-schema-extract-39 含める部分の間に元の文書で空行があれば空行1つで、無ければ改行1つでつながり、含めない部分を抜いた跡の空行は1つにまとまる。読み方を行（`reading: line`）にしても、文の行の間に元の文書に無い空行は足されない
- C-schema-extract-40 マーカーだけの行の後に lead 段落が来る箇条書きの値は、lead 段落を欠かさず、lead 段落と継続段落の間に元の空行が残る

## 見出しの名前と表のセルの値は、インラインの記法の記号を外した文字で読む

状態: 実装済み

### 問題

見出しの名前やセルの値として使うのは、記号ではなく文字のほうである。今の振る舞いを利用者が追認した。

### 決めたこと

mds は、見出しの名前と表のセルの値を、インラインの記法の記号を外した文字で読む。強調、太字、リンク、参照リンクは中の文字をつなげ、インラインコードは中身を残す。スキーマに宣言した見出しの名前との照合も、この記号を外した文字で行う。

### 確認すること

- C-schema-extract-42 節の名前を "Req" と宣言したスキーマで "## **Req** x" の見出しを持つ文書を `kotowari-mds check` にかけると、その見出しは "Req x" と読まれ、宣言していない見出しの指摘になる

## 導かれる値の name は節にも、end は箇条書きにも宣言できる

状態: 提案

### 問題

節の抽出は、見出しの文字を取り出せない。見出しの文字が自由な節（[節と項目の規則は、見出しを名前の一覧か正規表現で選ぶ](schema-language.ja.md#節と項目の規則は見出しを名前の一覧か正規表現で選ぶ)の "pattern" で選ぶ節）では、値がどの見出しの節のものかが分からない。箇条書きの抽出は、行の最後の行を取り出せず、行の本文の範囲を切り出せない。kotowari は、確認することの行の本文を返すのに、その行の最後の行を要る。

### 決めたこと

導かれる値の語を宣言できるノードは、次のとおりにする。語を、それを受けないノードに宣言したスキーマは停止にする。

| 語 | 宣言できるノード |
|---|---|
| `line`、`raw` | どのノードにも |
| `id` | 項目 |
| `name` | 項目、節 |
| `end` | 項目、節、箇条書き |

節の `name` は、節の見出しの文字（[見出しの名前と表のセルの値は、インラインの記法の記号を外した文字で読む](#見出しの名前と表のセルの値はインラインの記法の記号を外した文字で読む)の読み方）にする。箇条書きの `end` は、その一覧の項目の最後の行（継続段落と子の一覧を含む）の行番号にする。

### 見送った案

- 以前の決定: `id` と `name` は項目にだけ、`end` は項目と節にだけ宣言できる（[導かれる値は5つの語にし、語ごとに宣言できるノードを限る](#導かれる値は5つの語にし語ごとに宣言できるノードを限る)の決めたことの3段目）。節の見出しの文字と、箇条書きの行の最後の行を取り出せないので、やめた。

### 確認すること

- C-schema-extract-45 節の抽出の `of` に `name` を宣言すると、節ごとの要素の `name` の鍵に、その節の見出しの文字が入る
- C-schema-extract-46 箇条書きの抽出の `of` に `end` を宣言すると、各行の要素の `end` は、その一覧の項目の、継続段落と子の一覧を含めた最後の行の行番号（JSON の数値）になる
- C-schema-extract-47 `id` を項目の外のノードに、`name` を項目と節の外のノード（例えば箇条書き）に、`end` を項目・節・箇条書きの外のノード（例えば表）に宣言したスキーマでは、`values` が `schema_invalid` で停止する

## 名前付きキャプチャは、題名と箇条書きの of の鍵の値に group で書く

状態: 提案

### 問題

名前付きキャプチャ `group` は、題名の抽出にだけ、`path` と並べて書ける。値はキャプチャの文字だけになり、行番号のようなほかの導かれる値と並べて取り出せない。箇条書きの行を、正規表現で部分に切り分けて取り出すこともできない。kotowari の決定の文書の確認することの行（"- C-x-1 （読んで確認）文"）は、ID、「（読んで確認）」の有無、名前に切り出す必要があり、宣言できなかった。

### 決めたこと

`of` の鍵の値に `{ group: <名前> }` を書くと、その鍵に、ノードの正規表現の、その名前付きキャプチャが捕まえた文字を置く。題名と箇条書きに宣言できる。題名では題名の正規表現の、箇条書きでは箇条書きの正規表現（[箇条書きの正規表現は、一覧の項目の先頭の段落を1行につないだ文字と照合する](block-rules.ja.md#箇条書きの正規表現は一覧の項目の先頭の段落を1行につないだ文字と照合する)）のキャプチャを使う。

照合に加わらなかった名前付きキャプチャの鍵は、その要素に出さない。題名の要素の値（`value` の鍵）は、キャプチャを宣言しても、見出しの文字列のままにする。

`path` と並べて `group` を書く形は受けず、書いたスキーマは停止にする。題名と箇条書きの外のノードに `group` を書いたスキーマと、`group` を書いたノードに正規表現が無いか、正規表現がその名前付きキャプチャを含まないスキーマも、停止にする。

### 見送った案

- 以前の決定: 名前付きキャプチャ `group` は、`of` の下ではなく `path` と並べて書き、題名にだけ宣言できる（[抽出は、path・value・of を持つ1つの入れ子で宣言する](#抽出はpathvalueof-を持つ1つの入れ子で宣言する)の決めたことの3段目）。キャプチャを箇条書きに使えず、ほかの導かれる値と並べて取り出せないので、やめた。

### 確認すること

- C-schema-extract-48 箇条書きの正規表現 "^(?P<code>[A-Z]-[0-9]+) (?P<text>.*)$" と `of: { code: { group: code }, text: { group: text } }` を宣言すると、各行の要素の `code` と `text` に、それぞれのキャプチャが捕まえた文字が入る
- C-schema-extract-49 照合に加わらないことのある名前付きキャプチャ（例えば "(?P<flag>!)?"）を `of` に宣言すると、そのキャプチャが加わらなかった行の要素には、その鍵が無い
- C-schema-extract-50 マーカーの行に空行を挟まずに続く行を持つ箇条書きでは、キャプチャの文字が、先頭の段落を空白1つでつないだ文字から取られる
- C-schema-extract-51 題名の `of` に `{ group: <名前> }` を宣言すると、その鍵に題名の正規表現のキャプチャの文字が入り、`value` の鍵には見出しの文字列が入る
- C-schema-extract-52 `path` と並べて `group` を書いた抽出、題名と箇条書きの外のノードの `of` に `group` を書いた抽出、正規表現の無いノードか名前付きキャプチャを含まない正規表現のノードに `group` を書いた抽出のどれかを宣言したスキーマでは、`values` が `schema_invalid` で停止する
