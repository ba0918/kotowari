# 任意の Tokio 対応

[English](library-async.md) | 日本語

kotowari と kotowari-markdown-schema-io の高水準の操作を Tokio から待つ入口と、同時に動かす数、待機をやめたときの振る舞いを扱う。ここで決める実行枠、待機の取り消し、ランタイムとの関係とランタイムが無いときの失敗は、kotowari の `AsyncProject` と kotowari-markdown-schema-io の `AsyncSchemaLoader` に共通である。`AsyncSchemaLoader` が同期の読み込みと同じ結果を返すことは、「スキーマと文書を読み込むライブラリ」の話題の[Tokio の feature を選んだ呼び出しにも、同期と同じ結果を返す](../schema/library-io.ja.md#tokio-の-feature-を選んだ呼び出しにも同期と同じ結果を返す)で決める。どのパッケージが Tokio に依存しないかは「ライブラリのクレート境界」の話題の[計算のクレートは環境を操作せず、Tokio と CLI の依存を持たない](library-crates.ja.md#計算のクレートは環境を操作せずtokio-と-cli-の依存を持たない)で決める。

## 高水準の操作を、既定で無効な tokio feature で Tokio から待てるようにする

状態: 実装済み

### 問題

非同期のアプリからも kotowari を使えるようにしたい。そのとき、同期の検査の処理と、既存の読み込みの処理は使い回したい。

非同期のために利用者が選ぶパッケージは増やさず、同期で使う利用者には Tokio への依存を求めない。

### 決めたこと

同期の API を基本にする。kotowari は、既定で無効な `tokio` feature で `AsyncProject` を提供し、同期の `Project` の高水準の操作を await できるようにする。`AsyncProject` は同期の処理を、呼び出し側の Tokio のランタイムの `spawn_blocking` に渡して動かし、検査の処理を別に持たない。同じ入力には、同期の `Project` と同じ値、指摘、失敗の種類を返す。

kotowari のコマンド（CLI）は、同期の API を使う。

### 見送った案

- 同期の API と、非同期のアプリから呼ぶ利用例だけを出す。利用者は、高水準の操作を await できる Tokio 対応まで出す案を選んだ。

### 確認すること

- C-core-libasync-1 `tokio` feature を有効にすると、`AsyncProject` の操作が、Tokio の上で、同期の `Project` と同じ値、指摘、失敗の種類を返す
- C-core-libasync-2 （読んで確認）`tokio` feature は既定で無効で、`AsyncProject` は同期の処理を `spawn_blocking` に渡して動かし、CLI は同期の API を使う

## 同時に動かす数は、非同期の入口のオブジェクトごとに限り、複製どうしは実行枠を共有する

状態: 実装済み

### 問題

非同期の呼び出しが多数来たときに、処理を動かすスレッドが増え続けるのを避けたい。どこまでの範囲で数を限るのかを明示し、利用者が実行の環境に合わせて調整できるようにしたい。オブジェクトを複製するだけで、意図した上限を迂回できてはならない。

### 決めたこと

`AsyncProject` と `AsyncSchemaLoader` は、同時に動かす処理の数を、オブジェクトごとに限る。上限は `AsyncOptions` で渡す。既定の上限は1で、変えるときは正の整数を `NonZeroUsize` で渡す。

処理は、実行枠を1つ得てから動き出す。別々に作ったオブジェクトは、それぞれの実行枠を持つ。複製したオブジェクトどうしは、同じ実行枠を共有する。

### 確認すること

- C-core-libasync-3 `AsyncOptions` の既定の上限は1で、上限を2にしたオブジェクトでは2つの処理が同時に動き、3つ目は実行枠が空くまで投入されない
- C-core-libasync-4 別々に作ったオブジェクトは実行枠を共有せず、複製したオブジェクトどうしは実行枠を共有する

## 待機をやめても、始まった処理は止めず、終わるまで実行枠を持つ

状態: 実装済み

### 問題

`spawn_blocking` に渡した処理は、動き出したあとは abort で止められない。呼び出し側が待機をやめることと、処理そのものが止まることは、区別しなければならない。

また、待機の取り消しを繰り返すことで、実際に同時に動く数が上限を超えてはならない。

### 決めたこと

実行枠を待っている間に待機をやめた処理は、投入しない。投入した処理は、呼び出し側が待機をやめても、終わるまで実行枠を持ち続ける。

待機をやめても、始まった HTTP の取得、計算、キャッシュの書き込みは止まらない。止めることは保証せず、そのことを公開 API の約束として利用者に示す。

### 見送った案

- HTTP の取得の待ちを非同期の I/O で作り直し、始まった処理を途中で止める仕組みも足す。利用者は、同期の処理を使い回して非同期のアプリから呼べるようにする案を選んだ。

### 確認すること

- C-core-libasync-5 実行枠を待っている間に待機をやめた処理は、あとで実行枠が空いても投入されない
- C-core-libasync-6 投入された処理への待機をやめても、その処理が終わるまで実行枠は空かず、複製したオブジェクトから求めた別の処理は投入されない
- C-core-libasync-7 （読んで確認）利用者向けのガイドに、待機をやめても始まった HTTP の取得、計算、キャッシュの書き込みは止まらないと書いてある

## ランタイムの外で待つか、ランタイムが止まったときは、panic せず種類を見分けられる失敗を返す

状態: 実装済み

### 問題

非同期の入口は、呼び出し側の Tokio のランタイムに処理を渡す。ランタイムの外で待たれたときや、待っている間にランタイムが止まったときに panic すると、呼び出し側のアプリごと落ちる。呼び出し側は、この失敗を、検査の結果や、ほかの失敗と見分けて扱えなければならない。理由は記録に残っていない。

### 決めたこと

`AsyncProject` と `AsyncSchemaLoader` は、呼び出し側の Tokio のランタイムの上で動き、内部のランタイムを作らない。

Tokio のランタイムの外で操作を待つと、panic せず、`RuntimeUnavailable` の種類の失敗を返す。処理を実行できずに終わったとき（待っている間にランタイムが止まったとき）は、panic せず、`TaskFailure` の種類の失敗を返す。

### 確認すること

- C-core-libasync-8 Tokio のランタイムの外で `AsyncProject` か `AsyncSchemaLoader` の操作を待つと、panic せず、`RuntimeUnavailable` の種類の失敗が返る
- C-core-libasync-9 実行枠を待っている処理があるうちにランタイムが止まると、待っていた処理は panic せず、`TaskFailure` の種類の失敗を返す
