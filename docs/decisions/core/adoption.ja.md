# 既存プロジェクトへの導入

[English](adoption.md) | 日本語

既存のプロジェクトに kotowari を途中から入れるための工程の skill kotowari-adopt が、1つの話題について旧資料と実装とテストを突き合わせて仕分け、決定の文書に書くまでを扱う。範囲の決め方と一覧の行の作り方は[導入の範囲と行の作り方](adoption-scope.ja.md)で決める。人が追認した振る舞いを状態が「実装済み」の決定として書くこと、取り込みごとの記録を書かないこと、人が追認していない振る舞いを書かず理由を作らないことは、工程の話題の[既存のコードを取り込むときは、人が追認した振る舞いを「実装済み」で書く](workflow.ja.md#既存のコードを取り込むときは人が追認した振る舞いを実装済みで書く)で決める。ここにあるのは、skill の文を人か LLM が読んで確かめる決定だけである。

## 導入は工程の skill kotowari-adopt が行い、承認は壁打ちの承認の手順で行う

状態: 実装済み

### 問題

壁打ちの skill kotowari-brainstorm は、問いの木を尽くすまで終わらず、妥協しない。導入は逆に、決めないものを残して先へ進むのが要である。同じ skill に入れると、どちらかの決まりが骨抜きになる。人に聞く場面のある手順は工程の skill の役目で、kotowari スキルは書き方の辞書である。

### 決めたこと

導入の手順は、工程の skill kotowari-adopt として持つ。承認は、kotowari-brainstorm の承認の手順を名指しして使う。

### 見送った案

- kotowari スキルの reference に導入の場面を足す。人に聞く手順を辞書の側に持ち込むことになる。

### 確認すること

- C-core-adopt-1 （読んで確認）`agent/skills/kotowari-adopt/` があり、その skill に、承認を kotowari-brainstorm の承認の手順を名指しして行うと書いてある

## 既存の仕様やコードを取り込みたい依頼は、入口で kotowari-adopt に振る

状態: 実装済み

### 問題

入口で振り分けないと、導入が壁打ちとして回り、導入を別の skill に分けた意味が無くなる。

### 決めたこと

kotowari-using-workflow は、既存の仕様やコードを決定の文書に取り込みたい依頼と、決定の文書が実装と合っているか分からない依頼を、kotowari-adopt に振る。

## 一致は実装を読んで判定し、テストの有無は一致の条件にしない

### 問題

### 決めたこと

## 旧資料と実装の突き合わせの結果で、行の行き先を決める

状態: 実装済み

### 問題

既存のプロジェクトでは、旧資料と実装が一致するもの、食い違うもの、片方にしか無いものが混ざっている。導入のその場で全部を決めようとすると面談が膨らむので、決めないものを決めないまま見える所に残し、先へ進む必要がある。

旧資料と実装が一致する振る舞いは、利用者が期待した結果そのものが空白期間で記憶から消えていて、項目ごとに期待を聞いても答えが出ない。2つの出所の一致を固める危険は、全部を見直すために導入が止まる損より小さい。旧資料に記述が無くても、利用者から見えてそれを確かめるテストがある振る舞いは、誰かが意図して守ってきた証拠がある。残っている判断の記録の決定は、追認より重い。旧資料にだけある振る舞いは、作るものと作らないものを人に分けてもらえば、作るものを、テストを求めない形で仕様に置ける。すべてを動かして確かめるのは費用として重いので、読み違えの可能性は、読み切れなかった行として見える所に残す。

すでに決定の文書がある話題でも、決定の切り方が怪しいことがある。決定を導入の場で書き換えると、人が決めたこととの関係が見えなくなる。作らないと人が答えた旧資料の記述を決定の文書に書かない理由と、旧資料に記述が無くテストも無い振る舞いを追認の候補にする理由は、記録に残っていない。旧資料の側は書き換えないので、作らない記述は旧資料に残る。

### 決めたこと

一覧の行は、次の表の行き先に仕分ける。「旧資料の記述」には、旧資料の中の判断の記録の決定も入り、話題にすでにある決定の文書の決定は入らない。すでにある決定は、表の「すでにある決定」の行でだけ扱う。

| 対象 | 状況 | 行き先 |
|---|---|---|
| 旧資料の記述 | 旧資料の判断の記録にある決定で、実装と一致する | 一覧で追認を求めず、その決定のとおりに、状態が「実装済み」の決定として書く |
| 旧資料の記述 | 実装と一致する（そう決めた判断の記録は無い） | 追認の候補 |
| 旧資料の記述 | 実装と食い違う | 「未決」の項目 |
| 旧資料の記述 | 読んでも、実装と一致するか食い違うか確信が持てない | 「未決」の項目 |
| 旧資料の記述 | 実装が無く、人が作る予定ありと答えた | 状態が「提案」の決定 |
| 旧資料の記述 | 実装が無く、人が作らないと答えた | 決定の文書に書かない |
| 旧資料に記述の無い振る舞い | 利用者から見え、それを確かめるテストがある | 旧資料なしと示した追認の候補 |
| 旧資料に記述の無い振る舞い | 利用者から見え、それを確かめるテストが無い | 旧資料なし・根拠のテストなしと示した追認の候補 |
| 旧資料に記述の無い振る舞い | 利用者から見えない内部の振る舞い | 書かない |
| 追認の候補 | 人が一覧で外さなかった | 状態が「実装済み」の決定 |
| 追認の候補 | 人が一覧で外した | 「未決」の項目 |
| すでにある決定 | 実装と一致する | そのまま残す |
| すでにある決定 | 実装と食い違う、または一致するか確信が持てない | 書き換えも削除もせず、「未決」の項目にしてその決定へリンクする |

「未決」の項目は、話題の文書の「未決」の節に、1件ごとに書く。何が食い違うか（人が外した行は人の期待と実装の食い違い、確信が持てない行は何が読み切れなかったか）と、旧資料の場所を書き、決めるのは利用者で、その機能を次に壁打ちするときに決める、と書く。導入のその場では決めない。

旧資料の判断の記録の決定を使うときは、その決定に理由が書いていなくてもそのまま使い、旧資料の側は書き換えない。

### 確認すること

- C-core-adopt-4 （読んで確認）kotowari-adopt の skill に、上の表の行がすべて同じ行き先で書いてある
- C-core-adopt-5 （読んで確認）kotowari-adopt の skill に、食い違いと読み切れなかった行は導入の場で決めず、話題の文書の「未決」の節に、何が食い違うか（または何が読み切れなかったか）と旧資料の場所と、決めるのは利用者でその機能を壁打ちするときだと書くと書いてある
- C-core-adopt-23 （読んで確認）kotowari-adopt の skill に、話題にすでにある決定は書き換えも削除もせず、実装との食い違いは「未決」の項目にしてその決定へリンクすると書いてある

## 人に聞くのは、範囲の確認、一覧の1ラウンド、承認の3回だけにする

状態: 実装済み

### 問題

人の手を借りる回数を決めておかないと、項目ごとの面談に戻る。

## 一覧の行には旧資料の記述と実装の振る舞いと根拠のテストを並べ、「未決」にする行は見せるだけにする

状態: 実装済み

### 問題

人が一覧で違和感のある行を見つけるには、旧資料が何と言い、実装が何をし、何がそれを確かめているかが、行ごとに並んでいる必要がある。人に聞く回数を3回に保つには、人が答えなくてよいものを、答えるものと分けて見せる必要がある。

### 決めたこと

一覧の振る舞いの行には、旧資料の記述、実装の振る舞い、根拠のテストの場所（無ければ「なし」）、その行を確かめる方法（[追認で書く確認することの行は、テストが無いことを理由に「（読んで確認）」にしない](#追認で書く確認することの行はテストが無いことを理由に読んで確認にしない)）を並べる。

「未決」の項目にする行と、テストの行き先の内訳は、一覧で見せるだけにし、人には聞かない。承認で人が読む決定の文書の差分が、一覧の最終版になる。

- C-core-adopt-10 （読んで確認）kotowari-adopt の skill に、「未決」にする行とテストの内訳は見せるだけで、承認で読む決定の文書の差分が一覧の最終版になると書いてある

## 追認で書く確認することの行は、テストが無いことを理由に「（読んで確認）」にしない

状態: 実装済み

### 問題

一致の判定にテストの有無を使わないので、根拠のテストの無い追認の決定が出る。テストが無いことを理由に、その行を人や LLM が読んで確かめる行にすると、テストの無さが仕様の側に隠れて見えなくなる。

### 決めたこと

追認して書く決定の、確認することの行の確かめ方は、振る舞いの中身で決める。実装の振る舞いと、入力の全体に成り立つ性質は、テストで確かめる行にする。コードの外のもの（文書、運用の手順）は「（読んで確認）」の行にする。テストが無いことを理由に「（読んで確認）」にしない。

行ごとの確かめ方は一覧に示し、人には聞かない。

### 確認すること

## 取り込みでは用語を仕分けない

## 範囲のテストを1件ずつ4つの行き先に仕分け、内訳を一覧のラウンドと承認で見せる

状態: 実装済み

### 問題

ある既存のプロジェクトの導入で、既存のテスト2,821件に対してマーカーは174個だった。マーカーを付けたテストの数が元のテストの数よりずっと少なく、利用者が不安になった。全体の数を比べても答えは出ず、1件ごとの行き先の内訳で説明できて初めて、テストが減ったのではないと分かる。

利用者から見えない振る舞いにも大事なテストがあるので、それを削除の候補にはしない。

### 決めたこと

話題の範囲にある既存のテストは、すべて1件ずつ、次のどれか1つに振り分ける。

- 決定の根拠: 決定になる行と追認の候補の行を確かめるもの。承認のあとにマーカーを付ける候補になる
- 「未決」にした振る舞いのテスト: 残し、その「未決」を決めるときに扱いを決める
- 実装の細部をなぞるだけのもの: 削除の候補
- 残す: 決定の文書に書かない内部の振る舞いを確かめるものと、判断がつかないもの

行き先ごとの件数の内訳は、一覧のラウンドと承認で見せる。

### 見送った案

- `kotowari status` に、マーカーの無いテストの数のような全体の数を足す。全体の数を並べる比べ方そのものが不安を生んでいて、意味のある数は話題ごとの内訳だけである。

### 確認すること

- C-core-adopt-14 （読んで確認）kotowari-adopt の skill に、範囲のテストをすべて、決定の根拠、「未決」にした振る舞いのテスト、実装の細部をなぞるだけのもの（削除の候補）、残す、の4つのどれか1つに振り分け、内訳を一覧のラウンドと承認で見せると書いてある

## 承認のあとの作業は、1つの依頼文にして会話で渡し、どの工程で回すかは入口が決める

状態: 実装済み

### 問題

テストの行き先の内訳の件数（たとえば根拠40、細部250）は、小さな作業の工程を超えることがある。件数に応じて、どの工程で回すかを入口が決めるほうが合う。候補は一覧と内訳から出し直せるので、ファイルに残さなくてよい。

細部をなぞるだけのテストは、実装を固めて作り直しを妨げ、変異テストでは全テストの時間が変異の数だけ掛け算になる。git で戻せるので、消すかをまとめて決めても危険は小さい。大事なテストを消していないかを機械的に確かめる手段は、変異テストの比べ方だけである。変異テストを回していないプロジェクトにその導入まで求めると、導入の費用が膨らむ。削除の作業をするのは取り込みのあとの工程なので、比べ方を依頼文に書かないと手順が届かない。

### 決めたこと

承認のあと、kotowari-adopt は1つの依頼文を会話で人に渡す。依頼文はファイルに残さない。どの工程で回すかは kotowari-using-workflow が決める。

依頼文には次を入れる。

- 細部をなぞるだけのテストを消すかを、人がまとめて決める作業
- マーカーを付けるテストを、設定の "tests.files" の範囲に入れる作業。中に移すか "tests.files" を広げるかは、プロジェクトの既存の設定に従う
- 変異テストを回しているプロジェクトでは、削除の前後で話題のコードに対して生き残る変異を比べ、増えたら消したテストを戻して「残す」に入れる手順。回していないプロジェクトには求めない

### 見送った案

- 以前の決定: 承認のあとのマーカー付け、細部のテストの削除、テストの置き直しを kotowari-iterate で回す。件数が小さな作業の工程を超えることがあるので、入口が工程を決める形にした。

## テストを書くまで残る誤りと、「未決」が残る間の complete が、狙いどおりだと案内する

状態: 実装済み

### 問題

根拠のテストの無い確認することの行は、テストを書くまで check の誤りとして残る。push や CI で check を求めるプロジェクトでは、それで止まる。また、「未決」が残る間は完了にならない。どちらも、壊れていると読まれないように、狙いを伝えておく必要がある。

### 決めたこと

kotowari-adopt は、利用者に次の2つを案内する。

- 根拠のテストが無い確認することの行は、テストを書くまで confirmation_without_test の誤りが残る。push や CI で `kotowari check` を求めるプロジェクトではそれで止まるので、導入と、あとのテストの作業を同じ枝で進める。コミットは `kotowari check --allow-test-findings` を走らせる pre-commit で通る（この扱いは[既存のコードを取り込むときは、人が追認した振る舞いを「実装済み」で書く](workflow.ja.md#既存のコードを取り込むときは人が追認した振る舞いを実装済みで書く)で決める）
- 「未決」の項目が残る間は、`kotowari status` の complete が false になる。それは決めるのを待っているものの一覧で、狙いどおりである

### 確認すること

- C-core-adopt-19 （読んで確認）kotowari-adopt の skill に、根拠のテストが無い確認することの行は confirmation_without_test がテストを書くまで残り、push や CI で止まるので、導入とあとのテストの作業を同じ枝で進めると案内すると書いてある
- C-core-adopt-20 （読んで確認）kotowari-adopt の skill に、「未決」が残る間は `kotowari status` の complete が false で、それが狙いどおりだと案内すると書いてある

## 面の規則を最初に書いたときに出る面は、すべて未記載の面の一覧に載せ、導入の話題ごとに減らす

状態: 実装済み

### 問題

既存のプロジェクトで面の規則を書くと、最初から大量の surface_without_spec が出る。それでも導入できるように、まだ仕様にしていない面を一覧に載せて誤りにしない仕組みがある（[まだ仕様にしていない面は、理由を付けて未記載の面の一覧に載せれば誤りにしない](surface-unspecified.ja.md#まだ仕様にしていない面は理由を付けて未記載の面の一覧に載せれば誤りにしない)）。その一覧を減らす作業は、導入の流れに乗せる。

### 決めたこと

面の規則を最初に書いたときの `kotowari check` が surface_without_spec を出す面は、すべて未記載の面の一覧に1件ずつ載せる。そのときには、その面の決定を書かない。一覧は、導入の話題ごとに減らす。

## 導入で話題の面を決定に書いたら、その面の1件を未記載の面の一覧から外す

状態: 実装済み

### 問題

一覧から外すのは、面を仕様に書いたときだけである。仕様にならなかった面は、一覧に残るのが帰結になる。

### 決めたこと

導入で、追認した決定の「決めたこと」か「確認すること」が話題の面の名前を引用したら、同じ回に、未記載の面の一覧からその面の1件を外す。「未決」になった面と、一覧のラウンドで人が外した面の1件は、一覧に残す。
