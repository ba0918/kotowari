# テストとマーカーの対応

[English](coverage.md) | 日本語

テストにマーカーがあるかの検査と、問い合わせの無い言語のファイルのマーカーの数え方と、決定の文書が無いときのテストの検査を扱う。確認することの行ごとに、それを指すテストがあるかを数える決まりは、[check は、確認することの行ごとに、それを指すテストがあるかを数える](confirmations.ja.md#check-は確認することの行ごとにそれを指すテストがあるかを数える)で決める。マーカーの形と、マーカーをテストに結び付ける規則は[テストのマーカー](test-markers.ja.md)で決める。

## マーカーの無いテストには test_without_id の誤りを出す

状態: 実装済み

### 問題

check が見つけたテストにマーカーが無いときに、どうするかを決める必要がある。マーカーの無いテストを誤りにすると決めた理由は残っていない。誤りの detail にテストの名前を使うと、名前を持たないテストでは detail が空になり、どのテストか分からない。

### 決めたこと

問い合わせのある言語のテストにマーカーが無いとき、check はそのテストの名前を detail にして test_without_id の誤りを出す。

テストの名前が null のとき（問い合わせが名前を捕まえないとき）は、テストの節の最初の行の、行全体の文字から前後の空白を除いたものを detail にする。ほかの種類の指摘でも、行の文字そのままを detail にしている。節が行の途中から始まる形（"const t = test(...)"）でも行全体を使うのは、指摘の "line" も行で決めているからである。

### 確認すること

- C-core-cover-1 問い合わせのある言語のテストにマーカーが無いと、check がそのテストの名前を detail にした test_without_id の誤りを出し、マーカーを付けると出さない
- C-core-cover-2 名前が null のテストにマーカーが無いと、test_without_id の detail は、そのテストの最初の行の全体から前後の空白を除いた文字になる

## 問い合わせの無い言語のファイルのマーカーも、確認することの行を満たす側に数える

状態: 実装済み

### 問題

問い合わせの無い言語のテストのファイルでは、check はテストを見つけられず、ファイルの中のマーカーを拾うだけである（[問い合わせの無い言語のファイルでは、ファイルの中のマーカーをすべて拾う](test-markers.ja.md#問い合わせの無い言語のファイルではファイルの中のマーカーをすべて拾う)）。拾ったマーカーをどう数えるかを決める必要がある。マーカーの扱いを、言語ごとに2つにしない。

### 決めたこと

問い合わせの無い言語のテストのファイルで拾ったマーカーは、問い合わせのある言語のテストのマーカーと同じく、確認することの行にテストがあるかを数えるときに、その行を満たす側に数える。

問い合わせの無い言語のファイルからは、テストを見つけないので、test_without_id の誤りを出さない。

### 確認すること

- C-core-cover-3 問い合わせの無い言語のファイル（".go"）のマーカーが、実装済みの決定の確認することの行を指していれば、その行に confirmation_without_test が出ない
- C-core-cover-4 問い合わせの無い言語のファイルからは、test_without_id が出ない

## 決定の文書が1つも無くても、テストの検査は行う

状態: 実装済み

### 問題

決定の文書の置き場に文書が1つも無いときに、テストの検査をするかを決める必要がある。そう決めた理由は残っていない。

### 決めたこと

決定の文書の置き場に文書が1つも無いとき、決定の文書の検査の指摘は0件にし、テストの検査は行う。確認することの行が無いので confirmation_without_test は出ず、マーカーの無いテストには test_without_id が出る。

### 確認すること

- C-core-cover-5 決定の文書の置き場に文書が無く、マーカーの無いテストが1つあると、check はそのテストの test_without_id だけを出し、終了コード1で終わる

## 行を持たないテストは `@kotowari[detail]` と宣言でき、宣言したテストには test_without_id を出さない

状態: 提案

### 問題

決定の文書には人が決めたことだけを書き、実装する側が決めた細部と、壁打ちで聞かずに決めたことは書かない（[実装の途中で見つかった細部は、実装する側が決める](workflow.ja.md#実装の途中で見つかった細部は実装する側が決める)、[壁打ちで聞かずに決めたことは、承認のときに一覧で見せ、仕様のコミットの本文に書いて実装する側へ運ぶ](workflow.ja.md#壁打ちで聞かずに決めたことは承認のときに一覧で見せ仕様のコミットの本文に書いて実装する側へ運ぶ)）。その振る舞いにもテストは書くが、テストが指す確認することの行が無い。マーカーの無いテストは誤りになり（[マーカーの無いテストには test_without_id の誤りを出す](#マーカーの無いテストには-test_without_id-の誤りを出す)）、マーカーにはそのテストが確かめる行の ID を書くので、正しい書き方が無かった。

人の役を LLM に務めさせた試しでは、同じ状況で、作業役の動きが割れた。ある回の作業役は、実装の途中で人に聞き、振る舞いを決定の文書に足した。承認のあとに人を待たせ、人が推奨を受け入れただけの振る舞いが、人の決定として文書に載った。別の回の作業役は、関係の薄い行の ID を書いて通した。行を確かめていないテストが、その行を指すことになった。

### 決めたこと

テストの直前のコメントの塊に `@kotowari[detail]` と書くと、そのテストは、確認することの行を持たない振る舞いを確かめるテストだと宣言したことになる。"detail" は ID ではなく決まった語で、マーカーの始まりと終わりは、行の ID を書くマーカーと同じである。

宣言したテストには、check は test_without_id を出さず、"detail" に unresolved_reference も出さない。宣言は、どの確認することの行も満たす側に数えない。マーカーが1つも無いテストには、test_without_id の誤りを出す。

### 見送った案

- いちばん近い決定の行の ID を書く。行を確かめていないテストがその行を指すので、行を確かめるテストが無くても confirmation_without_test が出なくなりうる。`kotowari query` も、関係の薄いテストを返す。
- 実装する側が、人に聞かずに決定と確認することの行を足す。決定の文書に、人が承認していない決定が混ざる。
- マーカーの無いテストを誤りにするのをやめる、または注意に下げる。テストの直前のコメントの塊に無くて結び付かなかったマーカーが、黙って消えても気づけなくなる。
- 宣言を `@kotowari[-]` と書く。記号の意味は、説明を読まないと分からない。
- 括弧の無い別のマーカー `@kotowari-detail` にする。マーカーの始まりが2種類になり、結び付けと形の誤りの規則を、2つ目のマーカーにも当てることになる。

### 確認すること

- C-core-cover-6 直前のコメントの塊に `@kotowari[detail]` があるテストに、check が test_without_id も unresolved_reference も出さない
- C-core-cover-7 実装済みの決定の確認することの行を指すテストが無く、`@kotowari[detail]` と宣言したテストだけがあるとき、その行に confirmation_without_test が出る
