# 変異の結果の検査

[English](mutants.md) | 日本語

"kotowari mutants" が変異の結果から見逃しと時間切れを指摘にし、集計を出すところを扱う。結果のファイルを変異の結果に写すところは[変異テストの結果の読み取り](mutants-input.ja.md)で、等価の一覧の置き場と一致の取り方は[等価の一覧](equivalents.ja.md)で決める。"--tool" と結果のファイルの引数は[kotowari mutants は道具の名前を --tool で必ず受け、結果のファイルをちょうど1つ受ける](cli.ja.md#kotowari-mutants-は道具の名前を---tool-で必ず受け結果のファイルをちょうど1つ受ける)で、停止の文言は[停止の理由は、英語の固定の文言で示す](cli-environment.ja.md#停止の理由は英語の固定の文言で示す)で、指摘の鍵は[指摘は kind、severity、path、line、detail の5つの鍵で出す](output.ja.md#指摘は-kindseveritypathlinedetail-の5つの鍵で出す)で、並べ方は[指摘は path、line、kind、detail の順に並べる](finding-order.ja.md#指摘は-pathlinekinddetail-の順に並べる)で決める。

## 変異テストは kotowari の外で走らせ、kotowari mutants はその結果のファイルを読んで指摘にする

状態: 実装済み

### 問題

check は、決めたことを指すテストがあるかまでを機械で見る。そのテストが実装を縛っているかは見ていない。テストが何も確かめていなくても、マーカーがあれば指摘は0件になる。変異テスト（実装に小さな変更を入れ、テストが落ちるかを見る手法）は、この縛る力を実測する。

変異テストを kotowari の中で起動すると、実行時間とメモリの問題を kotowari が抱え、kotowari が Rust 専用になる。一方、結果のファイルを読んで指摘を出すことは製品の振る舞いで、入力のファイルを置けばテストできる。

check は push の前に毎回0件を求められるが、変異テストは十数分かかり、毎回は回せない。古い結果のファイルを check が読むと、ずれた行を指したまま push を止める。

### 決めたこと

変異テストの実行は kotowari の外に置く。kotowari は、変異テストの道具が書いた結果のファイルを入力として読み、指摘に変える。

結果を読むのは check ではなく、別のコマンド "kotowari mutants" にする。読む結果のファイルは引数で渡すので、どの結果を読んだかがはっきりする。出力は check の指摘と同じ形で、見逃しがあれば終了コードは1になる。

"kotowari mutants" が読むのは、設定ファイル、結果のファイル、等価の一覧、変異の結果が指すファイル、等価の一覧の1件の "file" が指すファイルだけである。仕様の文書とテストのファイルは読まず、check の検査も行わない。check が読む置き場の指す先が無くても、"kotowari mutants" は停止しない。

「見逃しが0件（等価の一覧に載った分を除く）」という基準は、kotowari の仕様にはしない。"kotowari mutants" を呼ぶ側の関門が、終了コードで強制する。

### 見送った案

- 手順書とスクリプトだけにして、kotowari 本体を変えない。見逃しと決めたことの対応が、人の手に残る。
- kotowari が変異テストを起動する。実行時間とメモリの問題を本体が抱える。
- check に混ぜ、設定の鍵で結果のファイルを指す。check は毎回0件を求められるが、変異テストは毎回は回せず、古い結果を読むとずれた行で push を止める。
- 以前の決定: 「見逃しが0件」は、リリースの前に人が見る確認の項目にする。人が意識しなければならないので、呼ぶ側の関門が終了コードで強制することにした。

### 確認すること

- C-core-mutants-1 check が読む置き場の指す先が無くても、"kotowari mutants" は停止せずに結果のファイルを読む
- C-core-mutants-2 マーカーの無いテストがあっても、"kotowari mutants" は指摘を出さない

## 見逃しは誤り、時間切れは注意にし、捕まえた変異とビルド不能の変異には何も出さない

状態: 実装済み

### 問題

見逃しは、その変異を入れてもテストが全部通ったもので、テストが実装を縛っていない所を指す。時間切れは無限ループになる変異で多く出る。テストが捕まえたとは言い切れないが、壊れていることは観測できている。

見逃しを仕様のどの決定に結び付けるかも問題になった。見逃しは落ちたテストが0本なので、テストのマーカーから決めたことへ辿る道が無い。実装の側にマーカーを置くか、関数と決めたことの対応表を持てば辿れるが、どちらも人が維持する新しい対応で、ずれても検査できない。

### 決めたこと

結果が「見逃した」の変異の結果には、mutant_survived の誤りを出す。結果が「時間切れ」の変異の結果には、mutant_timeout の注意を出す。結果が「捕まえた」か「ビルド不能」の変異の結果には、何も出さない。

見逃しは、仕様のどの決定にも結び付けず、場所と変更の説明だけで出す。mutant_survived と mutant_timeout の指摘は、path が変異の結果のファイル、line がその行、detail が変更の説明（道具が出した文のまま）である。並べ方は check と同じにする。check の指摘と同じ形なら、受け取る側が1つの読み方で済む。

時間切れは、等価の一覧に載っていても外れない。注意で終了コードを変えないので、外す口が要らない（一覧で外せるのは見逃しだけである。[一覧の1件は、ファイル、変更の説明、行の文面で変異を同定する](equivalents.ja.md#一覧の1件はファイル変更の説明行の文面で変異を同定する)）。

同じ内容の変異の結果が2件以上あっても畳まず、1件ごとに指摘を出す。

### 見送った案

- 実装の側にマーカーを置く。関数と決めたことの対応表を持つ。どちらも人が維持する新しい対応で、ずれても検査できない。
- 以前の決定: 見逃しの補助として、同じ関数の中で捕まえた変異を落としたテストのマーカーから、関係しそうな決定の候補を並べる。実際に走らせると、落ちたテストの名前は結果のファイルに無く、ログの文面にしか無かった。その文面はテストの実行器の表示で契約ではなく、最初に失敗した実行ファイルで止まるので一覧も一部でしかないため、やめた。

### 確認すること

- C-core-mutants-3 見逃しの変異の結果には、path がそのファイル、line がその行、detail が変更の説明の mutant_survived の誤りが出て、終了コードは1になる
- C-core-mutants-4 捕まえた変異とビルド不能の変異だけの結果では、指摘が出ず、終了コードは0になる
- C-core-mutants-5 時間切れの変異の結果には、等価の一覧にその変異に合う1件があっても mutant_timeout の注意が出て、終了コードは0になる
- C-core-mutants-6 同じ内容の見逃しが2件あれば、mutant_survived の誤りも2件出る

## 集計を必ず出し、等価として外した件数を毎回見せる

状態: 実装済み

### 問題

見逃しを等価の一覧に載せると、その見逃しは指摘から外れる。等価が本当かは機械で判定できない。一覧に頼った量が毎回見えれば、増え方の異常に気づける。等価の件数に上限を置く案もあったが、上限の数字には根拠を持てない。

等価の申告への歯止めは3段にした。1段目がこの集計で、2段目（一覧に足す前に、別の文脈の LLM にその変異を落とすテストを書かせる）と3段目（一覧の変更は人の普段の差分のレビューに混ざる）は手順の側にある。

変異の数を結果の種類ごとに分けて数え、その合計が変異の総数に一致すれば、読み落としが数で分かる。差分に変異の入る行が無い push は変異0件の結果になり、それで止めてはいけない。

### 決めたこと

"kotowari mutants" は、変異の結果を結果の種類ごとに数えた集計を、出力に必ず出す。

JSON の最上位は、次の3つの鍵だけを持つ。

| 階層 | 鍵 | 中身 |
|---|---|---|
| 最上位 | findings | 指摘の一覧。鍵と並べ方は check と同じ |
| 最上位 | counts | 種類ごとの指摘の数。1件も無い種類は持たない |
| 最上位 | mutants | 下の5つの鍵を持つオブジェクト |
| "mutants" の中 | caught | 結果が「捕まえた」の変異の結果の数 |
| "mutants" の中 | survived | 結果が「見逃した」で、等価の一覧のどの1件にも一致しない変異の結果の数 |
| "mutants" の中 | timeout | 結果が「時間切れ」の変異の結果の数 |
| "mutants" の中 | unviable | 結果が「ビルド不能」の変異の結果の数 |
| "mutants" の中 | equivalent | 結果が「見逃した」で、等価の一覧の1件以上に一致する変異の結果の数 |

等価として外した見逃しは survived に数えず、equivalent にだけ数える。

"--format" が "text" のときは、指摘の行の後の最後の1行に、同じ集計を "mutants: caught=数 survived=数 timeout=数 unviable=数 equivalent=数" の形で出す。指摘が0件でも出す。

変異が0件の結果では、終了コードは0で、集計はすべて0になる。

### 見送った案

- 等価の件数に上限を置く。上限の数字には根拠を持てない。

### 確認すること

- C-core-mutants-7 JSON の最上位の鍵は findings、counts、mutants の3つだけで、mutants は caught、survived、timeout、unviable、equivalent を持つ
- C-core-mutants-8 mutants の5つの値の合計は変異の結果の数に等しく、survived は mutant_survived の指摘の数に、timeout は mutant_timeout の指摘の数に等しい
- C-core-mutants-9 "--format text" では、指摘の行の後の最後の1行に "mutants: caught=数 survived=数 timeout=数 unviable=数 equivalent=数" が出て、指摘が0件でもこの1行が出る
- C-core-mutants-10 変異が0件の結果では、終了コードは0で、集計の5つの値はすべて0になる

## 指摘の種類と detail に、変異テストの道具に固有の語を使わない

状態: 実装済み

### 問題

kotowari 自体は言語を限らない道具で、結果を作る変異テストの道具は替わりうる。今は Rust と cargo-mutants だけだが、道具に固有の語と形が指摘に漏れると、道具を足すときに既存の決まりと指摘を変えることになる。機械では確かめにくいが、書いておけば実装する側とレビューが読む。

### 決めたこと

指摘の種類と detail の形に、変異テストの道具に固有の語を使わない。指摘の種類は、変異テストの分野の一般の語で、mutant_survived（見逃し）、mutant_timeout（時間切れ）、equivalent_stale（一覧の1件の文面がソースに無い）、equivalent_invalid（一覧の1件の形が誤っている）の4つにする。cargo-mutants の語（missed）は使わない。

detail の中の変更の説明は、道具が出した文のままなので、この決まりの対象にしない。道具の結果の値を写す部品（[変異の結果は道具を知らない形で持ち、cargo-mutants の結果のファイルを表のとおりに写す](mutants-input.ja.md#変異の結果は道具を知らない形で持ちcargo-mutants-の結果のファイルを表のとおりに写す)）も対象にしない。

### 確認すること

- C-core-mutants-11 （読んで確認）指摘の種類（mutant_survived、mutant_timeout、equivalent_stale、equivalent_invalid）と detail を組み立てるコードに、道具の結果の値の綴り（CaughtMutant、MissedMutant）が現れない。道具の値を写す部品は対象外
