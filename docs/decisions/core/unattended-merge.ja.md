# 人を待たずにマージする

[English](unattended-merge.md) | 日本語

工程の skill が、1つの依頼を仕様の承認からマージまで人を待たずに通すやり方を扱う。計画を書かなくなった cycle が何を入力にするか、人がマージを確認するかを決める線、マージのしかた、その回について指摘のファイルに残すもの。実装する側が決めた細部を、何を・なぜ・証拠でコミットの本文とプルリクエストの本文に書くことは、工程の話題の[実装の途中で見つかった細部は、実装する側が決める](workflow.ja.md#実装の途中で見つかった細部は実装する側が決める)で決める。cycle の中で仕様との整合を見る段は[整合のフェーズ](consistency-phase.ja.md)で決める。

## 壁打ちと仕様の承認は人に残し、そのあとマージまでは人を待たない

状態: 実装済み

### 問題

以前の工程では、1つの依頼のあいだに人が4回出ていた。壁打ちの答え、仕様の承認、計画の承認、最後の確認とマージである。利用者は、最初の目的を渡したら完了まで LLM だけで走る形に近づけたい。4回のうち、計画の承認と最後の確認は、人の確認が要るマージと要らないマージの線を決めれば、機械と LLM に渡せる。仕様の承認まで外すと、仕様の書き間違いを人が読んで止める場面が無くなる。

人に戻しても、人がそれで正しい舵を切れるとは限らない。ほとんどのことは実測や機械の判定で決められ、本当に人の判断が要ることは一部しかない。承認のあとに人が実装を呼ぶ形だと、依頼ごとに手で起こす場面が1回残る。cycle だけを人なしにすると、小さい作業が今と同じ場所で人を待つ。

### 決めたこと

壁打ちと仕様の承認は人のままにし、そのあとマージまでは人を待たずに通す。人に戻すのは、人でないと決められないことだけにする。人に残すのは、何を作るか（壁打ちと仕様）、戻せない操作、物差しの根っこ（線を決める一覧と、検査の定義）である。ほかは実測と機械の判定で決め、測れないものは LLM が決めて理由を残し、人は事後に読める。機械で測れないことを、人に回す理由にしない。

人が仕様を承認してコミットした、またはコミットしてよいと言った時点を、実装を始めてよい合図とし、壁打ちは同じ流れで cycle に進む。後回しにしたいときは、人がそう言う。

人を待たずにマージまで通すのは、cycle が回す依頼と、kotowari-iterate が回す小さい作業である。主セッションが直接編集する変更は、コミットするところまでで終わる。

### 見送った案

- 仕様の承認も、条件つきで機械に任せる。仕様の書き間違いを人が読んで止める場面が無くなる。

### 確認すること

- C-core-merge-1 （読んで確認）kotowari-brainstorm の skill に、人が承認した仕様をコミットした、またはコミットしてよいと言ったら、人が後回しにすると言わない限り、同じ流れで kotowari-cycle に進むと書いてある
- C-core-merge-2 （読んで確認）kotowari-iterate の skill に、収束した回は cycle と同じ形でマージすると書いてあり、kotowari-cycle の `references/merge.md` に、主セッションが直接編集する変更はコミットで終わると書いてある

## 計画を書く段とその承認を置かない

状態: 実装済み

### 問題

計画の承認を外しても、計画を書く段が残れば、仕様と実装のあいだに書くものが1つ残る。手順を決めるのは、実装役の仕事にできる。

### 決めたこと

計画を、承認する成果物として扱わず、工程の段としても置かない。計画を書く工程の skill は持たない。大きい依頼で実装役が要ると判断したときだけ、実装役が自分の作業メモとして書く。人は読まず、コミットもしない。実装の順番と触るファイルは、実装役が決める。

計画の形を検査するコマンドは残す（[計画書の形は、本体に同梱したスキーマで kotowari plan が検査する](plan.ja.md#計画書の形は本体に同梱したスキーマで-kotowari-plan-が検査する)）。

### 見送った案

- 以前の決定: 承認のあと計画を書いて cycle で回す。計画を書く段が仕様と実装のあいだに残るので、やめた。
- 計画は書くが、人の承認を待たない。採らなかった理由は記録に残っていない。
- 計画の承認を人に残す。採らなかった理由は記録に残っていない。

### 確認すること

- C-core-merge-3 （読んで確認）`agent/skills/kotowari-plan/` が無く、kotowari-brainstorm と kotowari-cycle の skill に計画を書く段もその承認も無い

## cycle は、決定の文書の置き場と、今回作る決定の一覧と、マージ先を受け取る

状態: 実装済み

### 問題

計画は、cycle の入力、再開の手がかり、テストのコマンド、順番と触るファイルの4つの役目を運んでいた。計画の段を外したあと、それぞれの行き先を決めないと、仕様が黙る。計画の工程がしていた、仕様が承認済みかの確認も、工程と一緒に無くなった。決定を直接渡して始めた回では、承認されていない仕様でも走ってしまう。

レビューの範囲が枝の親との分かれ目から、プルリクエストがマージ先との分かれ目から、とずれていると、まだマージ先に入っていない枝から切った枝で、親のコミットがレビューされないままマージされうる。

### 決めたこと

cycle は、壁打ちから、決定の文書の置き場と、今回作る決定の一覧と、マージ先を受け取る。マージ先は、決めていなければリポジトリの既定の枝とする。最初のフルレビュー、整合のフェーズの最初の回、線の判定は、枝がマージ先から分かれたコミットから読み、プルリクエストはそのマージ先へ向ける。

決定の文書の置き場を受け取って始めるとき、cycle は、作業用のディレクトリで、決定の文書の置き場にコミットしていない変更が無いことと、`kotowari check` が、枝が変えた決定の文書に誤りを報告しないことを確かめる。どちらかが成り立たなければ、仕様が未承認だと言って止まる。

### 見送った案

- レビューの範囲とプルリクエストの範囲がずれていたら、プルリクエストで止まる。決まりが1つ増え、積んだ枝はいつも人がマージすることになる。

### 確認すること

- C-core-merge-5 （読んで確認）kotowari-cycle の skill に、決定の文書の置き場と、今回作る決定の一覧と、マージ先を受け取り、マージ先は決めていなければリポジトリの既定の枝だと書いてある
- C-core-merge-6 （読んで確認）kotowari-cycle の skill に、最初のフルレビュー、整合のフェーズの最初の回、線は、枝がマージ先から分かれたコミットから読み、プルリクエストはマージ先へ向けると書いてある
- C-core-merge-7 （読んで確認）kotowari-cycle の skill に、決定の文書の置き場を受け取って始めるとき、その置き場にコミットしていない変更が無いことと、枝が変えた決定の文書に `kotowari check` が誤りを報告しないことを確かめ、どちらかが成り立たなければ未承認と言って止まると書いてある

## 受け取った決定は指摘のファイルに書き、再開はそこから読む

状態: 実装済み

### 問題

再開のたびに、枝の差分から受け取った決定を数え直す形だと、仕様がすでにマージ先にある依頼では、枝の差分に仕様が無く、数え直しが0件になる。再開した回が、何も実装しないまま収束しうる。

### 決めたこと

cycle は、枝ごとの指摘のファイルに、受け取った決定を書く。再開はファイルから読み、ファイルに記録が無いときだけ、枝の差分のうち決定の文書の置き場の部分から数え直す。再開のために新しいファイルは作らない。

実装の途中の再開では、git の履歴と、受け取った決定のうちまだ状態が「提案」のものを手がかりに、実装役が残りを決める。実装役の作業メモがあれば、それも読む。

### 見送った案

- 数え直しが0件だったら、人に聞く。再開のたびに人が1回出る。
- 実装役に作業メモを必ず書かせ、それを cycle の入力と再開の手がかりにする。承認しないだけで、計画を書く段が実質的に戻ってくる。

### 確認すること

- C-core-merge-8 （読んで確認）kotowari-cycle の skill に、受け取った決定を指摘のファイルに書き、再開はそこから読み、記録が無いときだけ枝の差分の決定の文書の置き場の部分から数え直し、再開のために新しいファイルを作らないと書いてある
- C-core-merge-9 （読んで確認）kotowari-cycle の skill に、実装の途中の再開では git の履歴とまだ提案の決定から実装役が残りを決めると書いてあり、kotowari-implement の skill に、再開では作業メモがあればそれも読むと書いてある

## 小さい作業と指摘のファイルの形の説明でも、受け取ったものは決定の一覧として扱う

kotowari-iterate が同じ枝へのあとの依頼で指摘のファイルに足すものと、指摘のファイルの形の資料が説明する受け取ったものは、cycle と同じく決定の一覧とする。

## 枝の名前は依頼が終わったら使い回さず、始めと再開ではホスティングのサービスの状態を読んでから進む

状態: 実装済み

### 問題

枝の名前だけでプルリクエストを引くと、同じ名前の枝を使い回したとき、前の依頼のプルリクエストを今回のものとして読む。プルリクエストの先頭のコミットで見分ける形は、マージコミットでマージするリポジトリでは働かない（前の依頼の先頭がマージ先の祖先になり、そこから切った新しい枝の祖先にもなる。このリポジトリで確かめた）。見分ける決まりを足すより、使い回さないほうが単純である。指摘のファイルは消さないので、マージで終わった回のファイルを再開として読むと、前の回の指摘と終わり方を引き継いでしまう。

マージ先を推測すると、線とレビューの範囲が違う枝から読まれる。一方、プルリクエストを作れないホスティングでも cycle は回るので、ホスティングのサービスを読めないことを理由に始めで止めると、そこでは何も始められない。push の前には頼みを読み直すので、始めで省いた確かめはそこでできる。

新しい依頼の開始、同じ枝へのあとの依頼、再開を分けないと、あとの依頼が再開に畳まれる。差し戻しのあとに再開した壁打ちが仕様を変えて cycle に渡すと、承認の確かめが省かれ、最初のレビューが済んでいれば、新しい決定がどれも実装役に渡らない。あとの依頼のレビューをマージ先との分かれ目から読むのは、レビューされないコミットがマージされないためである。プルリクエストを作ったあとの再開で、ホスティングのサービスから状態を読む理由は、記録に残っていない。

### 決めたこと

枝の名前は、その依頼が終わったあと使い回さない。新しい依頼を受け取った開始で、その枝の名前のマージ済みか閉じたプルリクエストがあれば、cycle は止まって新しい枝の名前を人に求める。枝の開いたプルリクエストの先頭が手元の枝に無ければ、どの開始でも再開でも、止まって人に伝える。マージで終わった回の指摘のファイルは、あとで同じ名前の枝で始めた回の再開としては読まない。

マージ先を決めておらず、リポジトリの既定の枝も読めないときは、推測せずに人に聞く。開始のときにホスティングのサービスを読めなければ、上の2つの確かめを省いて進み、push の前に確かめ、できなかった確かめを最後の報告に書く。

再開は、依頼を持たない開始とする。指摘のファイルがすでにある枝へ依頼を持ってきた開始は、再開ではなく同じ枝へのあとの依頼とし、仕様が承認済みかを確かめ、受け取った決定を足し、実装からやり直し、整合のフェーズの回とフルレビューをマージ先との分かれ目から読む。cycle の始めは、枝のプルリクエストを読む、仕様を確かめる、指摘のファイルを作るか書き換える、の順にする。

プルリクエストがある枝の再開は、プルリクエストがあるか、マージを頼んであるか、検査の状態、マージ済みかを、ホスティングのサービスから読む。

### 見送った案

- 以前の決定: プルリクエストの先頭のコミットで、前の依頼のプルリクエストと見分ける。マージコミットでマージするリポジトリでは働かないので、やめた。
- プルリクエストの番号を指摘のファイルに書いて見分ける。ファイルを失うと見分けられない。

### 確認すること

- C-core-merge-34 （読んで確認）kotowari-cycle の skill に、枝の名前は依頼が終わったあと使い回さず、新しい依頼を受け取った開始でマージ済みか閉じたプルリクエストがあれば止まって新しい枝の名前を求め、開いたプルリクエストの先頭が手元の枝に無ければどの開始でも再開でも止まって伝えると書いてある
- C-core-merge-35 （読んで確認）kotowari-cycle の skill に、ending が merged の指摘のファイルは、同じ名前の枝で始めた回の再開として読まないと書いてある

## テストのコマンドはプロジェクトの指示か言語の標準の道具で決め、決まらなければ人に聞く

状態: 実装済み

### 問題

テストのコマンドは計画が運んでいた。また、実装役が検査のコマンドは書かれたとおりには通らないと返したときは計画へ差し戻していたが、返す先が cycle になったのに、受ける決まりが無かった。

### 決めたこと

テストのコマンドは、プロジェクトの指示か、その言語の標準の道具で決める。どちらでも決まらなければ、人に聞く。実装役が、検査のコマンドは書かれたとおりには通らないと返したら、cycle は人に聞き、答えを付けて委譲し直す。

### 見送った案

- 検査のコマンドが通らないときは、壁打ちへ差し戻す終わり方にする。コマンドの書き間違いだけで、壁打ちからやり直すことになる。

### 確認すること

- C-core-merge-11 （読んで確認）kotowari-cycle の skill に、テストのコマンドがプロジェクトの指示か言語の標準の道具で決まらないときと、検査のコマンドが書かれたとおりには通らないと実装役が返したときは、人に聞いて答えを付けて委譲し直すと書いてある

## 壁打ちは新しい枝で仕様をコミットし、承認のあと作業用のディレクトリに出してから cycle を始める

状態: 実装済み

### 問題

同じ枝は2つの作業ツリーに出せない。主の作業ツリーでそのまま cycle を回すと、指摘のファイルが、片付けで消える場所の中になる。

ステージ済みのファイルは枝の切り替えに付いていく。コミットの前に主の作業ツリーを戻すと、仕様は元の枝へ持ち帰られ、新しい枝には何も入らないまま cycle に渡る。

### 決めたこと

壁打ちは、主の作業ツリーで、マージ先の先頭から新しい枝を切って仕様をコミットする。承認のあと、主の作業ツリーを元の枝に戻し、新しい枝を専用の作業用のディレクトリに出してから cycle を始める。主の作業ツリーを切り替えられないときは、止まって人に伝える。cycle が作業を差し戻したあとに再開する壁打ちは、その作業用のディレクトリで書く。

人が自分でコミットせず、コミットしてよいと言ったときは、壁打ちが新しい枝でコミットする。承認したファイルが新しい枝にコミットされていないあいだは、主の作業ツリーを戻さず、どのファイルがコミットされていないかを人に伝えて止まる。

### 見送った案

- 壁打ちの最初に作業用のディレクトリを作り、そこで仕様を書く。壁打ちが始まる時点で、枝の名前を決めることになる。

### 確認すること

- C-core-merge-12 （読んで確認）kotowari-brainstorm の skill に、主の作業ツリーでマージ先の先頭から新しい枝を切って仕様をコミットし、承認のあと主の作業ツリーを戻して新しい枝を作業用のディレクトリに出し、切り替えられないときは止まって人に伝え、差し戻しのあとの再開はその作業用のディレクトリで書くと書いてある
- C-core-merge-33 （読んで確認）kotowari-brainstorm の skill に、人がコミットしてよいと言ったときは壁打ちが新しい枝でコミットし、承認したファイルが新しい枝にコミットされていないあいだは主の作業ツリーを戻さず、どのファイルかを人に伝えて止まると書いてある

## 人がマージを確認するのは、戻せない操作、仕様を変える変更、検査と線を変える変更の3種類にする

状態: 実装済み

### 問題

確認の要否は、0か100かではなく、変更の種類で決まる。検査の定義を変える変更は、通す基準そのものを動かすので、同じ検査では測れない。

### 決めたこと

人が確認するのは、次の3種類とする。ほかは、機械の検査がすべて通ればマージする。

| 種類 | 受け持つもの |
|---|---|
| 戻せない操作（リリース、公開、タグ、消す操作） | 差分の性質ではなく操作そのもので、いまある止まる条件 |
| 仕様を変える変更 | パスではなく、工程の止まる条件 |

## 線は、git だけで、差分が .kotowari/confirm-paths のパスに触れたかで判定する

状態: 実装済み

### 問題

決めた線を守るのに要るのは、決めたパスに差分が触れたかどうかだけで、git がそれを答えられる。変更の種類分けや3段の扱いは、線に対して余計な複雑さだった。一覧を skill の中に書くと、ほかのプロジェクトでは skill を書き換えないと使えない。kotowari の本体の設定ファイルに書く手は、本体に何も足さないという決定と合わない。

仕様の置き場を一覧に入れると、壁打ちから始めた依頼がすべて止まる。kotowari の候補の一覧を過去のマージ済みの依頼32件に当てると、当たるのは8件だった。基点が1つなら、調べられずに通る区間が無い。行末に空白のある行は何にも当たらず（実測）、差分では見えにくい。

一覧の行を消す変更は一覧のファイルに触れるので、ファイル自身をいつも当たりにすれば、線をすり抜けられない。枝の一覧だけを読むと、枝が分かれたあとにマージ先の一覧へ足された行が効かない。行をまとめて照らすと、パスを除く行を1つ足すだけで、ほかの行の当たりを消せる。手順の失敗を当たりにするのは、一覧のファイルが無いときを当たりと同じにするのと同じ向きで、結果が2つの値だけという決まりとも合う。失敗には当たったパスが無いので、原因として見せるのは失敗そのものになる。移したファイルを元のパスと先のパスの両方で数える理由は、記録に残っていない。線を調べるのが1回だけだと、マージを頼んだあとに cycle が足した直しが、調べられずにマージされる。

### 決めたこと

人が確認する変更と、確認なしでマージする変更の線は、git だけで判定する。新しいコマンドは作らず、kotowari のコマンドも使わず、LLM は判定しない。結果は、当たりか当たりでないかの2つだけにする。

パスの一覧はプロジェクトごとのファイル `.kotowari/confirm-paths` に置き、1行に1つ、git のパスの書き方で書く。各行は、前後の空白と行末の復帰文字を落としてから、パスの指定として使う。skill には手順だけを書く。このファイルが無いプロジェクトでは、自動のマージに任せず、プルリクエストで止まる。

一覧に入れるのは2つである。検査の定義（CI、フック、検査を走らせるスクリプト、変異テストの設定、静的解析と道具の版の設定）と、線そのもの（一覧のファイルと、線の手順を書いた skill）。決定の文書の置き場は入れない。線の手順を書いた skill のほかの工程の skill は、ふつうのコードと同じに扱う。

線の判定は、どの依頼でも、枝がマージ先から分かれたコミットから枝の先頭までの差分をすべて調べる。cycle は、枝へコミットを足すたびに、差分の全体で判定し直す。

パスの指定は、マージ先の先頭にある一覧と、枝の先頭にある一覧の両方から読み、どちらかで当たれば当たりとする。1行ずつ別々に照らし、パスを除く行がほかの行の当たりを消さないようにする。一覧のファイル自身への変更は、一覧に何が書いてあっても当たりとする。移したファイルは、元のパスと先のパスの両方で数える。手順のコマンドが失敗したら、当たったパスの無い当たりとし、失敗として、その誤りの出力と一緒に報告する。

### 見送った案

- 差分を読んで扱いを返す kotowari の新しいコマンドを作る。
- 線の判定を、skill を読んだ LLM に任せる。同じ差分でも判定が揺れ、線が守られたかを後から確かめられない。
- 線の判定をホスティングのサービスの側の設定に任せる。そのサービスを使わないプロジェクトでは働かない。
- 工程の skill をすべて一覧に入れる。skill を直す依頼がすべて1回止まる。
- 検査の定義を一覧から外し、壊した見本で検査を実測する仕組みを今回作る。検査の定義を変える依頼で止まった回数を記録で見てから決める。
- 何にも当たらない行を、手順の失敗にする。まだ無いパスを先に一覧へ書いておけなくなる。
- 線を調べる差分の基点を、仕様の承認のコミットにする。仕様の置き場を一覧から外したあとは理由が無く、承認のコミットより前の変更が線にかからない。
- パスの一覧を、プロジェクトの指示の文書の中の節に書く。文書から一覧を抜き出す手順が要り、文書のほかの直しでも線に当たる。

## 線に当たらない回は、プルリクエストを作り、必須の検査が通ったらマージするようホスティングのサービスに頼む

状態: 実装済み

### 問題

手元でマージして push する形は、必須の検査を求めるマージ先の保護に拒まれる。人がボタンを押す形は、待ちが1回残る。リポジトリの設定は、通す基準の一部で、物差しの根っこにあたる。自動のマージの設定だけを条件にすると、必須の検査が1つも無いプロジェクトで、何も確かめずにマージされうる。

マージ先が承認のレビューを必須にしていると、頼みが残ったまま、人が自分の承認が要ると知らされずに待ち続ける。枝の保護の規則は、それを見られないアカウントには無いものとして返るので、設定だけを読む2つの読みでは、承認のレビューが必須のマージ先でも「必須でない」の値がそろう。プルリクエスト自身の reviewDecision は、どの設定が求めているかにかかわらず、ホスティングのサービスが判定した結果を返す。枝の保護の、承認のレビューの人数を返す REST の問い合わせは、承認のレビューを必須にしていないマージ先でも人数を1と返した（実測）。向き先を変えられたプルリクエストは、ある枝に対して線とレビューを読み、別の枝へマージされる。条件を確かめられないときに止まる理由は、記録に残っていない。

### 決めたこと

人の確認が要らない回では、cycle がプルリクエストを作り、必須の検査が通ったら自動でマージするよう、ホスティングのサービスに頼む。実際にマージするのはホスティングのサービスで、マージ先の保護が最後の関門になる。cycle はマージを自分で行わない。

頼むのは、リポジトリの自動のマージの設定が有効で、マージ先が必須の検査を1つ以上持ち、マージ先が承認のレビューを必須にしておらず、プルリクエストが cycle の受け取ったマージ先へ向いていると確かめたときだけにする。どれかが欠けているか、確かめられなければ（読むコマンドが失敗したときを含む）、プルリクエストで止まり、自動のマージが使えないことと理由を報告し、人がマージする。

マージ先が検査を必須にしているかは、枝の保護とルールセットの2つで読む。どちらかが空でない一覧を出し、どちらも失敗しなければ必須、どちらも成功して何も出さなければ必須でない、とし、1つでも失敗したら、もう片方が何を出していても確かめられなかったものとする。承認のレビューを必須にしていないと確かめたとするのは、枝の保護（GraphQL の requiresApprovingReviews）の読みが false、ルールセットの読みが 0、プルリクエスト自身の reviewDecision が空、の3つがそろったときだけにする。ほかの出力は、空の出力も含めて、確かめられなかったものとする。

再開のときに、開いているプルリクエストが受け取ったマージ先と別の枝へ向いているか、向き先を読めなければ、残っている頼みを取り消し、その理由を付けてプルリクエストを人に渡す。

自動のマージを使えるようにするリポジトリの設定は人が有効にし、cycle はリポジトリの設定を変えない。プルリクエストを作れないホスティングでは、枝を push したところで止まる。

### 見送った案

## マージへ進むのは収束した回だけにし、マージの頼みは、枝へコミットを足す前と条件が崩れたときに取り消す

- プルリクエストを人に渡すとき

頼み直すのは、新しい先頭について、収束したこと、線に当たらないこと、人が確認する場合に当たらないことを確かめてからだけにする。

push の前に頼みが残っているかを読めないときは、push せず、誤りの出力を付けて、止まって人に伝える。プルリクエストを作れないホスティングだけは、push へ進む。

## 人が確認するときは、マージを頼まずにプルリクエストを開いたままにし、場所と止まった原因だけを見せる

状態: 実装済み

### 問題

パスでは、細部の具体化と仕様の変更を見分けられない。その見分けは、整合のフェーズの決まりがすでに持っている。止まり方が1つなら、人が見る場所も1つになる。人の判断を待つ指摘の出どころを整合のフェーズに限ると、レビューが残した判断待ちがあってもマージされる。止まったときに変更の要約まで付けると、人が要約を読んで承認し、差分そのものを読まずに通す形になりうる。

### 決めたこと

マージへ進む回のうち、線に当たったときと、人の判断を待つ指摘（human_judgment）が、出どころ（整合のフェーズ、レビュー）を問わず開いたまま残っているときは、人がマージを確認する。そのとき、cycle はプルリクエストを作り、自動のマージを頼まず、開いたままにして、プルリクエストの場所と、止まった原因（当たったパス、または開いている指摘）を人に見せる。変更の要約は付けない。人は差分を読み、よければ自分でマージする。

実装役が、人の決めた意図そのものがぶつかると返したときは、人が出て、何もマージしない。戻せない操作（リリース、公開、タグ、手元の外にあるものを消すこと）は、いまある止まる決まりのもとで人に残る。

承認のあとに実装する側や整合のフェーズが決めた細部と、決めた向きを変えずに事実に合わせて直した決定の文は、止まる理由にしない。

## レビューの指摘のうち、回の収束を止めるのは3種類だけにする

状態: 実装済み

### 問題

設計の良し悪しは、人が読んでも正しく舵を切れるとは限らない。それを止まる理由にすると、人に戻すのは人でないと決められないことだけ、という原則と逆向きになる。

確かめ方を「既存の検査がすべて通ること」に置き換えた指摘を数えないと、レビュー役が走らせて落ちるのを見た間違いが、直されないまま人なしでマージされうる。差分が足した検証が証拠の条件を満たさないことは、条件に照らして読めば決まるが、確かめ方が「消したあとも既存の検査が通ること」なので、いま落ちるものではない。走らせて示す決まりのままだと必ず記録だけになり、証拠にならないテストが残る。

直すしかないセキュリティの指摘を人に戻しても、人が選べるものが無い。ほかの指摘と同じ決まり（落ちるのを見たものだけ直す）を当てると、走らせていないセキュリティの指摘が、直されないまま人なしでマージされうる。修正役に渡すものを、直すことを提案する指摘に限る理由は、記録に残っていない。人の判断を求めるセキュリティの指摘を開いたまま人の確認に数えないと、人の判断を待たずにマージされる。

### 決めたこと

レビューの指摘のうち、回の収束を止めるのは、次の3種類だけにする。

- 走らせて示せる間違い。確かめ方を「既存の検査がすべて通ること」に置き換えた指摘も、レビュー役が置き換える前に自分の確かめ方を走らせて落ちるのを見たなら、これに数える
- 提案された扱いが直すことである、セキュリティの指摘
- 差分が足した検証を、証拠の条件を満たさないので消すという提案。落ちるのを見ていなくても直す

セキュリティの指摘では、人を待って止まらない。落ちるのを見たかどうかにかかわらず修正役に渡し、直らないまま進まなくなったら、進まないときのいまある終わり方で人に渡る。直した内容は、判断の1行として事後に読む。

修正役に渡すのは、提案された扱いが直すことであるセキュリティの指摘だけにする。人の判断を求めるセキュリティの指摘は、人の判断を待つ指摘として開いたまま残り、人がマージを確認する場合に数える。記録だけを提案するセキュリティの指摘は、記録だけのまま残る。

- 設計が割れているときだけ、見直しの席を1つ当てる。割れていることを機械が言える形で決める必要があり、効きの根拠がまだ無い。

- 証拠の条件を満たさない検証を消す提案を、記録だけのままにする。証拠にならないテストが残る。

- セキュリティの指摘に、ほかの指摘と同じ決まりを当てる。走らせていない指摘が、直されないまま人なしでマージされうる。
- セキュリティの指摘では、今のまま必ず止めて人に渡す。直すしかない指摘では、人が選べるものが無い。

## テストの削除、検査の抑制、依存の変更、読みやすさと構造の選び方では、人を待たない

状態: 実装済み

### 問題

消されたテストが質の悪いテストなら、消すことは改善にあたる。人が読んでも良し悪しを正しく判定できるとは限らず、守りが減ったかは変異テストのほうが正確に測れる。要求の唯一のテストを消す変更は、既存の検査が落とした（決めた時点の実測）。依存の変更は、理由と目的が残っていれば事後に確かめられ、リリースまでは外して戻せる。読みやすさや構造の好みを人に回すと、人に戻すのは人でないと決められないことだけ、という原則と逆向きになる。実装役の判断を最後の報告にだけ出すと、セッションを閉じたあと読み返せない。

### 決めたこと

既存のテストを消す変更、検査の抑制を足す変更、依存を足す・変える変更を、それを理由に人に回さない。読みやすさと構造の選び方は実装役が決め、止まる理由にも、レビューの席を足す理由にもしない。

実装役が自分で下した判断は、足した依存も含めて、何を決めたか・なぜか・証拠を持つ1行にする。その行は、プルリクエストの本文（[実装の途中で見つかった細部は、実装する側が決める](workflow.ja.md#実装の途中で見つかった細部は実装する側が決める)）と同じものを、cycle の最後の報告にも出す。

### 見送った案

- 既存のテストを消す変更を、人が確認する側に入れる。消されたテストが質の悪いテストなら改善にあたり、人が読んでも判定できるとは限らない。
- 新しい依存を足すときは、人が確認する。理由と目的が残っていれば事後に確かめられ、リリースまでは外して戻せる。

## 回について、新しい記録は作らず、指摘のファイルに線の結果と手直しの元と終わり方を足す

状態: 実装済み

### 問題

あとで記録を読んで工程を直すループを作るには、どこに払うと出戻りが減るかを読むのに要る最小の項目を、残しておく必要がある。レビューと修正の往復の回数は、cycle が依頼ごとに書いている指摘のファイルの、回ごとの判定と修正の記録から、すでに数えられる。指摘のファイルの置き場は git の外なので、検索に当たって今の決まりと取り違えられる心配も無い。記録を何件残せば読めるかは、まだ分からない。

### 決めたこと

cycle は、回についての新しい記録のファイルを作らない。枝ごとに書いている指摘のファイルに、次を足す。

- 線の判定の結果と、当たったパス
- この依頼がどの依頼の手直しか。前の依頼の枝の名前で指す。依頼の文が前の依頼の手直しだと言っているときだけ書き（小さい作業では kotowari-iterate が書く）、分からなければ空のままにする
- どの終わり方で終わったかと、その理由。前の段への差し戻しと、人を呼んで止まったことを含む

費用は記録しない。指摘のファイルはコミットせず、工程は消さない。

### 見送った案

- 出戻りの記録を、依頼ごとの小さいファイルとしてリポジトリにコミットし、検索から外す設定と、今の決まりとして読まないという指示を足す。ほぼ同じ内容を cycle がすでに git の外に書いていた。同じ内容が2か所に書かれ、抜き出す手順と除外の設定を作ることになる。
- どの依頼の手直しかを、差分が前の依頼の変えた行に触れているかを git で調べて書く。調べる手順を作ることになり、たまたま同じ行に触れただけの依頼も手直しに数えられる。

## マージのあとは、手元の作業用のディレクトリと枝だけを片付け、ホスティングのサービスの側のものは消さない

### 問題

マージのあとに何を片付けるかを決める必要があった。手元の外にあるものを消すのは戻せない操作で、人に残すものにあたる。
