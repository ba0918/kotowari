# 確認することとテスト

決定の「確認すること」の行と、テストの対応を決める。check が何にテストを求めるか、テストで確かめない行をどう書くか、決定の状態を誰がいつ変えるかを扱う。決定の文書の形そのものは[決定の文書](decision-documents.md)で決める。

## check は、確認することの行ごとに、それを指すテストがあるかを数える

状態: 提案

### 問題

決定の文書から、決まった文型の要求文と場面が無くなる。これまで check は、要求の ID と場面の ID を単位に、それを指すテストのマーカーがあるかを数えていたので、単位を決め直す必要がある。

マーカーが保証するのは「決めたことを指すテストが1つはある」までで、そのテストが決めたことを本当に確かめているかは保証しない。品質を見ているのはレビューと変異テストである。それでも、在ることの保証は飾りではなかった。作業の記録から、check が「テストが無い」と実際に出した事例を40件選んで、そのあとを追った。31件は、これから実装する予定のものに出ただけだった。6件では、指摘が無ければ書かれなかったと読めるテストが入り、そのうち1件では、書いたテストが落ちて実装の誤りが見つかった。残りは、既存のテストにマーカーを付けただけが2件、仕様の側を消したのが1件だった。

マーカーにはもう1つ使い道がある。決定を変えたときに、直すべきテストを ID で引けることである（`kotowari query`）。

### 決めたこと

確認することの行に ID を付ける。ID は `C-<まとまりと話題の短い名前>-<連番>` の形にする。連番は、その話題で使ったいちばん大きい番号の次を使い、消した行の番号を詰めたり、別の行に使い回したりしない。テストの側のマーカー `@kotowari[...]` は、この ID を指す。

check は、状態が「実装済み」の決定の、確認することの行すべてに、それを指すテストがあるかを数える。無ければ誤りにする。状態が「提案」の決定には求めない。性質として書いた行は、性質のテスト（どんな入力でも成り立つことを確かめるテスト）が指す。

### 見送った案

- 以前の決定: 要求の ID と場面の ID を単位に数える。場面を Given / When / Then で文書に書き、その ID をテストに書く。場面を文書に書かなくなるので、単位を確認することの行に変えた。
- 決定を単位にして、実装済みの決定に、それを指すテストが1つ以上あるかを数える。確認することが複数あってテストが1つでも通る。決定を変えたときに、どの確認が変わるかまで絞ってテストを引けない。
- 数えない。テストがあるかは、レビューとテスト自身に任せる。決めたことにテストが無いまま実装済みになっても、機械が止めない。
- ID を、決定ごとの番号と枝番にする。話題の名前を変えても ID は変わらないが、ID を見ても、どの話題かが分からない。

### 確認すること

- C-core-confirm-1 実装済みの決定の、確認することの行を指すテストが無ければ、check がその行に誤りを出す
- C-core-confirm-2 実装済みの決定の、確認することの行すべてをテストが指していれば、check はその決定に誤りを出さない
- C-core-confirm-3 同じ ID の確認することの行が2つあれば、check が誤りを出す
- C-core-confirm-4 テストのマーカーが、どの文書にも無い ID を指していれば、check が誤りを出す
- C-core-confirm-5 `kotowari query` に確認することの ID を渡すと、それを指すテストのファイル・行・名前が返る

## テストで確かめない行は、頭に「（読んで確認）」と書く

状態: 提案

### 問題

確認することの中には、テストでは確かめられず、人や LLM が読んで確かめるものがある（skill の文にこう書いてある、など）。テストで確かめる行と区別できないと、check がテストを求めてしまう。

### 決めたこと

人や LLM が読んで確かめる行は、行の頭（ID のあと）に「（読んで確認）」と書く。その行には、check はテストを求めない。読んで確かめるのは、実装する側と、レビューである。

### 見送った案

- 確認することを「テストで確認」と「読んで確認」の2つの節に分ける。読んで確かめる行が無い決定がほとんどなので、空の節を書かない決まりが別に要る。
- 以前の決定: 要求ごとに確認の方法（テストか、読んで確認か）の行を持たせ、読んで確認するものには確かめ方の行を足す。決定ではなく確認することの行ごとに分かれるので、行の側に書くことにした。

### 確認すること

- C-core-confirm-6 頭に「（読んで確認）」と書いた行には、それを指すテストが無くても、check が誤りを出さない

## 状態は実装する側が変え、まだ作らない決定は「提案」のまま置く

状態: 提案

### 問題

仕様を先に書いてコミットすると、テストがまだ無いので check が止まる。これを通すために、テスト側の指摘を見逃すフラグを足していた。また、決めたが今は作らない要求は「後回し」の宣言を書いて検査から外し、後回しなのにテストがある、後回しに依存している、という注意も出していた。どちらも「決めたが、まだ作っていない」という同じ状態を、別々の仕組みで扱っていた。

### 決めたこと

決めたが、まだ作っていない決定は、状態を「提案」にして文書に書く。提案の決定にはテストを求めないので、仕様だけを先にコミットしても check は止まらない。

壁打ちは、今回作る決定の一覧を、実装のループに渡す。実装する側は、その決定の確認することの行すべてを満たしたとき（テストで確かめる行にはテストを付け、読んで確かめる行は読んで確かめたとき）に、状態を「実装済み」に変える。確認することの無い決定は、決めた内容を実際に行ったとき（skill に書いた、設定を変えた、など）に変える。一覧に無い提案は、そのまま残る。提案のまま残っている決定の数は、status が数えて見せる。

提案の決定を指すマーカーがあっても、check は何も出さない（テストを先に書く途中で必ず起きるため）。後回しの宣言と、それに関する注意は持たない。

### 見送った案

- 以前の決定: 今は作らない要求には「後回し」の宣言の行を書き、理由の決定を出典に引く。後回しの項目を指すマーカーと、後回しの要求に依存する参照には注意を出す。「提案」の状態が同じ役目を持つので、やめた。
- 状態を3つにする（提案・着手・実装済み）。作業のたびに、文書の状態を2回書き換えることになる。

### 確認すること

- C-core-confirm-7 提案の決定の、確認することの行を指すテストが無くても、check が誤りを出さない
- C-core-confirm-8 提案の決定の、確認することの行を指すマーカーがあっても、check が誤りも注意も出さない
- C-core-confirm-9 status が、提案の決定の数と、実装済みの決定の数を分けて出す
- C-core-confirm-10 （読んで確認）壁打ちの skill に、今回作る決定の一覧を実装のループに渡すと書いてある
- C-core-confirm-11 （読んで確認）実装の skill に、確認することの行すべてを満たしたときに状態を「実装済み」に変えると書いてある
