# 面の検査

[English](surface.md) | 日本語

設定の "surface.rules" と "surface.files" でコードから利用者に見える面を取り出し、面の名前が決定の文書に書かれているかを "kotowari check" が確かめるところと、外した面の数の出し方、面を読むコマンド、skill に置く書き方を扱う。未記載の面の一覧の置き場と1件の扱いは[未記載の面の一覧](surface-unspecified.ja.md)で決める。

## 面は、設定の surface.files と surface.rules で、ast-grep の規則に当たった節としてコードから取り出す

状態: 実装済み

### 問題

仕様に書かれないまま実装された機能を、kotowari は機械で見つけられなかった。テストの無い新しいコードは差分の変異テストで、マーカーの無いテストは test_without_id で止まる。しかし、近い既存の決定の ID でマーカーを付けたテスト、工程を通らない変更、変異テストを回さないプロジェクトでは抜ける。根は、利用者から見える振る舞いの一覧を kotowari が持たず、仕様に無い振る舞いが増えても数えて比べられないことにある。

面（CLI のサブコマンドとフラグ、設定の鍵、HTTP のルートなど）の形はフレームワークごとに違う。テストを見つける "tests.rules" と同じ作りにすれば、規則の書き方を1つ覚えれば済み、言語を選ばない。名前の形を kotowari が決め打ちで整えると（"--" を補う、など）、設定の鍵や HTTP のルートのような CLI 以外の面で困る。kotowari 自身の CLI で動かせば、判定の甘さと厳しさをこの仕様の中で確かめられる。

### 決めたこと

面は、設定の "surface.files"（探すファイルの glob）と "surface.rules"（ast-grep の規則のファイル）で取り出す。規則に当たった構文木の節1つが面1つで、規則の "id" が面の種類、メタ変数 "$NAME" で捕まえた節の文字が面の名前になる。規則は、その "language" と同じ言語の面のファイルにだけ当てる。

名前の文字の前後が同じ引用符で囲まれていれば、1組だけ外す。それ以上は kotowari が整えない。形を変えたいときは、規則を書く人が ast-grep の規則の中で整える。

kotowari は面の規則を同梱しない。書き方の例は skill に置く（[面の検査の書き方と直し方は skill の reference に置き、未記載の面の一覧に足すのは壁打ちと導入の skill だけにする](#面の検査の書き方と直し方は-skill-の-reference-に置き未記載の面の一覧に足すのは壁打ちと導入の-skill-だけにする)）。kotowari 自身の設定には、サブコマンドの文字列と、"--" で始まるフラグの文字列（比べる場所が match の腕でも if でも）を取り出す規則を書き、自分の CLI の面を検査する。

### 確認すること

- C-core-surface-1 規則に当たった節1つが面1つになり、規則の "id" が種類、"$NAME" で捕まえた文字が名前になる
- C-core-surface-2 捕まえた文字の前後が同じ引用符なら1組だけ外し、それ以外の形はそのまま名前にする
- C-core-surface-3 規則の "language" と違う言語の面のファイルには、その規則を当てない
- C-core-surface-4 （読んで確認）kotowari 自身の設定に、サブコマンドの文字列と、"--" で始まるフラグの文字列を取り出す面の規則がある

## 面の規則と面のファイルは、tests.rules と tests.files と同じ作りで読む

状態: 実装済み

### 問題

面を取り出す規則とファイルの読み方が、テストを見つける規則とファイルの読み方と違えば、利用者は2つの書き方を覚えることになる。面の規則をテストを見つける問い合わせに加えないと決めた理由は残っていない。

規則の "severity" を "off" にした規則を当てないことにすると、規則のファイルの1行で面の検査が止まり、検査する面が黙って減る。"severity" が "off" の規則も当てると決めた理由は、記録に残っていない。

### 決めたこと

"surface.rules" の規則のファイルは、"tests.rules" と同じ ast-grep の規則の YAML として読む。規則の "severity" が "off" でも、その規則を当てる。面の規則は、テストを見つける問い合わせには加えない。"surface.files" の glob の読み方と走査は "tests.files" と同じにする。

### 確認すること

- C-core-surface-5 面の規則は "tests.rules" と同じ ast-grep の規則として当たり、テストを見つける問い合わせには加わらない（面の規則が当たる関数があっても、テストとして数えない）
- C-core-surface-26 "severity: off" と書いた面の規則も、ほかの規則と同じく当たって面を取り出す

## 規則の言語の面のファイルだけを読んで構文木にし、ほかの面のファイルは読まない

状態: 実装済み

### 問題

"surface.files" を "src/**" のように広く書くと、関係の無い文書や別の言語のファイル、画像のようなバイナリのファイルが当たる。それらを読んで構文の誤りを出したり、UTF-8 でないことで停止したりすると、規則と関係の無いファイルで検査が止まる。規則の言語でないファイルから面は取り出さないので、読む必要が無い。

### 決めたこと

面のファイルのうち、拡張子から決まる言語が面の規則のどれかの "language" と同じファイルだけを読み、tree-sitter で構文木にする。構文の誤りがあれば、テストのファイルと同じく、そのファイルに unparsable_file の誤りを出す（[構文の誤りがあるテストのファイルは、unparsable_file を出して飛ばす](test-discovery.ja.md#構文の誤りがあるテストのファイルはunparsable_file-を出して飛ばす)）。そのファイルが読めないか UTF-8 でなければ、テストのファイルと同じく停止する。

ほかの面のファイルは読まない。構文の誤りも出さず、読めないことも UTF-8 でないことも停止の理由にしない。

### 確認すること

- C-core-surface-6 規則の言語の面のファイルに構文の誤りがあれば、そのファイルに unparsable_file の誤りが出る
- C-core-surface-7 規則の言語でない面のファイルは読まれず、構文の誤りがあっても UTF-8 でなくても、誤りも停止も出ない
- C-core-surface-8 規則の言語の面のファイルが UTF-8 でないか読めなければ、check は停止する

## 面の設定の鍵が揃っていないときは、設定を読むどのコマンドも停止する

状態: 実装済み

### 問題

規則だけ書いて探すファイルが空、探すファイルだけ書いて規則が空、という設定を何もせずに通すと、検査しているつもりで何もしていない状態に気づけない。未記載の面の一覧の鍵だけが書かれて黙って読まれない場合も同じで、鍵の書き誤りに気づけない。

### 決めたこと

次のどれかの設定では、設定ファイルを読むどのコマンドも、設定の誤りで停止する。

| 設定 | 扱い |
|---|---|
| "surface.rules" が空でなく、"surface.files" が空 | 停止する |
| "surface.files" が空でなく、"surface.rules" が空 | 停止する |
| "surface.unspecified" があり、"surface.rules" が空 | 停止する |

面の規則のファイルが、"tests.rules" のファイルなら停止する形（[ルールのファイルに誤りがあれば、設定の誤りとして停止する](query-rules.ja.md#ルールのファイルに誤りがあれば設定の誤りとして停止する)）に当たるときは、check と status が同じ扱いで停止する。面の規則のファイルを読まないコマンドは、そのファイルの誤りでは止まらない（[面を読むのは check と status だけにする](#面を読むのは-check-と-status-だけにする)）。

### 確認すること

- C-core-surface-9 "surface.rules" だけがある設定、"surface.files" だけがある設定、"surface.unspecified" があって "surface.rules" が空の設定では、check、status、list、query、mutants が設定の誤りで停止する
- C-core-surface-10 面の規則のファイルが無いか、ファイルでないか、規則として読めないか、同じパスが2つ書かれているとき、check と status は停止する

## 面の名前が、決定の「決めたこと」か「確認すること」に引用されていれば、その面は仕様にある

状態: 実装済み

### 問題

面が仕様にあるかを、どう判定するかを決める必要があった。コードに何も書き足さず、仕様の側はふだんの書き方の決まり（具体的な値は二重引用符で囲む）どおりに書けば通るようにしたい。判定は名前が出てくるかだけで、中身が正しいかは見ない。

状態が提案の決定は、決めたがまだ作っていないもので、仕様には書いてある。作ってあるのに提案のままというずれは、この検査の範囲の外にある。

### 決めたこと

面の名前が、どこかの決定の文書の決定の「決めたこと」か「確認すること」に、二重引用符の対かバッククォートの対で囲んだ中身として、そのままの文字で出てくるとき、その面は仕様にあるとする。表は、セルごとに見る。名前が囲んだ中身の一部であるだけでは、出てくるとしない。決定の状態が提案でも実装済みでも数える。

「問題」と「見送った案」と「未決」に出てくる名前は数えない。コードブロックの中も読まない（[決定の文書のコードブロックの中は、決定の形としても引用としても読まない](ir-document.ja.md#決定の文書のコードブロックの中は決定の形としても引用としても読まない)）。

決定の文書を多言語の対で持つときに、どの側の引用を数えるかは、[決定の文書の対は、数えることと出力を先頭の言語の側だけで行う](translation-pairs.ja.md#決定の文書の対は数えることと出力を先頭の言語の側だけで行う)で決める。

### 見送った案

- 面の定義のそばに、テストと同じマーカーを書かせる。どの決定が面を決めるかは正確に分かるが、コードに書く手間が増え、関係の薄い ID を付ける穴が残る。

### 確認すること

- C-core-surface-11 決定の「決めたこと」か「確認すること」に、二重引用符かバッククォートで囲んで名前をそのまま書いた面には、決定の状態が提案でも、surface_without_spec の誤りが出ない
- C-core-surface-12 名前が、囲んだ中身の一部であるだけなら（例: "--verbose true" の中の "--verbose"）、その面を仕様にあるとしない
- C-core-surface-13 「問題」、「見送った案」、「未決」にだけ書いた名前の面は、仕様にあるとせず、surface_without_spec の誤りが出る
- C-core-surface-14 決定の「決めたこと」か「確認すること」の中でも、コードブロックの中（一覧の項目や引用の中のものを含む）にだけ書いた名前の面は、仕様にあるとしない

## 仕様に無い面は、コードで最初に見つかった場所に surface_without_spec の誤りを1件出す

状態: 実装済み

### 問題

この検査の狙いは、仕様に無い機能を通さない関門である。注意にしたのでは意味が薄い。一方で、規則を書かないプロジェクトには何も起きないようにする。

同じ面が何か所にも出てくることがある（kotowari 自身でも、同じフラグが2つの match の腕に出てくる）。同じ面を何度も数えると指摘が膨らむ。

### 決めたこと

仕様に無く、未記載の面の一覧のどの1件にも外されない面には、surface_without_spec の誤りを出す。場所は、面が見つかった面のファイルとその行で、detail は面の種類と名前にする。同じ種類と名前の面が何か所にあっても、最初の1か所に1件だけ出す。

"surface.rules" が空の一覧なら、面を取り出さず、この誤りを出さない。

### 確認すること

- C-core-surface-15 仕様に無く、一覧にも載っていない面には、面のファイルのパスと行を場所に、detail を種類と名前にした surface_without_spec の誤りが出て、終了コードは1になる
- C-core-surface-16 同じ種類と名前の面が2か所以上にあっても、surface_without_spec の誤りは最初の1か所の1件だけになる
- C-core-surface-17 "surface.rules" が空なら面を取り出さず、surface_without_spec の誤りは出ない

## 未記載の面の一覧で外した面の数を、check の出力の最後に必ず出す

状態: 実装済み

### 問題

未記載の面の一覧は、既存のプロジェクトで最初から大量の誤りが出ても導入できるようにするためのものである。誤りを出さない面を黙って増やせると、一覧に頼っている量が見えなくなる。一覧に頼った量を、毎回見えるようにしたい。

### 決めたこと

"surface.rules" が空でないとき、"kotowari check" は、未記載の面の一覧で外した面の数を、出力に必ず出す。JSON では最上位の "surface" の "unspecified" に出し、"--format" が "text" のときは指摘の行のあとの最後の1行に "surface: unspecified=数" と出す。指摘が0件でも、数が0でも出す。

"surface.rules" が空なら、JSON の "surface" の鍵も、文字の行も出さない（JSON の最上位の鍵は[check の JSON の最上位には、指摘と種類ごとの数と、読んだものの数を出す](output.ja.md#check-の-json-の最上位には指摘と種類ごとの数と読んだものの数を出す)で決める）。

### 確認すること

- C-core-surface-18 "surface.rules" が空でなければ、check の JSON の "surface" の "unspecified" に一覧で外した面の数が出て、指摘が0件でも数が0でも出る
- C-core-surface-19 "--format" が "text" の check は、指摘の行のあとの最後の1行に "surface: unspecified=数" を出す
- C-core-surface-20 "surface.rules" が空なら、check の JSON に "surface" の鍵が無く、"--format" が "text" の出力に "surface: " で始まる行が出ない

## 面を読むのは check と status だけにする

状態: 実装済み

### 問題

status の complete は check の誤りの数で決まるので、面の誤りもそこに入る。一方で、面を要らないコマンドが、読まない一覧や規則の誤りで止まるのは困る。一覧に頼った量は、status でも見えるようにする。

### 決めたこと

面のファイル、面の規則のファイル、未記載の面の一覧を読むのは "kotowari check" と "kotowari status" だけにする。status は check と同じ面の検査を行い、面の数を出す（[status は check と同じものを読んで同じ検査をし、指摘の代わりに数と complete を出す](status.ja.md#status-は-check-と同じものを読んで同じ検査をし指摘の代わりに数と-complete-を出す)、[集計は、テストのマーカー、ガイド、全体像、面、指摘の数を群ごとに出す](status.ja.md#集計はテストのマーカーガイド全体像面指摘の数を群ごとに出す)）。

"kotowari list"、"kotowari query"、"kotowari plan"、"kotowari mutants" は、それらを読まず、その読み込みによる停止をしない（list と query は[list は check と同じ条件で停止し、ガイドと面は読まない](list.ja.md#list-は-check-と同じ条件で停止しガイドと面は読まない)と[query は check と同じ条件で停止し、ガイドと面は読まない](query.ja.md#query-は-check-と同じ条件で停止しガイドと面は読まない)で決める）。"kotowari list" の出力には面の数を出さない。

### 確認すること

- C-core-surface-21 "kotowari mutants" は、未記載の面の一覧のファイルが無くても、面の規則のファイルや面のファイルが UTF-8 でなくても、停止しない

## 面の検査の書き方と直し方は skill の reference に置き、未記載の面の一覧に足すのは壁打ちと導入の skill だけにする

状態: 実装済み

### 問題

面の検査は、書き方も直し方も、テストのマーカーとは別の場面になる。面の規則は同梱しないので、規則の書き方の例が要る。

surface_without_spec の直し方として、実装役が未記載の面の一覧に1件を足すだけで、仕様に無い機能が関門を通ってしまう。一覧に1件を足すのは仕様の変更で、実装の中で決めることではない。一覧を減らす作業は、導入の流れに乗せる。一覧から外すのは面を決定に書いたときだけなので、決定にならなかった面の1件は一覧に残る。

### 決めたこと

kotowari の skill の references に、面の検査の書き方と直し方の文書 "surface.md" を置き、CLI のフラグとサブコマンドを取り出す面の規則の例を載せる。設定の鍵 "surface.files"、"surface.rules"、"surface.unspecified" は "config.md" に、指摘の種類 surface_without_spec、surface_unspecified_invalid、surface_unspecified_stale は "findings.md" に載せる。

surface_without_spec の直し方として、未記載の面の一覧に1件を足すのは kotowari-brainstorm と kotowari-adopt だけにする。実装役には、仕様に無い面を壁打ちに戻すことだけを書く。

kotowari-adopt は、面の規則を最初に書いたときに出る仕様に無い面をすべて一覧に載せ、話題ごとに減らす。話題の面を決定に書いたら、一覧からその1件を外す。決定にならず未決に残った面と、一覧のラウンドで人が外した面の1件は、一覧に残す。

### 確認すること

- C-core-surface-22 （読んで確認）kotowari の skill の references に "surface.md" があり、面の検査の書き方と直し方と、CLI のフラグとサブコマンドを取り出す面の規則の例が載っている
- C-core-surface-23 （読んで確認）"config.md" に "surface.files"、"surface.rules"、"surface.unspecified" の鍵が、"findings.md" に surface_without_spec、surface_unspecified_invalid、surface_unspecified_stale の種類が載っている
- C-core-surface-24 （読んで確認）skill に、surface_without_spec の直し方として、未記載の面の一覧に1件を足すのは kotowari-brainstorm と kotowari-adopt だけで、実装役は仕様に無い面を壁打ちに戻すと書いてある
- C-core-surface-25 （読んで確認）kotowari-adopt に、規則を最初に書いたときの仕様に無い面をすべて一覧に載せて話題ごとに減らすこと、面を決定に書いたら一覧からその1件を外すこと、決定にならなかった面の1件は一覧に残すことが書いてある
