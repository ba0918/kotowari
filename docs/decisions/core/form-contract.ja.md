# 文書の形の固定

[English](form-contract.md) | 日本語

決定の文書の形をどこで決めるかと、決定の文書をどのエンジンで読むかと、検査の前段に外部の道具を使わないことを扱う。決定の文書の形そのもの（題名、決定の節、状態の行、確認することの行）は[1つの決定は、問題・決めたこと・見送った案・確認することの文章で書く](decision-documents.ja.md#1つの決定は問題決めたこと見送った案確認することの文章で書く)で決める。

## 決定の文書の形はコードに固定し、形を宣言したファイルを読まない

状態: 実装済み

### 問題

文書の形を設定やスキーマのファイルで変えられるようにすると、kotowari が小さなスキーマの言語を持つことになり、作る量の上限に響く。形は今1つしかない。形を固定しないと、「形が崩れている」という検査の意味も揺れる。配布先にスキーマのファイルをどう用意するかという問いも生まれる。

### 決めたこと

kotowari は、コードに固定した1つの形で決定の文書を読む。形を宣言したファイル（例: ".kotowari/schema.yaml"）は、置いてあっても読まない。形を設定で変える口は持たない。文書の側も形を宣言しない。

### 確認すること

- C-core-formc-1 ".kotowari/schema.yaml" に YAML として読めない中身を置いても、check は停止せず、置く前と同じ終了コードと標準出力になる

## 検査の前段に外部の道具を使わない

状態: 実装済み

### 問題

文書の形の検査に、別の言語で書かれた外部の道具を前段として使うと、利用者にその道具の導入を求めることになる。

### 決めたこと

kotowari は、外部のプロセスを検査の前段に使わない。文書の読み取りと形の検査は、kotowari の中で行う。

### 確認すること

- C-core-formc-2 環境変数 "PATH" を空のディレクトリだけに向けても、check の終了コード、標準出力、標準エラーは変わらない

## 決定の文書は、本体に埋め込んだスキーマで mds のエンジンが読む

状態: 実装済み

### 問題

kotowari は、決定の文書を自前のコードで読む。Markdown の読み取りの結果の木を辿り、状態の行、節、確認することの行を手で読み分けている。Markdown の文書の構造を読む仕組みが、汎用のエンジン mds（kotowari-markdown-schema）と kotowari の2か所にある。

仕様を IR で持っていたときは、kotowari は文書の Markdown の構造を自前で読まず、スキーマを読むエンジンに任せると決めていた。決定の文書の形は、mds のスキーマの言葉で宣言できなかった。節の名前が1つの文字列に限られ、項目の見出しに "ID: 名前" の形を求め、深さ4以上の見出しと閉じないコードブロックを表せなかったためである。そこで自前の読み取りが書かれた。

### 決めたこと

kotowari は、決定の文書を mds のエンジンで読む。読むときのスキーマは、本体に埋め込んだ1つのスキーマで、決定の文書の形（題名、話題の段落、決定の見出し、状態の行、4つの節、確認することの行、「未決」の節）を、日本語と英語の両方の形の語で宣言する。日本語と英語の形の語を混ぜて書いた文書も、同じスキーマで読む。埋め込んだスキーマは本体の一部で、形は[決定の文書の形はコードに固定し、形を宣言したファイルを読まない](#決定の文書の形はコードに固定し形を宣言したファイルを読まない)のとおり本体に固定したままである。

kotowari は、決定の文書の形を読み分けるコードを自分で持たない。題名、決定、状態、節、確認することの行の ID・「（読んで確認）」の有無・名前・行の範囲は、エンジンの抽出の値から取る。形の誤りは、エンジンの指摘を kotowari の指摘に写して出す。写し先の無いエンジンの指摘は、[kotowari の中の写しの食い違いは、利用者の入力の誤りと分けて mapping error で止める](cli-environment.ja.md#kotowari-の中の写しの食い違いは利用者の入力の誤りと分けて-mapping-error-で止める)のとおり止める。

次の5つは、エンジンの外で kotowari が扱う。

- 見出しのアンカーと、決定の文書の中のリンクの検査
- 対の側どうしの骨組みの比べ
- ガイドのマーカーの指紋
- 面の名前の引用
- 確認することの ID と、テストのマーカーの照合

### 見送った案

- 自前の読み取りを残す。Markdown の文書の構造を読む仕組みが、kotowari と mds の2か所に残る。
- 形の語の言語ごとに、別のスキーマを持つ。どちらを使うかを決めるのに言語の推測が要り、日本語と英語の形の語を混ぜた文書を通せなくなる。
- 確認することの ID を緩いキャプチャで取り出し、形は kotowari が確かめる。形の違う ID を、エンジンが指摘しなくなる。

### 確認すること

- C-core-formc-3 （読んで確認）`crates/kotowari-core/src/decisions.rs` に、決定の文書の題名、決定と節の見出し、状態の行、確認することの行を、生の行か Markdown の木から読み分ける関数が無い。生の行か Markdown の木を読む関数は、決めたことに挙げた5つのためのものと、エンジンが返した行番号の範囲や行を切り出して使うもの（確認することの行の本文、誤りの detail）だけである
- C-core-formc-4 埋め込んだスキーマは mds のスキーマとして読み込め、その中の状態の値（"提案"、"実装済み"、"proposed"、"implemented"）、状態の行の頭（"状態:"、"Status:"）、4つの節の日本語と英語の名前、「未決」の節の名前（"未決"、"Open"）が、kotowari が状態と節を見分けるのに使う語と一致する
- C-core-formc-5 日本語の形の語と英語の形の語を1つの文書の中で混ぜて書いた決定の文書には、check が形の誤りを出さない
- C-core-formc-6 閉じないコードブロック、2つ目の題名、状態の行の無い決定、「提案」でも「実装済み」でもない状態、「決めたこと」の節の無い決定、形の違う確認することの ID を持つ決定の文書には、それぞれ unclosed_code_block、multiple_titles、decision_state_invalid、decision_state_invalid、decision_section_missing、invalid_id の誤りが出る

## 決定の中の知らない名前の深さ3の見出しは、その下の内容もブロックごとに誤りにする

状態: 実装済み

### 問題

決定の中に、4つの節のどれでもない名前の深さ3の見出しがあると、今の読み取りは、その見出しだけを unknown_heading の誤りにし、その下の内容を誤りにしない。mds は、宣言していない見出しの下の内容を、ブロックごとに宣言していない行の指摘にする。その内容は、ガイドのマーカーの指紋にも、面の名前の引用にも、確認することの行にも読まれない。

### 決めたこと

決定の中と、最初の決定の見出しより前にある、知らない名前の深さ3の見出しは unknown_heading の誤りにし、その下の内容も、ブロックごとに unknown_line の誤りにする。

### 見送った案

- 見出しだけを誤りにする（今の読み取りの振る舞い）。エンジンの指摘を写すときに、内容の指摘を捨てるコードが要る。
- 宣言していない見出しの下の内容を指摘にしないように、mds の決まりを変える。mds のすべての利用者の振る舞いが変わる。

### 確認すること

- C-core-formc-7 決定の中に "### 補足" の見出しと、その下に段落と箇条書きを持つ文書では、"### 補足" の行に unknown_heading の誤りが、段落と箇条書きのそれぞれの開始の行に unknown_line の誤りが出る
- C-core-formc-8 最初の "## " の見出しより前にある "### " の見出しとその下の段落にも、unknown_heading と unknown_line の誤りが出る
