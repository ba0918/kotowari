# メモリの入力と読み込んだ結果

[English](library-inputs.md) | 日本語

検査に要る入力をメモリで渡すときの入力の群と、足りないときの扱い、読み込んだ結果の使い回し、操作ごとに読む範囲を扱う。操作の入口と失敗の種類は[プロジェクトを使う Rust API](library-api.ja.md)で、メモリの入力のパスは[ライブラリの入力のパス](library-paths.ja.md)で決める。

## 必須の入力の群が渡されなければ InputMissing を返し、空の群は通常の規則で検査する

状態: 実装済み

### 問題

ファイルを保存せずに、生成した文書や保存していない文字列を検査したい。そのとき、検査に要る情報が欠けているのを、対象が存在しないことや、検査の成功として扱いたくない。解析に失敗して見つけたものが空になった入力も、成功と取り違えたくない。

一方で、kotowari はメモリの入力からファイルを探さないので、群の中にどのファイルが入っているべきかを知らない。`InputMissing` が出なかったことを、入力が全部揃っていることと取り違えると、渡し忘れたファイルが検査されないまま完了になる。この切り分けの理由は記録に残っていない。

### 決めたこと

`ReadModel::build` と `Inspection::build` は、設定と、次の表の入力の群を受ける。群ごとに、渡していないのか、渡したのか（空の集合を渡した場合を含む）を区別する。

必須の群を渡していなければ、完了した結果を返さず、`InputMissing` を返す。空の集合として渡した群は、通常の規則で検査する。表の条件に当たらない群は、渡さなくてもよく、渡しても判定に使わない。

`InputMissing` が見つけるのは、渡していない群だけである。渡した群の中で、設定が対象にするファイルが欠けていても見つけない。どのファイルを群に入れるかを揃えるのは、呼び出し側である。同じ群の中の重複と、群の間の内容の食い違いは、[同じ論理パスの入力が重なったら、同じファイルとして扱えるときだけ受け付ける](library-paths.ja.md#同じ論理パスの入力が重なったら同じファイルとして扱えるときだけ受け付ける)で決める。

| 入力の群 | 中身 | `ReadInputs` で必須 | `CheckInputs` で必須 |
|---|---|---|---|
| 仕様の文書 | パスと内容 | 常に | 常に |
| テスト情報 | 対象のファイルの `SourceText`、その言語の問い合わせの有無、見つけたテストとマーカー、解析のときの指摘 | `tests.files` が空でない | 同左 |
| ガイド | パスと内容 | 不要 | `guides.files` が空でない |
| 面の解析結果 | 対象のファイルの `SourceText`、その言語の問い合わせの有無、見つけた面、解析のときの指摘 | 不要 | `surface.rules` が空でない |
| 未記載の面の一覧 | 設定された一覧のパスと内容 | 不要 | `surface.rules` が空でなく、`surface.unspecified` が指定されている |
| 追加の指摘の群 | [名前を付けた追加の指摘の群を受け取り、ほかの指摘と一緒に並べて数える](#名前を付けた追加の指摘の群を受け取りほかの指摘と一緒に並べて数える)で決める | 不要 | 不要（渡したときだけ加える） |

テスト情報と面の解析結果が持つ解析のときの指摘は、検査の結果に引き継ぐ。

### 確認すること

- C-core-libinputs-1 必須の群を渡さずに `ReadModel::build` か `Inspection::build` を呼ぶと、完了した結果ではなく `InputMissing` が返る
- C-core-libinputs-2 必須の群を空の集合として渡すと、`InputMissing` にならず、通常の規則で検査した結果が返る
- C-core-libinputs-3 表の条件に当たらない群は、渡さなくても `InputMissing` にならず、渡しても検査の結果に入らない
- C-core-libinputs-4 解析に失敗して、見つけたテストが空のテスト情報を渡すと、解析の失敗の指摘が検査の結果に残る
- C-core-libinputs-13 `guides.files` か `surface.files` で対象のファイルを指定していても、その群を空の集合で渡せば `InputMissing` にならない（群の中のファイルの漏れは見つけない）

## メモリの入力の検査は、ファイルを読み足さず、ファイルから読んだときと同じ規則で結果を出す

状態: 実装済み

### 問題

ファイルを保存せずに検査する使い方では、渡したもののほかにファイルを読まれては困る。また、内部をライブラリとして作り直しても、検査の結果の意味は変えない（[CLI は、ライブラリの結果を既存の出力と停止の理由に写すだけにする](library-api.ja.md#cli-はライブラリの結果を既存の出力と停止の理由に写すだけにする)と同じ理由）。

### 決めたこと

メモリの入力から検査するとき、kotowari はファイルを読み足さない。渡された群の中身だけから、ファイルから読んで検査するときと同じ規則で、指摘の重複の抑制、数え方、ガイドとテストの置き場の重なりの検査を行う。

### 確認すること

- C-core-libinputs-5 メモリで渡したテスト情報、ガイド、面の解析結果は、ファイルを読まずにそのまま判定に使われ、マーカーの数、ガイドの古さの指摘、仕様の無い面の指摘が出る
- C-core-libinputs-6 メモリで渡した入力にも、ファイルから読むときと同じ、指摘の重複の抑制、数え方、ガイドとテストの置き場の重なりの検査が当たる

## 名前を付けた追加の指摘の群を受け取り、ほかの指摘と一緒に並べて数える

状態: 実装済み

### 問題

core は全体像を知らない。それでも、全体像の指摘を検査の結果に入れたい。検査の結果は core だけが組み立て、外から組み立てたり書き換えたりさせない、という公開 API の決まりは保ちたい。指摘の並べ方と集計を、2か所に持ちたくない。

### 決めたこと

core の検査の入力は、名前を付けた追加の指摘の群を受け取れる。群は、名前、読んだファイルの数、マーカーの数、指摘を持つ。core は群の意味を知らず、その指摘をほかの指摘と合わせて並べ、counts、終了コード、complete に数え、群ごとの数を結果に持たせる。kotowari のライブラリは、全体像の指摘を "overview" の群としてこの形で渡す。

### 見送った案

- kotowari の側で、core の結果を包む別の結果型を作る。core の型をそのまま再公開する決まり（[公開にするかは外の利用者が頼るかで決め、kotowari は入口から届く下位の型だけを同じ型のまま再公開する](library-crates.ja.md#公開にするかは外の利用者が頼るかで決めkotowari-は入口から届く下位の型だけを同じ型のまま再公開する)）とぶつかり、集計が2か所になる。

### 確認すること

- C-core-libinputs-7 `Inspection::build` に追加の群を渡すと、その指摘がほかの指摘と同じ規則で並んで counts と complete に数えられ、`check` と `status` の結果に、群の名前、ファイルの数、マーカーの数が出る
- C-core-libinputs-8 追加の群を渡さなければ、検査の結果に群は出ない

## 読み込んだ結果は使い回せ、明示して読み直すまで変わらない

状態: 実装済み

### 問題

1回の呼び出しで結果を得る簡単な使い方と、同じ入力に対して複数の操作をする使い方の、両方を支えたい。

### 決めたこと

`Project::read` は list と query のための `ReadModel` を、`Project::inspect` は check と status のための `Inspection` を返す。`ReadModel` の `list` と `query`、`Inspection` の `check` と `status` と読み取りの結果は、ファイルを読み足さずに結果を返す。使い回している間は、ファイルを暗黙に読み直さない。ファイルの変更を反映するには、`Project` から読み直す。

`Project` の操作を直接呼ぶときは、呼ぶたびに要る入力を新しく読む。

### 確認すること

- C-core-libinputs-9 `ReadModel` と `Inspection` を得たあとで元のファイルを変えても、それらの `list`、`query`、`check`、`status` は、読んだときの内容から結果を返す
- C-core-libinputs-10 元のファイルを変えたあと、`Project` から読み直した結果と、`Project` の操作を直接呼んだ結果は、変えたあとの内容から結果を返す

## 操作は、その操作が使う入力だけを読む

状態: 実装済み

### 問題

読み込んだ結果を使い回せるようにしても、すべての操作に、全部のファイルの読み込みを求めたくない。それまで要らなかったファイルの問題で、操作が失敗するのを避ける。list と query はガイドを読まない、という既存の動きも保つ。

### 決めたこと

list と query のための入力（`ReadInputs`）には、check と status だけが使うガイドと面を求めない。読み込んだ結果を作るときも同じである。`plan` と `mutants` は、仕様の文書を読まずに結果を返す。

### 確認すること

- C-core-libinputs-11 `guides.files` を設定していても、ガイドを渡さずに `ReadModel` を作れ、その `list` と `query` が結果を返す
- C-core-libinputs-12 仕様の文書の置き場が無いプロジェクトでも、`Project` の `plan` と `mutants` が結果を返す

## 決定の文書の文字列を解析して、取れた決定と確認することを読み取り専用で返す公開の入口を置く

状態: 提案

### 問題

エディタとの連携や独自の道具から、仕様の文書を解析した結果を使いたい。形に誤りのある文書でも、取れたものと指摘を参照できなければ、書きかけの文書を扱えない。解析だけを使う利用者に、テスト情報やガイドのような検査のための入力を求めたくない。

今の公開の入口 `ir::parse` は、IR の文書を解析して項目、参照、位置を返す。仕様を決定の文書だけで持つので（[仕様は、話題ごとの、今有効な決定の文書だけで持つ](decision-documents.ja.md#仕様は話題ごとの今有効な決定の文書だけで持つ)）、IR の文書を解析する入口は使う先が無くなる。

### 決めたこと

kotowari-core は、決定の文書の文字列を論理パスと一緒に受け取り、その文書の決定と確認することを、元の文書の行と一緒に読み取り専用で返す公開の入口を持つ。形に誤りのある文書でも、取れた決定と確認することと、形の誤りの指摘を返す。この入口は、文書の文字列のほかの入力の群を求めない。

IR の文書を解析する `ir::parse` は、この入口に置き換える。

### 確認すること

- C-core-libinputs-14 決定の文書の文字列だけを入口に渡すと、文書の中の決定と確認することが、元の文書の行と一緒に返る
- C-core-libinputs-15 形に誤りのある決定の文書を渡しても、取れた決定と確認することと、形の誤りの指摘が返る
