# 変異テストの結果の読み取り

[English](mutants-input.md) | 日本語

"kotowari mutants" が、変異テストの道具の結果のファイルを変異の結果に写すところと、写せない結果のファイルで停止するところを扱う。指摘と集計は[変異の結果の検査](mutants.ja.md)で決める。どの道具の結果かを選ぶ "--tool" の引数の扱いは[kotowari mutants は道具の名前を --tool で必ず受け、結果のファイルをちょうど1つ受ける](cli.ja.md#kotowari-mutants-は道具の名前を---tool-で必ず受け結果のファイルをちょうど1つ受ける)で、パスの正規化は[設定ファイルの値のパスは、比べる前と出力の前に正規化する](base-directory.ja.md#設定ファイルの値のパスは比べる前と出力の前に正規化する)で決める。

## 変異の結果は道具を知らない形で持ち、cargo-mutants の結果のファイルを表のとおりに写す

状態: 実装済み

### 問題

kotowari 自体は言語を限らない道具で、結果を作る変異テストの道具は替わりうる。今は Rust と cargo-mutants だけである。道具に固有の形を指摘と決めたことに漏らすと、道具を足すたびに既存の決まりが変わる。

結果を作る道具が今は1つしか無いので、kotowari 独自の中立なファイル形式を決めると、想像で決める契約になる。道具の結果をその形式に変換するスクリプトは、誰にも検査されない。実物の形式を読むなら、結果のファイルを置くだけでテストできる。

どの道具の結果かを省けるようにすると、既定の道具が Rust の前提として焼き付く。ファイルの中身から道具を判別すると、道具が増えたときに誤って判別する場面が生まれる。

### 決めたこと

kotowari の中に、道具を知らない変異の結果の形を1つ持つ。変異の結果は、ファイル、行、変更の説明（道具が出した文のまま）、結果（捕まえた、見逃した、時間切れ、ビルド不能の4値）を持つ。指摘と集計は、この形の語だけで決める。道具ごとの読み取りは、その道具の結果のファイルをこの形に写す部品にする。道具を足すときは、既存の決まりを変えず、部品と写し方の表を足す。

初めの版が読むのは、cargo-mutants の結果のファイル（outcomes.json）そのままである。どの道具の結果かは、"kotowari mutants" の "--tool" で必ず指定する。値は今は "cargo-mutants" だけである。

"--tool" が "cargo-mutants" のとき、結果のファイルは、最上位の "outcomes" の鍵に並びを持つ JSON である。"scenario" が文字列 "Baseline" の1件は基準の実行（変異を入れない実行）で、変異の結果にしない。それ以外の1件は、"scenario" の下の "Mutant" に変異を持つ。1件ごとに次のとおりに写す。

| 変異の結果の項目 | 写す元 |
|---|---|
| ファイル | "scenario.Mutant.file"（文字列）。基準のディレクトリからの相対パスとして読み、設定のパスと同じ正規化（[設定ファイルの値のパスは、比べる前と出力の前に正規化する](base-directory.ja.md#設定ファイルの値のパスは比べる前と出力の前に正規化する)）を掛ける |
| 行 | "scenario.Mutant.span.start.line"（数） |
| 変更の説明 | "scenario.Mutant.name"（文字列）の先頭から、"scenario.Mutant.file" の値、":"、"span.start.line" の値、":"、"span.start.column" の値、": " をこの順につないだ前置きを除いた残り |
| 結果「捕まえた」 | "summary" が "CaughtMutant" |
| 結果「見逃した」 | "summary" が "MissedMutant" |
| 結果「時間切れ」 | "summary" が "Timeout" |
| 結果「ビルド不能」 | "summary" が "Unviable" |
| 基準の実行の成功 | 基準の実行の1件の "summary" が "Success" |

表に挙げた鍵のほかは見ず、知らない鍵があっても止まらない。道具があとで足す鍵に巻き込まれないためである。基準の実行が1件も無い結果のファイルも読む。cargo-mutants には基準の実行を省くオプションがある。

結果のファイルのパスの正規化は、書き方の違いだけで等価の一覧との一致が外れないようにするためで、指摘の path にも正規化したパスを出す。

### 見送った案

- kotowari 独自の中立なファイル形式を決め、道具ごとの変換スクリプトを外に置く。中立な形式は想像で決める契約になり、変換スクリプトは誰にも検査されない。
- どの道具の結果かに既定値を置く。Rust の前提が焼き付く。
- ファイルの中身から道具を判別する。道具が増えたときに誤って判別する場面が生まれる。
- 以前の決定: 変異の結果に関数名も持たせる（cargo-mutants では "function.function_name"）。写すだけでどの指摘にも集計にも使われておらず、cargo-mutants の変更の説明には関数名が入っているので、外した。

### 確認すること

- C-core-mutin-1 cargo-mutants の結果の1件の "file"、"span.start.line"、"name" から前置きを除いた残りが、それぞれ指摘の path、line、detail になる
- C-core-mutin-2 "summary" の "CaughtMutant"、"MissedMutant"、"Timeout"、"Unviable" が、それぞれ捕まえた、見逃した、時間切れ、ビルド不能として数えられる
- C-core-mutin-3 基準の実行が無く、表に無い鍵を持つ結果のファイルも、停止せずに読める
- C-core-mutin-4 結果の "file" を "./src/a.rs" と書いた結果でも、指摘の path には正規化したパス "src/a.rs" が出る

## 形の合わない結果のファイルでは、結果の誤りで停止する

状態: 実装済み

### 問題

知らない値を黙って読み飛ばすと、見逃しを落とす。変異を入れない基準の実行でテストが落ちている結果は、全体に意味が無い。等価の一覧との一致は変更の説明の文字列に懸かるので、道具の形式が変わったら、黙って通さずに止めたい。基準のディレクトリの外は読まない。

### 決めたこと

次のどれかに当たる結果のファイルでは、新しい停止の理由「結果の誤り」で停止する。停止の文言は "results error" で、詳細は結果のファイルの相対パスと誤りの説明である。

- JSON として読めない
- 写し方の表の写す元の鍵が無いか、型が違う
- 1件の結果が、写し方の表のどの行にも当たらない（変異の1件に "Success" や "Failure" が付いているときを含む）
- 基準の実行の結果が「基準の実行の成功」でない
- 行が1未満
- 変更の説明の前置きが、写し方の表の形でない
- ファイルが絶対パスか、".." の要素を含む

結果のファイルが無い、読めない、UTF-8 でないときは、今ある停止の理由（読めないファイル、UTF-8 でないファイル）で停止する。

### 確認すること

- C-core-mutin-5 JSON として読めない、要る鍵の型が違う、"summary" が知らない値、基準の実行が成功でない、行が0、"name" の前置きが形に合わない、のいずれかの結果のファイルでは、終了コード2で停止し、標準エラーの1行目が "results error: " と結果のファイルの相対パスで始まる。行が1の変異の結果は停止せずに読む
- C-core-mutin-6 結果の "file" が基準のディレクトリの外を指す（".." を含む）と、結果の誤りで停止する
- C-core-mutin-7 結果のファイルが無いと、終了コード2で停止し、標準エラーの1行目が "unreadable file: " で始まる
