# プロジェクトを使う Rust API

[English](library-api.md) | 日本語

別の Rust のアプリから kotowari の操作を呼ぶ入口と、検査の結果と失敗の分け方、CLI との関係を扱う。メモリで渡す入力と、読み込んだ結果の使い回しは[メモリの入力と読み込んだ結果](library-inputs.ja.md)で、作業開始位置とメモリの入力のパスは[ライブラリの入力のパス](library-paths.ja.md)で決める。クレートの分け方と再公開する型は[ライブラリのクレート境界](library-crates.ja.md)で、Tokio 対応は[任意の Tokio 対応](library-async.ja.md)で決める。

## 別の Rust のアプリは、kotowari の操作を Project のメソッドとして型付きの入力で呼ぶ

状態: 実装済み

### 問題

別の Rust のアプリが、kotowari の既存の機能を、CLI を通さずに呼び出せるようにしたい。CLI の引数を組み立てて渡すのではなく、操作ごとに要る入力を型で渡したい。ファイルを保存せずに検査する使い方と並んで、既存のプロジェクトをディレクトリを指定して検査する使い方も支える。

全体像も、check に統合する先は CLI ではなくライブラリにする。CLI は Project の上の薄い層なので、検査の統合は Project で行う。

全体像を配る serve は、元データの検査、ポートの確保、書き込みの順に進む。全体像を作る操作が1つの呼び出しで書いてしまうと、CLI は検査より先にポートを取るか、ポートより先に書くしかなく、ポートが使えないのに全体像を書いてしまう。

### 決めたこと

入口は `Project::new` で、`ProjectOptions` でプロジェクトの作業開始位置と、任意の設定ファイルの指定を受ける（位置の扱いは[ファイルを読む入口は作業開始位置を受け取り、既存の CLI と同じ規則でそこから解く](library-paths.ja.md#ファイルを読む入口は作業開始位置を受け取り既存の-cli-と同じ規則でそこから解く)で決める。作業開始位置は絶対パスで受け、`Project` はプロセスのカレントディレクトリを変えない）。`Project` は、次の操作をメソッドとして持つ。

| メソッド | すること | 返すもの |
|---|---|---|
| `check` | 設定に従ってプロジェクトを検査する。全体像の元データの指摘と "overview" の群も含める | 指摘と集計 |
| `list` | 仕様の文書から読み取れたものを一覧にする | 型付きの一覧 |
| `query` | 指定した ID を問い合わせる | 本文と、それを指すものを含む型付きの結果 |
| `status` | `check` と同じ範囲を検査する | 集計と完了の状態 |
| `plan` | 指定した計画書を検査する | 指摘と集計 |
| `mutants` | 指定した変異テストの結果と、等価の情報を検査する | 指摘と変異の集計 |
| `overview_prepare` | 全体像の元データを検査して描画する | 書く前の描画の結果 |
| `overview_build` | `overview_prepare` に続けて、描画の結果を全体像の置き場へ書く | 書いたファイルと消したファイルの一覧、書かなかったファイルの数 |

`check`、`status` と、読み込み済みの検査の結果を返す `inspect` は、全体像の指摘と "overview" の群を含める。

`overview_prepare` は、検査と描画をメモリの中で済ませ、何も書かない。全体像を書くのは、`overview_build` と、準備の結果の `write` だけである。全体像の置き場と、書く・消す・書かないの決まりは[overview build は、毎回すべてを描き、中身の違うファイルだけを書き、作られなくなったファイルを消す](overview-commands.ja.md#overview-build-は毎回すべてを描き中身の違うファイルだけを書き作られなくなったファイルを消す)で決める。非同期の入口（[`AsyncProject`](library-async.ja.md#高水準の操作を既定で無効な-tokio-feature-で-tokio-から待てるようにする)）も同じ操作を持つ。全体像を配る serve は、ライブラリに置かない。

`plan` と `mutants` が仕様の文書を読まないことは、[操作は、その操作が使う入力だけを読む](library-inputs.ja.md#操作はその操作が使う入力だけを読む)で決める。

### 見送った案

- 全体像の build を、同期の `Project` だけに置く。非同期の入口が同期の高水準の操作に対応する、という形が崩れる。
- 全体像の操作を、ライブラリに公開しない。

### 確認すること

- C-core-libapi-1 `Project` の `check`、`list`、`query`、`status`、`plan`、`mutants` は、CLI を通さずに、型付きの入力から型付きの結果を返す
- C-core-libapi-2 全体像の元データがあるプロジェクトでは、`check`、`status`、`inspect` の結果に全体像の指摘が入り、`check` と `status` の結果に "overview" の群が出る
- C-core-libapi-3 `overview_build` は全体像のファイルを書き、書いたファイル、消したファイル、書かなかったファイルの数を返す。書き直す必要の無いファイルは、書かなかったファイルの数に入る
- C-core-libapi-13 `overview_prepare` を呼んでも全体像の置き場は作られず、`overview_build` を呼んだときに書かれる

## 検査で見つけた指摘と、検査を終えられなかった失敗を分けて返す

状態: 実装済み

### 問題

呼び出し側が、表示用の文字列を解析せずに結果を扱えるようにしたい。また、検査の対象に問題が見つかった結果と、読み込みに失敗するなどで検査を完了できなかった失敗とを、呼び出し側が別々に処理できるようにしたい。

### 決めたこと

検査を終えたときは、文書の指摘を持つ結果を返す。指摘は、種類、重要度、パス、あれば行を、読み取り専用で持つ。ライブラリは結果を表示せず、表示の仕方は呼び出し側が決める。

検査を実行できないときは、`Result` の `Err` を返す。失敗は種類をプログラムで見分けられ、`std::error::Error` と `Display` を実装する。失敗の種類の例として、入力の誤り（`InvalidInput`）、読み込みの失敗（`ReadFailure`）、未知の問い合わせの ID（`UnknownQuery`）がある。必須の入力が渡されなかったとき（`InputMissing`）は、[必須の入力の群が渡されなければ InputMissing を返し、空の群は通常の規則で検査する](library-inputs.ja.md#必須の入力の群が渡されなければ-inputmissing-を返し空の群は通常の規則で検査する)で決める。

### 確認すること

- C-core-libapi-4 指摘の出る仕様の文書があるプロジェクトで `check` を呼ぶと、`Err` ではなく、指摘を持つ結果が返り、指摘の種類を型で見分けられる
- C-core-libapi-5 検査や全体像の書き出しを終えられないとき（例えば、検査に要るファイルが読めないとき、設定が正しくないとき、全体像の置き場に書けないとき）は、指摘の無い結果ではなく、種類を見分けられる `Err` が返る
- C-core-libapi-6 （読んで確認）kotowari のライブラリは、検査の結果を標準出力にも標準エラーにも書かない

## 渡した設定ファイルがディレクトリなら入力の誤り、既定の場所がディレクトリなら読めない失敗にする

状態: 実装済み

### 問題

渡された設定ファイルが無いときは、入力の誤りになる。ディレクトリのときにライブラリがそれを読もうとして失敗すると、読み込みの失敗になり、同じ指定の誤りが失敗の種類で分かれてしまう。判定をライブラリの1か所にまとめれば、CLI とライブラリで揃う。

一方、設定ファイルを渡していないときは、利用者は引数を渡していないので、引数の誤りにはしない。既定の場所に置かれたものが読めない、という扱いになる。

### 決めたこと

`ProjectOptions` で渡した設定ファイルが無いとき、またはディレクトリのときは、入力の誤り（`InvalidInput`）にする。読み込みの失敗（`ReadFailure`）にはしない。CLI は自前で判定せず、ライブラリの結果を写す。

`ProjectOptions` が設定ファイルを渡さず、基準のディレクトリの ".kotowari/config.yaml" がディレクトリのときは、読み込みの失敗（`ReadFailure`）にする。

### 確認すること

- C-core-libapi-7 `ProjectOptions` で渡した設定ファイルがディレクトリのときも、無いときも、`check` は同じ `InvalidInput` の種類の `Err` を返し、`ReadFailure` にはならない
- C-core-libapi-8 設定ファイルを渡さず、基準のディレクトリの ".kotowari/config.yaml" がディレクトリのときは、`check` が `ReadFailure` の種類の `Err` を返す

## 未知の ID の問い合わせの失敗から、その ID を取り出せる

状態: 実装済み

### 問題

CLI が、ライブラリの失敗の文から決まった前置きを剥がして ID を取り出すと、文言を変えたときに壊れやすい。ID を返すメソッドを足すだけなら、壊れる変更にならず、CLI の出力も保てる。

### 決めたこと

`kotowari::Error` に `pub fn unknown_id(&self) -> Option<&str>` を持たせる。失敗の種類が `UnknownQuery` のときだけ、問い合わせた ID を返し、ほかの種類の失敗では ID を返さない。名前は CLI の文（unknown id）と揃え、何の ID かが名前で読めるようにする。CLI はこのメソッドで ID を取り出し、CLI の出力は変わらない。

### 確認すること

- C-core-libapi-9 どこにも無い ID で `query` を呼ぶと、`UnknownQuery` の種類の `Err` が返り、`unknown_id` からその ID を取り出せる
- C-core-libapi-10 ほかの種類の失敗では、`unknown_id` は ID を返さない

## CLI は、ライブラリの結果を既存の出力と停止の理由に写すだけにする

状態: 実装済み

### 問題

内部をライブラリとして作り直しても、CLI の利用者の入力や処理を壊したくない。CLI と外のアプリが、同じ高水準の操作を使う形に揃えたい。それまでは CLI のバイナリだけを提供していたので、既存の Rust の API と内部の構造の互換は保たなくてよい。

### 決めたこと

kotowari-cli は、kotowari のライブラリの上の薄い層にする。CLI はライブラリの結果を、既存の JSON と text の出力と、停止の理由に写す。

kotowari と mds の両方のバイナリについて、コマンド、引数、終了コード、出力、設定とスキーマの受け付け方、検査の結果の意味は、ライブラリの上に載せても変えない。ソースからインストールするときのパッケージの名前が変わっても、実行するコマンドの名前は変えない（パッケージの名前は[用途ごとにパッケージを分け、利用者は用途でパッケージを選ぶ](library-crates.ja.md#用途ごとにパッケージを分け利用者は用途でパッケージを選ぶ)で決める）。

### 確認すること

- C-core-libapi-11 CLI の契約テストが定める入力では、ライブラリの上に載せた CLI が、期待する JSON、text、終了コードをそのまま返す
- C-core-libapi-12 （読んで確認）kotowari-cli は、検査と問い合わせを kotowari のライブラリの `Project` の操作で行い、その結果を JSON か text に整形し、停止の理由に写すだけである
