# ライブラリの入力のパス

[English](library-paths.md) | 日本語

メモリで渡す入力の論理パスと、ファイルを読む入口が受け取る作業開始位置を扱う。入力の群と、足りないときの扱いは[メモリの入力と読み込んだ結果](library-inputs.ja.md)で、入口の操作は[プロジェクトを使う Rust API](library-api.ja.md)で決める。

## メモリの入力は、内容と論理パスの組で受け取り、ファイルを探さない

状態: 実装済み

### 問題

ファイルを保存せずに、生成した文書や保存していない文字列を検査したい。複数の文書を検査するには、それぞれの内容と、それがどの文書かを示す論理的なパスを、組にして渡せる必要がある。

内部をライブラリとして作り直しても、既存の CLI が受け付けていた、親ディレクトリにある仕様の置き場の設定は壊さない。

論理パスが空か絶対パスでも受け付けると、プロジェクトの中のどの文書かが決まらない入力が検査に入る。これを拒む理由は記録に残っていない。

### 決めたこと

メモリの入力は、`SourceText` で、プロジェクトの中の位置を表す論理パスと、文字列の組として受け取る。論理パスに当たるファイルは無くてもよく、kotowari はファイルを探さない。論理パスは文字列として扱い、ファイルシステムで正規化しない。

論理パスは、プロジェクトの基準からの相対パスとする。空の論理パスと、絶対パスの論理パスは拒む（絶対パスは入力の誤り `InvalidInput` にする）。

既存の CLI が受け付ける、親ディレクトリを指す論理パス（".." を含むもの）は、拒まずにそのまま保つ。

### 確認すること

- C-core-libpaths-1 ファイルの無い論理パスと文字列から `SourceText` を作ると、ファイルを読まずに、その文字列を内容として持つ
- C-core-libpaths-2 ".." で始まる論理パスの `SourceText` は拒まれず、パスの ".." がそのまま残る
- C-core-libpaths-5 空の論理パスと絶対パスの論理パスからは `SourceText` を作れず、絶対パスのときの失敗は `InvalidInput` の種類になる

## 同じ論理パスの入力が重なったら、同じファイルとして扱えるときだけ受け付ける

状態: 実装済み

### 問題

同じファイルを、綴りの違う2つのパスや、内容の違う2つの入力として渡せると、同じファイルを別物として扱うことになる。数え方と指摘が二重になり、どちらの内容で検査したかも決まらない。

テストと面の解析結果は、解析に使った本文を持っていないと、同じパスの別の入力と内容が同じかを、ファイルを読み足さずに比べられない。

### 決めたこと

同じ群の中で、区切り文字の違い、先頭の "./"、途中の "/./"、重なった区切り、末尾の区切りを揃えたあとに同じになる論理パスがあれば、入力の誤り（`InvalidInput`）にする。

別の群に同じ論理パスの入力があり、内容が異なれば、入力の誤り（`InvalidInput`）にする。内容が同じなら受け付け、群の間の重なりは既存の重なりの規則で判定する（[メモリの入力の検査は、ファイルを読み足さず、ファイルから読んだときと同じ規則で結果を出す](library-inputs.ja.md#メモリの入力の検査はファイルを読み足さずファイルから読んだときと同じ規則で結果を出す)）。テスト情報と面の解析結果は、解析に使った `SourceText` の全文を持ち、比べるのはこの本文とする。解析の結果や指摘が同じでも、本文が違えば同じ内容とはしない。

ファイルから読んで取り込むときも、元のファイルで見分ける。同じ群に同じ元のファイルが2回入っていれば、表示のパスの綴りが違っても拒む。読み込みと検査のあいだ、または解析と取り込みのあいだで、同じ元のファイルの本文が食い違えば拒む。

### 確認すること

- C-core-libpaths-6 同じ群の中に、区切りを揃えると同じになる2つの論理パスがあると、`InvalidInput` の種類の失敗が返る
- C-core-libpaths-7 別の群に同じ論理パスの入力があり、内容が異なれば `InvalidInput` の種類の失敗が返り、内容が同じなら受け付ける
- C-core-libpaths-8 テスト情報と面の解析結果に、同じ論理パスで本文の違う `SourceText` を渡すと、`InvalidInput` の種類の失敗が返る
- C-core-libpaths-9 ファイルから読んで取り込むとき、同じ群に同じ元のファイルが2回あれば、表示のパスの綴りが違っても拒む
- C-core-libpaths-10 ファイルから読んで取り込むとき、読み込みと検査、または解析と取り込みで、同じ元のファイルの本文が食い違えば拒む

## ファイルを読む入口は作業開始位置を受け取り、既存の CLI と同じ規則でそこから解く

状態: 実装済み

### 問題

外の Rust のアプリが、ディレクトリを指定して既存のプロジェクトを検査できるようにしたい。そのとき、既存の設定の受け付け方と、相対パスの解き方の意味は、CLI と変えない。スキーマの読み込みでも、CLI のファイルの探索とキャッシュの処理を、そのまま使い回す。

作業開始位置は、プロセスのカレントディレクトリという共有の状態から切り離しておく。相対パスの作業開始位置を受け付けたり、入口がカレントディレクトリを変えたりすると、同じプロセスのほかの処理がカレントディレクトリを変えたときに、別のディレクトリを検査することになる。

### 決めたこと

`ProjectOptions` は、作業開始位置と、任意の設定ファイルの指定を受ける。スキーマを読む `LoaderOptions` は、作業開始位置と、任意のキャッシュ基準を受ける（スキーマの読み込みの入口は[スキーマと文書の読み込みは、別のクレートに置いて CLI と外のアプリで共用する](../schema/library-io.ja.md#スキーマと文書の読み込みは別のクレートに置いて-cli-と外のアプリで共用する)で決める）。

作業開始位置と、明示するキャッシュ基準は、絶対パスで受ける。相対パスなら、入力の誤り（`InvalidInput`）として拒む。

設定ファイルの相対パスは、既存の CLI と同じく、作業開始位置から解く。設定の探し方と、読み込む文書の相対パスの解き方も、既存の CLI のままにする。キャッシュ基準を省いたときは、作業開始位置から、既存の CLI と同じ探し方でキャッシュ基準を探す。

`Project` と `SchemaLoader` は、プロセスのカレントディレクトリを変えない。作ったあとでカレントディレクトリが変わっても、解く基準は変わらない。

### 確認すること

- C-core-libpaths-3 `ProjectOptions` に設定ファイルを相対パスで渡すと、作業開始位置から解いた設定ファイルで操作する
- C-core-libpaths-4 `SchemaLoader` に相対パスで渡した文書は、`LoaderOptions` の作業開始位置から解いて読む
- C-core-libpaths-11 相対パスの作業開始位置では `Project::new` も `SchemaLoader::new` も失敗を返し、`LoaderOptions` に相対パスのキャッシュ基準を渡したときも `SchemaLoader::new` が失敗を返す
- C-core-libpaths-12 `Project` と `SchemaLoader` を作ったあとでプロセスのカレントディレクトリが変わっても、作業開始位置から解いて読む
- C-core-libpaths-13 `Project` の操作と `SchemaLoader` の読み込みは、プロセスのカレントディレクトリを変えない
