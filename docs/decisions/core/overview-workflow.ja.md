# 全体像を書く工程

[English](overview-workflow.md) | 日本語

工程の skill が全体像の元データをどう書くか、全体像の単位、目次の置き方、壁打ちの承認で全体像を作り直す段、実装の工程が全体像の元データを直さないことを決める。kotowari の skill の文を人か LLM が読んで確かめる決定だけを持つ。元データの検査や build と serve の振る舞いは[全体像の元データ](overview-data.ja.md)と[全体像を作るコマンドと見せるコマンド](overview-commands.ja.md)で、元データが決定の文書を指すことは[全体像の元データは、決定の文書を指す](languages-and-guides.ja.md#全体像の元データは決定の文書を指す)で決める。

## 全体像の元データは、冒頭の結論から始め、題材に合わせた部品で、決定のつながりと振る舞いと今の状態を表す

状態: 提案

### 問題

壁打ちは判断を1問ずつ詰めるので、1問ずつは人に分かる。しかし判断が数十から百を超えると、全部を組み合わせた最終的な姿を人が思い描けず、出来上がったものが何で、なぜそうなったかを後から説明できなくなる。規模が大きくなると、判断どうしのつながりと、出来上がるものの姿（使う人から見てどう動くか）の両方が分からなくなる。

同じ題材を、要約と話題のグループを文章で説明する形と、図・表・装飾を多く使う形で並べて比べたところ、文章の形は分かりづらく、視覚情報の多い形は全く違った。冒頭の結論と要約は、構成として正しかった。一方で、説明の最適な形は題材によって変わるので、構成は固定できない。

元データは描画を通して見るもので、人は描いたページだけを読む。毎回一から作ると、費用と見た目のぶれが戻る。壁打ちごとにその時点の写真を作ると、後の壁打ちで置き換えられたときに嘘になる。

全体像の読み手は製品を作る人（壁打ちをした本人、実装役、レビュー役）で、ガイドの読み手は製品を使う人である。同じ機能でも答える問いが違うので、書き分ければ同じ説明を2か所で保守しなくて済む。ある節が使い方か判断かを機械で判定する方法は無いので、書き分けは検査にせず、書き方の指針にする。

### 決めたこと

kotowari の skill に、全体像の元データを書く場面を置き、次の書き方を求める。元データは LLM が書き、人は描いたページだけを読む。

- 題名の直後に、結論と要約の lead の部品を置く。
- 図・表・装飾の部品を、題材に合わせて選んで並べる。部品の並びを固定しない。
- 判断どうしのつながりと、判断の結果としての振る舞いの両方を表す。振る舞いは短く示すだけにし、使い方の手順（コマンド、オプション、設定の例）はガイドに任せて、全体像では機能の名前に触れるだけにする。
- 今の状態と、決めたがまだ作っていないこと（状態が「提案」の決定）と、未決を表す。
- 前回の元データを直して書き、一から書き直さない。
- 節の見出しの隣に、その節が説明する決定を指すガイドのマーカーを付ける。
- 部品の参照は、"refs" か "ref" の欄に書く。

全体像とガイドの書き分けには、境目の例を添える。工程の流れの図は判断の結果としての振る舞いなので全体像に置いてよく、コマンドの書き方や選択肢の例はガイドに置く。

### 見送った案

- 要約、話題のグループ、危険度と確かさ、項目を文章で並べる形。比べたときに分かりづらかった。
- 結論、要約、流れ図、3列の表…と、部品の並びを固定する。題材によって最適な形が変わる。
- 承認のたびに一から作る一時のデータにする。費用と見た目のぶれが戻る。
- 壁打ちごとに、その時点の写真を作る。後の壁打ちで置き換えられると嘘になる。
- 全体像をやめてガイドに寄せる。判断のつながりと、予定と未決を見せる場所が無くなる。
- ガイドをやめて全体像に寄せる。全体像は手元で描く HTML で、GitHub で読めず、ページの外へリンクしない。

### 確認すること

- C-core-ovflow-1 （読んで確認）kotowari の skill に全体像の元データを書く場面があり、題名の直後に結論と要約の lead を置くこと、部品の種類と並びを題材に合わせて選ぶこと、判断どうしのつながりと判断の結果としての振る舞いの両方を表すことが書いてある
- C-core-ovflow-2 （読んで確認）同じ場面に、今の状態と、状態が「提案」の決定と、未決を表すこと、前回の元データを直して書くこと、節の見出しの隣に決定を指すガイドのマーカーを付けること、参照を "refs" か "ref" の欄に書くことが書いてある
- C-core-ovflow-3 （読んで確認）kotowari の skill に、全体像には決まっていることとその理由、予定と未決を書き、使い方の手順はガイドに任せるという書き分けが、境目の例とともに書いてある

## 全体像の単位は、使う人が1つの機能として名前で呼べるものにし、人が決める

状態: 提案

### 問題

全体像の単位を LLM に毎回任せると、切り方がぶれる。単位は仕様の話題を基にするのが妥当で、使う人が1つの機能として名前で呼べるものにすれば、ガイドと同じ形になる。既にある話題の全体像を一度にまとめて作ると、触らない話題の分の費用を先に払うことになる。

### 決めたこと

全体像は、決定の文書の話題を基にした単位で持つ。単位の目安は、使う人が1つの機能として名前で呼べるものにする（その例: ガイドのマーカー、導入、変異テスト）。機能を横断するもの（その例: 出力の形、設定）は単独の全体像にせず、関わる機能の全体像の中で触れる。

初めて全体像を作るときと、どの全体像にも属さない話題の文書を変えたときは、LLM が単位の案（既にある全体像に足すか、新しく作るか）を出し、人が決める。決めた単位は、壁打ちで分けるか統合すると決めたときのほかは変えない。触れていない話題の全体像は、まとめて作らない。

### 見送った案

- 機能を入れた時点で、すべての話題の全体像を作る。触らない話題の分の費用を先に払う。

### 確認すること

- C-core-ovflow-4 （読んで確認）kotowari の skill に、全体像の単位の目安が使う人が1つの機能として名前で呼べるもので横断的なものを単独にしないこと、どの全体像にも属さない話題の文書を変えたときは単位の案を LLM が出して人が決めること、決めた単位は壁打ちで決めない限り変えないこと、触れていない話題の全体像をまとめて作らないことが書いてある

## 目次の置き場所は、全体像を書く LLM が人に聞かずに決め、承認の対象にしない

状態: 実装済み

### 問題

新しいページを目次のどこに置くかは、全体像の単位ほど重い判断ではない。人を待たずに進めるのが理想で、違和感があれば、人が見たときに直せる。一覧を製品の地図にするなら、使う順や工程の順という順番そのものが情報になる。1段は階層の特別な場合なので、小さい製品は1段のままでよい。

### 決めたこと

新しい全体像を目次のどこに置くかと、目次の群を分けるか新しく作るかは、全体像を書く LLM が決めて目次を直し、人に聞かない。目次は承認の対象にしない。目次の群を分けるのは、その群が大きくなってからにする。同じ階層の中は、読む人に意味のある順（使う順や工程の順）に並べる。

### 確認すること

- C-core-ovflow-5 （読んで確認）kotowari の skill に、新しい全体像の目次の中の置き場所と、目次の群を分けるか新しく作るかを全体像を書く LLM が決めて人に聞かないこと、目次を承認の対象にしないこと、群を分けるのはその群が大きくなってからにすること、同じ階層の中を使う順や工程の順に並べることが書いてある

## 壁打ちの承認の手順に全体像を作り直す段を置き、全体像は承認の対象にしない

状態: 提案

### 問題

壁打ちの判断は1問ずつなら分かるが、結局どうなるのかが分からなくなることが多い。全体像は、承認の時と後から読み返す時の両方に使う1つの成果物で、壁打ちの承認のたびに関わる全体像を作るか直す。壁打ちの途中で毎回作ると、ラウンドごとに費用がかかる。承認の流れに組み込むと承認が重くなり、重さは以前作っていた要約（brief）が定着しなかった理由の1つだった。

cycle と実装は全体像の元データを直さない（[cycle と実装は、全体像の元データを直さない](#cycle-と実装は全体像の元データを直さない)）ので、壁打ちにこの段が無いと、誰も全体像を作らず直さず、古い節が残り続ける。

### 決めたこと

設定に "overview" のキーがあるプロジェクトでだけ、壁打ちの承認の手順に、全体像を作り直す段を置く。段では、次の順に行う。

1. この壁打ちで変えた決定の文書から、元データの一覧で関わる全体像を決める。どの全体像にも属さない話題の決定の文書なら、既にある全体像に足すか新しく作るかの案を LLM が出し、人が決める（[全体像の単位は、使う人が1つの機能として名前で呼べるものにし、人が決める](#全体像の単位は使う人が1つの機能として名前で呼べるものにし人が決める)）。
2. 関わる全体像の元データを作るか直し、新しいページを足したら目次も直す（[目次の置き場所は、全体像を書く LLM が人に聞かずに決め、承認の対象にしない](#目次の置き場所は全体像を書く-llm-が人に聞かずに決め承認の対象にしない)）。全体像の元データへの guide_stale の注意は、ここで直す。
3. "kotowari overview build" を走らせ、誤りを直す。
4. "kotowari overview serve" の URL を、参考として示す。

全体像は承認の対象にせず、見るかどうかは人に委ねる。承認の材料（決定の文書の差分）と読む順番は変えない。既にある話題の全体像は、壁打ちがその話題の決定の文書に触れたときに初めて作る。

### 見送った案

- 承認の場面で、最初に全体像を開かせる。承認が重くなる。
- 全体像も承認の対象にする。承認が重くなる。
- 壁打ちの途中で、ラウンドごとに全体像を作る。ラウンドごとに費用がかかる。

### 確認すること

- C-core-ovflow-7 （読んで確認）壁打ちの skill の承認の手順に、設定に "overview" のキーがあるプロジェクトでだけ、変えた決定の文書から関わる全体像を決め、元データと目次を作るか直し、"kotowari overview build" で誤りを直し、"kotowari overview serve" の URL を参考として示す段がある
- C-core-ovflow-8 （読んで確認）同じ段に、どの全体像にも属さない話題の決定の文書なら単位の案を LLM が出して人が決めること、全体像の元データへの guide_stale をこの段で直すこと、既にある話題の全体像は壁打ちがその話題に触れたときに初めて作ることが書いてある
- C-core-ovflow-9 （読んで確認）壁打ちの skill に、全体像は承認の対象にせず、承認の材料と読む順番を変えないと書いてある

## cycle と実装は、全体像の元データを直さない

状態: 実装済み

### 問題

全体像の元データの節が古くなっても、読む人はページのマーカーで古い部分を見分けられる。cycle の作業は増やしたくない。直すのは、次にその話題に触れた壁打ちの承認の段である（[壁打ちの承認の手順に全体像を作り直す段を置き、全体像は承認の対象にしない](#壁打ちの承認の手順に全体像を作り直す段を置き全体像は承認の対象にしない)）。

### 決めたこと

cycle と実装の工程は、全体像の元データを直さない。全体像の元データへの guide_stale の注意を消すためにも直さない。

### 確認すること

- C-core-ovflow-6 （読んで確認）cycle の skill に、全体像の元データを実行の中で変えず、その指摘と guide_stale を委ねないと書いてあり、cycle と実装の skill に全体像の元データを直す手順が無い
