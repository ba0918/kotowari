# 穴を埋めながら進む工程

[English](workflow.md) | 日本語

壁打ちから実装、マージまでの進め方のうち、仕様に書いていないことが見つかったときに、誰がどこで決めるかを決める。仕様を先に完成させようとせず、穴は出る前提で進める。ここで決めたことは、工程の skill の文に書く。決定の文書の形は[決定の文書](decision-documents.ja.md)、テストとの対応は[確認することとテスト](confirmations.ja.md)で決める。

kotowari を使っている9つのリポジトリの作業の記録から、仕様の穴が出た事例65件を読んで分けた。人の方針や前提と、agent の推奨や決めた仕様がずれて人が訂正したものが22件、実装やレビューの途中で出た未定の細部が16件、使って初めて分かった見え方・使い勝手が15件、仕様の文どうしの食い違い・古さ・出典の不備が10件、その他が2件だった。事例は調査した側の選抜で、分類は1人の読みである。下の決定は、この種類ごとの手当てになっている。

## 実装の途中で見つかった細部は、実装する側が決める

状態: 実装済み

### 問題

実装やレビューの途中で、仕様に書いていない細部が見つかる。これまでは人に聞いて、仕様に書いてから進めていた。調べた16件のうち12件は、人に聞いた答えが推奨の採用だった。止めて聞いても、答えはほぼ変わらない。

決めたことどうしがぶつかる、または2通りに読める、と実装の途中で分かることもある。読み方の確認を人に戻した事例も、答えは推奨の採用だった。

### 決めたこと

実装やレビューの途中で見つかった、決定の文書に書いていない細部は、実装する側が根拠を付けて決める。人には聞かない。決めたことどうしがぶつかる、または2通りに読めるときも、実装する側が根拠を付けて読みを決める。

人に戻すのは、人が決めた意図そのものがぶつかるとき（どちらを取っても、人が決めたことの片方を捨てることになるとき）だけにする。そのときは、関係する話題の文書の「未決」の節に書く。意図がぶつかっているかは、決定の文書に書いてある2つの文が両立しないことで見分けられる。

実装する側が決めた細部と読みは、何を・なぜ・証拠を、コミットの本文と、プルリクエストの本文の判断の一覧に書く。決定の文書には書かない。決定の文書を、人が決めたことだけに保つためである。

実装のループの中で仕様の側を直す段（整合の段）も同じにする。実行ごとの記録は書かず、直した理由はプルリクエストの本文に書く。

### 見送った案

- 以前の決定: 細部も人に聞いて、仕様に書いてから進める。仕様が黙っていることを、実装する側が決めてはいけない。答えがほぼ推奨の採用で、人を止める意味が薄いので、やめた。
- 以前の決定: 整合の段は、実行ごとに新しい判断の記録を書く。足していく記録を持たなくなるので、やめた。
- 利用者から見える振る舞いに関わる細部だけは人に聞く。「利用者から見えるか」は程度の問題で、文書を見ても線が引けず、聞きすぎるか聞かなすぎるかに振れうる。
- 実装する側が決めた細部を、決定の文書の関係する決定の下に書く。人が決めたことと区別がつかなくなり、コードが変わるたびに書き直す対象が増える。

### 確認すること

- C-core-flow-1 （読んで確認）実装の skill に、書いていない細部と読みは実装する側が根拠を付けて決め、人に聞かないと書いてある
- C-core-flow-2 （読んで確認）実装の skill に、人が決めた意図そのものがぶつかるときだけ、話題の文書の「未決」に書いて人に戻すと書いてある
- C-core-flow-3 （読んで確認）実装とマージの skill に、決めた細部の何を・なぜ・証拠を、コミットの本文とプルリクエストの本文に書くと書いてある
- C-core-flow-4 （読んで確認）整合の段の手順に、実行ごとの記録を書かず、直した理由をプルリクエストの本文に書くと書いてある

## 壁打ちは、推奨を出す前に、利用者共通の方針の文書を読む

状態: 実装済み

### 問題

人の方針と agent の推奨がずれて訂正された22件のうち10件ほどは、案件をまたぐ利用者の決まった方針に、agent の推奨が反したものだった。同じ形の訂正が、別のリポジトリで繰り返されていた。agent のメモリはプロジェクトごとで、ほかのリポジトリの壁打ちからは読めない。

### 決めたこと

利用者共通の方針の文書を1つ持つ。置き場は、利用者の設定の置き場の下の `kotowari/principles.md` とする（`XDG_CONFIG_HOME` があればそれに従う）。壁打ちは、推奨を出す前にこれを読む。推奨が方針に反していて訂正されたら、利用者が訂正した内容を、その場でこの文書に1行足す。

文書が無いとき、読めないときは、読めなかったと壁打ちの最初に伝えて、読まずに進む。

### 見送った案

- プロジェクトごとに方針の文書を持つ。案件をまたぐ方針を、リポジトリごとに書き直すことになる。
- agent の指示のファイルや、agent のメモリの置き場に置く。agent の種類ごとに置き場が違い、プロジェクトをまたいで読めない。
- 持たず、訂正はその場で直すだけにする。同じ訂正が繰り返される。

### 確認すること

- C-core-flow-5 （読んで確認）壁打ちの skill に、推奨を出す前に利用者共通の方針の文書を読み、訂正されたら1行足すと書いてある
- C-core-flow-6 （読んで確認）壁打ちの skill に、方針の文書が読めないときは、読めなかったと最初に伝えて進むと書いてある

## 壁打ちは、最初に困っている場面を1つ組み、承認の前にその場面がどうなるかを見せる

状態: 実装済み

### 問題

求めた場面を解決しないものが、記録には範囲が正しく書かれたまま承認を通って作られたことがあった。1問ずつは判断できても、合わせて目的に届くかは見えなかった。

また、場面を組むために人に聞いたところ、利用者がそのリポジトリを覚えておらず答えられなかったことがあった。答えは、依頼を出した側の記録に書いてあった。

### 決めたこと

壁打ちの最初に、人が困っている場面を1つ、具体的に組む。組む前に、依頼の出どころ（依頼を出した人やリポジトリの記録、issue、過去のやりとり）を調べる。場面と、決めることの答えが出どころに書いてあれば、利用者に聞かずにそれを根拠にする。書いていないときだけ、利用者の言葉から場面を組み、合っているかを確認する。

承認の前に、決めたものでその場面がどうなるかを見せる。解決していなければ、承認に進まない。実物が無くて解決したかを判断できないときは、いつ・何を見て判断するかを決めて、未決として残す。

承認で利用者が読むのは、決定の文書の差分である。

### 見送った案

- 承認の前に、決めたことの全体を1枚で見せるだけにする（場面は組まない）。全体が見えても、目的の場面に届くかは分からない。
- 目的のずれは、作ったあとに人が気づいて直す。作る費用を払ったあとになる。
- 以前の決定: 承認で利用者が読むのは、判断の記録の差分（1行が1つの決定）で、IR の差分は読ませない。記録を持たなくなり、決定の文書そのものが読める文章になるので、それを読むことにした。

### 確認すること

- C-core-flow-7 （読んで確認）壁打ちの skill に、最初に困っている場面を1つ組み、組む前に依頼の出どころを調べると書いてある
- C-core-flow-8 （読んで確認）壁打ちの skill に、承認の前に、決めたものでその場面がどうなるかを見せ、解決していなければ承認に進まないと書いてある
- C-core-flow-9 （読んで確認）壁打ちの skill に、承認で見せるのは決定の文書の差分だと書いてある

## 見える振る舞いを変える依頼は、壁打ちの中で見本を見せて決める

状態: 実装済み

### 問題

見え方・使い勝手の事例15件は、ほぼすべて、人がマージのあと・本番・実機で見つけていた。文で聞いて決めたものは、触って初めて違うと分かる。見本で合意してから進めた回は、利用者の評価が高かった。

### 決めたこと

利用者から見える振る舞いを変える依頼は、壁打ちの中で、文で聞かずに見本を作って見せ、反応を決定にする。見本は、動く試作、モック、出力のサンプルのどれかにする。何を作るか（作らないことを含む）は、壁打ちを進める agent が理由を付けてその場で決め、人には聞かない。マージの前に人が触って確認する段は足さない。

動く試作は、決めるための使い捨てとし、製品のコードの土台にしない。実装する側に渡して、見比べる相手にする。試作で決めた動きのうち、機械で確かめられるものは、確認することの行にしてテストにする。

### 見送った案

- マージの前に、動くものを人が触ってからマージする。人を待つ依頼が増える。
- マージのあとに使って見つけ、小さい依頼で直す。これまでのやり方で、見つかるのが遅い。
- 何を作るかを、人が毎回選ぶ。聞くことが増える。
- 試作を土台にして、そのまま育てて製品にする。テストを先に書く流れとレビューを通らないコードが製品に入る。

### 確認すること

- C-core-flow-10 （読んで確認）壁打ちの skill に、見える振る舞いを変える依頼では見本を作って見せ、何を作るかは agent が理由を付けて決めると書いてある
- C-core-flow-11 （読んで確認）壁打ちと実装の skill に、試作は使い捨てで製品の土台にせず、実装する側の見比べる相手にすると書いてある

## 壁打ちのラウンドに入れる問いは3種類に絞り、ほかは壁打ちを進める agent が決める

状態: 実装済み

### 問題

壁打ちのラウンドに何を入れてよいかの基準が無く、前提が決まった問いは、推奨を付けてすべて人に聞いていた。人の役を LLM に務めさせて3つの依頼を通した試しでは、壁打ちの29問のうち11問に、人が答えを持っていなかった。休憩の打刻が片方だけの日の扱い、順序がおかしい打刻の扱い、警告があるときの終了コードがそうで、人の答えは「分からない。任せる」だった。人は、答えを持たない問いを読んで、任せると返す手間を払う。

11問のうち4問は、どの選択肢でも合意した振る舞いが変わらず、後から安く変えられるものだった。残りの7問は、人が触れておらず、見本にも記録にも手がかりが無い、端の振る舞いだった。自明でも、調べれば分かることでもないので、読めば分かることを聞かない、という基準だけでは残る。

一方、聞かずに決める範囲を広げると、人が気にしている所を黙って決める恐れが上がる。同じ試しで、残業時間の列を足す依頼に、週40時間を超えた分を残業に入れるかという問いがあり、これを黙って決めると、給与の計算に関わる読みが人に届かない。

### 決めたこと

壁打ちのラウンドに入れる問いは、次の3種類のどれかに当たるものだけにする。

- 読んでも試しても決まらない、製品の方向・好み・トレードオフ
- 決めたあとで変えると、作ったものや貯まったデータを作り直すことになるもの
- 依頼の文、見本、記録に、人がそこを気にしている手がかりがあるもの

読めば分かる事実は読んで確かめ、試せば分かることは小さく試し、その結果を問いの背景に書く。

どれにも当たらない問いは、壁打ちを進める agent が根拠を付けて決める（[壁打ちで聞かずに決めたことは、承認のときに一覧で見せ、仕様のコミットの本文に書いて実装する側へ運ぶ](#壁打ちで聞かずに決めたことは承認のときに一覧で見せ仕様のコミットの本文に書いて実装する側へ運ぶ)）。どれかに当たるか判断がつかない問いは聞く。

この基準を当てるのは壁打ちである。kotowari-iterate が回す小さい作業と、既存のコードの取り込みには当てない。

### 見送った案

- 前提が決まった問いを、推奨を付けてすべてラウンドに入れる。人が答えを持たない問いも並び、人は任せると返す手間を払う。
- 端の振る舞いは、壁打ちでは触れず、実装の途中で実装する側が決める。人がその決め方を見るのが、マージのあとになる。
- 聞く側に残す線を引かず、判断がつかない問いも決める。承認で見せる一覧が長くなり、そこで人が拾えなければ、外れたまま作られる。
- 利用者から見える振る舞いは、すべて聞く。試しで人が答えを持たなかった端の問いが、ほぼすべて聞く側に残る。

### 確認すること

- C-core-flow-15 （読んで確認）壁打ちの skill に、ラウンドに入れる問いは、読んでも試しても決まらない製品の方向・好み・トレードオフ、決めたあとで変えると作ったものや貯まったデータを作り直すことになるもの、依頼の文・見本・記録に人が気にしている手がかりがあるもの、の3種類だけだと書いてある
- C-core-flow-16 （読んで確認）壁打ちの skill に、読めば分かる事実は読み、試せば分かることは小さく試して、その結果を問いの背景に書き、3種類のどれにも当たらない問いは根拠を付けて決め、判断がつかない問いは聞くと書いてある
- C-core-flow-19 （読んで確認）壁打ちの skill に、この基準は壁打ちに当て、kotowari-iterate が回す小さい作業と既存のコードの取り込みには当てないと書いてある

## 壁打ちで聞かずに決めたことは、承認のときに一覧で見せ、仕様のコミットの本文に書いて実装する側へ運ぶ

状態: 実装済み

### 問題

壁打ちを進める agent が聞かずに決めたことを、人に見せないまま進めると、人が気にしていた所を外しても、マージのあとまで分からない。決定の文書には人が決めたことだけを書くので、聞かずに決めたことの置き場が無い。会話の中にだけ残すと、壁打ちのあと cycle を別のセッションで始めたときに失われ、承認で人が見た決め方と、実装する側があとで決める中身が違うことがありうる。

### 決めたこと

承認のとき、利用者は、決定の文書の差分と一緒に、壁打ちで聞かずに決めたことの一覧を読む。一覧に入れるのは、[ラウンドに入れる3種類](#壁打ちのラウンドに入れる問いは3種類に絞りほかは壁打ちを進める-agent-が決める)のどれにも当たらず、壁打ちを進める agent が根拠を付けて決めた問いで、何を・なぜの1行ずつで書く。聞かずに決めたことが無いときは、無いと伝える。人が違うと言ったものは、人が決めたこととして決定の文書に書く。

残りは決定の文書に書かず、決定の文書をコミットするコミットの本文に、同じ何を・なぜの形で書く。人が自分でコミットしたときは、壁打ちが、ファイルの変更を持たないコミットを同じ枝に足し、その本文に書く。一覧は承認ごとに作る。一覧を変えた者は、変えたコミットの本文に、今の一覧を丸ごと書き直し、枝でいちばん新しい一覧が一覧になり、前のものは丸ごと置き換わる。

cycle は、[壁打ちから受け取るもの](unattended-merge.ja.md#cycle-は決定の文書の置き場と今回作る決定の一覧とマージ先を受け取る)に加えて、聞かずに決めたことの一覧を受け取り、実装する側へ渡す。実装する側はそれに従う。実装の途中で、違う決め方が要ると分かったら、実装する側が決め直し、[実装の途中で見つかった細部](#実装の途中で見つかった細部は実装する側が決める)と同じく、何を・なぜ・証拠をコミットの本文とプルリクエストの本文に書き、そのコミットの本文に、更新した一覧を丸ごと書き直す。

### 見送った案

- 決定の文書に、agent が決めたことを書く節を足す。人が決めたことだけを書く決まりを覆し、check が読む形とガイドを変えることになる。コードが変わるたびに書き直す対象も増える。
- 承認で見せるだけにして、実装する側へは運ばない。承認で人が見た決め方と、作られるものが違うことがありうる。

### 確認すること

- C-core-flow-17 （読んで確認）壁打ちの skill に、承認のとき、決定の文書の差分と一緒に、聞かずに決めたことを何を・なぜの1行ずつで見せ、無いときは無いと伝え、人が違うと言ったものは決定として書き、残りは決定の文書をコミットするコミットの本文に書き、人が自分でコミットしたときはファイルの変更を持たないコミットを同じ枝に足してその本文に書くと書いてある
- C-core-flow-18 （読んで確認）壁打ちの skill に、cycle への受け渡しに聞かずに決めたことの一覧を入れると書いてあり、cycle の skill に、それを受け取って実装する側へ渡すと書いてあり、実装の skill に、それに従い、違う決め方が要ると分かったら決め直して、何を・なぜ・証拠をコミットの本文とプルリクエストの本文に書くと書いてある

## 確認することの行が無い振る舞いのテストには、実装する側が宣言のマーカーを付け、人に聞かない

状態: 実装済み

### 問題

実装する側が決めた細部と、壁打ちで聞かずに決めたことは、決定の文書に書かない。その振る舞いのテストには指す行が無く、実装の skill にも、マーカーの説明にも、どうするかが書かれていなかった。

人の役を LLM に務めさせた試しで、作業役は、確認することの行に結び付かないテストは置けないと読み、実装の途中で、3つの振る舞いを決定に足すかを人に聞いた。人の答えは推奨の採用だった。承認のあとは人を待たない、という進め方が崩れた。

### 決めたこと

実装する側は、決定の文書に確認することの行が無い振る舞いのテストに、行を持たないテストの宣言（[行を持たないテストは `@kotowari[detail]` と宣言でき、宣言したテストには test_without_id を出さない](coverage.ja.md#行を持たないテストは-kotowaridetail-と宣言でき宣言したテストには-test_without_id-を出さない)）を付ける。そのために人に聞かず、決定の文書に決定も確認することの行も足さず、テストが確かめていない行の ID も書かない。テストが確かめる行があるときは、その行の ID を書く。

### 確認すること

- C-core-flow-20 （読んで確認）実装の skill に、確認することの行が無い振る舞いのテストには宣言のマーカーを付け、そのために人に聞かず、決定の文書に決定も行も足さず、テストが確かめていない行の ID を書かないと書いてある
- C-core-flow-21 （読んで確認）kotowari の skill のマーカーの説明と指摘の表に、test_without_id の直し方として、テストが確かめる行があればその ID を書き、無ければ宣言のマーカーを書くと書いてある

## 既存のコードを取り込むときは、人が追認した振る舞いを「実装済み」で書く

状態: 実装済み

### 問題

仕様の無い既存のコードを kotowari に取り込むとき、これまでは1回の取り込みで判断の記録を1つ書き、テストの無い振る舞いは問題の記録へ送っていた。どちらも持たなくなるので、行き先が要る。旧資料の判断の記録の決定は、取り込みで人に追認を求めないので、追認済みと数えなければ、人が追認していない振る舞いを書かないという決まりと食い違う。check の「テストが無い」の指摘でテストが入った6件（[check は、確認することの行ごとに、それを指すテストがあるかを数える](confirmations.ja.md#check-は確認することの行ごとにそれを指すテストがあるかを数える)の調べ）のうち4件は、あとから仕様を付けた既存のコードだった。

### 決めたこと

取り込みでは、人が追認した振る舞いを、状態が「実装済み」の決定として話題の文書に書く。テストの無い確認することの行は、check の誤りとして出て、それがテストを書く作業の一覧になる。取り込みごとの記録は書かない。テストが揃うまで check は誤りを出したままになる。テストが無いことの誤りは、コミットでは止めず push で止める、今のやり方（`--allow-test-findings`）を残す。

コードがそうしているだけで、人が追認していない振る舞いは書かない。旧資料の判断の記録にあって実装と一致する決定は、人が以前に決めたものなので、追認済みとして数える（[旧資料の判断の記録にあって実装と一致する決定は、追認済みと数え、記録にある理由を「問題」に書く](adoption.ja.md#旧資料の判断の記録にあって実装と一致する決定は追認済みと数え記録にある理由を問題に書く)）。なぜそうなっているかが分からなければ、問題の節に「理由は残っていない」と書く。理由を作らない。

### 見送った案

- テストの無い振る舞いを「提案」の状態で書く。「提案」が、まだ作っていないものと、作ってあるがテストの無いものの両方を指すことになる。
- 以前の決定: 1回の取り込みで判断の記録を1つ書き、テストの無い振る舞いは問題の記録へ送る。記録も問題の記録も持たなくなるので、やめた。

### 確認すること

- C-core-flow-12 （読んで確認）取り込みの skill に、人が追認した振る舞いを「実装済み」の決定として書き、取り込みごとの記録は書かないと書いてある
- C-core-flow-13 （読んで確認）取り込みの skill に、人が追認していない振る舞いは書かず、理由が分からなければそう書いて、理由を作らないと書いてある
- C-core-flow-14 （読んで確認）取り込みの skill に、旧資料の判断の記録にあって実装と一致する決定は追認済みとして数えると書いてある
