# 整合のフェーズ

[English](consistency-phase.md) | 日本語

実装した、または変えたコードと決定の文書の食い違いと、決定どうしのぶつかりを、cycle の中の専用の段（整合のフェーズ、英語で consistency phase）で LLM が見つけて片付けることを扱う。人は最後の手段としてだけ関わる。決定の文書に書いていない細部と読みは実装する側が根拠を付けて決めること、整合のフェーズが実行ごとの記録を書かず、直した理由をプルリクエストの本文に書くことは、工程の話題の[実装の途中で見つかった細部は、実装する側が決める](workflow.ja.md#実装の途中で見つかった細部は実装する側が決める)で決める。フェーズが人の確認を待つ指摘を残したときのマージの止まり方は、[人が確認するときは、マージを頼まずにプルリクエストを開いたままにし、場所と止まった原因だけを見せる](unattended-merge.ja.md#人が確認するときはマージを頼まずにプルリクエストを開いたままにし場所と止まった原因だけを見せる)で決める。

## コードと仕様の整合は、品質のレビューと別の段の整合のフェーズが見る

状態: 実装済み

### 問題

cycle で実装が先に進み、仕様に無い選択が入るのを捕まえたかった。以前の仕組みは、変更したファイルごとに実装役とレビュー役に記録を書かせ、機械は記録の漏れと古さだけを見るものだった。ある変更で、実装役が面のファイルを用語集より狭く実装し、記録に「既存の仕様の範囲」と書いたとき、その仕組みは通した。捕まえたのは cycle の適合のレビュー（LLM）だった。過去の記録にもその仕組みが起点の発見は無く、記録のためのコミットが136個あった。

守るべきは手順ではなく仕様である。記録が機械で保証するのは、変更が記録で覆われていることと、記録のあとに変わっていないこと（手順）だけで、記録の申告が仕様に合っているかは保証しない。整合は記録に対してではなく、コードに対して確かめる。また、適合のレビューは条件つきで立つだけで、整合を見ることが専任の仕事になっていなかった。kotowari を重くしすぎないことも前提である。skill を増やすと、入口の案内や skill どうしの受け渡しの決まりまで増える。

実装役や修正役がフェーズを走らせると、自分の実装を自分で追認することになる。別の文脈に限る理由は、記録に残っていない。

### 決めたこと

コードと仕様の整合は、cycle の中の、品質のレビューとは別の段である整合のフェーズが見る。cycle の工程は、実装、整合のフェーズ、品質のレビューの順である。新しい skill は作らず、フェーズ役に渡す指示は kotowari-cycle の reference に1つ置く。

フェーズは、実装役と別の文脈の LLM が走らせ、実装役にも修正役にも任せない。実装役と別系統のモデルで走らせるのが望ましいが、必須にしない。

### 見送った案

- 整合をレビューの観点の1つにする。品質の指摘と同じ席で読まれ、整合が薄まる。

### 確認すること

- C-core-consist-1 （読んで確認）kotowari-cycle の skill に、工程が実装、整合のフェーズ、品質のレビューの順だと書いてある
- C-core-consist-2 （読んで確認）フェーズ役に渡す指示が kotowari-cycle の reference に1つあり、整合のフェーズのための skill が無い
- C-core-consist-22 （読んで確認）kotowari-cycle の skill に、整合のフェーズは実装役と別の文脈の委譲先が走らせ、実装役にも修正役にも任せず、別のモデルは望ましいが必須ではないと書いてある

## レビューは品質の観点だけで立てる

状態: 実装済み

### 問題

### 決めたこと

kotowari-review のレビュー役は、品質の観点だけで立てる。コードと仕様の整合を見る適合の観点の席も、それを足す決まりも置かない。文書が仕様と矛盾していないかは、品質の観点の中で見る。

### 確認すること

## 整合のフェーズは、実装のあとと、品質のレビューの直しが収束したあとに走らせる

状態: 実装済み

### 問題

捕まえ損ねは、走らせる回数ではなく、読む範囲と分け方で起きる。直しのたびに走らせると、レビューの往復ごとに席が増える。直し全体の差分を読む回は、再開しても同じ範囲を再現できる必要がある。足す状態はできるだけ少なくしたい。

### 決めたこと

整合のフェーズは、実装のあとに1回と、品質のレビューの直しが収束したあとに、直し全体の差分に対して1回走らせる。フェーズ自身の直しのあとは、新しい指摘が出なくなるまで走らせる。

直し全体の差分の起点として、cycle の指摘のファイルに、最初の品質のレビューが見た先頭のコミットを1つだけ持つ。フェーズのために持つ状態は、これだけである。

### 見送った案

- 品質のレビューの直しのたびに走らせる。レビューの往復ごとに席が増える。

### 確認すること

- C-core-consist-4 （読んで確認）kotowari-cycle の skill に、整合のフェーズは実装のあとに1回と、品質のレビューの直しが収束したあとに直し全体の差分に対して1回走り、フェーズ自身の直しのあとは新しい指摘が出なくなるまで走ると書いてある
- C-core-consist-5 （読んで確認）kotowari-cycle の skill に、指摘のファイルが持つフェーズの状態は、最初の品質のレビューが見た先頭のコミットの1つだけだと書いてある

## 走らせるかは段取りを持つ役が決め、利用者から見える振る舞いが動かない差分だけ理由を残して省く

状態: 実装済み

### 問題

走らせるたびに、それなりの費用がかかる。走らせるかを毎回決めてよいが、それを決められるのは段取りを持つ役だけである。隙間の生まれやすさは、差分の行数ではなく、振る舞いが動くかで決まる。仕組みを決め直すきっかけになった変更は、小さな差分で振る舞いを足していた。このリポジトリでは skill の文言が、利用者から見える振る舞いそのものである。急ぎの直接の修正ほど、点検が抜けやすい。

### 決めたこと

走らせるかは cycle（オーケストレータ）が決める。メインセッションでの直接の修正では、メインセッションのエージェントが同じ目安で決める。kotowari-iterate は cycle の流れに乗るので、フェーズを通す。

省いてよいのは、差分が利用者から見える振る舞いを足しも変えもしないとき（文書だけの差分（ガイドはその例）、テストだけの差分、振る舞いを変えないリファクタリング）だけにする。skill の文章は文書ではなく振る舞いとして扱い、省かない。迷ったら走らせる。省いたときは、最後の報告に1行の理由を書く。

### 見送った案

- 1件の指摘の直しを、省いてよいものに入れる。指摘の直しも振る舞いを変えうる。

### 確認すること

- C-core-consist-6 （読んで確認）kotowari-cycle の skill に、走らせるかは cycle が決め、省いてよいのは利用者から見える振る舞いを足しも変えもしない差分だけで、skill の文章は省かず、迷ったら走らせ、省いたら最後の報告に1行の理由を書くと書いてある
- C-core-consist-7 （読んで確認）kotowari-iterate の skill に cycle の流れでフェーズを通すと書いてあり、kotowari-using-workflow の skill に、直接の修正ではメインセッションが同じ目安で走らせるかを決めると書いてある

## 直接の修正で走らせる整合のフェーズも、決定の文書を相手にする

状態: 実装済み

### 問題

メインセッションの直接の修正でも、整合のフェーズを cycle と同じ目安で走らせる（[走らせるかは段取りを持つ役が決め、利用者から見える振る舞いが動かない差分だけ理由を残して省く](#走らせるかは段取りを持つ役が決め利用者から見える振る舞いが動かない差分だけ理由を残して省く)）。適合のレビューを外したので、仕様の無い話題と仕様の突き合わせも、フェーズのほかに残る所が無い。

### 決めたこと

メインセッションの直接の修正で走らせる整合のフェーズは、決定の文書の置き場を相手にする。範囲の決定は、差分が文を触った決定と、それがリンクする決定である。仕様の無い話題では、承認済みの仕様の文書、無ければ依頼の文を相手にする。

### 確認すること

- C-core-consist-8 （読んで確認）kotowari-using-workflow の skill の直接の修正での整合のフェーズの節に、相手は決定の文書の置き場で、仕様の無い話題では承認済みの仕様の文書か依頼の文だと書いてある

## 整合のフェーズが読むのは、差分のコードとその周辺と、範囲の決定である

状態: 実装済み

### 問題

仕組みを決め直すきっかけになった件は、差分の中のコードと用語集を突き合わせれば捕まる。全体を毎回読むのは重い。一方で、食い違いが既存の関数や値の使い回しで起きると、呼ぶ・呼ばれるの関係だけでは値の作り元を読まない。その件も、面のファイルの集まりは別の段で作られていた。適合のレビューを外したので、skill の文章や仕様の無い話題と仕様の突き合わせも、どこかに残す必要がある。

### 決めたこと

整合のフェーズが読むのは、記録ではなくコードそのものである。コードには、製品として配る文章を含める。skill の文章はその例である。

範囲は、次のとおりにする。

- コード: 差分で変わったコードと、それが呼ぶ・呼ばれる直接の周辺、差分が使う値の作り元を1段
- 決定: 差分が実装した決定（cycle が受け取った決定）と、差分が文を触った決定。それらがリンクする決定と、使う語

仕様の無い小さい作業では、依頼の文を相手にする。コード全体と決定の文書全体の突き合わせは、別に頼まれたときだけ行う。

- C-core-consist-9 （読んで確認）整合のフェーズの reference に、読むのは記録ではなくコードそのもので、コードには製品として配る文章（skill の文章はその例）を含むと書いてある
- C-core-consist-10 （読んで確認）整合のフェーズの reference に、読むコードは差分で変わったコードと直接の呼ぶ・呼ばれる周辺と、差分が使う値の作り元を1段だと書いてある
- C-core-consist-11 （読んで確認）整合のフェーズの reference に、読む決定は差分が実装した決定（cycle が受け取った決定）と文を触った決定と、それらがリンクする決定と使う語で、仕様の無い小さい作業では依頼の文を相手にすると書いてある
- C-core-consist-12 （読んで確認）整合のフェーズの reference に、コード全体と決定の文書全体の突き合わせは別に頼まれたときだけ行うと書いてある

## 整合のフェーズは、決定と違う振る舞い、理由の書いていない細部、決定どうしのぶつかりを見つける

状態: 実装済み

### 問題

捕まえたいのは、仕様と違うことをしているものと、仕様のほうの隙間と矛盾である。仕組みを決め直すきっかけになった件（面のファイルを用語集より狭く実装した）がその実例で、実装して初めて見える隙間は多い。

### 決めたこと

整合のフェーズは、次の3つを見つける。

- 決定と違う振る舞い
- 決定の文書に書いていない細部で、実装する側が決めたもの。決定の文書には書かず、どの決定とも食い違わないかと、理由が書いてあるかを見る
- 範囲の決定のうち、両方は成り立たない2つの文

## 見つけたものは、決定の文書とコードが整合した状態に片付け、書いていない細部をコードから戻さない

状態: 実装済み

### 問題

片付けの条件は多岐にわたる。一律にコードを仕様に合わせると、正しい細部まで捨てる。仕様に穴があるときにコードを仕様の範囲に戻すと、正しいものを捨てて欠けた仕様に合わせることになる。利用者の望みは、整合した良い状態に着地することである。自分の実装の追認と分けるのは、根拠と実測である。

### 決めたこと

整合のフェーズは、見つけたものを自分で直し、必ず決定の文書とコードが整合した状態に片付ける。観測で決まるものは、実測や再現で確かめて決める。

決定の文書に書いていない細部は、どの決定とも食い違わなければコードに残し、何を決めたか・なぜか・証拠を書く。仕様に書いていないことを理由に、コードを戻さない。

### 見送った案

- 既定でコードを仕様に合わせ、仕様を足すのは承認済みの記録に根拠があるときだけにする。狭すぎる。
- 根拠から決められない意味の決めごとが出たときは、コードを仕様の書いてある範囲に戻し、足した振る舞いを外して、人の判断を待つ。利用者が、仕様に穴があるのにコードを戻すのはおかしいと指摘した。

### 確認すること

- C-core-consist-14 （読んで確認）整合のフェーズの reference に、見つけたものは必ず決定の文書とコードが整合した状態に片付け、観測で決まるものは実測か再現で決め、どの決定とも食い違わない細部はコードに残して何を・なぜ・証拠を書くと書いてある

## 決定と食い違うときは、決定の理由を制約として読み、コードを決定に合わせる

状態: 実装済み

### 問題

片付けの拠り所は根拠と実測である。決定と食い違う選択は、その食い違いに十分に配慮したうえで選ぶ必要がある。

テストが通ることを根拠に決定の文を直せると、実装に合わせて書いたテストが通るだけで、人が決めた文が実装の側へ書き換わる。テストを根拠から外す理由は、記録に残っていない。

### 決めたこと

コードが決定と食い違うときは、その決定の「問題」と「見送った案」を制約として読み、コードを決定に合わせる。決定の文を直すのは、再現で文字どおりには成り立たないと示せて、人が決めた向きが変わらないときだけで、事実の書き直しとして直す（[事実が変わったら書き直し、決定を覆すときは古い決定を見送った案に書く](decision-documents.ja.md#事実が変わったら書き直し決定を覆すときは古い決定を見送った案に書く)）。テストが通ることは、決定の文を直す根拠にしない。

### 確認すること

- C-core-consist-15 （読んで確認）整合のフェーズの reference に、食い違いは決定の問題と見送った案を制約として読んでコードを決定に合わせ、決定の文を直すのは再現で文字どおりには成り立たないと示せて向きが変わらないときだけだと書いてある
- C-core-consist-21 （読んで確認）整合のフェーズの reference に、テストが通ることは決定の文を直す根拠にならないと書いてある

## 人が決めた意図そのものがぶつかるときだけ、既定で進めて「未決」に書き、人の判断を待つ指摘として最後の報告に回す

状態: 実装済み

### 問題

人の判断を待つ指摘は、ループを止めずに最後の報告へ回す扱いである。止まらずに既定で進め、最後に覆す一言と一緒に報告する形と合う。利用者は、人の判断を極力減らすべきだとしている。

### 決めたこと

範囲の決定のうち、両方は成り立たない2つの文があり、どちらを取っても人が決めたことの片方を捨てることになるときだけ、人が決める。整合のフェーズは、両方の決定をできるだけ残す既定を取ってコードを合わせ、話題の文書の「未決」の節に、ぶつかる2つの文と取った既定と、決めるのは人であることを書く。

その指摘は、人の判断を待つもの（human_judgment）として開いたまま最後の報告に回す。指摘には、既定とそれを覆す一言、試した根拠と実測、それで決められなかった理由を書く。

フェーズが人に戻して止まる道は無い。人の判断は最後の手段で、極力減らす。

## フェーズの指摘は cycle の指摘のファイルに載せ、cycle の既存の止め方に従う

状態: 実装済み

### 問題

フェーズに cycle と別の独自のループを持たせたところ、指摘の ID、止め方、往復、人の答えの受け渡し、再開をフェーズ用に作り直す穴が、直すたびに出た。レビューのループの仕組みに乗せれば作り直しが要らず、kotowari を重くしない。

### 決めたこと

整合のフェーズが見つけたものは、cycle の指摘のファイルに、レビューの指摘と同じ形で載せ、観点を consistency とする。毎回の実行で、フェーズは前の回までのフェーズの指摘に still_present か no_longer_visible を返し、新しく見つけたものと、直したもののコミットを返す。

止め方は、cycle の既存の決まり（2回続けて still_present、閉じた原因が戻る、利用者の上限、再開）にそのまま従う。フェーズ用の独自の状態は持たない（持つのは、[整合のフェーズは、実装のあとと、品質のレビューの直しが収束したあとに走らせる](#整合のフェーズは実装のあとと品質のレビューの直しが収束したあとに走らせる)の先頭のコミットだけである）。

### 見送った案

- フェーズ用の状態（実行ごとの記録、新しい指摘と繰り返した指摘の印）を足して、穴を一つずつ埋める。

### 確認すること
