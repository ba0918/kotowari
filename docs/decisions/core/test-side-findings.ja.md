# テスト側の指摘

[English](test-side-findings.md) | 日本語

テストがまだ揃っていないコミットを止めないために、check の終了コードの判定から外せるテスト側の指摘を扱う。オプションの振る舞い、どの指摘がテスト側の指摘に当たるか、フックへの組み込み方の案内を決める。オプションの受け口は[コマンドごとに受けるオプションを決め、オプションと位置引数はどの順に書いてもよい](cli.ja.md#コマンドごとに受けるオプションを決めオプションと位置引数はどの順に書いてもよい)、終了コードの一覧は[終了コードは、誤りが無ければ0、誤りがあれば1、停止したら2にする](cli.ja.md#終了コードは誤りが無ければ0誤りがあれば1停止したら2にする)で決める。

## check に --allow-test-findings を付けると、テスト側の指摘を終了コードに数えない

状態: 実装済み

### 問題

仕様を承認するコミットは実装より先で、そのとき新しく決めたことには必ず「テストが無い」の誤りが出る。テストを先に書く途中のコミットでも、テストのファイルの誤りは出る。kotowari を使う別のプロジェクトでは、pre-commit のフックに check を入れると、仕様を承認するコミットが止まる事例が何度か起きた。

kotowari 自身は、フックの設定の中にテスト側の指摘の種類を直書きして避けていた。その知識は kotowari 本体に無く、ほかのプロジェクトに伝わらず、指摘の種類が増えると古くなる。どの指摘でコミットを止めないかは、kotowari の側で持つ。止める場所を push に移せば、テストの無いものを共有のブランチに届けないことは保てる。

今は、まだ作っていない決定を「提案」の状態で書けば、仕様だけを先にコミットしても check は止まらない（[状態は実装する側が変え、まだ作らない決定は「提案」のまま置く](confirmations.ja.md#状態は実装する側が変えまだ作らない決定は提案のまま置く)）。それでも、実装済みの決定にテストがまだ揃っていないコミットは起きるので、このオプションを残す（[既存のコードを取り込むときは、人が追認した振る舞いを「実装済み」で書く](workflow.ja.md#既存のコードを取り込むときは人が追認した振る舞いを実装済みで書く)）。

### 決めたこと

check に `--allow-test-findings` を付けたときだけ、テスト側の指摘（範囲は[テスト側の指摘は、テストのファイルが原因の誤りに限り、範囲を表で定める](#テスト側の指摘はテストのファイルが原因の誤りに限り範囲を表で定める)）を終了コードの判定に数えない。

オプションを付けても、テスト側の指摘は出力から除かず、severity も "error" のまま出す。出力の指摘の種類、severity、並びは、オプションを付けないときと同じで、変わるのは終了コードの判定だけである。同じ指摘の意味が呼び方で変わると、status や読む側と食い違い、見えなくなると未完の量が分からなくなるからである。名前を allow にしたのは、指摘を出したままにするので、無視（skip、ignore）より許すのほうが中身に合うからである。

このオプションを受けるのは check だけにする。止めるかどうかを決めるのは、ゲートに使う check の終了コードだけだからである。status の complete は変えない。

### 見送った案

- 以前の決定: pre-commit のフックの設定の中に、止めない指摘の種類を並べて絞り込む。種類ごと外すので、面のファイル（製品のコード）が読めないときや、ガイドのマーカーの形の誤りまで素通りさせていた。知識が kotowari 本体に無く、ほかのプロジェクトに伝わらない。
- 指摘の JSON に分類のフィールドを足す。絞り込みは、結局フックの側が書くことになる。
- 設定ファイルに書く。設定は1つなので、pre-push と CI まで緩む。
- テスト側の指摘を注意に格下げする。同じ指摘の意味が呼び方で変わる。
- テスト側の指摘を出力から除く。未完の量が分からなくなる。
- フックを飛ばすオプションで、そのコミットだけ通す。ゲートを飛ばす癖がつく。
- 新しく決めたことを、一旦テストで確かめない形で仕様に入れる。仕様に嘘を書くことになる。

### 確認すること

- C-core-testside-1 テスト側の指摘のほかに誤りが無いとき、`--allow-test-findings` を付けた check は終了コード0で、付けない check は終了コード1で終わる
- C-core-testside-2 `--allow-test-findings` を付けても付けなくても、check の出力の指摘の種類、severity、並びが同じで、テスト側の指摘の severity は "error" のままである
- C-core-testside-3 status に `--allow-test-findings` を付けると停止する

## テスト側の指摘は、テストのファイルが原因の誤りに限り、範囲を表で定める

状態: 実装済み

### 問題

テスト側の指摘を種類だけで決めると、同じ種類でも、テストのファイルでないところ（面のファイル、ガイドのマーカー）から出た誤りまで素通りする。原因をテストのファイルに限れば、仕様を先にしたコミットとテストを先に書く途中のコミットは通り、それ以外は止まる。

テストのファイルと面のファイルの両方に当たるファイルが読めないときは、どちらの側としても読めないので、製品のコードが壊れているのと同じである。

「テストのファイルが原因の指摘」という一般の文だけでは、どの種類が入るかが読み手で割れ、テストで確かめる範囲も定まらない。表なら、ずれが差分としてレビューで見える。

### 決めたこと

テスト側の指摘は、テストのファイルが原因の誤りとし、範囲を次の表で定める。表に無い種類の誤りは、テスト側の指摘でない。

| 種類 | テスト側の指摘になる条件 |
|---|---|
| confirmation_without_test | 常に |
| test_without_id | 常に |
| invalid_marker | テストのファイルで出たとき |
| unresolved_reference | テストのファイルで出たとき |
| unparsable_file | テストのファイルで出て、そのファイルが面のファイルでないとき |

ガイドのマーカーと面のファイルから出た誤りは、テスト側の指摘に含めない。テストのファイルから出る指摘の種類を将来足すときは、その種類を決める壁打ちで、この表にも行を足す。

### 見送った案

- 表を置かず、一般の文だけで定める。どの種類が入るかが読み手で割れ、テストで確かめる範囲も定まらない。

### 確認すること

- C-core-testside-4 confirmation_without_test と test_without_id は、どのファイルで出てもテスト側の指摘になる
- C-core-testside-5 テストのファイルで出た invalid_marker、unresolved_reference、unparsable_file のほかに誤りが無ければ、`--allow-test-findings` を付けた check は終了コード0で終わる
- C-core-testside-6 表に無い種類の誤りは、テストのファイルから出ても、`--allow-test-findings` を付けた check を止める
- C-core-testside-7 ガイドのマーカーの形の誤りは、`--allow-test-findings` を付けた check を止める
- C-core-testside-8 テストのファイルと面のファイルの両方に当たるファイルの unparsable_file と、面のファイルだけの unparsable_file は、`--allow-test-findings` を付けた check を止める

## フックの組み方を、スキルと check のガイドで案内する

状態: 実装済み

### 問題

オプションがあっても、ほかのプロジェクトが組み方を知らなければ、同じ事故が起きる。

### 決めたこと

kotowari のスキル、kotowari-adopt の導入の案内、check のガイドの「フックに入れる」の節に、pre-commit のフックでは `--allow-test-findings` を付けて check を走らせ、pre-push のフックと CI では付けずに走らせる組み方を書く。

### 確認すること

- C-core-testside-9 （読んで確認）"agent/skills/kotowari/references/findings.md"、"agent/skills/kotowari-adopt/"、"docs/guides/commands/check.md" の3か所すべてに、pre-commit のフックでは check に `--allow-test-findings` を付け、pre-push のフックと CI では付けないと書いてある
