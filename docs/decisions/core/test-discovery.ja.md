# テストの見つけ方

[English](test-discovery.md) | 日本語

check がテストのファイルをどう選び、拡張子からどう言語を決め、その言語の問い合わせでテストとその名前をどう見つけるかを扱う。言語ごとに同梱する問い合わせの中身は[同梱の問い合わせ](test-queries.ja.md)、設定で足す問い合わせは[設定で足す問い合わせ](query-rules.ja.md)で決める。見つけたテストにマーカーをどう結び付けるかは、[マーカーは、テストの直前のコメントの塊にあるものだけをそのテストに結び付ける](test-markers.ja.md#マーカーはテストの直前のコメントの塊にあるものだけをそのテストに結び付ける)で決める。

## テストのファイルは tests.files の glob で選ぶ

状態: 実装済み

### 問題

テストをどこに置くかはプロダクトによって違う。kotowari が決まった場所だけを探すと、ほかの置き方のプロジェクトで使えない。

走査で読めないものに当たったとき、黙って読み飛ばすと、そこにあるテストのマーカーが数えられないまま検査が通る（[読めない入力と壊れた入力は、停止か誤りの指摘にし、黙って読み飛ばさない](cli-environment.ja.md#読めない入力と壊れた入力は停止か誤りの指摘にし黙って読み飛ばさない)）。ディレクトリでも通常のファイルでもないもの（ソケット、名前付きパイプ、デバイス）は、読むと固まりうる。

### 決めたこと

設定の "tests.files" の glob に当たるファイルを、テストのファイルとして読む。テストを探す場所はプロダクトによるので、設定で変えられるようにする、と利用者が判断した。既定の glob は、[設定のキーは表のものだけにし、書かなかったキーは表の既定の値にする](config.ja.md#設定のキーは表のものだけにし書かなかったキーは表の既定の値にする)で決める。

走査では、ファイルのシンボリックリンクは読み、ディレクトリのシンボリックリンクは辿らない。シンボリックリンクの扱いを決めた理由は残っていない。

走査は、基準のディレクトリ全体を歩いてから glob で選ぶ（[隠しディレクトリの扱いは glob の読み方と同じ](config.ja.md#glob-の--は再帰で読み隠しディレクトリにはパスの成分で名指ししたときだけ入る)）。先の無いシンボリックリンクがあれば、glob に当たらない場所にあっても、読めないファイルを理由に停止する。読めないディレクトリに当たったときも、読めないファイルを理由に停止する。ディレクトリでも通常のファイルでもないものは、glob に当たっても読まない。

### 確認すること

- C-core-discover-1 "tests.files" の glob に当たるファイルが、テストのファイルとして読まれる
- C-core-discover-2 "tests.files" の走査で、ファイルのシンボリックリンクの先のファイルが読まれる
- C-core-discover-3 "tests.files" の走査で、ディレクトリのシンボリックリンクの先は読まれない
- C-core-discover-14 "tests.files" の glob に当たる場所に先の無いシンボリックリンクがあると、check は終了コード2で停止し、標準出力に何も出さない
- C-core-discover-15 どの glob にも当たらない場所にある先の無いシンボリックリンクでも、check は終了コード2で停止し、標準出力に何も出さない
- C-core-discover-16 "tests.files" の glob に当たるソケットは読まれず、テストのファイルの数に入らない
- C-core-discover-17 "tests.files" の glob の下に読めないディレクトリがあると、check は終了コード2で停止し、標準出力に何も出さない

## テストは構文木に問い合わせを当てて見つけ、行の正規表現では探さない

状態: 実装済み

### 問題

テストの定義を見つけるには、何がテストかを言語ごとに判定する必要がある。ファイルの行に正規表現を当てて定義の行を探すやり方は、万能ではなく、意図しないものを拾う。言語ごとの判定をコードで手書きすると、言語を足すたびに重くなる。

### 決めたこと

テストのファイルは tree-sitter で構文木にし、その言語の問い合わせ（テストを見つける ast-grep のルール）をすべて当てて、テストを見つける。tree-sitter なら範囲の取り方が確実である。Rust も含め、すべての言語でこの1つの仕組みを使う。言語ごとに仕組みを分けると、マーカーをテストに結び付ける処理が2通りになり、言語によって結び付き方がずれる元になるからである。

設定ファイルに書く正規表現で、テストの定義の行を見つけることはしない。設定から来る正規表現は、ast-grep のルールの中で構文木の節に当てるものだけにする。

### 見送った案

- 設定に書く正規表現で、テストの定義の行を見つける。万能でなく、意図しない検出が起こる。
- Rust だけ構文木を手で辿る形に残し、新しい言語だけ ast-grep にする。マーカーの結び付けの処理が2通りになる。

### 確認すること

- C-core-discover-4 Rust のテストのファイルの "#[test]" の関数が、同梱の問い合わせでテストとして見つかる
- C-core-discover-5 （読んで確認）テストを見つけるコードは、テストのファイルの行に正規表現を当てて定義の行を探していない。設定から来る正規表現は、ast-grep のルールの中で構文木の節に当てるものだけである

## 問い合わせが1つも無い言語のファイルは構文木を読まない

状態: 実装済み

### 問題

kotowari は多くの言語の文法を持つ。文法を入れただけで振る舞いが変わると、たとえば ".md" を glob に入れている利用者に、急に unparsable_file が出る。

### 決めたこと

問い合わせのある言語は、同梱か設定の問い合わせが1つ以上ある言語とする。文法があっても問い合わせが1つも無い言語は、問い合わせの無い言語のままで、そのファイルは構文木を読まない。問い合わせの無い言語のファイルからマーカーをどう拾うかは、[問い合わせの無い言語のファイルでは、ファイルの中のマーカーをすべて拾う](test-markers.ja.md#問い合わせの無い言語のファイルではファイルの中のマーカーをすべて拾う)で決める。

### 確認すること

- C-core-discover-6 言語は決まるが問い合わせが1つも無いファイル（".go"）は構文木を読まず、構文の誤りがあっても unparsable_file が出ない

## 拡張子と言語の対応は ast-grep と同じにし、大文字小文字を区別する

状態: 実装済み

### 問題

問い合わせを ast-grep のルールの形で書く（[設定で足す問い合わせ](query-rules.ja.md)）ので、どのファイルがどの言語かの読み方が ast-grep とずれると、"ast-grep scan" で試したときと結果が変わる。読める言語を絞ると、kotowari を使える場面が狭くなる。

### 決めたこと

読める言語は絞らず、一般的な言語を広く読めるようにする。ルールで判定する形なら言語を足す手間が小さく、読める言語が多いほど kotowari を使える場面が広がる、と利用者が判断した。文法は ast-grep-language の全27個を入れ、言語は28個になる（TypeScript の文法が TypeScript と Tsx の2つの言語を持つ）。

拡張子と言語の対応は、入れた ast-grep-language が持つ対応をそのまま使う。"ast-grep scan" と同じファイルが同じ言語になる。TypeScript と Tsx は ast-grep と同じく別の言語として扱う。

拡張子は、ファイル名の最後の "." より後ろの文字とし、大文字小文字を区別する。表に無い拡張子のファイルは言語が決まらず、問い合わせの無い言語として扱う。大文字小文字を区別する理由は残っていない。

| 言語 | 拡張子 |
|---|---|
| Bash | bash、bats、cgi、command、env、fcgi、ksh、sh、tmux、tool、zsh |
| C | c、h |
| Cpp | cc、hpp、cpp、c++、hh、cxx、cu、ino |
| CSharp | cs |
| Css | css、scss |
| Dart | dart |
| Elixir | ex、exs |
| Go | go |
| Haskell | hs |
| Hcl | hcl、nomad、tf、tfvars、workflow |
| Html | html、htm、xhtml |
| Java | java |
| JavaScript | cjs、js、mjs、jsx |
| Json | json |
| Kotlin | kt、ktm、kts |
| Lua | lua |
| Markdown | markdown、md |
| Nix | nix |
| Php | php |
| Python | py、py3、pyi、bzl、bazel |
| Ruby | rb、rbw、gemspec |
| Rust | rs |
| Scala | scala、sc、sbt |
| Solidity | sol |
| Swift | swift |
| TypeScript | ts、cts、mts |
| Tsx | tsx |
| Yaml | yaml、yml |

### 見送った案

- 文法を、利用者が使う5つの言語か、プログラミング言語の16個に絞る。全27個との差は 6.7MB で、全部を入れればどれを選ぶかの判断が要らなくなり、使う人が設定でルールを足すだけでその言語を使える。

### 確認すること

- C-core-discover-7 表の拡張子のファイルは表の言語になり（".py3"、".bzl" は Python、".mts" は TypeScript）、大文字小文字の違う綴り（".PY"、".Rs"、".RS"）のファイルは言語が決まらず、問い合わせの無い言語として扱われる

## 構文の誤りがあるテストのファイルは、unparsable_file を出して飛ばす

状態: 実装済み

### 問題

テストのファイルには、書きかけなどで構文の誤りがあるものが混ざりうる。構文木を読めないファイルをどう扱うかを決める必要がある。止めずに飛ばすと決めた理由は残っていない。言語を足したときは、それまでの Rust の振る舞いを、言語を問わず保つことにした。

### 決めたこと

問い合わせのある言語のテストのファイルを tree-sitter で読み、構文の誤りが1つでもあれば、そのファイル全体に unparsable_file の誤りを出してそのファイルを飛ばし、停止しない。問い合わせの無い言語のファイルは構文木を読まないので、unparsable_file を出さない（[問い合わせが1つも無い言語のファイルは構文木を読まない](#問い合わせが1つも無い言語のファイルは構文木を読まない)）。

### 確認すること

- C-core-discover-8 問い合わせのある言語のファイルに構文の誤りがあると、そのファイルの unparsable_file が1件出て、check は停止せずに検査を続ける

## テストの名前は、問い合わせが捕まえた文字から取る

状態: 実装済み

### 問題

問い合わせは使う人も書くので、ルールが当たった節のどこをテストの名前にするかを、kotowari の側の約束として決める必要がある。TypeScript の "it(\"does x\", ...)" では、名前の位置に引用符ごとの文字列が捕まる。

### 決めたこと

問い合わせが当たった構文木の節を1つのテストとし、メタ変数 "$NAME" に入った節の文字を、そのテストの名前にする。

その文字の最初と最後が同じ引用符（一重引用符、二重引用符、バッククォートのいずれか）なら、その1文字ずつを外す。それ以外の形（例: Python の三重引用符の文字列、"f" の接頭辞の付いた文字列）は、そのまま名前にする。文字列リテラルを言語に依存せずに見分けるのは難しく、名前が文字列になるのは TS/JS と Pest の "it('...')" くらいなので、この規則で足りる、と利用者が判断した。

問い合わせが "$NAME" を捕まえないとき、テストの名前は null にする。list の "name" は null を取れる（[確認することの行にはそれを指すテストを、決定には指紋を付ける](list.ja.md#確認することの行にはそれを指すテストを決定には指紋を付ける)）。

入れ子の "describe" の中の "it" の名前は、"it" 自身の最初の引数だけにし、外の "describe" の名前を付けない。名前は list に出す情報で、マーカーの結び付けには使わない。つなげると、つなぐ区切り文字の決めごとが増える。

### 確認すること

- C-core-discover-9 "$NAME" の文字の最初と最後が同じ引用符なら1文字ずつ外し、ほかの形（例: 片方だけの引用符、式）はそのまま名前にする
- C-core-discover-10 "describe" の中の "it" の名前に、"describe" の名前が付かない
- C-core-discover-11 "$NAME" を捕まえない問い合わせで見つかったテストは、list の "name" が null になる

## 同じ節に重なって当たっても1つと数え、テストの中のテストは別に数える

状態: 実装済み

### 問題

同梱の問い合わせと設定で足した問い合わせが、同じ "it(...)" に当たることがある。そのまま数えると、1つのテストが2つになる。一方で、テストの中に別のテストが書かれることもある。

### 決めたこと

同じ節に複数の問い合わせが当たったら、その節を1つのテストと数える。テストの節の中でさらに当たった節は、別のテストとして数える。

### 確認すること

- C-core-discover-12 同梱の問い合わせと設定の問い合わせが同じ節に当たっても、テストは1つと数える
- C-core-discover-13 テストの節の中でさらに問い合わせが当たった節は、外のテストとは別のテストとして数える
