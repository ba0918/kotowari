# 計画書の検査

[English](plan.md) | 日本語

`kotowari plan` が、実装の手順を書いた計画書を1つ読み、本体に同梱したスキーマで形を検査するところを扱う。指摘の並べ方と line の数え方は[指摘の並べ方と行](finding-order.ja.md)で、停止の理由の文言は[停止の理由は、英語の固定の文言で示す](cli-environment.ja.md#停止の理由は英語の固定の文言で示す)で、終了コードは[終了コードは、誤りが無ければ0、誤りがあれば1、停止したら2にする](cli.ja.md#終了コードは誤りが無ければ0誤りがあれば1停止したら2にする)で、text の形は[--format text は、1つの指摘を1行で出す](output.ja.md#--format-text-は1つの指摘を1行で出す)で、JSON の指摘の鍵は[指摘は kind、severity、path、line、detail の5つの鍵で出す](output.ja.md#指摘は-kindseveritypathlinedetail-の5つの鍵で出す)で決める。

## 計画書の形は、本体に同梱したスキーマで kotowari plan が検査する

状態: 実装済み

### 問題

工程が書く計画書の形は雛形で決まっていたが、書いた本人が雛形と見比べて文章で自己点検するだけで、機械の検査が無かった。kotowari には Markdown の形をスキーマで検査するエンジンがあるのに、自分の工程の成果物を自分の道具で検査していなかった。

スキーマを本体に同梱するのは、kotowari が提供する機能として説明がつくからである。工程は既に kotowari のコマンドを使うので、本体がある前提にでき、エンジンが別に入っているかを問わなくてよい。計画書は完了すれば消すので、いつも利用者の手元の本体のスキーマで書かれ、過去の計画書を検査し直す機会はほとんど無い。

検査を check に入れずに別のコマンドにしたのは、check が位置引数を受けず、ファイルを1つ受けて読むコマンドには mutants の前例（[変異テストは kotowari の外で走らせ、kotowari mutants はその結果のファイルを読んで指摘にする](mutants.ja.md#変異テストは-kotowari-の外で走らせkotowari-mutants-はその結果のファイルを読んで指摘にする)）があるからである。

### 決めたこと

計画書の形は、kotowari の本体がコンパイル時に取り込んだ計画書のスキーマで検査する。実行時にスキーマのファイルを読まない。計画書は自分でスキーマを指さず、プロジェクトにスキーマを写さない。検査に落ちたときは、本体のスキーマに合わせて計画書を直す。

検査は `kotowari plan <path>` で行う。位置引数は計画書のファイル1つである。

計画書の先頭の frontmatter は、中身を問わず読まずに飛ばす。形の宣言としては使わず（`$schema` の鍵があっても使わない）、指摘にも停止にもしない。

### 見送った案

- 以前の決定: 工程の skill が持つスキーマを、計画書を書くたびにプロジェクトの `.kotowari/schemas/plan.yaml` へ写して上書きし、計画書の frontmatter の `$schema` で相対パスで指す。写す手順とコミットするファイルが増え、エンジンが入っていない環境の扱いも別に要るので、やめた。
- スキーマを URL で指す。キャッシュに期限が無いので、skill を更新しても古いスキーマが使われ続ける。
- check に計画書の置き場の設定を足し、仕様と一緒に検査する。pre-commit で自動で回るが、計画書の指摘が status の完了の判定に響き、その回の指摘だけを扱う決まりとも絡んで広がりすぎる。

### 確認すること

- C-core-plan-1 frontmatter の `$schema` が無いファイルを指していても、`kotowari plan` はそれを使わず、同梱のスキーマで検査して終了コード0で終わる
- C-core-plan-2 先頭の frontmatter が YAML として読めなくても、`kotowari plan` は読まずに飛ばし、指摘も停止も出さない

## kotowari plan は設定を読まず、引数と読めないファイルの扱いを mutants に揃える

状態: 実装済み

### 問題

`kotowari plan` は計画書1つの形を同梱のスキーマで検査するだけで、設定を使わない。設定を受けて黙って無視すると、付けた人が効いていると誤解する。引数と読めないファイルの扱いは、ファイルを1つ受けて読むコマンドの前例（mutants）に揃えれば、決めることが増えない。

### 決めたこと

`kotowari plan` が受けるオプションは `--format`、`--help`、`--version` だけにする。`--config` を受けたら、引数の誤りで停止する。設定ファイルは読まない。

位置引数がちょうど1つでなければ、引数の誤りで停止する。位置引数のパスは、カレントディレクトリからの相対パスとして読む。ファイルが無い、ディレクトリである、読めないときは読めないファイル、UTF-8 でないときは UTF-8 でないファイルを理由に停止する。plan のための新しい停止の理由は作らない。

### 確認すること

- C-core-plan-3 位置引数の無い `kotowari plan` と、計画書を2つ渡した `kotowari plan` は、終了コード2で止まり、標準エラーの1行目が "argument error: " で始まる
- C-core-plan-4 `kotowari plan` に `--config` を付けると、指す先がファイルでもディレクトリでも、引数の誤りで止まる
- C-core-plan-5 YAML として読めない設定ファイルがあっても、`kotowari plan` は止まらずに計画書を検査する
- C-core-plan-6 計画書が無いかディレクトリなら標準エラーの1行目が "unreadable file: " で、UTF-8 でなければ "non-UTF-8 file: " で始まり、どちらも終了コード2で止まる

## 計画書は、決まった計画全体の節と、8つの欄を持つステップで書く

状態: 実装済み

### 問題

スキーマで検査するのは、計画書の形だけにする。欄の中身の良し悪し（Done when が他人に観測できるか、など）は機械で決まらないので、書いた実装役の自己点検に残す。計画書が指す仕様の ID が実在するかは、`kotowari query` で確かめる（[位置引数がちょうど1つの ID でないか、その ID が無ければ、引数の誤りで停止する](query.ja.md#位置引数がちょうど1つの-id-でないかその-id-が無ければ引数の誤りで停止する)）。

それまでの雛形の形（ステップの見出しの繰り返し、地の文のラベル、Shown by の頭の語）は、今のエンジンでは検査できなかった。エンジンは節を名前の完全一致で照合し、欄として読むのは一覧の「名前: 値」の行だけで、値の許可リストは値全体との一致である。汎用のエンジンを計画書の都合で広げるより、計画書の書式をエンジンに寄せるほうが安い、と利用者が決めた。必須の節とステップの欄の数を縛るのは、計画書の各部分が欠けず重ならないことを形で保つためである。

### 決めたこと

計画書は、題名の後に次の計画全体の節を置く。"## Goal"、"## Specification"、"## Approach and why"、"## Scope of change"、"## Step order and prerequisites"、"## Verification map"、"## Left to the implementer"、"## Stop conditions"、"## Out of scope"、"## Steps" はちょうど1つずつ、"## Test command" は0個か1個である。

"## Steps" の節には、ステップを1つ以上置く。ステップの見出しは "### S" と1桁以上の数字の後に ":" がある形にする。各ステップの下には、次の欄の行をこの順で1回ずつ書く。

| 順 | 欄 |
|---|---|
| 1 | Purpose |
| 2 | Specification |
| 3 | Prerequisites |
| 4 | May change |
| 5 | Done when |
| 6 | Shown by |
| 7 | Left to the implementer |
| 8 | Stop and hand back if |

欄の行は「名前: 値」の一覧の行で、一覧の記号は "-"、"*"、"+" のどれでもよい。"Shown by" の値は "test"、"check"、"artifact"、"external" のどれかの語で始まり、その語の後は空白か値の終わりである。

### 見送った案

- エンジンに、節の名前の正規表現や節の順序の検査を足す。エンジンは汎用のもので、kotowari の都合を持ち込まない。

### 確認すること

- C-core-plan-7 必須の節がそろい、"## Steps" の下に8つの欄を順に持つステップがある計画書には、指摘が出ず、終了コードは0になる
- C-core-plan-8 必須の節のどれかが欠けるか2つある計画書は invalid_plan の誤りになる。"## Test command" の節は無くても誤りにならず、2つあれば誤りになる
- C-core-plan-9 "## Steps" の節にステップが1つも無い計画書は、誤りになる
- C-core-plan-10 ステップの見出しが "### S" と数字と ":" の形でない（例: "### Step 1: …"、":" の無い見出し）と、誤りになる
- C-core-plan-11 ステップの欄のどれかが欠ける、同じ欄が2回ある、欄の順が違う、のどれでも誤りになる
- C-core-plan-12 "Shown by" の値が4つの語のどれでもない語で始まるか、語の後に空白でない文字が続くと誤りになり、4つの語のどれかだけか、語の後に空白が続く値は誤りにならない
- C-core-plan-13 欄の行の一覧の記号を "*" や "+" にしても、誤りにならない

## ステップの下には欄の行だけを置き、計画全体の節には文・一覧・表・コードブロックを置ける

状態: 実装済み

### 問題

計画全体の節は、Verification map は表、Approach は散文のように、中身に合った書き方をしたい。一方、ステップは替わった実装役が残りを決めるときに読むので、形を固めたい。

欄の値を複数行に書けると、段落として読んだとき、欄の直後に空行なしで続く行が欄の値に吸われ、空行の後の字下げした行は続きの段落として指摘にならない。それでは、ステップの下にほかの行を置かないことが成り立たない。

番号付きの一覧は、エンジンに規則の種類が無く宣言できない。要約は Goal に書けばよいので、題名と最初の節の間にも行を置かない。

### 決めたこと

ステップの下には8つの欄の行だけを置き、ほかの空でない行は誤りにする。欄の値は1行に書き、計画書は1行ずつ読む。

計画全体の節の下には、文、番号の無い一覧とその子の一覧、表、コードブロックを置いてよい。番号付きの一覧と、"### " とそれより深い見出しは置けない。題名と最初の "## " の節の間には、空でない行を置けない。

### 確認すること

- C-core-plan-14 ステップの欄の行の直後に空行なしで地の文を続けるか、空行の後に字下げした行を置くか、知らない名前の欄の行を置くと、誤りになる
- C-core-plan-15 計画全体の節に表、コードブロック、子の一覧を持つ箇条書きを置いても、誤りにならない
- C-core-plan-16 計画全体の節の番号付きの一覧、計画全体の節の中の "### " や "#### " の見出し、題名と最初の節の間の地の文は、どれも誤りになる

## 節の並び順、ステップの番号、ステップの見出しの名前は検査しない

状態: 実装済み

### 問題

節の並び順を検査する仕組みはエンジンに無く、そのためにエンジンを広げない。ステップの番号の飛びや重なりは中身の問題で、形として検査する理由が無い。ステップの見出しの ":" の後の名前を検査するにはエンジンを広げることになり、書式をエンジンに寄せると決めた向きに反する。

### 決めたこと

計画全体の節の並び順、ステップの番号が連番かどうか、同じ番号のステップが2つあるかどうか、ステップの見出しの ":" の後の名前（空か、":" の後に空白があるか）は検査しない。

### 確認すること

- C-core-plan-17 "## Goal" の節が "## Out of scope" の節の後にあり、ステップの番号が S1 と S3 に飛んでいる計画書は、誤りにならない
- C-core-plan-18 同じ番号のステップが2つある計画書と、ステップの見出しの ":" の後に名前が無い計画書は、誤りにならない

## 形の指摘は invalid_plan の1種類にまとめ、スキーマの側の種類と詳細を detail に入れる

状態: 実装済み

### 問題

エンジンが出す指摘の種類をそのまま kotowari の種類として並べると、指摘の種類の一覧と、それを本体と突き合わせるテストの対象が増える。計画書を直すのは LLM で、何が悪いかは詳細を読めれば足りる。

どの行を指すかが決まっていなかった。欄の欠けたステップをどこで指すかと、text での出し方を、観測した今の振る舞いに合わせて決めた。path の書き方は、設定ファイルの停止の詳細（基準の外なら "../" を含める）と揃える。

### 決めたこと

計画書が形から外れるとき、スキーマの側が出した指摘を1件ごとに、種類 invalid_plan、重さ「誤り」の指摘にして出す。スキーマの側の指摘は捨てず、kotowari のほかの種類へは写さない。終了コードは、誤りがあれば1である。

- detail は、スキーマの側の種類と詳細を ": " でつないだ文字列にする。
- line は、スキーマの側が出した行をそのまま使う。ステップに必須の欄が無いときは、そのステップの見出しの行にする。行の数え方は[line は1始まりで数え、文書全体にかかる指摘は null にする](finding-order.ja.md#line-は1始まりで数え文書全体にかかる指摘は-null-にする)のとおりである。
- path は、計画書のファイルの、基準のディレクトリからの相対パスにする。基準の外にあれば "../" を含める。"./" や ".." を含む形や絶対パスで渡されても、正規化して同じ形で出す。

### 確認すること

- C-core-plan-19 欄の欠けたステップを持つ計画書では、出る指摘がどれも種類 invalid_plan、severity が "error" で、detail がスキーマの側の種類に ": " と詳細を続けた形になり、終了コードは1になる
- C-core-plan-20 invalid_plan の line は、スキーマの側が指摘を出した行で、欄の欠けたステップでは、そのステップの見出しの行になる
- C-core-plan-21 invalid_plan の path は、"./" や ".." を含めて渡しても基準のディレクトリからの相対パスに正規化され、基準の外の計画書では "../" で始まる

## kotowari plan の出力は check と同じ指摘の鍵を使い、JSON は findings と counts だけにする

状態: 実装済み

### 問題

check の JSON の数のうち files、lines、tests は、仕様とテストのファイルを読んだ量で、計画書1つには当たらない。text は、check の text と同じ形にしたい。

### 決めたこと

`--format json` のとき、最上位には "findings" と "counts" の2つの鍵だけを持たせる。"findings" の指摘の鍵は、check と同じ kind、severity、path、line、detail である。

`--format text` のとき、指摘を check の text と同じ形で1件1行に出し、ほかの行を出さない。指摘が0件なら何も出さない。

### 確認すること

- C-core-plan-22 `kotowari plan --format json` の最上位の鍵は "findings" と "counts" の2つだけで、指摘の鍵は kind、severity、path、line、detail の5つである
- C-core-plan-23 `kotowari plan --format text` は、指摘を1件1行で "<path>:<line> [error] invalid_plan " で始まる行として出し、ほかの行を出さず、指摘が0件なら何も出さない
