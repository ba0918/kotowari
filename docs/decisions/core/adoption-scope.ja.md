# 導入の範囲と行の作り方

[English](adoption-scope.md) | 日本語

工程の skill kotowari-adopt が、1回の導入で扱う話題の範囲をどう決め、旧資料と実装とテストを読んで一覧の行をどう作るかを扱う。行の行き先と、人に聞く回数は[既存プロジェクトへの導入](adoption.ja.md)で決める。ここにあるのは、skill の文を人か LLM が読んで確かめる決定だけである。

## 1回の導入で扱う話題は1つで、人が選ぶ

状態: 実装済み

### 問題

既存のプロジェクトに途中から kotowari を入れると、旧資料と判断の記録と実装とテストが食い違っていたり欠けていたりする。全部を導入の時点で決めようとすると面談が膨らみ、推奨の丸呑みになる。ある既存のプロジェクトの導入では、移行の判断54件を1つの記録で最初に決め切ろうとして、52件が推奨の採用だった。

### 決めたこと

1回の導入で扱う話題は1つにする。どの話題にするかは、範囲の確認のラウンドで人が選ぶ。既定として出すのは、次に変更する予定の機能である。プロジェクト全体の棚卸しはせず、選ばなかった話題は旧資料のまま置く。

### 確認すること

- C-core-adoptscope-1 （読んで確認）kotowari-adopt の skill に、1回で扱う話題は1つで、範囲の確認のラウンドで人が選び、既定は次に変更する予定の機能だと書いてある

## 範囲の確認のラウンドで、話題の利用者の入口と、コードとテストのファイルと、読む旧資料を人に確かめる

状態: 実装済み

### 問題

範囲が曖昧なまま仕分けると、テストの行き先の内訳の分母がぶれる。また、コードは入口の間で共有されるので、ファイルで範囲を切ると、別の入口の振る舞いまで行になる。ある導入では、確かめた範囲の外のファイルまで読み、そこで見つけた別の入口の振る舞いまで行にしたため、追認の候補32行のおよそ半分がその話題でない側の振る舞いになった。

読む旧資料を絞るのは、読む量を抑えるためである。コードのコメントやコミットログにある理由は、判断の記録の代わりにならない。

### 決めたこと

人が話題を選んだら、同じラウンドで、話題の利用者の入口（利用者が触るコマンドやサブコマンド、画面の操作）、範囲のコードファイルとテストファイルの案、読む旧資料の候補を出して、人に確かめる。

旧資料は、導入より前からある、仕様や判断を書いた文書とする。旧仕様、既存の判断の記録と ADR、README のうち振る舞いを説明する部分がこれにあたる。コードのコメントとコミットログは旧資料に入れない。

### 確認すること

- C-core-adoptscope-2 （読んで確認）kotowari-adopt の skill に、範囲の確認のラウンドで、話題の利用者の入口、範囲のコードファイルとテストファイルの案、読む旧資料の候補を人に確かめると書いてある
- C-core-adoptscope-3 （読んで確認）kotowari-adopt の skill に、旧資料は旧仕様、既存の判断の記録と ADR、README のうち振る舞いを説明する部分で、コードのコメントとコミットログは入れないと書いてある

## 読んで仕分けるのは主セッションで、読み切れなければ話題を割ることを提案する

状態: 実装済み

### 問題

kotowari は、利用者が費用をかけられない前提で作っている。理由の無い委譲の席は足さない。1回で読み切れない大きさは、話題の単位が大きすぎる合図である。

### 決めたこと

旧資料、コード、テストを読んで仕分けるのは主セッションにする。1回で読み切れない大きさなら、別の agent に読ませず、話題を小さく割ることを人に提案する。この提案と話題の選択は、範囲の確認のラウンドの中で行う。

### 確認すること

- C-core-adoptscope-4 （読んで確認）kotowari-adopt の skill に、読んで仕分けるのは主セッションで、読み切れない大きさなら別の agent に読ませず、範囲の確認のラウンドで話題を小さく割ることを提案すると書いてある

## 設定が無ければ、先に kotowari スキルの準備の手順を行い、その問いは人に聞く回数に数えない

状態: 実装済み

### 問題

導入するリポジトリに kotowari の設定がまだ無いことがある。準備の手順を2か所に持つと食い違う。準備での問いは kotowari スキルの手順の側にあるので、導入で人に聞く回数（[人に聞くのは、範囲の確認、一覧の1ラウンド、承認の3回だけにする](adoption.ja.md#人に聞くのは範囲の確認一覧の1ラウンド承認の3回だけにする)）に数えるかを決めておく必要があった。

### 決めたこと

kotowari-adopt は、最初に対象のリポジトリに `.kotowari/config.yaml` があるかを確かめる。無ければ、kotowari スキルの `references/config.md` の準備の手順を先に行う。準備の中身は kotowari-adopt に書かず、場所を名指しする。準備で人に聞いた問いは、導入で人に聞く回数に数えない。

### 確認すること

- C-core-adoptscope-5 （読んで確認）kotowari-adopt の skill に、最初に `.kotowari/config.yaml` があるかを確かめ、無ければ kotowari スキルの `references/config.md` の準備の手順を名指しして先に行い、その問いは人に聞く回数に数えないと書いてある

## 行にするのは、話題の利用者の入口から観測できる振る舞いだけにする

状態: 実装済み

### 問題

ある導入で、保存と復元の処理を理解するために範囲の外のファイルまで読み、その中で見つけた振る舞いまで行にしたため、話題が膨らんだ。理解のために読む範囲を広げることは要るが、読んだものを全部仕様にすると話題が膨らむ。見つけたことは、次の話題の手がかりとして残したい。

### 決めたこと

一覧の行にするのは、話題の利用者の入口から観測できる振る舞いだけにする。同じコードを共有していても、別の入口から観測される振る舞いは範囲の外とする。

理解のために範囲の外のファイルを読んでよい。そこで見つけた範囲の外の振る舞いは行にしない。一覧のラウンドでは、範囲の外で見つかった振る舞いの件数と、次の話題の候補の名前だけを見せる。

### 確認すること

- C-core-adoptscope-6 （読んで確認）kotowari-adopt の skill に、行にするのは話題の利用者の入口から観測できる振る舞いだけで、同じコードを共有していても別の入口から観測される振る舞いは範囲の外だと書いてある
- C-core-adoptscope-7 （読んで確認）kotowari-adopt の skill に、範囲の外のファイルは読んでよいが、そこで見つけた振る舞いは行にせず、一覧のラウンドで件数と次の話題の候補の名前だけを見せると書いてある

## 同じ規則で値や文言だけが違う振る舞いは、1行にまとめて決定表の候補にする

状態: 実装済み

### 問題

ある導入で、1つの規則の文言の違い（スキップの理由の文言）が別々の行になり、行が膨らんだ。

### 決めたこと

同じ規則で値や文言だけが違う振る舞いは、一覧の1行にまとめ、決定表で書く候補にする。一覧の実装の振る舞いの欄に、表の中身を短く並べる。

### 確認すること

- C-core-adoptscope-8 （読んで確認）kotowari-adopt の skill に、同じ規則で値や文言だけが違うものは1行にまとめて決定表の候補にし、実装の振る舞いの欄に表の中身を短く並べると書いてある

## 一覧の1行は、決定1つの候補にする

状態: 提案

### 問題

一覧の1行は、以前は要求1つの候補だった。仕様を決定の文書だけで持つようになり、要求が無くなったので、1行を何の候補にするかを決め直す必要があった。決定1つにした理由は、記録に残っていない。

### 決めたこと

一覧の振る舞いの1行は、決定1つの候補にする。

### 確認すること
