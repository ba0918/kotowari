## Approach and why

Work from the lower dependency boundary upward. The schema API changes first because core and the mds binary already call it. Core-owned input and comparison types precede source-analysis so that the latter can depend on core without a reverse edge. Move the kotowari environment operations and CLI in one buildable transition after those inputs exist. Optional async wrappers come last among the APIs, when they can delegate to tested synchronous operations.

The final normal dependency graph must equal `TBL-core-040`. The root package is `kotowari-cli`, with `src/main.rs` still producing `kotowari`. Libraries occupy `crates/kotowari`, `crates/kotowari-core`, `crates/kotowari-source-analysis`, `crates/kotowari-markdown-schema` and `crates/kotowari-markdown-schema-io`. The other CLI occupies `crates/kotowari-mds`. Do not leave temporary forwarding APIs or inverse dependencies after S4.

Reuse the algorithms and fixtures enumerated in the planning record. Keep configuration data and validation in the calculation layer where needed; move configuration file loading, directory walks, Git acquisition and process state access into the high-level library. Move argument parsing, formatting and exit-code decisions into the binary packages. Results need read-only accessors and typed errors, not a public copy of every internal structure. Preserve identity when re-exporting lower-level input/result types. Keep expandable kind enums non-exhaustive. Preserve CLI serialization through CLI-owned presentation types rather than promising serialization of every public model.

Core currently calls `kotowari_markdown_schema::ast::parse_mdast` in guides.rs and surface.rs and already depends directly on markdown. Replace those cross-crate internal calls with a private core helper using the existing GFM/frontmatter parse options. No third-party AST or regex capture type may appear in a public signature. Move the canonical embedded ir.yaml, context.yaml, flags.yaml and plan.yaml to `crates/kotowari-core/schemas/`; remove the four legacy `.kotowari/schemas/` links and update only the schema-location text on REQ-core-179 and REQ-core-041's how_to_verify lines to those canonical paths, as authorized in [planning A11](../decision/records/2026-10-03-public-crate-api-plan.md#A11). Keep original schema bytes, requirement behavior, selected-symlink rejection, change selection/exclusions and all gates unchanged. Do not touch unrelated overview.yaml references. Move bundled source queries to `crates/kotowari-source-analysis/queries/` when their owner moves.

Keep the root package version as the kotowari-series authority and the schema manifest as the schema-series authority. The four kotowari packages remain 0.3.0, and the three schema packages remain 0.1.0. Each internal path dependency also declares the dependency's registry version. A schema-series release must update core's schema dependency even though core's own series does not change. Version automation must cover incoming dependency declarations, all seven lock entries, and rollback of every changed file.

The parent orchestrates Sol implementation and fixes using `openai/gpt-6.1-sol`, without a required variant, after this plan is approved and committed. Separate-context review remains parent-owned. This is an execution instruction, not a product contract. Local implementation commits are allowed after approval; this plan author does not commit or stage anything.
