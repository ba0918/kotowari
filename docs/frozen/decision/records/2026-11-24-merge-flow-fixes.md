# 人を待たずにマージする工程の手直し

## Context

仕様の承認からマージまで人を待たない工程を入れたあと、そのプルリクエストのレビューで、直していない指摘が残った。
人の確認をすり抜けうる経路が2つ、工程が書いたとおりに進まない箇所がいくつか、測っていない道具の挙動に頼る箇所が2つ。
整合のフェーズが人の判断待ちとして残した問いも1つ開いている。
自動マージの設定を有効にする前に、これらを決めて塞ぐ。

Position: 壁打ちは収束した（2026-11-24）。

## Agreements

- A1 マージ先を cycle の入力にする。最初のフルレビュー、整合のフェーズの最初の回、線の判定は、マージ先との分かれ目から読み、プルリクエストはそのマージ先へ向ける。決めていなければ既定の枝とする。あとの差分のレビューと、修正のあとの整合のフェーズの回は、いまの範囲のままにする。前の回がすでにレビューした枝で続ける小さい作業は、その回が終わったところから読む
  - why: レビューの範囲が「枝の親との分かれ目から」、プルリクエストが「マージ先との分かれ目から」とずれていると、まだマージ先に入っていない枝から切った枝で、親のコミットがレビューされないままマージされうる
  - rejected: 範囲がずれていたらプルリクエストで止まる（決まりが1つ増え、積んだ枝はいつも人がマージすることになる）
  - decided_by: 利用者（推奨を採用）。どの回がマージ先との分かれ目から読むかの切り分けは、主セッションが仕様のレビューの指摘から足し、見直しのラウンドで利用者に示した

- A2 確かめ方を「既存の検査がぜんぶ通ること」に置き換えた指摘は、レビュー役が走らせて落ちるのを見たものなら、直す指摘として残す
  - why: 数えないと、レビュー役が落ちるのを見た間違いが、直されないまま人なしでマージされうる
  - decided_by: 利用者（推奨を採用）

- A3 差分が足した検証が証拠の条件を満たさないので消す、という提案は、落ちるのを見ていなくても直す指摘にする
  - why: 証拠の条件を満たさないことは、条件に照らして読めば決まる。確かめ方が「消したあとも既存の検査が通ること」で、いま落ちるものではないので、走らせて示す決まりのままだと必ず記録だけになり、証拠にならないテストが残る
  - rejected: 記録だけのままにする。実装役に証拠の条件を最初から渡す（それでも足されたものは、記録だけのまま残る）
  - decided_by: 利用者（推奨を採用）

- A4 cycle は、始めるときに枝ごとの指摘のファイルを作り、受け取った要求の ID とマージ先をそこに書く（ID が0件のときも、0件として書く）。同じ枝へのあとの依頼は、その ID を足す。再開はどちらもファイルから読み、ファイルに ID の記録が無いときだけ、枝の差分の仕様の部分から数え直す。再開のために新しいファイルは作らない
  - why: 仕様がすでにマージ先にある依頼では、枝の差分に仕様が無く、数え直しが0件になる。再開した回が何も実装しないまま収束しうる
  - rejected: 数え直しが0件だったら人に聞く（再開のたびに人が1回出る）
  - decided_by: 利用者（推奨を採用）。書く時点、マージ先も書くこと、0件の扱い、あとの依頼の足し方は、主セッションが仕様のレビューの指摘から足し、見直しのラウンドで利用者に示した

- A5 提案された扱いが直すことであるセキュリティの指摘では止めない。落ちるのを見たかどうかにかかわらず、修正役に渡す。人の判断を求めるセキュリティの指摘は、人の判断待ちとして開いたまま残り、記録だけの指摘は記録だけのままにする。直らないまま進まなくなったら、いまある終わり方（進まない）で人に渡る。直した内容は、判断の1行として事後に読む
  - why: 直すしかない指摘を人に戻しても、人が選べるものが無い。ほかの指摘と同じ決まり（落ちるのを見たものだけ直す）を当てると、走らせていないセキュリティの指摘が、直されないまま人なしでマージされうる
  - rejected: ほかの指摘と同じ決まりを当てる。今のまま必ず止めて人に渡す
  - decided_by: 利用者（利用者の指摘から。推奨を採用）。直すことを提案する指摘に限ったのは主セッションで、見直しのラウンドで利用者に示した

- A6 一覧の各行は、前後の空白と行末の CR を落としてから、パスの指定として渡す
  - why: 行末に空白のある行は何にも当たらず（実測）、差分では見えにくい
  - rejected: 何にも当たらない行を手順の失敗にする（まだ無いパスを先に一覧へ書いておけなくなる）
  - decided_by: 利用者（代決を承認）

- A7 枝の名前は、その依頼が終わったあと使い回さない。新しい依頼を受け取った開始で、ホスティングの側にその枝の名前のマージ済みか閉じたプルリクエストがあれば、cycle は止まって新しい枝の名前を求める。枝のプルリクエストが開いていて、その先頭が手元の枝に無いときは、止まって人に伝える
  - why: 枝の名前だけで引くと、同じ名前の枝を使い回したとき、前の依頼のプルリクエストを今回のものとして読む。先頭のコミットで見分ける案は、マージコミットでマージするリポジトリでは働かない（前の依頼の先頭がマージ先の祖先になり、そこから切った新しい枝の祖先にもなる。このリポジトリで確かめた）。見分ける決まりを足すより、使い回さないほうが単純
  - rejected: プルリクエストの先頭のコミットで見分ける。プルリクエストの番号を指摘のファイルに書く（ファイルを失うと見分けられない）
  - decided_by: 主セッション（利用者が代決で承認した「先頭のコミットで見分ける」を、仕様のレビューの指摘で取り替え、見直しのラウンドで利用者に示した）

- A8 壁打ちは、主の作業ツリーで、マージ先の先頭から新しい枝を切って仕様をコミットする。承認のあと、主の作業ツリーを壁打ちを始めたときの枝に戻し、新しい枝を作業用のディレクトリに出してから cycle を始める。主の作業ツリーを切り替えられないときは、止まって人に伝える。cycle が差し戻したあとに再開する壁打ちは、その作業用のディレクトリで書く
  - why: 同じ枝は2つの作業ツリーに出せない。主の作業ツリーでそのまま回すと、指摘のファイルが片付ける場所の中になる
  - rejected: 壁打ちの最初に作業用のディレクトリを作り、そこで仕様を書く（壁打ちが始まる時点で枝の名前を決めることになる）
  - decided_by: 利用者（代決を承認）。戻す先を「マージ先」から「壁打ちを始めたときの枝」に改めたのは主セッションで（マージ先がほかの作業用のディレクトリに出ていると切り替えられない）、見直しのラウンドで利用者に示した

- A9 仕様の置き場を受け取った開始では（再開のときと、仕様の無い小さい作業を除く）、cycle は、作業用のディレクトリに仕様の置き場と判断の記録の置き場のコミットしていない変更が無いことと、`kotowari check` が、枝が変えた文書か受け取った ID について、仕様の側の誤りを報告しないことを確かめる。どちらかが成り立たなければ、未承認と言って止まる
  - why: 計画の工程がやっていた確認が、工程と一緒に無くなった。ID を直接渡して始めた回では、承認されていない仕様でも走る
  - decided_by: 利用者（代決を承認）。確かめる場面と誤りの範囲の絞り込みは、主セッションが仕様のレビューの指摘から足し、見直しのラウンドで利用者に示した

- A10 プルリクエストを作る回はどれも、マージ先が検査を必須にしているかを確かめ、必須にしているときは、検査がまだ報告されていないことを失敗と読まず、現れるまで読み直す。検査が通ったあと、頼みが残っているあいだは、マージされるのを待つ。マージしないと読むのは、頼みが消えたときか、待っても変わらない状態（衝突、枝がマージ先に遅れている）のときだけとする。自動マージを頼む条件に、マージ先が承認のレビューを必須にしていないことを足す。人が確認する回では、プルリクエストを作ったらすぐ、見届けの前に、プルリクエストと止まった原因を人に見せる
  - why: プルリクエストを作った直後や、検査が通った直後に、道具が返す状態を読み違える恐れがある。道具の挙動はまだ測っていないので、どちらの挙動でも読み違えない書き方にする
  - rejected: 測ってから決める（自動マージを有効にする前に、もう1回依頼が要る）
  - decided_by: 利用者（代決を承認）。承認のレビューの条件、どの回でも確かめること、見せる時点は、主セッションが仕様のレビューの指摘から足し、見直しのラウンドで利用者に示した（承認のレビューが必須だと、頼みが残ったまま、人が自分の承認が要ると知らされずに待ち続ける）

- A11 実装役が、検査のコマンドは書かれたとおりには通らないと返したら、cycle は人に聞き、答えを付けて委譲し直す
  - why: 前は計画へ差し戻していた。返す先が cycle になったのに、受ける決まりが無かった
  - rejected: 壁打ちへ差し戻す終わり方にする（コマンドの書き間違いだけで、壁打ちからやり直すことになる）
  - decided_by: 利用者（代決を承認）

- A12 人が確認する場合を挙げた文から、「人が残すと決めた指摘」という出どころを外す
  - why: セキュリティの指摘で止まらなくなる（A5）ので、人が指摘を開いたまま残す場面が無くなる
  - decided_by: 主セッション（A5 から導き、結果のラウンドで利用者に示した）

- A13 プルリクエストを作った直後と、検査が通った直後にホスティングの側が返す状態を、このリポジトリで測った（2026-11-24、自動のマージは頼んでいない回）。作った直後は、必須の検査の一覧に「報告された検査は無い」と返り、マージの可否の状態は「止められている」だった。そのあと約45秒は、必須の検査2つのうち1つだけが見え、2つめは遅れて現れた。検査が2つとも通った直後は、状態は「問題なし」になり、承認のレビューの判定は空のままだった
  - why: A10 の待ち方が、実際の挙動と合っているかを確かめるため。必須の検査が1つだけ見えている時間があるので、数ではなく名前がそろうまで読み直す決まりが要る。作った直後の「止められている」は検査待ちの一時的な値なので、これを「マージされない」と読まない決まりも要る
  - decided_by: 主セッション（未決だった測定の一部を測った事実の記録。残りは A14）

- A14 自動のマージを頼んだ回で、頼んだ直後からマージが見えるまでにホスティングの側が返す状態を、このリポジトリで測った（2026-11-24、プルリクエスト 58、約4秒おきに読んだ）。頼んだ直後は、自動のマージの依頼が見え、マージの可否の状態は「止められている」、承認のレビューの判定は空だった。必須の検査2つのうち1つだけが通ったあいだも「止められている」のままだった。2つとも通った直後は、プルリクエストは開いたまま、依頼も残ったまま、状態は「問題なし」になった。その約5秒後にマージ済みになり、状態は「不明」に変わり、依頼はマージ済みになったあとも見えたままだった
  - why: 見届けの待ち方（A10）が、自動のマージを頼んだ回の実際の挙動と合っているかを確かめるため。検査が通ってからマージまでに、開いたまま「問題なし」と返る時間があるので、これを「マージされない」と読まずに読み直す決まりのままでよい。依頼はマージのあとも消えないので、依頼が消えたことをマージの合図にはできず、マージ済みかどうかはプルリクエストの状態で読む
  - decided_by: 主セッション（未決だった測定を、自動のマージを初めて頼んだ回で測った事実の記録）

- A15 自動マージの設定は、利用者が GitHub の側で有効にした。2026-11-25 に、リポジトリの設定が「マージを任せてよい」を返すことを読んで確かめた
  - why: 未決だった「有効にする時期」は、利用者が有効にしたことで決まった。設定を変えるのは利用者で、cycle は変えない（[設定は人が有効にする決定 A28](./2026-11-24-unattended-merge.md#A28) のまま）
  - decided_by: 利用者（設定を有効にした）。記録は主セッション

- A16 kotowari の次のリリースの変更履歴で、互換性を壊す変更の印を4つの項目に付ける。収束した回がプルリクエストを作って自動のマージを頼むこと、壁打ちが承認のあとそのまま cycle に進むこと、security の指摘などで cycle が人を待たなくなったこと、kotowari-plan の skill を消したこと。ライセンス文の一覧を配布物に足したことと、マージのあとの片付けには付けない
  - why: skill は agent への指示なので、入れた人の手元で agent の動きが前と変わる変更は、意味の変わる変更にあたる。印を付けた4つは、前は人を待っていた場面で待たなくなるか、呼べた skill が呼べなくなる。付けない2つは、前の使い方がそのまま通る。リリースのときに決めるとしていた（R1）
  - decided_by: 主セッション（利用者に「妥当な方向性で進めて」と任された）
