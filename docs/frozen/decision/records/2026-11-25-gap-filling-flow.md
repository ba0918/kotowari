# 仕様の穴を補完しながら回る工程と、決定の持ち方の候補を決める

## Context

[仕様の正本を IR から降ろす向きを決めた壁打ち](./2026-11-25-spec-source-direction.md)のあと、作り替えの形と、ログの調査でいちばん多かった仕様の穴の扱いを、1つの方針として決める。
仕様を先に完成させようとせず、穴は出る前提で、種類ごとにどこで誰が埋めるかを決めた。あわせて、人が決めたことの持ち方の候補を決め、kotowari 本体に入れる前に小さいリポジトリで試すことにした。
決めたのは工程の向きと試し方で、利用者から見える製品の振る舞いはこの壁打ちでは変えないので、IR には何も書かない。

実測の1つ目。前の壁打ちのログの調査から、仕様の穴の場面65件（調査役が種類の1つ目か2つ目に仕様の穴を付けたもの）を抜き出し、主セッションが場面の文を読んで分け直した。人の方針・前提と、agent の推奨や決めた仕様がずれて人が訂正したものが22、実装やレビューの途中で出た未定の細部が16、使って初めて分かった見え方・使い勝手が15、仕様の文どうしの食い違い・古さ・出典の不備が10、その他が2。未定の細部16件のうち12件は、人に聞いた答えが推奨の採用だった。方針のずれ22件のうち10件ほどは、案件をまたぐ利用者の決まった方針に agent の推奨が反したものだった。見え方の15件は、ほぼすべて人がマージ後・本番・実機で見つけた。文の食い違い10件のうち6件は、IR を別の層として持つことで生まれたもの（IR の遅れ、出典の漏れ）だった。元の場面は調査役1席あたり40件までの選抜で、分類は主セッション1人の読みである。

実測の2つ目。6つのリポジトリで、IR の要求が出典に引く決定の数と、判断の記録の決定の行の数を機械で数えた。1つの要求が引く決定の数の中央値は1〜4（2つのリポジトリで4）で、決定の行のうち IR が引くものは46〜81%だった。改められた決定の行は、行全体の6〜12%だった（このリポジトリで1782行のうち111、いちばん小さいリポジトリで310行のうち32）。決定と要求は1対1ではなく、IR は複数の決定を今有効な1つの文にまとめる仕事と、確認の対象になる決定を選ぶ仕事をしている。

Position: 壁打ちは収束した（2026-11-25）。次は、kotowari を採用している小さいリポジトリ1つの移行と試しで、その結果を受けて kotowari 本体の仕様の壁打ちをする。

## Agreements

- A1 実装やレビューの途中で見つかった、仕様に書いていない細部は、実装役が根拠を付けて決める。人には聞かず、人はマージ後の報告で読める
  - why: 調査で、未定の細部の場面16件のうち12件は、人に聞いた答えが推奨の採用だった。止めて聞いても、答えはほぼ変わらない
  - rejected: 利用者から見える振る舞いに関わる細部だけは人に聞く（線引きを LLM がするので、聞きすぎるか聞かなすぎるかに振れうる）。細部も人に聞いて、仕様に書いてから進める（今のまま）
  - decided_by: 利用者（推奨を採用）

- A2 実装の途中で、決めたことどうしがぶつかる、または2通りに読めると分かったときは、細部と同じく、実装役が根拠を付けて読みを決める。人が決めた意図そのものがぶつかるとき（どちらを取っても、人が決めたことの片方を捨てることになるとき）だけ、人に戻す
  - why: 調査で、読み方の確認を人に戻した場面は、答えが推奨の採用だった
  - rejected: ぶつかりと曖昧さは、いつも人に戻す
  - decided_by: 利用者（推奨を採用）

- A3 実装役が決めた細部と読みの理由の1行は、コミットの本文と、プルリクエストの本文の判断の一覧に書く。決定の文書には書かない
  - why: 決定の文書を人が決めたことだけに保つ（A9）。実装役の細部を混ぜると、人が決めたことと区別がつかなくなり、コードが変わるたびに書き直す対象が増える
  - rejected: 決定の文書の、関係する項目の下に書く。コードのその場所のコメントに書く（どの細部が実装役の判断だったかを一覧で見られない）
  - decided_by: 利用者（推奨を採用）

- A4 利用者共通の方針の文書を1つ持ち、壁打ちは推奨を出す前に読む。推奨が方針に反していて訂正されたら、その場で1行足す
  - why: 調査で、案件をまたぐ利用者の決まった方針に agent の推奨が反して訂正された場面が10件ほどあり、同じ形の訂正が別のリポジトリで繰り返されていた。agent のメモリはプロジェクトごとで、ほかのリポジトリの壁打ちからは読めない
  - rejected: プロジェクトごとに方針の文書を持つ（案件をまたぐ方針を、リポジトリごとに書き直すことになる）。持たず、訂正はその場で直すだけ
  - decided_by: 利用者（推奨を採用）

- A5 利用者共通の方針の文書は、利用者の設定の置き場の下（`~/.config/kotowari/principles.md`。`XDG_CONFIG_HOME` があればそれに従う）に置く
  - why: どのリポジトリの壁打ちからも読めて、リポジトリの外にあり、ほかの利用者にも同じ場所で通じる
  - rejected: agent の指示ファイルの中の節に置く（agent の種類ごとに置き場が違い、工程の skill から書き足しにくい）
  - decided_by: 利用者（代決を承認）

- A6 見える振る舞いを変える依頼は、壁打ちの中で、文で聞かずに見本を作って見せ、反応を決定にする。見本は、動く PoC、モック、出力のサンプルのどれかで、何を作るか（作らないことを含む）は、壁打ちを進める agent が理由を付けてその場で決め、人には聞かない。マージ前の確認は足さない
  - why: 調査で、見え方・使い勝手の場面15件は、ほぼすべて人がマージ後・本番・実機で見つけた。見本で合意してから進めた回は評価が高かった。触って初めて分かる動きは、絵のモックでは出てこない。人がすでに居る壁打ちの段に寄せれば、人を待たない工程の範囲は狭くならない
  - rejected: マージ前に、動くものを人が触ってからマージする（人を待つ依頼が増える）。マージ後に使って見つけ、小さい依頼で直す（今のまま）。何を作るかを人が毎回選ぶ
  - decided_by: 利用者（UI が関わる依頼は簡単な PoC を作って意思決定する、モックで足りるかはその時々で判断する、は利用者の言葉。何を作るかを agent が決める点は推奨を採用）

- A7 PoC は決めるための使い捨てとし、製品のコードの土台にしない。実装役に渡して見比べる相手にする。PoC で決めた動きのうち機械で確認できるものは、テストにする
  - why: 土台にすると、テストを先に書く流れとレビューを通らないコードが製品に入る。文だけで渡すと、文に書き切れなかった動きが落ち、合意したモックが実装で守られなかった場面と同じ形のずれが起きうる
  - rejected: PoC を土台にして、そのまま育てて製品にする。PoC を捨て、決めた動きは文で書くだけにする
  - decided_by: 利用者（推奨を採用）

- A8 壁打ちの最初に、人が困っている場面を1つ具体的に組み、合っているかを確認する。承認の前に、決めたものでその場面がどうなるかを見せ、解決していなければ承認に進まない
  - why: 調査で、求めた場面を解決しないものが、記録には範囲が正しく書かれたまま承認を通って作られた。1問ずつは判断できても、合わせて目的に届くかは見えなかった。方針の文書（A4）では、その案件の目的のずれは防げない
  - rejected: 承認の前に、決めたことの全体を1枚で見せる（場面は組まない）。目的のずれは、作ったあとに人が気づいて直す（今のまま）
  - decided_by: 利用者（推奨を採用）

- A9 人が決めたことは、話題ごとの、今有効な決定の文書として持つ。項目は、決定の文、理由、見送った案、状態（提案・出荷済み）を持つ。事実が変わったらその場で書き直し、決定をひっくり返すときは新しい項目を作る。役目を終えたものは凍結した木へ移し、根拠として読まない。壁打ちごとに足していく履歴と、書き直した IR はやめる。テストのマーカーは決定を1対1で指し、提案の状態の決定にはテストを求めない。これは候補で、A11 の試しの結果で確定する
  - why: 二重管理の正体は、足していく履歴と、今有効な形にまとめ直したものの2つを手で書いていることだった。足していく履歴のままだと、最新を知るために古い決定まで読むことになる。今の木に今有効な決定だけを置けば、古い記録を今の決まりと取り違えることも、記録と IR の照合も無くなる。提案の状態を持てば、仕様だけを先にコミットするとテストが無くて止まる問題と、後回しの宣言が、同じ仕組みで片づく
  - rejected: 状態も凍結も持たず、その場で書き換えて履歴は git だけにする（決めたことを黙って書き換えられ、理由が git の中にしか残らない）。足していく履歴のまま、決定にまとまりの名前を付ける（最新を知るために古い決定も読む問題が残る）。今の2層のまま、IR に書く対象を人が決めたことだけに絞る（二重管理と照合が残る）
  - decided_by: 利用者（今の記録は履歴なので最新を見るために古いものまで見てしまう、という指摘は利用者の言葉。形は推奨を採用）

- A10 決定の文書は、話題ごとのファイルに項目を並べる。状態は項目ごとに書く。凍結だけは別の木へ移す。これは候補で、A11 の試しの結果で確定する
  - why: 1決定1ファイルにすると、ファイルが数百になり、壁打ち1回で十数ファイルを書くことになる
  - rejected: 1決定1ファイルにし、状態をフォルダで表す
  - decided_by: 利用者（推奨を採用）

- A11 決定の持ち方（A9、A10）は、kotowari を採用している小さいリポジトリ1つ（要求66件）を新しい形に移し、小さい依頼を1つ壁打ちからマージまで通した結果で確定する。kotowari 本体に入れるかは、そのあとで決める
  - why: 既存のリポジトリを移す作業の重さ、事実の書き直しと決定のひっくり返しの線引きが実際に回るか、壁打ちが直接この文書に書く流れが回るかは、使ってみないと分からない
  - rejected: 加えて、実装を書く仕事で今の IR ありと比べる対照実験もする（新しい決定の文書は今の IR に理由を足したものに近く、読んで実装する側の条件はほぼ変わらない）。試さずに決めて、kotowari 本体の仕様に進む
  - decided_by: 利用者（推奨を採用）

- A12 試しの1件は、新しい決定の持ち方と、この壁打ちで決めた工程の変更（A1〜A8）の両方で通す。試しのあいだは skill を書き換えず、agent がこの記録を読んで従う。そのあと1回の壁打ちでまとめて仕様にする
  - why: 工程の変更を今の2層の形で先に仕様にすると、試しのあとに決定の持ち方が変わったとき、書いた仕様を移し直すことになる
  - rejected: 工程の変更は今の形の上で先に仕様にして skill に入れ、試しは決定の持ち方だけにする
  - decided_by: 利用者（推奨を採用）

- A13 試しで記録するのは、移す作業の量（移した項目の数と、機械で移せた割合）、事実の書き直しか決定のひっくり返しかで迷った箇所、人に聞いた回数と中身、マージ後に人が直させた点、費用の5つとする。回ったとするのは、移した文書で数え方（決定にテストがあるか、提案中の決定にはテストを求めない）が成り立ち、依頼がマージまで通り、線引きの迷いが人を呼ばずに片づいたときとする。どれかが満たせなければ、形を選び直す問いを立てる
  - why: 結果を見てから基準を作ると、どんな結果でも回ったことにできてしまう
  - rejected: 基準は決めず、試したあとで所感を聞く
  - decided_by: 利用者（代決を承認）

- A14 試しに通す依頼は、試しのリポジトリで次に実際に必要になった依頼を使う。当面無ければ、利用者が1つ出す。移す作業は先に済ませる
  - why: agent が選んだ依頼は、利用者が実際に欲しいものとは限らず、困っている場面を組む段（A8）を試しにくい
  - rejected: agent が試しのリポジトリの課題から1つ選ぶ
  - decided_by: 利用者（代決を承認）

## Prohibitions

- P1 この壁打ちの決定をもとに、kotowari 本体の IR、check、工程の skill、PROJECT.md を変えない。仕様にするのは、試しのあとの壁打ちとする
  - why: A11 と A12 のとおり、形は試しの結果で確定する
  - decided_by: 主セッション（A11 と A12 から導き、結果の画面の「作らないもの」として利用者に示した）

- P2 試しのために check を作り替えない。数え方は使い捨てのスクリプトで代用する
  - why: 確定していない形に合わせて製品を変えると、形を選び直したときに戻す作業が出る
  - decided_by: 主セッション（A11 から導き、結果の画面の「作らないもの」として利用者に示した）
