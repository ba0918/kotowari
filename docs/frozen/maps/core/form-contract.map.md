## 迷った判断と、どう決めたか

- 決めたことの「".kotowari/schema.yaml" のようなもの」を、例だと分かる「例: ".kotowari/schema.yaml"」に直した。意味は変えていない。
- 決定の文書を読むエンジン: 利用者の答え（6）は「決定の文書は、kotowari に埋め込んだスキーマで mds が読む。手で書いた読み取りを残す案は採らない」。前の版の推奨（使わない）は採られなかった。これで REQ-core-169 を決定の文書に読み替えて残し、「決定の文書は、本体に埋め込んだスキーマで mds のエンジンが読む」（提案）にした。
- 答え5（決定の中の知らない名前の "###" の見出しの下の内容は、ブロックごとに誤り）は、kotowari の側の振る舞いなので、この話題に別の提案の決定として書いた。決定の文書の unknown_heading と unknown_line を決めた決定は、ほかの下書きに無い（findings の対応表は、IR の形の unknown_heading と unknown_line を「消える」としている。今のコードは決定の文書にも unknown_heading と unknown_line を出す）。findings.md の種類の表にこの2つの行が無いことは、この依頼の外として触っていない。
- 新しい決定と「決定の文書の形はコードに固定し、形を宣言したファイルを読まない」の関係: 古い決定の問題の節は「kotowari が小さなスキーマの言語を持つことになる」を理由に、形を設定やファイルで変えることを退けている。新しい決定のスキーマは mds のスキーマの言葉で書き、本体に埋め込むので、kotowari は自分のスキーマの言語を持たず、形もファイルから読まない。古い決定は変わらないと読み、新しい決定の決めたことからリンクした。
- 「自前の読み取りを残す」の見送った理由（Markdown の構造を読む仕組みが2か所に残る）は、前の版の問いの「変わる条件」（kotowari の中の Markdown の読み取りを mds の1つにしたい）で、利用者がそちらを選んだので、その理由として書いた。利用者が別に理由を述べた記録は無い。
- 設計の「見送った案」の割り当て: 言語ごとのスキーマと、緩いキャプチャで ID を取り出す案は「本体に埋め込んだスキーマで…」に、mds の決まりを変えて内容を指摘にしない案は「知らない名前の深さ3の見出し…」に置いた。節を入れ子のオブジェクトにする案と、状態の段落だけ行で読む案は、どの決定の代わりでもない（抽出の値の形と、エンジンの読み方の細部）ので置かなかった。
- C-core-formc-3（読んで確認）は、元の REQ-core-169 の how_to_verify の形を借りた。生の行か木を読んでよい例外は、エンジンの外に残す5つと、エンジンが返した範囲や行を切り出すもの（設計の §4 の、確認することの行の本文 `row.line..row.end` と、写しの detail に使う状態の行・形の違う行の最初の語・題名の文字）にした。元の how_to_verify も、query の本文を「スキーマの側が返す範囲の行を切り出すだけ」として例外にしていた。設計の §4 が挙げる、ほかのエンジンの外のもの（ID の重複、list と query、公開の関数、対、切り替えの行、BOM、用語集、凍結した木）は、形を読み分けるものではないので、行の例外に名前を挙げなかった。
- 確かめていないこと: ir-input の「閉じないコードブロックは unclosed_code_block の誤りにし、開始から文書の終わりまでを読まない」の C-core-input-4（閉じないコードブロックの後の行を読まない）が、エンジンで読んでも成り立つかは、設計が書いていない。CommonMark ではフェンスが文書の終わりまで伸びるので成り立つと思われるが、実装で確かめる。
- 決定の文書の形の語（"状態:"、"決めたこと" ほか）を、英語が先頭の側で何語で書くかは、形の固定に関わる。98c3fe1 で、今のコードは形の語を日本語と英語のどちらの綴りでも読むようになった（step23 の a_document_written_with_the_english_keywords_is_read_like_the_japanese_one）。形はどちらの綴りでもコードに固定したままなので、この文書の決定は変わらない。
- REQ-core-090 と REQ-core-091 のテストは、形に依らない観測（ファイルを置いても、PATH を変えても結果が変わらない）なので、決定を残して行に当てた。ほかの話題（cli-scope.md）には、これを受ける決定が無かった。

## 実装する側が決める細部

- 埋め込むスキーマの中身（設計の §2）: 規則の書き方、正規表現、どの節を "open: true" にするか、出現回数の書き方。決めたことには、スキーマが宣言する形の部分と、2つの言語の形の語を1つのスキーマで受けることだけを書いた。
- エンジンの指摘から kotowari の指摘への写し方の表（設計の §4）: どの指摘をどの種類のどの行と detail に写すか、写しで捨てる指摘、対のほかの言語の側にも出すか。どれも、今の種類（unclosed_code_block、multiple_titles、missing_title、topic_lead_missing、decision_state_invalid、decision_section_missing、invalid_id、unknown_heading、unknown_line）に写す。
- エンジンの抽出の値を決定ごとに分けるやり方（行の範囲で分ける）と、抽出の値を読む型。
- 確認することの行の名前に、行の中のインラインの記法が残ること（設計の §7。list と query の名前が変わる）。実装する側が決め、プルリクエストに書く。
- 状態の段落の中で、状態の行の前に別のブロックがあるときの誤り（設計の §7: unknown_line になり、状態は読める）。
