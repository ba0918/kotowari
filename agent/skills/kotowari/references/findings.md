Based on the kotowari specification (revised 2026-09-25; the version of kotowari itself is not pinned)

Look at the exit code first. 2 means a stop. Standard output is then empty, so do not read it. Look up the message on the first line of standard error in the stop table below. On 0 or 1, read the JSON on standard output and look up each entry of `findings` in the table below. Entries whose `severity` is `notice` (notices) do not change the exit code.

`tests` groups the test files read by extension, and holds for each extension the number of files with it (`files`) and whether it is a language with a query (`query`). For an extension whose `query` is true (a language with a bundled rule or a rule from `tests.rules`; mark.md), tests are found with the ast-grep rules on the tree-sitter tree, so a test without a mark is reported as test_without_id. An extension whose `query` is false is a language without a query: every mark in the text of its files is picked up and only counted toward clearing requirement_without_test and scenario_without_test, and the number of tests is not looked at. A test in such a language without a mark raises no finding, so the check does not reach the extensions whose `query` is false.

`guides` holds `files` (the number of guides read, one per path) and `marks` (the number of entries of well-formed guide marks). Both are 0 when `guides.files` is not configured. Like `tests`, it is how a glob that matches nothing shows itself; it does not appear with `--format text`. How guides and their marks are written is in guides.md.

The top level of the JSON of `kotowari mutants` is only the three keys `findings`, `counts` and `mutants`; `files`, `lines` and `tests` do not appear. The shape of a finding and the rules for the exit code are the same as check, and are looked up in the table below. How to read the `mutants` tally and the steps to investigate mutant_survived are in mutants.md.

`kotowari plan <path>` checks the form of one plan file against the plan schema bundled in kotowari. It reads only that file, relative to the current directory; it reads neither the configuration file, the IR, the decision records nor the test files, and does not take `--config`. A frontmatter block at the top of the plan is skipped unread. The top level of its JSON is only the two keys `findings` and `counts`; the keys of a finding and the content of `counts` are the same as check, and the exit code follows the same rules (0, 1, 2). Every finding is invalid_plan: `path` is the plan file relative to the base directory (with `../` when it lies outside), `line` is the line the schema side reported (null when it has none), and `detail` is the schema side's kind and its detail joined by `: `. A missing file or a directory stops as `unreadable file`, and a file that is not UTF-8 as `non-UTF-8 file`.

`kotowari list` reads the IR and the test files from the same configuration and places as check, and writes the items and scenarios it could read to standard output. The output grows with the number of items (with 150 requirements the JSON exceeds 200KB), so when an LLM reads it, take only the keys needed with `jq` (for example, the requirements and examples without marks: `kotowari list | jq -r '.items[] | select(.tests == [] and .verification != "review" and (.deferred | not)) | .id'`). It raises no findings; the exit code is 0 when it could read, and 2 only when it stops. The reasons and messages of a stop are the same as check, and are looked up in the stop table below. The items that could be read are listed even when the IR has errors, so list is no substitute for check.

The top level of the JSON of `kotowari list` is only `items`; neither `findings`, `counts` nor the `tests` tally appears. The keys of one entry of `items` depend on the kind of item. `kind` is one of `requirement`, `table`, `property`, `scenario` and `flag`, and every kind has `id`, `kind`, `name`, `path`, `line`, `sources`, `tests`, `fingerprint` (the 8 hexadecimal characters a guide mark copies; guides.md) and `deferred` (true for a deferred requirement and a deferred scenario, false otherwise; ir-form.md "Deferred requirements"). A requirement also has `type`, `verification`, `definition`, `examples` and `how_to_verify`; a decision table and a property have `examples` (in ascending order of ID); a flag has `type` and `relations`. When there is no value, the key does not disappear; it becomes null or an empty array. `how_to_verify` is the value of the requirement's `- how_to_verify:` line, and how a person verifies a requirement whose verification is review is found there. There is no correspondence table kept by hand.

The `tests` of one entry is the array of tests whose marks contain that ID; if the same test has several marks with the same ID, there is one entry per occurrence of the mark. One entry has `path` (the test file's path relative to the base directory), `line` (the line of the mark, not the line of the test function) and `name` (the name of the test function). An entry whose `name` is null is a mark in a file of a language without a query, where there is no test function name.

With `--format text`, one item becomes one line `ID verification name path:line tests=N` (`verification` is `-` for anything but a requirement, and for a requirement without a `- verification:` line; an item whose `deferred` is true gets ` deferred` at the end of the line), followed immediately by one line `path:line name` per entry of `tests`, indented by two spaces (`name` is `-` when it is null). Items are in ascending order of `path`, and within the same `path` in ascending order of `line`; the `tests` of one entry follow the same order.

`kotowari query <ID>` is one entry of list in more detail. What it reads and the rules for stopping are the same as list, and the top level of the JSON is also only `items`. One entry is an entry of list with `body` and `referenced_by` added, and if several items have the same ID, all of them appear. `body` is the array of raw lines of the IR: for an item, from the line after the heading up to before the next `### ` or `## ` heading; for a scenario, from the `@id` tag line to the last step (blank lines at the start and end are dropped). `referenced_by` is the array of items and scenarios that point at that ID; one entry has `id`, `kind`, `path`, `line` (the heading line of the pointing side; for a scenario, the `Scenario:` line) and `via`, in ascending order of `path`, and within the same `path` in ascending order of `line`. `via` is one of `definition` (the `- definition:` line), `relations` (the `- related:` line), `about` (the `@about` tag) and `text` (an ID enclosed in backticks outside double quotes in the statement of a requirement or property, or in a step of a scenario; the same judgement as check's unresolved_reference, so IDs in plain text or inside quotes are not picked up). There is exactly one positional argument, an ID; if no item or scenario has that ID, it stops, writing `argument error: unknown id: ` followed by that text. With `--format text`, after the same first line and test lines as list, each line of `body` is written indented by two spaces, and finally one line `  <- ID via path:line` per entry of `referenced_by`.

`kotowari status` reports whether the IR is complete, as counts and booleans. What it reads and the rules for stopping are the same as check; it raises no findings and writes only counts. The top level of the JSON is the eight keys `documents` (the number of documents and their lines), `items` (the number of items per kind), `requirements` (the count per verification value, the numbers of requirements with and without tests, whether review requirements have a how_to_verify line, the number of requirements without examples, and `deferred`, the number of deferred requirements), `scenarios` (the numbers of examples with and without tests, and `deferred`, the number of deferred scenarios; deferred requirements and scenarios are counted in neither `with_tests` nor `without_tests`, so they do not keep `complete` false), `tests` (the number of marks and the test files read), `guides` (the same as `guides` of check), `findings` (the numbers of errors and notices from check) and `complete`. `complete` is true only when check has 0 errors and there are 0 flag items; the exit code is 0 when complete, 1 otherwise, and 2 on a stop. The counting is aligned with check. If `complete` is false, the reasons are: when the `error` of `findings` is not 0, one per finding of `kotowari check`; when the `flag` of `items` is not 0, in the flags (FLAGS.md). With `--format text`, one line `group key=value key=value` per group is written in the order above, and the last line is `complete true` or `complete false`.

A requirement whose verification is review needs a `- how_to_verify:` line. How a person or an LLM verifies a requirement without tests can be written only on this line, so if the line is missing, a missing_field error with detail `how_to_verify` is raised. A line with an empty value counts as present, and this error is not raised.
