Based on the kotowari specification (revised 2026-11-27; the version of kotowari itself is not pinned)

Look at the exit code first. 2 means a stop. Standard output is then empty, so do not read it. Look up the message on the first line of standard error in the stop table below. On 0 or 1, read the JSON on standard output and look up each entry of `findings` in the table below. Entries whose `severity` is `notice` (notices) do not change the exit code.

`kotowari check --allow-test-findings` leaves test-side findings out of the exit code and changes nothing else: the findings, their order and the output are the same as without it. A test-side finding is a test_without_id or confirmation_without_test error; an invalid_marker or unresolved_reference error whose `path` is a test file; or an unparsable_file error whose `path` is a test file and not a surface file. Every other error still makes the exit code 1. Only check takes the option; any other command stops with `argument error`. Put check into hooks this way: the pre-commit hook runs `kotowari check --allow-test-findings`, so that the commit approving a specification is not stopped before its tests are written; the pre-push hook and CI run `kotowari check` without the option, so that rows to confirm without tests do not reach the shared branch. Do not filter the JSON with a list of finding kinds in a hook instead; the range is kotowari's to decide.

`tests` groups the test files read by extension, and holds for each extension the number of files with it (`files`) and whether it is a language with a query (`query`). For an extension whose `query` is true (a language with a bundled rule or a rule from `tests.rules`; mark.md), tests are found with the ast-grep rules on the tree-sitter tree, so a test without a mark is reported as test_without_id. An extension whose `query` is false is a language without a query: every mark in the text of its files is picked up and only counted toward clearing confirmation_without_test, and the number of tests is not looked at. A test in such a language without a mark raises no finding, so the check does not reach the extensions whose `query` is false.

`guides` holds `files` (the number of guides read, one per path) and `marks` (the number of entries of well-formed guide marks). Both are 0 when `guides.files` is not configured. Like `tests`, it is how a glob that matches nothing shows itself; it does not appear with `--format text`. How guides and their marks are written is in guides.md.

`overview` holds `files` (the number of overview data files read) and `marks` (the number of entries of well-formed guide marks in them). Both are 0 when the configuration has no `overview` key. It does not appear with `--format text`. Findings on overview data have the overview data file as `path` and join the other findings; how overview data is written and what `kotowari overview build` and `serve` print is in overview.md.

`surface` appears only when `surface.rules` is not empty, and holds one key, `unspecified`: the number of surfaces (counted per kind and name) that are not in the decision documents and are excluded by a correct entry of the list of unspecified surfaces. With `--format text` it is the last line, `surface: unspecified=N`, written after the findings even when there are none and N is 0. How surfaces are taken and checked is in surface.md.

The top level of the JSON of `kotowari mutants` is only the three keys `findings`, `counts` and `mutants`; `files`, `lines` and `tests` do not appear. The shape of a finding and the rules for the exit code are the same as check, and are looked up in the table below. How to read the `mutants` tally and the steps to investigate mutant_survived are in mutants.md.

`kotowari plan <path>` checks the form of one plan file against the plan schema bundled in kotowari. It reads only that file, relative to the current directory; it reads neither the configuration file, the decision documents nor the test files, and does not take `--config`. A frontmatter block at the top of the plan is skipped unread. The top level of its JSON is only the two keys `findings` and `counts`; the keys of a finding and the content of `counts` are the same as check, and the exit code follows the same rules (0, 1, 2). Every finding is invalid_plan: `path` is the plan file relative to the base directory (with `../` when it lies outside), `line` is the line the schema side reported (null when it has none), and `detail` is the schema side's kind and its detail joined by `: `. A missing file or a directory stops as `unreadable file`, and a file that is not UTF-8 as `non-UTF-8 file`.

`kotowari list` reads the decision documents and the test files from the same configuration and places as check, and writes the decisions and rows to confirm it could read to standard output. The output grows with the number of decisions, so when an LLM reads it, take only the keys needed with `jq` (for example, the rows checked by tests that have no marks: `kotowari list | jq -r '.items[] | select(.kind == "confirmation" and .tests == [] and (.by_reading | not)) | .id'`). It raises no findings; the exit code is 0 when it could read, and 2 only when it stops. The reasons and messages of a stop are the same as check, and are looked up in the stop table below. The entries that could be read are listed even when the decision documents have errors, so list is no substitute for check.

The top level of the JSON of `kotowari list` is `items`, plus `translations` only when `languages` has two or more languages; neither `findings`, `counts` nor the `tests` tally appears. `translations` has one entry per pair (a pair without its first-language side too), in ascending order of `path`: `path` is the first-language side, and `sides` lists, in `languages` order, `language`, `path` and `blob` (the side's git blob hash, null when the side is missing). With `--format text` each pair is one line after the items: the first-language path followed by ` language=hash` per side (`language=-` for a missing side). These hashes are what a consistency record copies (translations.md). Only then does list also walk the places of guides, overview data and the table of contents, stopping as check does, without checking their content.

`items` has one entry of kind `decision` per decision of a first-language side and one entry of kind `confirmation` per row of a `### 確認すること` (`### Confirmations`) section of a first-language side whose ID is well formed, in ascending order of `path` and `line`. A `decision` entry has `id` (`<document path>#<heading anchor>`, what a guide mark points at), `kind`, `name` (the heading's text), `path`, `line` (the heading's line), `state` (`proposed`, `implemented`, or null when the state line is wrong) and `fingerprint` (the 8 hexadecimal characters a guide mark copies; guides.md). A `confirmation` entry has `id`, `kind`, `name` (the row's text after the ID and after `（読んで確認）` or `(by reading)`, with wrapped lines joined by one space), `path`, `line` (the row's line), `decision` (the heading of the decision holding the row), `state` (the state of that decision, or null), `by_reading` (true for a row that starts with `（読んで確認）` or `(by reading)`) and `tests`.

The `tests` of one entry is the array of tests whose marks contain that ID; if the same test has several marks with the same ID, there is one entry per occurrence of the mark. One entry has `path` (the test file's path relative to the base directory), `line` (the line of the mark, not the line of the test function) and `name` (the name of the test function). An entry whose `name` is null is a mark in a file of a language without a query, where there is no test function name.

With `--format text`, one item becomes one line `ID verification name path:line tests=N` (`verification` is `reading` for a row confirmed by reading and `-` otherwise), followed immediately by one line `path:line name` per entry of `tests`, indented by two spaces (`name` is `-` when it is null). Items are in ascending order of `path`, and within the same `path` in ascending order of `line`; the `tests` of one entry follow the same order.

`kotowari query <ID>` is one entry of list in more detail. What it reads and the rules for stopping are the same as list, and the top level of the JSON is also only `items`. One entry is an entry of list with `body` and `referenced_by` added, and if several entries have the same ID, all of them appear. For a `decision` entry, `body` is every raw line of the decision from its heading to its last section, and `referenced_by` holds each other decision with a link to its heading (`kind` `decision`, `line` the linking decision's heading, `via` `link`), once per linking decision, in ascending order of `path` and `line`. For a `confirmation` entry, `body` is the row's raw lines as written in the decision document, and `referenced_by` is always empty: decision documents point at decisions by links to headings, not by row IDs. There is exactly one positional argument, a row ID of the form `C-<name>-<number>` or a decision's `<document path>#<heading anchor>`; anything else stops with `argument error: not an id: `, and if no entry has that ID, it stops, writing `argument error: unknown id: ` followed by that text. With `--format text`, after the same first line and test lines as list, each line of `body` is written indented by two spaces, then one line `  <- ID via path:line` per entry of `referenced_by`, and for a `confirmation` entry a last line `  decision state heading` (`state` is `-` when null).

`kotowari status` reports whether the specification is complete, as counts and booleans. What it reads and the rules for stopping are the same as check; it raises no findings and writes only counts. The top level of the JSON is the keys `documents` (`files`, the number of decision documents read, and `lines`, their total lines; the glossary is not counted), `tests` (the number of marks and the test files read), `guides` (the same as `guides` of check), `overview` (the same as `overview` of check), `surface` (`total`, the number of surfaces counted per kind and name; `specified`, those in the decision documents; `unspecified`, those not in them and excluded by the list of unspecified surfaces; all three 0 when `surface.rules` is empty), `decisions` (`proposed` and `implemented`, the numbers of decisions in each state; a decision whose state line is wrong is counted in neither), `confirmations` (the numbers of rows with a well-formed ID, in decisions of either state: `with_tests`, a test's mark points at it; `without_tests`, none does; `by_reading`, rows starting with `（読んで確認）`, counted only there), `findings` (the numbers of errors and notices from check) and `complete`. `complete` is true only when check has 0 errors and no decision document has an item in its open section; the exit code is 0 when complete, 1 otherwise, and 2 on a stop. Decisions remaining proposed do not make it false. If `complete` is false, the reasons are: when the `error` of `findings` is not 0, one per finding of `kotowari check` (a surface_without_spec counts too); otherwise the items of the `## 未決` (`## Open`) sections. With `--format text`, one line `group key=value key=value` per group is written in the order above, and the last line is `complete true` or `complete false`.
