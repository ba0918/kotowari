# Changelog

Changes to kotowari that its users can notice. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).
The skills in `agent/skills/` ship under the same tags as kotowari, so changes to the skills are written here too. Changes to the bundled `kotowari-mds` are not written here.

## [Unreleased]

### Changed

- `kotowari-brainstorm` asks the person only three kinds of question: the product's direction, preferences and trade-offs that neither reading nor trying settles; something whose change after it is decided means rebuilding what was built or the accumulated data; and something the request, the sample or the records show the person cares about. It reads what reading answers and tries small what trying answers, writing the result in the question's background, and asks a question when it cannot tell whether it is one of the kinds. Every other question it decides itself with grounds instead of putting it before the person. This applies to the brainstorm only, not to `kotowari-iterate` or `kotowari-adopt`. At approval it shows, with the diff, the list of what it decided without asking, one line each of what and why, or says there is none; an item the person says is wrong becomes a decision in the decision documents. The rest goes in the body of the commit of the decision documents under a line `聞かずに決めたこと:` (`Decided without asking:` in English history), with `なし` (`None`) when the list is empty; when the person committed the files themselves, the brainstorm adds a commit with no file change carrying it. Whoever changes the list writes it again whole in the body of the commit carrying the change, and the newest such list on a branch replaces earlier ones. `kotowari-cycle` receives the list from the brainstorm, or reads it from the commit bodies since the branch parted from the merge target on a resume or a start in another session, and passes it to `kotowari-implement` and to the fixer, which follow it and, when an item needs deciding differently, decide again, write what, why and the evidence in the commit body and the pull request body, and write the updated list again in that commit body.

## [0.8.1] - 2026-11-27

### Changed

- `kotowari-cycle` has a plan written when it judges, before its first delegation, that the work is more than a single implementer can hold (no number decides it), and writes the one-line reason in the findings file as `plan_reason`. The implementer writes the plan at `docs/plans/<branch>.md` in the form `kotowari plan` checks (described in `kotowari-implement/references/plan.md`), commits it on the working branch, and goes on to implement; nobody approves it. An implementer that finds part way that it cannot hold the work commits at a boundary where the tests pass, leaves the remaining procedure in the plan, and hands back, and the cycle delegates the rest. A plan does not bind the implementer: it rewrites the plan when it takes another way, its stop conditions add no stop, its test command does not decide the test command, and it holds no progress. The cycle passes only the plan's path and never reads it; reviews and the consistency phase leave only that file out of their range, and read any other file under `docs/plans/` like any other file. A converged run commits the deletion of the plan before it pushes, with only that path in the commit and without another review; when anything else changed since the head before that commit or the plan is still at the head, it pushes nothing, puts the branch back with the plan restored, ends as a hand-back and reports, and a resume runs the deletion and its confirmations again. A run that ends without converging keeps the plan for the resume. `kotowari-iterate` never has a plan written.

## [0.8.0] - 2026-11-27

### Added

- `kotowari check` reads decision documents as the specification from the place `decisions.documents` names (default `docs/decisions`): one topic per Markdown file, each decision a `## ` heading with a state line (`状態: 提案` or `状態: 実装済み`) and `### 問題`, `### 決めたこと` sections, and the rows of `### 確認すること` carrying IDs of the form `C-<name>-<number>`. It reports a state other than those two (decision_state_invalid), a missing problem or decided section (decision_section_missing), a document without the paragraph after its title (topic_lead_missing), malformed and repeated row IDs (invalid_id, duplicate_id), a link inside the place to a document or heading that does not exist, with heading anchors following GitHub's rule (link_target_missing), and a row of an implemented decision that no test's mark points at (confirmation_without_test, a test-side finding), except a row that starts with `（読んで確認）`. Marks may point at the row IDs; a mark pointing at an ID in no document is still unresolved_reference. The JSON of check carries `decisions` with the numbers of documents, decisions and rows read. An item under a `## 未決` heading makes `complete` of `kotowari status` false. Files under `docs/frozen/` are not read. A fenced code block that is never closed hides what follows it, so it is an error at its opening line (unclosed_code_block), and each `# ` title after the first is multiple_titles, on every language side of a document. Likewise, on every side, a block the form has no place for is an error instead of being skipped: a `###` heading inside a decision that is not one of its keyword sections, and a `###` or deeper heading before the first decision, are unknown_heading, and so is each block under such a heading, block by block, as unknown_line; a second line in the paragraph of a decision's state line, a block other than the state line between a decision's heading and its first `###` section, a block under `### 確認すること` that is not a list (an ordered list included), and a block under `## 未決` that is not a list, are unknown_line (unknown_heading for a heading), so an open question written as a paragraph no longer leaves `complete` true. Link reference definitions are allowed in both places, and further paragraphs, lists, tables and code blocks between the title and the first decision are allowed.
- Decision documents are read by the mds engine with a schema built into `kotowari`; the form stays fixed and no file in your project declares it. A finding of the engine that kotowari has no mapping for stops with `mapping error`.
- `kotowari query` accepts the ID of a row of a decision document (`C-<name>-<number>`) and returns the row with the file, line and name of each test whose mark points at it, the heading and state of its decision, and the row as written. `kotowari list` lists these rows as entries of kind `confirmation`. `kotowari status` adds `decisions` with the numbers of proposed and implemented decisions, and `confirmations` with the numbers of rows with a test, without one, and confirmed by reading (`with_tests`, `without_tests`, `by_reading`; a by-reading row counts only there), over decisions of either state.
- A guide mark can point at a decision of a decision document as `<path>#<anchor of its heading>:<fingerprint>`. The fingerprint covers only the decision's `### 決めたこと` and `### 確認すること` sections, so changing its state, problem or rejected options does not make the guide section stale; a target that names no decision is guide_stale with `-` as the current fingerprint. `kotowari list` lists each decision as an entry of kind `decision` whose `id` is that target, with its `state` and `fingerprint`, and `kotowari query <target>` returns it with every line of the decision, from its heading to its last section, as its body, and with the decisions whose sections link to its heading as `referenced_by` (`kind` `decision`, `line` the linking decision's heading, `via` `link`, one entry per linking decision, by path and line).
- A surface quoted in the `### 決めたこと` or `### 確認すること` section of a decision counts as specified.
- Decision documents can be written with English keywords as well as the Japanese ones: `Status: proposed` or `Status: implemented`, `### Problem`, `### Decision`, `### Rejected options`, `### Confirmations`, a row starting with `(by reading)` after its ID, and `## Open`. Each keyword may be spelled in either language in any document. `state` in `kotowari list` and `query` stays `proposed` or `implemented` whichever spelling the document uses; decision_section_missing names the missing section in the language of the decision's state line (Japanese when the line is missing).
- With two or more `languages`, decision documents are kept as pairs, like the guides: `x.md` is the first-language side, `x.<tag>.md` each other side, and `x.i18n.yaml` the agreement record. A missing side is translation_missing, a side changed after the record is translation_stale, a side without its switcher line is translation_switcher_invalid, and a side whose headings (levels and order, and which keyword section each is), decision states or row IDs and their by-reading flag differ from the first-language side is translation_structure_mismatch. Only the first-language side is read for decisions, row IDs, marks, fingerprints, guide-mark targets and surfaces; links on the other sides are checked for missing targets (link_target_missing) and for pointing at another language (link_language_mismatch). The switcher line does not count as the paragraph after the title. A group's `CONTEXT.md` is paired too, but only its sides and record are checked. `kotowari list` lists these pairs under `translations`. Errors of decision-document pairs do not stop `kotowari overview build`.
- The `kotowari` skill describes both keyword sets of decision documents and how their language pairs are kept; `kotowari-brainstorm` writes every side of a paired decision document in the same change and brings the agreement record up to date before approval, showing the person the side in the language they read; `kotowari-implement` turns a state on every side and updates the record.
- A `CONTEXT.md` directly inside a group folder of the decision-document place (`<place>/<group>/CONTEXT.md`) is a glossary for people: `kotowari check` does not read it as a topic document, checks nothing inside it, and counts it in no number of `decisions`. A link from a topic document to it, or to one of its headings, is checked like a link to any document in the place. A `CONTEXT.md` directly in the place or deeper than a group folder is still read as a topic document.
- A word of `vague_words` in the `### 決めたこと` or `### 確認すること` section of a decision is a vague_word error on its line, on every language side, matched inside words, once per occurrence, the longest word first. Code blocks and text inside double quotes are not checked, nor are `### 問題` and `### 見送った案`.
- In a decision document under a group folder of the place (`<place>/<group>/...`), a row ID whose group name (`C-<group>-...`) differs from that folder's name is an id_domain_mismatch error on its row. Documents directly in the place are not matched.
- `kotowari-core` has `parse_decision_document`, which takes only a `SourceText` (logical path and text) of a decision document and returns, read-only, its decisions (heading, anchor, line, last line, state) and their confirmation rows (ID, line, by-reading flag, name) at their lines in the original text, with the findings on its form; a document with form errors still returns what was read. It needs no configuration, test information or guides, and does not check vague words, whose list is in the configuration.
- A link from a decision document, on any language side and with one language too, to anything under `docs/frozen/` is a link_to_record error at the link's line, whether or not the target exists.

### Removed

- **BREAKING** The old form of the specification is no longer read: the IR (`docs/ir`), the decision records and the ADRs. `kotowari check`, `list`, `query`, `status` and `overview build` and `serve` read only decision documents; files left in the old places raise nothing. To migrate, rewrite the specification as decision documents under `docs/decisions` (or keep using 0.7.0 until you do).
- **BREAKING** The configuration keys `ir`, `decisions.records`, `decisions.adr`, `limits.lines` and `limits.requirements` are gone. Written in the configuration file, each now stops every command with a config error, like any unknown key. Migrate by deleting them; `decisions.documents` defaults to `docs/decisions`, and that directory must exist.
- **BREAKING** The finding kinds that only the old form raised are gone: algorithm_without_definition, deferred_with_test, depends_on_deferred, duplicate_field, duplicate_term, glossary_invalid, glossary_title_invalid, invalid_gherkin_line, invalid_glossary_row, missing_document, missing_field, missing_scope, missing_source, missing_statement, missing_table, missing_tag, record_field_missing, record_field_unknown, requirement_without_test, revision_link_invalid, scenario_without_test, source_invalid, too_many_lines, too_many_requirements, unclosed_backtick, unknown_code_block, unknown_field, unknown_kind, unknown_tag, unknown_term, verification_invalid and verification_missing. The notices are now mutant_timeout, equivalent_stale, guide_stale and surface_unspecified_stale. Drop these kinds from anything that reads the JSON.
- **BREAKING** `kotowari list` and `query` list only decisions and rows to confirm; the kinds `requirement`, `table`, `property`, `scenario` and `flag` and their keys are gone, and the `text` line no longer ends with ` deferred`. `kotowari query` accepts only a row ID (`C-<name>-<number>`) or a decision target (`<path>#<anchor>`); anything else is an argument error. A guide mark entry must point at a decision target.
- **BREAKING** The JSON of `kotowari check` no longer has `files` and `lines`; `decisions` is always there. `kotowari status` no longer has the groups `items`, `requirements` and `scenarios`; `documents` counts the decision documents read (first-language topic documents, the glossary not counted) and their lines, and `decisions` and `confirmations` are always there. Read `decisions` of check and `documents`, `decisions` and `confirmations` of status instead.
- **BREAKING** A guide's link into the places of decision records and ADRs is no longer link_to_record; only a link from a decision document into `docs/frozen/` is.
- **BREAKING** In the Rust API of `kotowari-core`, the modules `ir` (with `ir::parse`, `IrOptions` and the IR document types) and `sources` are gone, and so are `ListItem::Requirement`, `WithExamples`, `Scenario` and `Flag` with their item types, `status::Items`, `Requirements` and `Scenarios`, `ReadModel::documents` and `source_target`, `CheckReport::files` and `lines`, `RepositoryReadPreparation::push_ir` and `collect_known_ids`. `ReadInputs` and `RepositoryReadInputs` take the decision documents as `decisions` in place of `ir`, `records` and `adr`. `CheckReport::decisions`, `StatusReport::decisions` and `confirmations` return the value, not an `Option`. `surface::check_analysis` takes the decision documents as `SourceText` in place of IR documents. Use `parse_decision_document` to parse one decision document. `kotowari` no longer re-exports `IrDocument`, `is_valid_id` and the removed item types.
- The default English text of the UI key `stale_mark` is now "Not reviewed since the decisions changed".
- The `kotowari` skill no longer has the scene `write` and its references `ir-form.md`, `records.md` and `collate.md`; decision documents are written with the scene `decide`.

### Changed

- **BREAKING** Overview data points at decision documents. The frontmatter key `ir` is renamed `documents` and lists decision documents (first-language topic documents in `decisions.documents`); `ir` is now an unknown key. overview_ir_missing is renamed overview_document_missing and overview_ir_shared overview_document_shared. A reference in `refs` or `ref` is a decision, written as a guide-mark target (`<path>#<anchor>`), or a confirmation ID; IR IDs and decision-record sources are overview_ref_unresolved. A reference shows the decision's heading (or the row's ID) and opens every line of the decision (or the row as written); it is deferred when its decision is proposed, current otherwise, and never superseded. On another language's pages the body comes from the same decision on that language's side of the decision document, and a missing side leaves the reference a label only. Rewrite the frontmatter and the references of your overview data.
- **BREAKING** In the Rust API, `FindingKind::OverviewIrMissing` and `FindingKind::OverviewIrShared` are renamed `OverviewDocumentMissing` and `OverviewDocumentShared`, and `kotowari_overview::Translation` carries `decisions` (the other-language sides of decision documents, read with `kotowari_core::translations::decision_side_documents`) in place of `ir`. `kotowari-core` adds `ReadModel::decision_documents`, `is_frozen` and `ConfirmationCounts` (status's `confirmations`, read with `StatusReport::confirmations`).
- missing_title on a decision document carries the file name without its directory as its detail; it was empty.
- `kotowari plan` reports a fenced code block that is never closed in a plan as one more `invalid_plan` finding at its opening line (detail `unclosed_codeblock: ...`), beside the finding it already gave for the code block.
- In overview data, a block quote, an HTML block other than HTML comments, or a thematic break between the title and the first `## ` heading is now an `overview_form_invalid` finding (detail `undeclared_line`); it used to pass silently, although only parts and HTML comments belong there. A fenced code block never closed anywhere in overview data is an `overview_form_invalid` finding too (detail `unclosed_codeblock`).
- `kotowari-brainstorm` writes each decision straight into its topic's decision document as proposed, with open questions under the topic's open section, and the person approves the diff of the decision documents; it no longer writes a decision record or the IR, and runs no collation. A decision that concerns two topics goes in the topic where the behavior is visible, and rows added to an implemented decision leave it implemented. In a project with the `overview` key, the approval still rebuilds the overviews of the changed decision documents (found through the overview data's `documents`), as reference material that is not approved.
- The workflow skills `kotowari-cycle`, `kotowari-implement`, `kotowari-review`, `kotowari-iterate`, `kotowari-investigate` and `kotowari-using-workflow` no longer mention the IR, decision records, deferral lines or collation, and trigger on `.kotowari/` or `docs/decisions/`. In the findings file, `ids` holds the decisions received as `path#anchor` (also what `kotowari-iterate` adds), and a premise ladder's `lives_in` is `implementation` or `decision_document`. A review reads a proposed decision as not built yet, and a change that is not product behavior against its decision without rows. On a direct edit, the consistency phase takes the place of the decision documents as its counterpart, the decisions whose text the diff touches and those they link to being in range. A request to bring existing code into the decision documents, or one unsure whether they match the implementation, is routed to `kotowari-adopt`.
- `kotowari-adopt` writes one topic into its decision document instead of the IR and a per-adoption decision record: the behavior the person ratifies becomes implemented decisions whose problem says they were taken as the specification without review, a legacy statement the person will build becomes a proposed decision, and each disagreement, unreadable row or removed candidate becomes an item under the topic's open section (one that concerns an existing decision links to it, which is never rewritten or deleted). One list row is a candidate for one decision, terms are no longer sorted, and the request text after approval asks to review the grounds tests and write tests per confirmation row.

## [0.7.0] - 2026-11-25

### Changed

- **BREAKING** A converged `kotowari-cycle` run (and a `kotowari-iterate` run) now opens a pull request and asks the hosting service to merge it once the required checks pass, without waiting for you, and watches those checks: a failing required check becomes a finding and is fixed in the loop. It stops at the open pull request and shows you why when the diff from where the branch parted from the merge target touches a path listed in `.kotowari/confirm-paths` (or that file itself), when a finding awaits your judgment, or when the consistency phase revised an approved requirement. A project without `.kotowari/confirm-paths` always stops at the pull request. List in that file, one git pathspec per line, the definitions of your checks: CI, hooks, check scripts, and the configuration of mutation tests, static analysis and tool versions; blanks around a line and a carriage return at its end are ignored. The merge target is the branch the brainstorm or you decided, else the repository's default branch, and the first review and the first consistency phase run read from where the branch parted from it. Merging by itself is used only when the repository allows it, the merge target requires at least one check, it requires no approving review, and the pull request points at the merge target the cycle received; enabling that setting is yours, and the cycle never changes a repository setting or performs a merge itself. Required checks that have not reported yet are waited for, not read as failures, and after they pass the cycle waits for the merge while the request stands; it hands the pull request to you only when the request is gone, or on a conflict or a branch behind its target. When a read of the required checks fails, the cycle does not ask for the merge: it watches the checks that show and hands the pull request to you with the failure. When it cannot read whether a request to merge still stands on the pull request, it pushes nothing and tells you, except on a host where it cannot create a pull request. When it stops for you, it shows the pull request and the cause as soon as the pull request is created.
- After a merge it saw, the cycle removes the run's local worktree and local branch, and nothing on the hosting service. Each decision the implementer made by itself is listed as one line of what, why and evidence in the pull request body and the final report. The findings file, now kept in the main working tree, created when the cycle starts and never deleted, also records the requirement IDs and the merge target the cycle received, the line, the earlier request a fix belongs to, and how the run ended; a resume reads the IDs from it rather than counting them again.
- **BREAKING** After you approve and commit a specification, `kotowari-brainstorm` goes straight on to `kotowari-cycle` with the place of the specification and the IDs of the requirements it added or changed, unless you say to put it off. The brainstorm commits the specification on a new branch it cuts from the head of the merge target, then puts your main working tree back on the branch it was on and checks the new branch out in a worktree of its own; it stops and tells you when the main working tree cannot be switched. When you said the specification may be committed rather than committing it, the brainstorm commits it on the new branch, and it does not switch back while an approved file is not committed there. A cycle started with the place of a specification first checks that it is approved: no uncommitted change in the specification or the decision records, and no specification-side error from `kotowari check` on a document the branch changed or an ID it received; otherwise it says the specification is not approved and stops. A branch name is not reused: a new request on a branch whose pull request was merged or closed stops and asks for a new name. A start that brings a request to a branch a cycle already ran on is a later request, not a resume: it checks the approval again, adds its IDs, and implements and reviews again from where the branch parted from the merge target; a resume is a start that brings no request. When the hosting service cannot be read at the start, the cycle asks you for the merge target if none was decided, goes on without the checks of the branch name and of the open pull request, makes them before it pushes if it can then, and lists in its final report the checks it could not make. When the implementer reports that a check command cannot succeed as written, the cycle asks you and goes on with your answer. The implementer decides the order and the files to touch, and resumes from the git history and the requirements that still have no marked test.
- **BREAKING** Three kinds of review finding keep a cycle from converging: a mistake that running something shows, a security finding that proposes a fix, and a proposal to delete verification the change added because it does not meet the evidence conditions; any other finding not shown by a run is recorded, not fixed. A security finding no longer pauses the cycle for you: one proposing a fix is fixed and listed as a decision line, one asking for your judgment stays open and stops the merge for you, and one that cannot be fixed reaches you through the no-progress ending. Deleting a test, adding a suppression of a check, or adding or changing a dependency does not stop the cycle for you.
- The release archives of `kotowari` now carry `THIRD-PARTY-LICENSES.txt`: the crates built into the binary, each with its licence, authors and source, followed by their licence texts. Earlier archives carried only kotowari's own licences. Where a crate's package ships no licence file, the standard text of its licence is given and the list names the crate's authors.

### Removed

- **BREAKING** The `kotowari-plan` skill is removed: no plan is written or approved between the specification and the implementation. The `kotowari plan` command stays.

## [0.6.0] - 2026-10-24

### Fixed

- A new `kotowari-iterate` request starts with implementation even when the branch already has findings from an earlier request; resuming the same request keeps its place in the loop.
- `kotowari overview build` and `serve` no longer read the contents of test files or `tests.rules`. They only collect the paths `tests.files` matches, to check the overlaps with guides and overview data, so a test file that is not UTF-8 or cannot be read, or a broken `tests.rules`, no longer stops them. `kotowari check` still stops on these.
- With two or more `languages`, a file that `guides.files` matches now counts in the overlap with `tests.files` and `overview.files` even when it is a side whose first-language side is missing, so that overlap stops with its configuration error instead of being skipped.

### Added

- When the improvement loop stops making progress, `kotowari-cycle` now questions the premise before it stops. If fixes keep raising new findings next to the ones they closed — or a finding stays present, a closed cause returns, or new findings do not shrink — the cycle writes down the premises its fixes shared, from the most specific up, replaces the top one and tries once more: through the fixer when the premise lies in the implementation, through the consistency phase when it lies in the IR or a decision record and grounds can settle it. Only a premise no grounds can settle goes to you, with the list of premises in the final report. A second firing after the attempt stops the loop as before. A new stop condition joins the others: for two fixes in a row, the review right after the fix raises a new finding next to where the fix was made, which the cycle judges from the findings' file and line locations (overlapping lines in the same file are one example). The findings file records each fix — the findings it addressed, its commits and the review after it (`fixes`) — for resuming and the final report. Each attempt is recorded in the findings file (`premise_attempts`), so a resumed cycle does not try the same firing twice. `kotowari-iterate` and a direct fix in the main session take the same step, and `kotowari-implement` replaces its own premise once before handing back to the cycle.
- `kotowari::Error::unknown_id()` returns the ID a query did not find when the error's kind is `ErrorKind::UnknownQuery`, and `None` for every other kind, so the ID no longer has to be cut out of the error's text.
- `kotowari::GuideReader`, the type `ReadModel::guide_reader` returns, is now re-exported from `kotowari`.

### Changed

- `kotowari check`, `status` and `list` run faster. On kotowari's own IR (about 150 documents in English and Japanese), `check` takes about a third less time. The output is unchanged.
- `kotowari-cycle` takes optional review items: what the person or the caller asks every full and diff review to look at beyond the profiles. They are carried to the reviewers with the reviewer prompt.
- The workflow skills are proofread: rules written in several places now live in one and are pointed to from the others, descriptions say only when to use each skill, and text a caller follows is kept apart from text pasted into a delegate's prompt. What you can notice: the contract the cycle pastes into its fixer and consistency phase is `kotowari-cycle/references/editing-contract.md`; the Evidence conditions live only in `kotowari-review/references/oracle-evidence.md`, with their four conditions numbered; how a caller launches optional seats is in `kotowari-review/references/optional-seats.md`; and `kotowari-brainstorm/references/records.md` is removed, its record kinds now in the skill's body. A finding raised by a diff review is now matched against closed findings like any other, and a finding kept only for the record no longer counts toward the "still present twice" stop.
- A `--config` that points at a directory now stops with `argument error: config file is a directory: <path>` instead of `argument error: --config is a directory: <path>`, with the path as you gave it. The exit code is still 2 and standard output stays empty. The directory is now detected when the configuration is read, like a missing file, so when another argument error is present too, that other error is reported first.
- **BREAKING (Rust API)** When the configuration file given through `ProjectOptions.config` is a directory, the `kotowari` library now fails with `ErrorKind::InvalidInput`, the same kind as when the file does not exist, instead of `ErrorKind::ReadFailure`. Its detail is `argument error: config file is a directory: <path>`. With no configuration file given, a directory at the default location `.kotowari/config.yaml` is still a `ReadFailure`.
- The `Display` of `kotowari_source_analysis::AnalysisError::InvalidRules` is now `invalid rules: <detail>`, without the `config error: ` that used to sit between them. `AnalysisError::detail()` returns the same text as before.
- **BREAKING (Rust API)** `kotowari::IrDocument` now names the type `ReadModel::documents` returns (`kotowari_core::ir::IrDocument`), so a document read through `Project::read` can be written with the `kotowari` name. Until now it named the result of the partial parse `kotowari_core::ir::parse` (`kotowari_core::IrDocument`), which no `Project` operation returns; code that parses in memory takes that type from `kotowari-core`.

### Removed

- **BREAKING (Rust API)** `kotowari` no longer re-exports `CheckInputs`, `ReadInputs`, `IrOptions`, `SourceText`, `TestAnalysis`, `SurfaceAnalysis` and `ParsedItem`; no `Project` operation takes or returns them. Code that checks inputs in memory takes them from `kotowari-core` (for example `kotowari_core::ReadInputs`), `ParsedItem` comes only from `kotowari_core::ir::parse`, and `kotowari-source-analysis` still re-exports the ones its `Analyzer` uses.
- **BREAKING (Rust API)** `Tool` is removed from `kotowari-core`. It is now defined in `kotowari`, so `kotowari::Tool::CargoMutants` still names it.
- **BREAKING (Rust API)** Intermediate parts of the checks are no longer public in `kotowari-core`: the `terms` module with `check_unknown_terms`, `check_vague_words`, `check_document_references` and `check_terms_and_vague_words_with_duplicates`; `ir::CodeFence`, `ir::parse_opening_fence` and `ir::is_closing_fence`; `ir::check_documents_with_duplicates` and `ir::GlossaryDuplicates`; and `sources::check_sources_with_duplicates`. Check documents with `ir::check_documents`, which stays public, or check inputs in memory through `ReadModel`.
- **BREAKING (Rust API)** The `language` field of `kotowari_core::TestAnalysis` and `kotowari_core::SurfaceAnalysis` is removed, and `kotowari-source-analysis` no longer fills one. Nothing read it; whether a file's language has a query is still carried by `has_query`. Remove the field from code that builds these values.

## [0.5.0] - 2026-10-06

### Removed

- **BREAKING** The `kotowari changes` command and change records are removed. kotowari now has seven commands. The `changes` section of the configuration (`changes.files`, `changes.exclude`, `changes.records`) is gone, and a configuration that still has it stops with a configuration error as an unknown key: delete the `changes` section from `.kotowari/config.yaml` and delete `.kotowari/changes/`. `check` and `status` no longer read change records, the finding kinds `change_uncovered`, `change_stale`, `change_ir_stale`, `change_conclusion_conflict`, `change_deferred` and `change_record_invalid` are gone, and so is the `git error` stop.
- **BREAKING (Rust API)** The public API that served only `changes` is removed. From `kotowari`: `Project::changes`, `AsyncProject::changes`, `ChangesOptions`, `ChangesReport`, `Target`, `Phase`, `ChangesConfig`, `Comparison` and `ErrorKind::GitFailure`. From `kotowari-core`: the modules `changes`, `change_records` and `comparison` (with `Comparison`), `ChangesConfig` and the field `changes` of `Config`, `CheckInputs` and `RepositoryCheckInputs`, `RepositoryInspectionPreparation::changes`, the `FindingKind` variants `ChangeStale`, `ChangeIrStale`, `ChangeUncovered`, `ChangeDeferred`, `ChangeConclusionConflict` and `ChangeRecordInvalid`, and `StopReason::GitError`. A repository inspection now starts at the guides phase. The glob set builder that `check` still uses is `kotowari_core::config::glob_set`.

### Added

- The `kotowari-cycle` skill runs a consistency phase: once after implementation and once after the quality review's fixes converge, a separate agent reads the code the diff changed against the IR, finds behaviour the IR does not state, behaviour different from it and gaps or contradictions in the IR around it, and resolves each on grounds and measurements into a state where the IR and the code agree. It fixes and commits the IR, the decision record, the flag record and the code itself, and writes what it decided to a new decision record. Its findings go into the cycle's findings file beside the review's, with the perspective `consistency`, and the phase is rerun and stopped by the same rules as the review loop. A question of meaning the grounds cannot settle continues with a default and stays open for the final report with the word that reverses it; the phase never stops to hand it back to a person. A run is skipped only when the diff adds or changes no behaviour a user can observe (skill text counts as behaviour), with the reason in the final report. `kotowari-iterate` runs it through the cycle, and a direct fix in the main session runs it by the same measure.

### Changed

- `kotowari-review` launches reviewers with the quality perspective only. There is no conformance reviewer comparing code with the specification any more; that is the consistency phase's. Whether a plan or a document contradicts the specification is still read within the quality perspective.
- The skills no longer write or ask for change records. The implementer and the fixer leave IR-side findings to the consistency phase instead of adding IR themselves.
- Workflow skills share the editing and review hand-off rules instead of repeating conflicting fixer instructions in the consistency phase. Delegates read writing and marker references only when needed, and direct edits use the same finding and stopping rules as cycle.

## [0.4.0] - 2026-10-06

### Changed

- The minimum supported Rust version (`rust-version`) of every crate is now 1.99. Crates that declared 1.89 have a higher floor, and `kotowari`, `kotowari-core`, `kotowari-source-analysis`, `kotowari-overview` and `kotowari-cli`, which declared none, now declare 1.99.

- The README, the guides and the IR are now pairs of English and Japanese. `README.md` and `docs/guides/*.md` without a suffix are English, `*.ja.md` is Japanese, and the line under each page's title switches between them. The guides no longer have the "why it is built this way" sections that explained the history of decisions (the history is in the decision records).

- The `kotowari` skill now states more clearly how guides and overviews divide the work: a guide explains usage to the people who use the product, and an overview explains decisions, reasons, plans and open questions to the people who build it. An overview shows behaviour briefly as the result of a decision, and commands, configuration and usage steps go in the guides.

- **BREAKING (Rust API and package layout)** The root package is now `kotowari-cli`, and `kotowari` is split out as a library operated from an explicit starting point. In-memory computation uses `kotowari-core`, and source analysis uses `kotowari-source-analysis`. Code that called the old core's CLI or acquisition API needs to migrate. The binary's commands, output and exit codes are unchanged.

- The `kotowari` skill has a new "What the IR holds" section stating that the IR holds only behaviour a user of the product can observe. CI and workflows, hooks, release steps, build configuration, the repository's own data, and the project's own tests and checks are not written in the IR; they go in the decision records and carry neither requirements nor tests. When in doubt, leave it out, and adding to the IR to justify a test is forbidden. Brainstorm, plan, implement, cycle, review and iterate refer to this definition.
- The change conformance reference now states that a change to CI, hooks, release or build configuration alone is recorded as a `new` entry citing a decision, with `ir` and `requirements` empty, and is not a `missing_spec` gap.
- An element of `tests.files`, `guides.files`, `surface.files` or `overview.files` that starts with `/` now stops with a configuration error, as an absolute-path value. Such an element never matched anything, since globs are matched against paths relative to the base directory.

### Added

- `kotowari check --allow-test-findings`, a flag without a value. It leaves test-side findings out of the exit code, so the commit that approves a specification ahead of its tests can pass a pre-commit hook: `requirement_without_test`, `scenario_without_test` and `test_without_id`; `invalid_marker` and `unresolved_reference` on a test file; and `unparsable_file` on a test file that is not a surface file. Every other error still exits with 1, and the findings and output are the same as without the flag. Run it with the flag in the pre-commit hook and without it in the pre-push hook and in CI; the guide to check, the `kotowari` skill's findings reference and the `kotowari-adopt` skill now say so. Only `check` takes the flag; any other command stops with an argument error.

- An introduction page, in English and Japanese, explaining how specifications, decision records and tests connect and what the mechanical checks cover.

- `kotowari overview build` and `kotowari overview serve`. They check the overview data matched by `overview.files` in the configuration (frontmatter `ir`, a title, a leading `lead` part, and Markdown with sections and parts), and when there are no errors write an index and one HTML page per overview under `.kotowari/cache/overview/`. serve serves them at `http://127.0.0.1:<port>/` (4590 by default, changed with `--port`) and ends on Ctrl-C. Errors in the overview data stop with `overview error` without writing anything; a port that cannot be used, or a failure to accept connections while serving, stops with `port error`. When `.kotowari`, `.kotowari/cache` or `.kotowari/cache/overview` is a symbolic link or not a directory, they stop with `cache error` without writing or deleting anything, and so does a failure to create, write or delete in that location.
- With the `overview` key in the configuration, `kotowari check` and `kotowari status` read the overview data and report errors in its form, part contents, leading `lead`, IR documents covered, references inside parts and overlapping page names (`overview_form_invalid`, `overview_part_unknown`, `overview_part_invalid`, `overview_lead_missing`, `overview_ir_missing`, `overview_ir_shared`, `overview_ref_unresolved`, `overview_name_conflict`), along with stale guide marks in sections of the overview data. The JSON of check and status always has the `overview` group (`files` and `marks`), both 0 without the key.
- The overview index is drawn from a table of contents. `overview` in the configuration now also requires `overview.toc`, pointing at the table of contents YAML file. The index uses the table of contents' title as its heading and draws its groups (`title`, an optional one-line `note`, and `items`) in the written order and nesting, as collapsible blocks. Cards show the number of unreviewed sections, open questions and plans, and group headings show the page count and the totals of unreviewed sections and open questions. Every page gets its position in the table of contents and links to the other pages in the same group. Errors in the table of contents' form, pages missing from it, names without overview data, second and later occurrences of a name, and empty groups are `kotowari check` and `kotowari status` errors (`overview_toc_invalid`, `overview_toc_page_missing`, `overview_toc_page_unknown`, `overview_toc_page_duplicate`, `overview_toc_group_empty`) and stop build and serve. A missing or unreadable table of contents stops, and a table of contents matched by the scan of `overview.files`, `guides.files` or `tests.files` stops with a configuration error. With no overview data at all, no table of contents can pass, so write the `overview` key together with the first overview data and the table of contents.
- `overview_prepare`, which writes nothing, and `overview_build`, which then writes, on `Project` and `AsyncProject`. `check`, `status` and `inspect` include the findings on the overview data and the `overview` group. A new `kotowari-overview` crate performs the overview checks.
- A synchronous `Project`, `ReadModel` and `Inspection` that are kept and reused, and `AsyncProject` behind the `tokio` feature, disabled by default.
- A procedure for verifying the actual release archives of the nine crates in an independent offline environment. The version numbers and the release names of the two products are unchanged.
- IR, guides and overviews can be kept as multilingual pairs. Listing two or more language tags in `languages` in the configuration keeps the IR (glossaries and flag records included), guides, overview data and tables of contents as pairs `foo.md` and `foo.<language tag>.md` in the same directory, with the git blob hash of each side recorded in `foo.i18n.yaml` beside them. `kotowari check` and `kotowari status` report a missing side (`translation_missing`), an error in the consistency record (`translation_record_invalid`), a hash differing from the record (`translation_stale`), a mismatch in the non-sentence skeleton (`translation_structure_mismatch`), an error in the switcher line after the title (`translation_switcher_invalid`), a link to another language's side (`link_language_mismatch`) and a link to a decision record (`link_to_record`) as errors. The other language sides of the IR are checked for terms, vague words, document name references, unclosed backticks and the glossary's form against that language's glossary. `kotowari list` outputs the blob hash of every side of each pair in the top-level `translations`. Overviews are drawn per language: pages of languages other than the first are written under `.kotowari/cache/overview/<language tag>/` and link to each other, and a missing side or a skeleton mismatch in a pair of IR, overview data or table of contents stops without writing. The overview UI text is held in English by kotowari itself and written for other languages in `labels` in the configuration (an error in its form stops with a configuration error), and the labels of the `status` part are now `decided`, `planned`, `open` and `dropped`. The `kotowari` skill has a new procedure for keeping pairs aligned. Without `languages`, everything stays English only, as before, and no pairs are read.

### Fixed

- `kotowari overview serve` returns a 403 with no body to requests whose Host header is not `127.0.0.1:<port>` or `localhost:<port>` (including requests without Host). An outside site could point its own name at 127.0.0.1 (DNS rebinding) and read the overview pages through the browser.
- In a repository with two or more languages in `languages`, `kotowari changes` also read the other language sides (`foo.ja.md` and the like) as IR, and treated a record naming the first language's side as `change_record_invalid`. It now reads only the first language's side as IR, the same as `kotowari check`.
- In multilingual pairs, reference-style links and images are also checked on the line where they are used, and a mismatch in the sequence of link destinations is detected. A configuration where only the translated side of an overview overlaps the test glob also stops with a configuration error.
- The setup steps of the `kotowari` skill now say to create a `.gitkeep` in the directory for decision records and include it in the commit. Otherwise the empty directory is lost in a clone or worktree and `kotowari check` fails.
- Pages from `kotowari overview build` no longer draw GFM footnote syntax (`[^1]`) as footnotes. Drawing them put the English heading "Footnotes" and back-link characters even on Japanese pages.
- `kotowari overview build` now removes only HTML comments from headings and titles. Before, parts of a line read as HTML, such as `<String>` in `Vec<String>`, were removed too, and the heading became "Vec".
- `kotowari changes` no longer reads hidden directories under the places for the IR and decision records (such as `docs/ir/.drafts/`), the same as `kotowari check`. Before, it judged a change record citing IR there as valid, while `check` reported the same record as `change_record_invalid`.
- When the same requirement ID is in two IR documents, `kotowari check` now takes the document earlier in path order as the IR defining it for change records (the same as `kotowari changes`). Before, it took the later document and reported records citing the earlier one as `change_record_invalid`.
- Fixed the library's in-memory entry points (`ReadModel::build`, `Inspection::build`) failing to find the title and the language switcher line of a document starting with a BOM, which reported the switcher line as `translation_switcher_invalid` and also counted it as a scope line of the document. `kotowari check`, which reads from files, has always skipped the BOM.
- `kotowari changes` now starts the detail of an error in the target configuration file with the configuration file's relative path, the same as `kotowari check` (`config error: .kotowari/config.yaml: ...`).
- `kotowari changes` with `--port` now stops with an argument error, like the other commands. Before, it silently ignored it and ran the check.
- Fixed a panic inside the library when `changes.records` or `overview.files` had a brace glob spanning the `/` separator (such as `{docs/.changes,docs/changes}/*.yaml`).
- `kotowari overview build` and `kotowari overview serve` now stop with `cache error` when they cannot enumerate the files under `.kotowari/cache/overview`, like the other failures in that location. Before, they stopped with `unreadable file`.

## [0.2.0] - 2026-09-27

### Added

- The README's installation section has a way to install with mise's `github:` backend (`mise use -g 'github:ba0918/kotowari[version_prefix=kotowari-v]@0.1.0'`).
- Surface checks. `surface.files` and `surface.rules` (ast-grep rules) in the configuration pick out the surfaces of the code that users see (CLI subcommands, flags and the like), and `kotowari check` reports a `surface_without_spec` error when a name is not quoted in a requirement's statement, a decision table cell or a scenario step of the IR. Only files in the rules' languages are read among the surface files, so a broad `src/**` matching images and the like does not stop. Without rules, nothing happens.
- A surface not yet in the IR can be excluded by listing it, with a reason, in the list `surface.unspecified` points at. A malformed entry is a `surface_unspecified_invalid` error, and an entry no longer needed is a `surface_unspecified_stale` notice. The number excluded appears on the last line of `check` as `surface: unspecified=<n>` (`surface` in JSON), and the number of surfaces on the `surface` line of `status`.
- The `kotowari` skill has a new reference `surface.md` for surface checks, and `kotowari-adopt` explains how to shrink the list. Only `kotowari-brainstorm` and `kotowari-adopt` add to the list; the implementer sends a surface missing from the IR back to the brainstorm.

### Changed

- `kotowari-adopt` also confirms the topic's user entry points (commands and screen operations) when confirming the scope, and lists only behaviour observable from those entry points. Behaviour found outside the scope is shown only as a count and candidates for the next topic. One row is one candidate requirement; rows differing only in values or wording are merged into one row as a candidate decision table, and when the candidates exceed `limits.requirements`, it checks whether entry points are mixed.
- The output of `kotowari status` always has the `surface` group (`total`, `specified`, `unspecified`). Without surface rules, all three are 0.

## [0.1.0] - 2026-09-26

### Added

- `kotowari`, a CLI for writing a specification as Markdown in a fixed form called the "IR" and checking it mechanically. Output is JSON by default; add `--format text` for people to read.
- `kotowari check`: checks the IR's form, whether the decision records cited as sources of requirements exist, and which tests verify which requirements, and reports findings. The exit code is 0 for no findings, 1 for errors, and 2 when the check could not start. It also checks whether the marks placed in user guides disagree with the current IR.
- `kotowari list`: lists the IR's items and scenarios together with the marked tests.
- `kotowari query <ID>`: outputs the body of one item, the tests verifying it, and the items pointing at it.
- `kotowari status`: counts whether everything is in place and answers with `complete true` or `complete false` on the last line.
- `kotowari plan <file>`: checks the form of an implementation plan file against the bundled schema.
- `kotowari mutants --tool cargo-mutants <results file>`: reads mutation test (cargo-mutants) results and reports missed mutants as findings.
- Test marks `@kotowari[ID]` are read with bundled rules in Rust, TypeScript, JavaScript, Python and PHP tests. Other languages that ast-grep (tree-sitter) handles can be read by writing rules in `tests.rules` in the configuration.
- Ten Claude Code skills in `agent/skills/`. `kotowari` teaches how to write the IR and decision records, fix findings and place marks. The nine starting with `kotowari-` run the workflow from brainstorm through plan, implementation and review on top of kotowari (optional).
- Two ways to install: prebuilt binaries on GitHub Releases (Linux x86_64 and macOS arm64, with SHA256), and `cargo install --git https://github.com/ba0918/kotowari --tag kotowari-v0.1.0 kotowari` with the version pinned by tag. Passing the tag to `--pin` of `gh skill install` installs the skills at a pinned version.
